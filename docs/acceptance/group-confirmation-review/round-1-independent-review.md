## 2. 案例 A：审查结论与必需修订

### A1. 确定问题：新增入口复用旧 Guard 仍然引入被禁止的业务互斥

位置：合成计划“沿用旧 Guard、limitations 记不新增 SQL”；调用路径 `previewImport → DatasetGuard.lock() → select ... for update`。

当前请求明确禁止 `.last("for update")` 和 SQL `FOR UPDATE`，要求业务互斥使用 Redis。新增服务调用使该机制进入本次业务路径；SQL 文件没有新增不能改变这一事实。因此方案审查应要求修订设计，实现审查应保留规范违反发现，不能以已有测试通过、未观察到死锁或 limitations 备注关闭。已确认的是约定违反，不是“线上已经死锁”。

必需修订：

1. 核对旧 `src/views/details/AGENTS.md` 的来源、时效及适用范围。它位于页面目录不能自动推定支配服务端；即使适用，也不能覆盖本轮直接、明确的相反要求。同步修订本次相关设计和确实适用的说明，避免继续传播“必须行锁”的旧约定。
2. 追踪同一数据集资源的实际竞争入口，包括预览导入及确实可能与其冲突的审核/编辑操作；复用现有 Redis 业务锁，统一资源标识与互斥边界。没有现成入口时指出能力缺口并按原任务形成最小实现，不退回数据库悲观锁。
3. 锁内重读受保护状态，用同一最新对象完成校验、更新和相关事件构造；保护范围覆盖实际事务提交/回滚。保留数据库正常事务、唯一约束及完整性保护。
4. 不能只为 `previewImport` 新建一个互不协调的 Redis key；那会让旧冲突入口与新入口不再共同互斥。也不能以规范修订为由迁移不相关全仓锁。

实际依据：`review-code-implementation/SKILL.md:24,30-34`；实现 checklist 第 64–66、70–72 行；方案 checklist 第 56–59 行；业务程序第 97 行。

### A2. 确定问题：剥离确认后的条件会交付错误业务语义

位置：合成计划“先完成预览导入，点击编辑条件移除为另话题”；业务负责人完整原文：“可以，按原方案修复，但是点击编辑就变为待提交，刷新后保持。另外统计本月报表”。

本案例明确将“点击编辑就变为待提交，刷新后保持”提供为对原方案的条件，它修改同一交互和状态语义。原话题只拥有确认 Unit 不意味着可以忽略可读原文中的条件。必须将这一条件纳入原任务目标与验收；不能改成“再点一次保存才待提交”，也不能仅更新前端内存而刷新丢失。

必需修订：把点击编辑这个触发点、状态持久化及刷新后的回显一起进入最小方案和标准方案。结合当前真实前后端路径确定实现，验收至少覆盖点击动作后状态变化、实际持久化重读、刷新保持，以及已有流程中确实受影响的拒绝/失败行为。此处不能先由审查者自行补实现或真实页面操作。

实际依据：方案 SKILL 第 25 行；方案 checklist 第 72 行；实现 checklist 第 23、84–89 行；业务程序第 13–17、59–60 行。业务程序第 60 行明确禁止为了少改代码增加用户未要求的保存、重新打开或审批步骤。

### A3. 未收敛的风险：没有观察到死锁，不证明不存在循环等待

现有合成材料不能判定真实死锁是否发生或具体等待环是什么；不能凭 Redis 类型直接宣称已安全。应由原实现者围绕真实调用链说明并核验：

- 多资源获取顺序是否一致，是否存在 A→B 与 B→A、批量顺序不稳定、非重入锁重复获取、锁升级。
- 是否存在“持数据库写锁等 Redis”和“持 Redis 等数据库写锁”的相反顺序；回调/Future/远程调用是否等同一把锁。
- 部分取锁、异常、提前返回、中断、取消、等待超时的回滚和释放路径；仅释放自身持有锁，多锁释放顺序正确。
- TTL、续租失效、超时之后是否继续写入；事务代理提交是否发生在方法 `finally` 解锁之后而形成提前解锁窗口。

已有测试通过只能作为给定版本/场景的既有结果；此处没有原始报告和具体场景，不能推导并发安全、持久化正确或死锁风险已消除。后续实施者应在范围内安排真实依赖的相关并发及故障场景，审查者只检查设计和已有证据，不先要求未实施方案提供成功证明。
