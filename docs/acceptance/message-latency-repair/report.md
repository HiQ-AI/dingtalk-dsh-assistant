# 消息处理延迟修复结果

2026-10-22。基线 `192e808`，修复分支 `worktree-coordination-latency`。已修复有现场证据的重复规划、工具规则试错和处理迟到引起的过期澄清；最终相关验证 **530 PASS、0 FAIL、0 SKIP**。尚未部署，不能声明线上已经提速。

## 为什么慢

“三分钟后”消息在北京时间 15:31:45.381 发生，原定 15:34:45，澄清于 15:35:24.469 送达，共 219.088 秒。路由 6.826 秒；前两次规划分别 46.098/68.516 秒，全部 8 步用于读取，未提交；两段重试间隔合计 74.679 秒。模型先尝试未公开的超限参数，再读取全部 17 个任务详情，而纯查询原本只需确定目标。这些额外模型调用及退避构成主要可消除开销。

两条其他受理确认耗时 114.182/119.390 秒，分别提交了 5/3 次完整决策，原因是回复审阅的必填类型、同任务确认和替换集合规则未公开；路由的 limit=10000 越界也是公开工具说明缺失。数据库/工具执行的毫秒耗时不能解释这些分钟级延迟。

逐步元数据、时间口径和正常反例见 [现场审计](round-1/latency-audit.md)。取证时安装规划器 SHA256 为 `2199843226CDB043B89552801F9C54A1F80CC8A166BFFEAE6064DBEB86C1BFBE`，与未修改的基线文件一致。

## 修复及受控效果

- 协调上下文公开与执行侧复用同一有界 schema。纯定时查询允许选择已读取目录中的固定目标，执行时读取最新事实；任务变更、观察和条件续办仍读取完整合同并校验版本/群范围。
- 原生 Host 受控模型中，17 个任务只需一次协调调用直接提交，41 个任务补一页后提交。不将受控模型调用数等同于真实模型耗时或理解能力。
- 相对时间锚定原消息；系统处理期间到期仍保存原时刻，既有默认 15 分钟窗口决定补执行或过期。消息本身已过期或缺乏可靠来源时间仍拒绝，不能擅自改时刻或重放旧澄清。
- 补充回复审阅与 Topic 分页说明，保留原校验；成功接纳/澄清/交接后移除旧规划告警，保留持久重试次数。

## 验证与边界

最终单元 469、原生 Host 47、发布 smoke 14 项全部通过；映射仍为 299 文件各注册一次、历史 3、删除 0。命令、反例和输出位于 [第 3 轮](round-3.md)，各轮状态以 [matrix.csv](matrix.csv) 为准。README 与迁移 runbook 已同步。

仍有两类未收敛成本：一条消息至路由约 399 秒缺乏独立入站/排队时钟；投递耗时约 10–26 秒及另一样本约 61 秒没有网络层证据。另有正常多候选路由约 50 秒，大部分为模型响应区间，不属于已证实的重复读取错误。当前性能 API 不完整，未声称覆盖全日消息。

本轮无真实钉钉发送、历史重放、部署、CI或版本发布。后续实际提速需在部署同一变更后按同口径重新取样；不把健康状态或本地测试通过当作业务送达证据。变更不涉及 schema 或新配置，代码回退即可恢复旧行为；已经持久化的计划继续依赖既有账本与通知身份，不做数据清理。
