# 使用现有 UAT 账号完成受控数据库问答

## 决策与现状

用户 2026-09-28 明确要求沿用现有 UAT 账号，无需创建只读角色或另行申请授权。旧只读角色提案保留为历史记录，不再执行。

当前 `agent-query-database.js` 每次检查角色的超级用户、写入和 schema 权限，因现有账号高权限而拒绝查询。用户已授权的是 UAT 问答，不包括生产数据库或向 Agent 暴露原始 SQL、连接配置与凭据。

只读探针 `docs/tmp/existing-uat-readonly-probe.json` 使用现有 `hiq_editor_uat` 凭据：连接成功，`BEGIN READ ONLY` 生效，目标三列存在，SELECT 成功，写入被 PostgreSQL 以 `25006` 拒绝；探针没有打印凭据或数据行。

## 修改

1. 数据库资源可显式标记 `environment: uat` 与 `identityPolicy: host-enforced-readonly`。该组合只允许在可信 Host 配置中声明，缺少或写成其他环境则沿用当前严格只读角色门禁。
2. 此模式继续由 Host 构造固定的 SELECT 与元数据查询，模型仅能填结构化参数；每次连接设置只读默认事务，执行 `BEGIN READ ONLY` 并核验事务状态。资源仍限定表、列、条件、行数、超时、输出、主体与群授权。拒绝原始 SQL、跨资源/表列及生产环境标记。
3. 配置器校验新的资源字段，不读取凭据；正式提案只登记共享 UAT Editor 库的 `public.tw_process_drafts` 三列和测试群 owner。凭据别名仍在受保护的仓库外文件。
4. 同步查询工具说明、README、部署 runbook 和验收矩阵。第五包先完成已有调查修复部署；本改动经实测后另打包并依原维护流程部署。

## 验收

- 受控测试覆盖：默认严格角色门禁；显式 UAT 高权限账号只读事务；SQL 注入仅作参数值；跨表/列/主体拒绝；写入反例被数据库拒绝。
- 真实 UAT：仅在测试群向授权主体展示登记资源，Agent 实际读目标三列并返回来源；独立核对会话、工具工件、引用答复和通知账。数据库业务数据无写入。
- 部署前后分别独立核对包、配置、进程、健康、历史任务和可恢复性；失败记录保留。
