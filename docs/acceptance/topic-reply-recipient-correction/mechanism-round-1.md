# Topic 回复对象机制调查

## 结论与证据

- `topic-runtime.js:801` 至 `:812` 的普通 Topic 决策回复使用最后一条带真人标识的 basis 消息作为引用目标和唯一 @ 人。多个依据时，依据顺序不代表语义收件人，后发言的解释者会被误选。此处为代码路径反例，脱敏实跑由测试成员负责，本报告不声称已实跑现场。
- 已有 `replyRouting`（`topic-runtime.js:315`）用于任务结果回复和审阅通知（`:1220`、`:1306`），校验消息属于传入的固定消息集合、@ 标识属于该集合且不重复；但当前仅排除 `web`/`internal`，未显式排除助手身份。它把省略或空数组都默认成引用目标，不能表达显式不 @。
- 决策结构 `decision.js:39` 至 `:48` 已支持 `actions: []` 加回复和审阅，也允许 `actions: []` 加不回复原因；`topic-runtime.js:1028` 至 `:1035` 并非因为 actions 为空而禁止回复。具体纠正是回复还是不回复需语义判断，不应强制所有纠正另发一条或将无任务动作视作不回复。
- `createDecisionRequest`（`topic-runtime.js:454`）把固定 Topic 消息保存为 `request.messages`；引用内容单独作为背景投影（`:477` 至 `:491`），不能假定引用原消息自动是固定 Topic 内可验证参与者。路由阶段（`:603` 至 `:617`）可按当前群 outbox 的 deliveredMessageId 关联原发信及 Topic，但引用字符串或姓名本身不证明引用者、原作者或助手身份。若目标不在固定 Topic 的可信消息中，应明确拒绝或走人工/后续澄清，而不是猜测或扩展跨 Topic 权限。
- `task-session-service.js:181` 的 `isOwnNotification` 可利用同群的发送回执或配置的助手身份与信号识别自身通知；不能仅凭展示名、别名或用户引用里自称的 sender 将普通成员消息视为助手消息。`decision.js:367` 至 `:374` 的授权检查独立于路由，收件人纠正不应授予新任务或跨群授权。
- `task-session-service.js:769` 至 `:779` 的格式化会用 `group-reply-format.js:87` 返回的单目标 @ 覆盖既有 args；即使语义路由在 Topic 层正确，未修正该覆盖则通知仍错。`group-message.js:107` 至 `:110` 实际将 payload 的 @ 列表传给适配器。
- 恢复需要完整冻结目标和 @：`store.js:1336` 至 `:1340` 同 outboundId 校验正文、decision 和引用目标，但不校验 @；`:1361` 不存空数组。`task-session-service.js:762` 至 `:767` 已准备通知时只显式复用 text，`:771` 至 `:779` 的 outbox 已存在但通知未准备分支同样只复用旧 text，其他路由仍来自本次参数。若同引用目标而 @ 改变，两账可能不同而不触发身份冲突。上述是静态可达风险，具体恢复案例须定向验证。
- `decision.js:316` 至 `:317` 的不可用媒体分支重建 decision 并丢弃其他字段。增加路由字段时须保留并重新校验可信目标，避免自动失败回复丢路由或猜目标。

## 三种方案

1. 保持最后 basis 发言人或改为第一个：改动少，但多参与人顺序与目标无必然关系，不能修根因；排除。
2. Host 从姓名、纠正关键词、引用展示文本推断：容易误认同名、非助手引用或跨群对象，绕过语义和可信身份边界；排除。
3. 推荐：在有回复的 decision 中冻结语义选定的引用消息和明确 @ 集合，由 Host 基于固定 Topic 和群内可信真人消息校验，再传入 outbox/notification/adapter；无任务动作仍可合法选择 reply 或 reason。按已确认合同，省略 @ 或显式空数组均默认 @ 引用目标，非空数组则校验唯一同 Topic 参与者。持久副作用之前校验，执行与重启时复用同一冻结路由。保持原任务授权、所有权、审阅和幂等规则。

## 恢复与未决边界

- 旧 pending decision 无新字段时，若已有完整可信冻结 outbox/notification，应按既有实际路由恢复；若无完整路由证据，保守阻断并要求重新决策，不凭当前消息顺序或姓名推测。如何处理历史缺失的 @ 信息，须依据已有持久记录的真实语义决定；新决策省略或空数组均按已确认合同默认 @ 引用目标。
- 群消息回复必须明确可信真人目标；纯 web/internal 可无目标，但沿用既有外发限制，不因缺少真人来源增加群外发权限。`group-reply-format.js:67` 至 `:70` 的现有群回复格式化路径仍要求 source message/sender。引用的合法候选是否可从原始来源关联补齐，需以同群、版本和固定 Topic 证据为准，不引入跨 Topic 广泛架构。
- 需验证多依据 A 请求/B 解释、C 引用纠正、非助手引用伪造、同名歧义、跨群、空 @、多个 @、无真人来源、旧 pending/已准备通知/仅 outbox 中断及重复输入。以上结论均为当前源码只读分析，未重放真实消息、未操作正式库。

## 最终合同与初步建议差异

- 初步调查曾建议显式空 @ 不提及、无真人来源一律拒绝；最终合同保持省略和空数组均默认 @ 明确目标，避免改变既有通知语义。
- 纯 web/internal 场景可无目标，但沿用既有外发限制；真人群回复须指定并验证目标。上述差异是合同收敛记录，不代表已完成实现或实测。
