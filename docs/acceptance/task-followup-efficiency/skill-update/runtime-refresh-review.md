# 技能刷新机制的独立源码复核

只读复核 `session-skill-refresh.js` 及调用位置，并对照本机原生 DSH 的 registry、工具事件和 preset service 实现。未运行真实业务或发信。本记录是修订过程中的发现，不能直接作为最终候选通过证明。

## 已找到且已见修订的机制问题

1. 初稿仅通过 `ctx.get('fs')` 取文件服务。原生 preset 支持隔离 fs，正确服务需从 `agentPresets.serviceFor(agent, 'fs')` 获取；否则引用观察可能缺失或取错 provider。后续读回 SHA `0d2a2061c972cad0cbfead912056b7b3098e97017d90027037b1d3e07933437c` 第 18 行已使用 serviceFor。
2. 初稿在异步 `tools/result` 观察者中 await 两次 resolve 后才落账。原生 `dsh-tools/lib/index.js:3505-3524` 的 notifyResult 只捕获 Promise 拒绝，不等待完成，故下一模型步骤和会话排空可能先于版本记录。上述后续候选第 38-68 行已转为可等待的 post-execute 准备元数据，最终 result 同步落账。

这两项目前只确认代码修订方向正确，仍需原生测试证明实际 provider、记录顺序与恢复结果。

## 已反馈、需原作者处理或限定范围的事项

- **已有会话接入**：上述候选第 22-25 行仅恢复新 `skill-read` 事件。升级前已读取技能的会话没有该事件，在再次主动读取前 loaded 为空，自动变更提醒不起作用。可只从历史成功 skill 调用保守恢复待核对名称并提示重读，不把历史同名工具或旧正文当作可信当前规则；或明确这一边界，不能声称所有存量长会话已覆盖。
- **旧引用失效后持续提示**：技能成功切换到不同 provider/resourceBase 后，原 references 没有移除。第 85-89 行使用新根检查旧路径，可能永久 unavailable，即便新入口与新引用已读仍继续提示旧资源。应在实际成功重读改变根时回收不再属于当前技能根的引用，保留审计历史。
- **附加观察成为失败来源**：最新 post-execute 第 51-54 行的额外 resolve 没有错误隔离。原生 read 已成功后文件或技能目录变化导致解析失败，可能将观察错误升级为工具失败。版本观察应保留缺口，但不改写原已成功工具决定；信号取消仍遵循原会话语义。
- **每步重读成本**：第 74-79 行每个模型步骤串行调用所有已读技能的 registry.get。原生 `dsh-skill/lib/index.js:250-263` 每次都会调用 provider.get，只有目录收集有缓存。对当前少量本地文件可能成本很低，但远程或慢 provider 会增加每步延迟。应利用原生变更通知/恢复检查或给出实际基准；没有数据前不能声称没有额外耗时。

未发现本 helper 执行技能脚本、自动注入全部技能正文或主动改变业务授权。固定工具对象的方向合理；后续同名替换、不允许模型调用的技能、读取失败、恢复与引用变更仍需正式测试覆盖。

## 第二次定点复核

再次读回后，已看到以下针对性修订：实际 preset fs；可等待的 post-execute 元数据准备和最终成功结果同步观察；既有成功 skill 调用只形成待核对名称；成功换根时清除旧引用；观察解析失败不翻转原 read 结果；只在恢复或原生 skills/change 后读正文。提示使用原生 required runtime context，避免静态 section 比 pre-step 更早组装造成延迟。当前单元日志 `skill-refresh-unit-round-2.log` 为 5/5；原生完整测试由主线程复验，此记录不引用尚未结束的日志作通过证据。

SG1 diff 核查：事实答复只允许 humanReview + wait，在存储层重查当前待答申请和本轮 claimed 来源；原申请仍保持 waiting-reply。引用消息、发送群、作者、提及对象及来源版本须逐项匹配，内部 evidence 与公开 summary 分开。稳定通知 ID 与 followupReplies 在同一事务落账，可以防止原子保存后、wake ack 前的崩溃重发。没有看到因此开放新的业务写入、委派或解除批准路径。

仍向原作者报告两个需修正的具体反例：

1. **同轮多个事实追问**：`task.claim` 会认领全部待复核 wakes，但一次 submit 仅有一个 replySourceId，service 成功后会 ack 全部 wakeIds。只回答其中一条就可能消费其余未答来源。新增 replied 过滤只能防重复，不能恢复已 ack 来源。需覆盖多条 wake 和单条 wake 多个 sourceIds，保证未处置来源保留或逐项明确处理。
2. **版本摘要早于原生工具结果持久化**：原生 `dsh-tools/lib/index.js:3491` 在执行结果回传前 notifyResult；`dsh-agent-loop/lib/index.js:565-574` 随后才 appendToolResult。若在两者之间崩溃，当前独立 user/message 摘要可能已保存，而成功 tool/result 和正文尚未落账。恢复不能仅靠摘要当作已读。建议摘要关联 callId，并只恢复已有成功持久结果的观察；不完整历史转为待重读候选。

以上是源码控制流及可构造中断/批处理条件推导，未用虚拟判断冒充真实钉钉复现。修订后应定点复验，不因此扩大为全仓验收。
