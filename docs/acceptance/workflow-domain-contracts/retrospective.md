## 1. 已证实问题：混合流程绕过业务验收（P1）

触发场景：委托要求“修复生产故障并验证不再复现，同时保存调查记录”，验收项是“生产故障已修复”。调查输出明确故障仍在，验收项为 `insufficient_evidence`；随后通用阶段只写一份备忘录。Owner 引用备忘录产物，将修复项标为 `satisfied`。

最小复现输出：

```json
{"case":"mixed-investigation-and-unrelated-note","authorized":true,"semanticCalls":0,"manifestComplete":true,"validation":"structure-and-evidence-binding"}
```

调用链证据（路径均相对于本仓库）：

1. `packages/dingtalk-dsh-assistant/agent-work.js:195-203`：调查不足只要被随后非调查阶段的产物引用，就被认为获得补齐；没有要求该产物证明同一验收项。
2. `packages/dingtalk-dsh-assistant/task-general-workflow.js:181-194`：通用产物的写入结果摘要通过后，只要计划包含非通用阶段便直接返回 true，跳过 `completionCheck`。这里“文件成功写入”未证明“生产已修复”。
3. `packages/dingtalk-dsh-assistant/task-workflow-contracts.js:239-260`：逐个合同通过且清单完整后，公共门禁授权完成。

反证同时执行：只保留调查阶段时拒绝；只保留通用写入时调用语义检查并拒绝。问题是组合后的校验责任缺失，并非所有完成检查都没有作用。

归因边界：通用混合流程的跳过逻辑早于本 PR；新调查 v6 的不足补齐门禁与它组合时仍然放行。不能说全部根因由本 PR 新增，也不能用单独调查的反例测试代替混合流程验证。

建议：领域 validator 对其承担的验收项生成绑定当前输入、输出和规则版本的验证结果；Owner 只能汇总已验证结果。后续产物只有证明相同验收项时才能补齐调查缺口。不要只删除跳过分支，继而让每个写文件阶段承担整个任务的所有业务验收。

修复后至少验证：调查不足＋无关写入拒绝；调查不足＋真正的修复及验证证据通过；写入回执不能满足修复项；过期证据拒绝；有效组合仍可完成。还需通过真实服务入口验证最终状态，不能止于领域函数。

## 2. 两项合同设计缺口（与已证实漏洞分开）

### 交接缺少消费者支持的类型/版本声明

`task-workflow-contracts.js:55-74` 已核对当前计划、成功运行、generation、冻结定义、最终输出和必要字段，这部分值得保留。但它只提供生产者合同；`workflow-engineering.js:50` 只检查两个合同 ID，没有检查支持版本。

隔离 registry 验证中，假设受信生产者提供 `investigation-result@999`，工程准备适配器仍形成 `investigationHandoff`。该验证替换了更深的工程准备服务；真实工程服务在 `workflow-engineering.js:518-536` 还检查前序 workflow、运行身份和结果形状。因此这是合同扩展时的缺口，不是已经证明当前真实流程能接纳任意未知生产者或版本。

建议：在确实消费前序领域结果的入口声明可接受合同及版本，由统一入口检查，不依赖 ID 名称猜测。沿用冻结定义机制，不新增长期兼容分支。

### `requiredOutputs` 目前是目录元数据

`task-workflow-contracts.js:14-16` 将它复制到 descriptors；当前没有执行时的输出匹配或完成检查。实际结果字段检查读取的是另一份 `owner.resultContract.requiredFields`。

建议：明确区分展示信息与约束。目录从权威结果合同和交付要求派生；若不能派生就保留为说明，不把它宣称为执行门禁。不要再建立另一份必须手工同步的 `produces` 清单。

## 3. Cortex 最值得借鉴的约束与规范

以下是对当前源码/规范的归纳及针对本插件的建议，不代表 Cortex 所有业务路径均已实跑验证。

| 主题 | Cortex 的方法 | 对本插件的落地建议 |
|---|---|---|
| 受理契约 | 先确定受理/拒收、规则依据、材料与合法结局，再定义步骤 | 给调查、工程、发布、通用操作分别写清业务职责。通用写入可以证明保存成功，不能自动证明修复成功 |
| 约束分层 | schema 管形状；执行层管合法动作；领域 validator 管业务判据；prompt/Skill 提供专业上下文 | 长度、必填、身份与版本留代码；专业判据由领域维护；检索方法和表述建议留指令。不要用提示词承担状态转换或结果接纳 |
| 规则唯一来源 | 稳定规则 ID、依据版本、适用条件、证据要求共同定义；目录和返回 schema 同源生成 | 复用当前 acceptance item ID；补充真正需要的依据和适用性。任务冻结规则版本，避免模型临时发明阈值；简单任务无需引入通用规则引擎 |
| 候选与接纳分离 | candidate、validation receipt、accepted domain facts 分开 | 会话输出不能直接变成最终事实。产物绑定验收项及验证依据；Owner 汇总，不得凭叙述升级结论 |
| 业务结局与执行状态分离 | accepted/exhausted 是执行接纳状态；专业结论另存；允许部分交付与否由领域决定 | 明确“调查完成但无法确认根因”和“生产修复完成”的差别。仅在具体产品确有需求时增加带缺口交付，不能把所有不足改成成功 |
| 定向返修 | 反馈带 code/path/message，只重做受影响项；已接纳结果按输入/规则依赖决定是否失效 | 继续复用现有 repairCurrentStage 和预算；区分输出修正、业务返修、补料、外部结果回查、交付重试。当前分类是责任诊断，不等于所有恢复动作均已自动化 |
| 产物与交付 | 从已接纳的结构化事实渲染报告，冻结版本；投递状态独立表达 | 清单继续负责结构、身份和文件真实性；业务满足由领域验证负责，投递由真实回执负责，三者分别展示 |
| 质量验收 | 正确性、覆盖、证据有效性、一致性、成本与耗时有样本及分母 | 在结构性测试外增加阶段组合负例、领域样本及服务入口验证。504 个测试不能直接折算为业务质量百分比 |

## 4. 建议明确的职责分工

| 责任方 | 应承担的职责 | 不能替代的职责 |
|---|---|---|
| 产品/业务负责人 | 确认受理范围、判据、允许缺口和代表性样本 | 开发者或模型不能替其发明专业阈值 |
| Task Owner | 将目标编排为已注册能力，安排责任项，汇总有效验证结果，决定补料/返修/下一步 | 不能凭最终总结把不足改为满足，不能自行放宽领域结局 |
| 领域 workflow/validator | 输入输出合同、领域判据、证据有效性、逐项结果、合法结局和返修影响范围 | 不承包通用消息传输、UI 状态或宿主实现 |
| 节点模型/Agent | 在已给范围内检索、分析、产出候选并报告未知 | 不能自行接纳自己的产物、修改规则或绕过状态机 |
| Host/Controller/工具执行层 | 可信身份、版本绑定、状态转换、预算、持久化、效果回执、调用领域验收 | 不为每个领域内置业务规则，不把工具成功直接当作业务成功 |
| UI/钉钉渠道 | 收集用户输入与决策，展示同一权威状态，交付通知和文件 | 不维护第二套阶段状态或完成判断 |

当前 `task-owner-store.js:50-58` 的完成 assessment 只允许全部 satisfied。是否需要额外业务结局必须按调查、工程等各自受理承诺判断；这里列为产品设计议题，不直接把更严格的完成要求判为 bug。

## 5. 取舍及落地顺序

考察三个方向：

1. 只增强 Owner 提示词：成本最低，但实际错误路径发生在代码门禁，无法可靠阻止；不推荐作为修复。
2. 整体移植 Cortex 专家平台：超出当前目标，且现有持久化、Owner/Stage/Run、效果账已有价值；不推荐。本插件不需要本轮引入沙箱、网关或替换宿主/持久执行框架。
3. 在现有领域合同上补齐责任与接纳：与已实现机制相连，能够用组合反例验证；推荐。

实施优先级建议：

- P1 先封住混合流程验收漏洞，建立“同一验收项 → 负责领域 → 经过验证的证据”的关联；补服务入口反例与有效组合回归。
- 再将消费者类型/版本、权威结果 schema、派生目录落为一条清晰合同路径，避免 `requiredOutputs` 成为第二真相。
- 明确各领域受理范围、规则版本、允许的结局与返修责任。新增结构只服务真实领域需要，不建设任意 DAG/通用规则 DSL。
- 最后补代表性业务样本、恢复和交付链验证，分别报告代码测试、语义质量、真实服务入口、部署与钉钉交付的结果。

本轮没有证明开放语义可以完全由代码判定，也没有验证 Cortex 的真实部署或全面业务质量；借鉴结论只针对已读规范与实现。P1 尚未修复，PR 不应仅凭旧测试全绿就认定完成门禁已闭环。
