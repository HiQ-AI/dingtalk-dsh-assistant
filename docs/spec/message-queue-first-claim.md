# 消息排队执行时钟修复方案

## 现场问题

正式维护期受控重处理会提前执行message.activate。启动和Resume校验、调度排队消耗了90秒窗口；原请求尚无模型节点即被MESSAGE_DEADLINE_BEFORE_CLAIM置为失败。此前未把真实维护等待纳入隔离测试。

## 决定

- 首次成功领取非确定性模型节点时，在原生事务内建立执行时钟；维护和领取前排队不消耗执行恢复年龄。
- 已执行运行的恢复年龄使用真实执行起点；已有节点必须从真实startedAt推导，不能借升级清空已消耗的执行预算。
- 当前无节点的领取前超时走正常恢复路径，不按事故ID或版本添加例外。
- 纯系统状态通知已经独立送达且无业务命令，不应永久禁止显式重处理；保留送达审计，不重发旧通知。未知、发送中、仅ACK及业务回执仍不能被此规则放行。
- 不移除实际模型调用超时、执行次数或效果幂等校验。

## 验证

覆盖维护与排队超过90秒、未执行超过10分钟、已执行恢复预算不重置、实际调用超时保留，以及纯状态通知与未知/业务效果的区分。部署继续按现有维护、备份、精确包与独立回读流程。
