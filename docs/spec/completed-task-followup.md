# 已完成任务的批量续办

## 目标与现场证据

用户要求核查已完成事项的未合并 PR，新评论逐项修订并重新提测。协调器应识别原 Task，由各原 Owner 核查条件并继续处理；不因跨事项或未列 PR 编号，将已有交付转交一个新建总任务。

2026-10-20 原生会话只读取证：

- 路由会话 `session-coordination-ed87153213adadaab7a5777b-6748d22e` 的 JSONL 第 23–29 行：只查询 `group_topic_list(query=PR, limit=100)`，得到 12 个话题；以“跨已完成项目、未指明具体 PR”为由创建汇总话题。
- 决策会话 `session-coordination-07a87f3ceaef9f4d3a38ea93-6131f240` 的 JSONL 第 23–34 行：调用一次 `group_task_list(limit=100)`，随后两次提交 `new-task`（第一次仅因缺回复类型被拒绝）。没有 `group_task_context_get`、补分页或 `task-reopen` 调用。
- 完整任务目录回执为 177519 字节，14 项均为 completed，hasMore=false。模型可见结果出现 `Omitted 94607 bytes`；原生 spill 文件仍可独立读取。目录携带任务历史、来源和完成证据，超过模型工具输出预算。
- 安装目录与最新 origin/main 的 `task-topic-coordinator.js`、`decision.js`、`coordination-sessions.js` 内容一致；不是由旧主检出推断运行状态。

## 因果与反证

1. “没有读到已完成任务”不成立：调用及可见 completed 状态均有原生记录；但不能声称完整读了 14 项正文。
2. “重开不受支持或被拒绝”不成立：schema 和执行分支已有 task-reopen，同次会话没有尝试该动作；没有相应拒绝回执。
3. 已确认的决策错误：把批量跟进当作独立交付，把保留原 PR 当作保留原 Task。现有指引强调新建准入，没有解释完成后的增量续办、多目标 action，以及新 Topic 不代表新 Task。目录溢出加剧遗漏风险；不能据此断言溢出是唯一原因。

## 修改范围

- 在现有协调器内补充任务身份选择规则：旧交付新增核查、评审修改、返工、重新提测属于续办；completed 用 task-reopen，活动任务用 task-context，按当前版本和原授权分别构造 action。
- 跨任务指令先分页核对任务目录和必要详情；一个 effectOwner Topic 可提交多个原 Task action。单一事项沿原 Topic，多事项可以由一个协调 Topic 承接，但不据此创建总执行任务。
- 条件核验可交给对应原 Owner 先做，无新评论或 PR 已合并则如实结束，不重复修改/部署。仅引用旧资料、独立新交付或明确要求另建任务仍允许 new-task。
- group_task_list 改为有字节预算的轻量目录，返回身份、目标摘要、完成摘要、版本和话题引用；以实际返回数计算 nextOffset/hasMore，完整内容仍由 group_task_context_get 读取。保留未归档、当前群和查询过滤。
- 不增加 PR 业务关键词拦截、自动推断任务归属、批量自动重开或新的执行协议。

## 验证与交付边界

原生定向回归覆盖目录超量分页、不漏项、详情独立读取、多个 completed 原 Task 重开、原会话及历史保留、重复消息不重复动作；相邻独立新任务路径继续运行。模型决策修复另做隔离真实模型回放，只记录协调决定，不提供业务执行或钉钉发送能力；确定性测试不冒充真实模型语义验证。

更新 README 和当前任务会话运维说明，通过本地验证后提交 feature PR。普通分支不触发 CI，不执行生产任务重放或本地部署；现有总任务及原 Task 的现场处置需另按已发生效果核对，不能直接删除或重复派发。
