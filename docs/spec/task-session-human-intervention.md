# 任务会话人工介入闭环

用户新增要求：统筹无法自行解决或遇到受控边界时提出人工介入，任务进入等待中；人工给出答复后回到执行中并沿原任务处理。等待受控小目标仍属于执行中。

现状：task.wait.question只触发群提问，当前运行时listAuthorizationRequests为空，Observer人工介入入口已退化历史只读，缺少持久申请与答复路由。

方案：复用dynamic task JSON账的humanRequests，不新建表；申请绑定task、需求/控制版本及question，进入waiting-reply。复用原有介入列表展示当前申请，仅对当前任务申请提供原文答复表单。新增受信本机HTTP答复路径，实际webActor身份记录source；task.human.respond原子核对版本、请求、作者、群及任务排空，回答入账并唤醒原任务，旧任务状态/暂停/未知效果不被绕过。审批边界只针对申请事项，答复不扩权。已答/失效/其他作者/旧版本均拒绝或按原请求幂等。

普通任务修订或终态使旧请求失效；等待人工时新的执行结果先持久，不驱动统筹绕过人工等待。来源明确且已被话题路由接纳为本任务补充的本人回复，可沿同一原文回答路径闭环。保留原先删除的需求与控制区，不借此恢复通用操作面板。

验证：store原子状态和身份/版本反例；模型请求中专门介入工具；原生service申请→waiting→答复source→同task/session running，等待活小目标仍running；HTTP本机身份与校验，UI必填/loading/error/stale及成功刷新。部署以当前原业务执行静止为前提，不为部署中断活动业务。
