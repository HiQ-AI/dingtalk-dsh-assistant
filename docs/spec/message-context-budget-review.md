# 消息上下文限额审查与修订方案

日期：2026-09-24。状态：审查完成，方案待实施；本轮没有修改插件源码或部署。

## 1. 结论与范围

现有修复解决了 R 节点补材料后漏算输入的问题，但尚不足以作为统一上下文方案。必须同时处理计量单位、关键证据保护、跨节点材料传递和原节点恢复。否则“减少输入”会把容量故障变成错误关联或遗漏约束。

保留 S（事项拆分）→ R（话题/任务关联）→ I（处理意图）的职责划分，继续按时间逐条处理消息。最近 30 条消息、引用链及对应话题/任务历史由代码保留为完整可读取材料；各节点按职责读取，不要求模型重新记忆整段会话。

审查对象为 `24b55a66e4d5d8f473111159a7511bf3d4ebf800` 加当前未提交改动。`message-context.js`、`message-workflow.js`、`message-ledger.js`、`workflow-service.js` 均已独立比对本机 web profile 安装文件，SHA256 一致。

证据：只读运行账、源码、现有 50 项定向回归，以及真实工作流与隔离 SQLite 的四项反例。反例使用模拟判断器，没有模型调用、渠道发送或业务派发。详情见 `../acceptance/runtime-redesign/round-29.md`。

P1 是实现前必须消除的正确性/恢复缺口，不代表已发生生产写入事故。B02 反例证明信息传递缺口，没有执行生产动作。

运行反证：只读核查的 47 个 MessageRun 对应 31 个来源；各来源最新版本为 18 个 settled、13 个 outbound_echo/superseded，目前没有最新版本因容量仍等待。这个结果支持“两条重放已经通过”，不能消除以上可复现缺口。重放覆盖旧 reason，节点重试可能复用记录，不能用当前错误数推算历史发生率。

实际两条重放分别经过 S、R、补材料、R、I，共 4 次模型调用。节点模型段耗时合计约 35.0 秒、28.5 秒，尚未包括等待材料和排队。减少不必要的第二次 R 调用能直接降低耗时。

## 3. 三种候选方案

1. 统一提高字节上限：改动小，可以短期减少拒绝；无法修复候选误删、约束丢失、恢复失败，也不能准确控制 token 成本，不作为主方案。
2. 每次超限先让模型总结或删除最旧内容：额外增加调用和延迟；摘要可能遗漏否定、授权范围和目标变化，不作为普通消息必经步骤。
3. **采用职责明确的输入合同、完整请求 token 计量、保护关键证据的投影、按版本补取和恢复。** 代码负责检索、去重、裁剪、计量和状态迁移；只有确需语义判断/大材料提取时调用模型。

## 4. 节点输入合同

| 节点 | 必需输入 | 可选输入与取回方式 | 输出及校验 |
| --- | --- | --- | --- |
| 代码上下文准备 | 当前原文/来源版本/发送人，最近30条本地快照，引用定位，当前群职责版本 | 历史原文与话题/任务材料以索引保存 | 创建不可变 snapshot、短引用映射、材料版本、缺口；不直接产生业务动作 |
| S | 当前全文只发送一份、片段位置、必要指代背景、全局否定/条件/共享限制 | 一般背景仅给最小识别信息，按短引用补原文 | 事项覆盖全文；每项来源范围和限制可定位，未覆盖则不派发 |
| R | 当前事项、引用关系、明确命中的候选、候选关键差异与相关任务历史 | 非明确候选按相关度分页；保留可补取的召回批次引用 | 关联结果携带 evidenceRefs、候选覆盖状态；不能以裁剪造成的“没看见”证明应新建 |
| I | 关联身份、当前相关状态、适用群职责、有效约束及 R 依赖的证据 | 不传所有其他候选和整份历史；按范围读取具体证据 | 意图/参数/限制/replyPolicy，逐项追溯来源；Host 独立验证权限及目标版本 |
| 材料处理 | resourceRef、目的、来源版本、已有覆盖范围 | 代码先定向读；长材料分块提取相关事实 | 记录事实、原文位置、否定与限制、覆盖/遗漏情况；新材料使依赖节点失效或就绪 |

短引用如 h1/t1 仅在本次 snapshot 内有效，Host 保存到真实来源/任务 ID 的映射并校验返回值。权限范围、目标身份不能因缩短标识而放松。

R 补取材料应形成共享 evidence 项，I 按 R 的依赖集合及限制类别取用。原文约束与模型总结分别保存；限制汇总不能只保留“最新一条”，修订/撤销需有来源和版本依据。

群职责按规则范围分为接纳条件、动作限制、回复要求，保存原文及版本。先用结构化配置或已确认的规则组织投影；自由文本中尚未明确分类的要求保留并标记，不以字符截断或未验证的摘要代替原规则。

## 5. 计量与超限处理

把三个问题分开记账：

- 请求字节：保护存储、传输和单项材料内存，字段名使用 bytes。
- 模型输入/输出 token：对最终 system、schema、messages、材料和必要协议开销计量，优先使用与当前模型匹配的计数器；计数器不可用时保留经样本校准的保守估计及误差标记，不用未经校准的统一除数。
- 来源累计成本与尝试次数：节点补取、修正、失败和恢复共用可审计账；未知 usage 保留预留值并标 unknown，不能算作零。

一次生成不可变的最终请求，计量、hash、持久化及发送使用同一份内容。计量之后不再追加澄清答案、schema 或补取材料。提供商包装无法完全计量时显式预留，使用返回 usage 校准。

每个节点有软目标和硬门槛：超过软目标先整理输入；保留的必需证据大于软目标时允许使用本节点剩余的已配置额度。硬门槛为已验证的模型容量扣除输出/协议预留，并受该来源剩余额度限制。具体值通过冻结样本校准后绑定 policyVersion，不能每次故障临时涨限额。

本地成功调用账只能作为校准起点：S 42 次 input-token P95=2,916；R 42 次 P95=3,853；I 17 次 P95=3,773。包含重放、成功节点和不同代码时期，不能直接据此设生产硬上限或声明性能达标。

投影按固定顺序进行：删除重复字段/长标识冗余 → 删除可恢复的低相关背景 → 缩减非保护候选 → 对相关长材料走定向提取。每步保留机器可读的缺口与恢复引用。

保护集合至少包含当前正文、明确引用对象、当前选中目标、用于消歧的关键事实、否定/条件/授权边界以及未解决的证据冲突。保护集合过大时走材料处理，不能继续删除整个候选直到勉强装下。

## 6. 大材料与恢复

1. 原文入库后，代码按自然边界分块并保留 offset/hash；先读取与问题相关的结构化字段或章节，不把完整文件重复送入 R/I。
2. 必须语义提取时，启动受原来源预算约束的材料节点。提取保留原文位置、关键限制和覆盖清单；若全局限制仍未知，消息保持材料处理中。
3. 材料完成立即发布带版本的 ready 事件并恢复原节点。完整历史、材料正文、用户答复分别保存，避免在每次尝试中累计复制旧答案。
4. 重试依据 sourceVersion、policyVersion、projectionVersion、evidenceVersion 和 inputHash。确定性的容量/缺证问题只有输入或投影真实变化才重算；网络瞬断可按有限退避重试相同请求，原因单独分类。
5. 相同问题、相同材料、相同版本未产生新信息时停止语义循环，记录具体缺口；系统容量问题不能生成向群成员索要授权或重复澄清的消息。
6. 原节点没有效果时允许重新准备输入；已有 applied/unknown 命令保留原消费记录，只恢复受影响的未派发节点，unknown 先对账。不能用“存在已解决 request”一概拒绝恢复。
7. 人工重处理保留原始接收时间和历史总成本；如需新增额度，显式记录恢复决定及额度，不再依赖第5/6版等业务无关特例。节点成功不改写消息原始端到端时钟。

流程状态区分等待材料、准备模型输入、等待模型配额、模型失败、系统容量不足和业务歧义。服务商 429/配额不足应走 provider 准入/退避，本次样本没有证据说明它是主要原因，不能与本地字节门槛混报。

仍保持消息逐条处理；新补充形成版本化输入，按依赖关系使相关节点失效，成功且不受影响的节点复用。任务执行作为已移交工作流独立继续，不让工程执行时长占用消息分类流程。

## 8. 验收条件

- 四个已复现的反例改成预期通过：明确引用不被删除；R必要限制到达I且影响校验；确定性分支无模型容量拒绝；已解决材料的超限恢复保留原运行身份及副作用记录。
- 普通消息不默认新增总结模型调用；先用代码准备材料，能直接具备证据时只需 S/R/I，精确代码分支实际模型调用为零。
- 重放今天两条单位归一化消息，以及此前审核状态查询/两任务补充/三项澄清；由人工定义正确关联和动作，不能以模型返回合法JSON代替语义验收。
- 否定在长材料末尾、九个以上候选、完整引用超过窗口、职责变更、材料版本变化、补充到达期间重启、实际提供商429与本地超限分别覆盖。
- 端到端统计包含排队、材料、模型、提交及失败/等待，保留普通消息有效接纳 P95≤45秒的待验证目标。分别报告成本和正确率；不从分母删去失败，不用自动“无动作”减少耗时。
- 本轮没有为新方案宣称完整绿灯。既有50项通过只证明未动源码时已有路径仍符合旧测试；四项审查反例仍待修复。
