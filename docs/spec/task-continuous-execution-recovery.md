# 任务持续执行与恢复优化方案

日期：2026-10-01。状态：方案，尚未实施。

## 目标与范围

按用户要求，以任务正确完成为首要目标：删除应用层任务、Owner、执行节点及验收阶段的固定步数、重试次数和总时长窗口；可修正问题在原执行中继续，条件未变化时不反复启动模型。缺材料、缺实际权限或明确需要人工决定时，一次性说明缺口，满足条件后从原任务断点继续。取消仍立即生效。

本方案覆盖消息接入、群协调、Owner、编排节点、工具、验证、交付与通知的交接。现有恢复合同仅覆盖消息问答，执行时长文档仅覆盖统计，故单独记录本次跨层方案。不保留旧执行策略兼容分支，不重新启动已被用户结束的旧业务任务。

## 一条连续执行路径

消息持久接收 → 群常驻协调绑定唯一事项 → Owner建立/调整当前计划 → 节点执行及工具纠正 → 验证 → 必需审批/交付 → 独立回读 → Owner完成。

沿用现有Task、计划、节点、原生会话与控制账，不增加新调度器或多层代理。每个失败点只有一个恢复责任方：节点修正参数与结果，Controller恢复传输及进程故障，Owner处理真实依赖及计划变化；群协调只接纳新业务信息，不轮询催动同一执行。

## 修改方案

### 1. 去掉任务终止上限与运行窗口

删除maxSteps、节点总timeout、重试次数转终态和恢复预算字段及其上下游注入/校验；移除检查和验收的总墙钟截止。统计可保留步数、耗时和尝试数，统计值不再决定任务停止。不以超大数值、0哨兵或其他隐藏默认值模拟无限。

补充消息不再等待固定静默窗口：当前已持久化的同事项输入作为一个事务批次消费，后续输入进入下一批；只重算受影响的未完成后缀，无关执行继续。版本变化触发增量协调，不重放已成功效果。

队列满时任务继续持久排队，不拒收或终结；工作进程按资源承载逐个领取，逐批读取直到处理完。分页、并发调度用于承载任意总量，不成为任务数量或任务成功机会的上限。

连接建立、失联检测及外部服务本身的协议限制仍须识别，但不得转换为任务总截止。不要把单次I/O失败等同于任务失败。有进展的长任务持续运行；进程确已退出或连接明确失败时，释放本次调用后按事实恢复，不遗留无限挂起的死调用。

### 2. 用当前条件决定恢复，取消原样重试循环

- 参数/schema/查询容量可纠正：向当前节点返回准确原因和可行动反馈，修改参数或分页继续，不重建Task/Run。
- 传输临时故障：保存原进度，遵守服务Retry-After；无恢复事件时只由Controller退避探测依赖。指数退避须有防数值溢出的实现；取消/恢复事件优先唤醒，无尝试总上限、无总恢复期限，不每次启动整套模型。
- 同一输入、同一错误且没有任何新进展：不重复同一动作；节点改变处理方法，或等待已识别的依赖。不能仅比较原始错误文本，需绑定操作、输入版本和当前原因。
- 缺材料/权限：核对当前已登记能力和材料后，一次性询问具体缺口；回到对应Task继续，避免要求重交已有材料。
- 实现错误/服务不可用且无法自行修复：通知一次“处理遇到系统问题，无法继续推进，需要人工介入。 - 小小鹏代回”；依赖恢复或修复部署后唤醒。不得将真实程序错误当作无限重试的暂态。
- 外部写入结果不明：先读取实际效果并对账；确认未执行才重发。保持任务身份和效果幂等凭证。

删除Owner失败3次即blocked和恢复3次上限；blocked/waiting只由真实缺口决定。避免Owner、Controller和群协调分别重试同一错误。新输入、能力变化、依赖恢复与执行结果通过现有持久事件驱动。

### 3. 一次交接完整执行上下文

统一从当前Task事实构造节点输入：目标、验收条件、已提供材料引用、业务限制、已有工具能力及其授权范围、前序结果、尚缺依赖。启动前只验证当前节点必需项；后续审批和无关材料不能挡住前面的可执行调查。

读取现有生产只读配置并正确登记到任务能力目录；不把插件未注册能力误报为用户没有权限。遇到真正授权缺口立即询问，不自行扩展数据访问。

正文和大结果按引用及原生分页工具读取；已有结果复用。实际模型上下文容量由原生压缩/恢复及检查点处理，不新增材料总量或任务总步数限制，不静默裁掉业务约束。

### 4. 节点局部恢复与增量计划

已成功节点及已确认外部效果保留。仅重做失效输入影响的后缀；当前节点可自行修正的问题不提交给Owner反复重新编排。Owner只在新需求、真实依赖或阶段结果改变时决策。

进程重启使用原任务身份和已持久检查点恢复。应用决定前核对它当前可执行；明确无效果的非法决定返回当前Owner纠正；已有或未知效果先对账，禁止盲目重复应用。

任务删除同时清理其专用冻结定义、会话和工件；原始消息及幂等凭证保留。启动按存活Task/Run恢复定义，不让已删除任务的历史定义阻断其他任务。

### 5. 通知只对应用户可见进展

按事项发送实际开始、需要用户提供材料/权限、真实人工阻塞、关键交付和最终完成通知。内部纠正、暂态探测、重复补充不产生新回复。恢复后确有进展才更新，技术原因变化不重复通知同一业务阻塞。

撤回仅用于已失效或错误回复；替换正文仍只报告当前进度。不以消息条数、重试次数或版本次数生成通知。

### 6. 完成以验收事实为准

Owner完成须引用实际执行结果及验收证据；流程节点成功、消息已送达、服务健康均不能替代业务验收。可自动纠正的验收失败进入局部修改和再验证，不重启整条任务。不可自行解决的缺口一次告知。

对于原批次，完整业务链仍是只读核验/脚本核验→授权审批→两条测试执行→请求者确认→正式69条执行→独立结果核对。该任务已被明确结束，本方案验收使用独立测试任务，不擅自恢复原生产变更。

## 实施次序

1. 统一执行策略，删除链路上限、累计运行窗口及固定补充等待窗口；同步当前配置、接口和部署文档，不做兼容。
2. 明确单一恢复责任，补齐可纠正错误、真实等待、能力传递和原任务续跑。
3. 核对节点断点、效果对账、通知责任及历史清理一致性。
4. 定向集成→实际安装包→独立端到端测试任务→进程中断恢复；全链通过后报告稳定性边界。

## 验收标准

- 超过旧32步、120秒和3次纠正仍能正常推进；不得存在改名后的等价截止字段。
- 复杂材料可分批处理直至全部完成，不因条数/大小触发任务终止；有效业务约束完整保留。
- 同原因且输入/依赖未变时无原样高频模型重试；网络故障恢复后同Task继续，已成功节点不重复。
- 消息持续补充时按影响范围推进；独立事项不被长期材料等待阻塞。
- 缺权限时只询问实际缺口一次；提供权限后无需重交任务和已有附件即可继续。
- 查询容量场景自动缩小查询/分页完成；最终数据核对和产物验收通过。
- 长任务运行期间取消生效；进程重启及外部写入ACK丢失后，不重复业务效果。
- 一个事项只有一个Task；内部纠正不新增群回复；真实阻塞/完成分别准确通知。
- 清理已终止任务后重启成功，当前流程定义、原始消息和运行配置保持一致。
- 使用同一份case×round矩阵记录真实反例及最终证据；不能用局部单测或健康检查替代A14全链验收。

无法承诺外部服务永不故障或真实审批无需等待。本方案的保证目标是：有执行条件就持续推进，条件暂缺则准确等待并一次告知，条件恢复后原地继续，不因内部次数或时间预算丢弃任务。
