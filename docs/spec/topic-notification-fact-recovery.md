# 话题上下文、通知事实与恢复操作修复方案

## 1. 目标和本次边界

以 `6f1a8bb` 和本地控制库只读回查为基线。本文件是实施前方案，不修改运行数据、不重放消息、不撤回或补发消息。

可验证目标：同一问题的补充消息能读到关联任务及既有执行结果；已执行事实不会被重处理抹掉；承接、结果和澄清按不同业务事件判断重复；撤回有逐条证据和范围，补发与被替代消息可追溯；运行成功与业务目标满足程度分别表达。

既有话题批量归类、每话题独立意图判断和多阶段 Task 设计继续保留。本次针对真实案例暴露的事实缺口，不重建第二套 Topic、Task 或 Outbox。

## 3. 统一事实输入，补上话题到任务的关联

在现有控制库与 `workflow-service.js` 中增加一个复用的事实读取入口，供话题意图判断、任务查询、通知审核与运维预检调用。返回引用及必要摘要，不复制整库历史：

- 原始输入：sourceKey、真实 sourceVersion、发送者、时间、引用及话题绑定证据。
- 话题下关联任务：taskId、接纳目标、计划/需求版本；一个话题可以有多个任务。
- 执行事实：Run/阶段状态、outputRef、已核验证据、执行范围及 limitations。
- 通知事实：事件类型、关联任务/Run/来源、冻结正文、发送任务 ID、实际消息 ID、投递/撤回/补发状态。

任务集合通过消息命令与话题绑定的持久关系取得，不靠标题相似度重建。失效来源版本保留历史，但明确区分当前有效目标和已发生执行/发送。任务多于模型上下文容量时给可分页的引用与覆盖信息；未读完相关事实不能声称“没有任务”或据此新建相同任务。

IB 不再要求 binding.taskId 存在才拿到任务事实。它需要明确选择：补充既有任务、查询结果、追加阶段、修订目标或新建独立任务。Host 校验选择对象属于当前话题与会话，且源身份、需求/计划版本和任务语义状态未变化。任务完成、结果产生等变化使旧判断快照失效；不使用心跳时间作版本，避免无意义重判。

## 4. 关联、授权和执行目标分别判断

去掉这次特定句式加 90 秒直接绑定并授予准入的特例。明确引用优先；最近消息仅排序候选。语义判断必须结合原文、引用、话题目标和关联任务事实，输出可回读的来源引用；多目标或证据冲突时保留待确认状态。

授权由 Host 统一解析成明确结果：允许、明确无权、缺少目标/依据。R 的关联和“同一发送者”都不授予新增能力。预检、实际派发和任务内后续执行使用同一授权事实及目标范围；派发前重查当前授权。缺上下文、缺流程、缺能力分别报告，只有已确认权限不足时才能发送“无权”通知。

材料分析仍是合法工作。若目标是“根据所给材料分析”，分析输出可以完成目标；若目标是“去业务系统查账号”，则需选择已登记的查询能力或调查阶段，并给出实际账号/日志证据。能力缺失时将具体阶段标为受阻，不能以材料分析悄悄替代现场查询。任务执行中收到“继续查”应沿原 Task 增加或推进查证阶段，保留原分析 Run 及成果。

保留 `Run.status=succeeded` 的技术执行事实，复用计划/验收机制增加对当前目标的评估：满足、未满足、尚无足够证据，并记录逐项证据和阻塞原因。不能用 `limitations.length > 0` 自动判失败，也不能仅凭 Run 成功宣布目标完成。存量缺少评估的记录显示“未评估”，不回写历史 Run 为失败或编造验收证据。

## 5. 按业务事件去重，不把正常两条通知当成错误

复用现有 `message_items` 通知账，补充明确事件类型及业务身份：

| 通知类型 | 事实依据 | 去重边界 |
| --- | --- | --- |
| task.accepted | 已接纳的 Task/创建事件 | 同一接纳事件只发一次 |
| task.result | Run 或阶段结果、结果版本 | 同一结果事件只发一次；后续阶段是新结果 |
| task.blocked | 当前受阻阶段及原因版本 | 同一未变化阻塞不反复提醒 |
| request.clarification | 当前有效请求和问题版本 | 解决或被替代后不再发送 |
| action.rejected | 具体动作和 Host 拒绝依据 | 不能与任务承接共用含糊的 receipt 语义 |

给事件分配稳定 `eventKey`，由 Host 从 Task/Run/阶段/请求/版本计算，不以新一轮模型调用或新 commandId 自动产生新业务事件；通知投递实例另外有自己的 ID。承接与结果永远是不同事件，不因同源消息而互相去重。

对已发生发送的等价事件优先复用事实，禁止再发。发送前最终校验依据是否仍有效；新事实仅使尚未发送且确实过期的通知失效，不能把所有旧结果或承接记录失效。已发送通知是否有误走下一节的独立操作，不自动反推撤回。

## 6. 撤回和补发进入统一操作入口

在 `workflow-notifications.js` 复用发送/回读适配器，在 `message-ledger.js` 增加持久操作记录，通过现有服务/HTTP 层暴露预检和执行。无需新建独立消息子系统。工作流通知运维使用这个入口；外部手动操作通过有证据的对账入口登记，禁止直接改 SQL。

接口分为 `notification.operation.prepare` 和 `notification.operation.execute`：前者只保存可审阅的候选与事实快照，返回 operationId、逐条动作及摘要；后者消费 operationId、既有授权来源和 expectedFactDigest，在事务内校验后领取操作。`notification.operation.reconcile` 只接纳来自真实查询的外部事实，不调用发送或撤回。通知事件及操作记录复用 message_items，不建立平行 Outbox。

每次操作必须先生成逐条预检清单：通知 ID、真实消息 ID、正文、事件类型、Task/Run/输出引用、错误依据、拟执行动作和保留项。模型只可提出建议，不能只凭“错误回复”这类总结批量选中同话题全部通知。

- **内容与事实矛盾**：指出具体句子与相反事实。例如“无权”的 Host 判断缺失或被验证错误，才可标为错误拒绝。
- **确实重复投递**：证明同一个 eventKey 对应多个已发送实例，并选定保留实例；不把 task.accepted 与 task.result 当重复。
- **正确但存在局限**：保留。任务没有完成全部业务目标不使其真实承接通知或既有分析结果自动变成错误。
- **用户明确撤回某条**：尊重精确对象授权，不要求把正确内容伪装成错误；仍记录范围和原因。
- **证据不足**：不自动执行撤回，展示缺什么证据。

授权针对明确清单；用户已明确授权该清单时直接执行，不重复索要确认。执行前比较正文 hash、Task/Run/结果引用、通知版本和消息 ID；发生变化则预检失效。真正发送/撤回只消费一次操作 ID，崩溃或超时进入待核对，不能盲重试。

此次误撤回实际由 Coding Agent 直接调用 DWS 产生，Runtime 门禁无法拦住进程外的任意 CLI 调用。项目运维说明和 Agent 操作规则必须同步要求：受工作流管理的通知统一使用上述入口，先读逐条事实再确定操作范围；“重复”“错误”“任务未执行”等结论需对应证据。该规范能约束受管操作，但不宣称技术上阻止拥有同一钉钉凭据的人绕过入口；本方案不擅自改变全局凭据权限。

通知的投递、撤回、补发分开记录：ACK 只证明接口接受；实际消息 ID 和独立回读证明送达；撤回请求结果与会话列表核验分别留存。详情接口仍返回历史正文不单独作为撤回失败依据，完整会话查询无目标也不能单独推断此前从未送达。撤回结果未知时不生成补发。

补发默认恢复所选历史事件的冻结正文，记录 `restoresNotificationId` 和新的实际消息 ID；重复操作复用同一投递实例。需要改措辞时先形成可审阅正文，记录为更正通知并关联原事件，不能把“补发”默默扩大为自行改写或新增结论。补发不新建业务任务、不重跑已有 Run。

## 7. 恢复入口与界面修正

将“重新处理”收敛成两类明确操作：

1. **隔离验证**：基于已冻结输入在隔离存储中复核 S/R/IB，未配置真实发信和业务写入适配器。产生决策差异报告，不接触真实收信进度、任务与通知账。验收默认使用这一类。
2. **恢复未完成阶段**：保留 sourceVersion、topicId、taskId 与有效执行事实，只重试指定失败判断或在原任务上继续。派发前重新核对最新输入、任务状态、授权和全部相关历史版本的外部效果。

sourceVersion 只表示渠道原文确实改变；人工重试另记 attempt，不通过“新来源版本”绕开旧命令和通知。已有发送时拒绝整条重跑的保护保留；补充输入通过新的消息事实推进原话题。此次 retry 入口的效果检查统一复用同一预检函数，避免相邻入口各写一套。

界面直接显示“待发送、发送中、已提交待回读、发送结果待核对、已回读、发送前作废”，撤回/补发显示为独立附加状态及关联链接。不能把 acknowledged 或 unknown 都显示成待发送。Task 展示“运行完成”和“目标满足程度”，保留已执行结果和未完成事项，不再仅用一个成功标签解释两者。

## 8. 当前现场数据对账

只处理本次四条旧通知和两条补发消息：

1. 只读生成六条消息的证据清单，核对同一 profile、会话、发送者、引用、正文、发送及撤回结果。
2. 对原来只有 ACK 的澄清补记已经独立查询到的消息身份和送达证据，再登记撤回事实。
3. 登记四次撤回和两次补发的关系。此次补发正文已经改变，按实际正文记录，不能冒充逐字恢复。
4. 保留原 Task、Run、已接纳命令和分析产物；不重新派发、不删除历史通知、不恢复旧库覆盖新增事实。
5. 对账脚本支持 `--check` 零写；执行后独立查询确认六条记录能互相追溯，未增加外部消息或 Task。

## 9. 修改位置与实施顺序

| 阶段 | 主要文件 | 交付与放行条件 |
| --- | --- | --- |
| A：统一事实与通知对账 | `workflow-service.js`、`message-ledger.js`、`message-topics.js`、既有操作 runbook | 话题能读到关联 Task/结果/通知，补发撤回可审计；六条现场消息完成只读预检与受控对账 |
| B：通知事件和操作门禁 | `workflow-notifications.js`、`message-ledger.js`、`http.js`、消息列表客户端/Observer | 承接与结果不互斥，去重跨重试有效；撤回有逐条依据，补发严格幂等；状态不误报待发送 |
| C：关联、授权、恢复和目标核验 | `message-workflow.js`、`message-model.js`、`workflow-service.js`、`task-workflow.js`、现有 Task 计划/报告检查 | 移除特定句式授权，补充意图沿既有 Task，隔离验证零外部效果；运行成功不冒充实际查证 |

按当前存储扩展能力复用同库记录；需要新增唯一索引或结构时走显式 schema 迁移、`--check`、停机备份和版本回读，不在启动时猜测修补旧库。旧记录依据不足时标为未核验，不用补造身份来通过门禁。

## 10. 验收与发布门槛

实施时在 `docs/acceptance/topic-intent-task-composition/` 扩充矩阵与新的 round 记录，保留既有真实 FAIL；不覆盖历史轮次。

| 用例 | 必须观察到的结果 |
| --- | --- |
| 同一 Task 承接后产生真实结果 | 两类通知均合法且各一次，不互相去重或被批量判错 |
| 同一事件重复恢复、改 commandId、进程重启 | 无重复发信；原业务身份、Task/Run 保持一致 |
| 发送 ACK 后崩溃或回读延迟 | 显示待回读；只核对原发送任务，无第二次 send |
| 任务分析成功但实际查证目标证据不足 | 保留 succeeded 和分析成果；目标显示未满足/证据不足，不能宣称未执行或已查证 |
| 用户只要求分析给定材料，结果有局限 | 可正确满足目标，不因 limitations 非空误判失败 |
| 同话题追加“继续查”，原任务运行中或已结束 | 正确关联并沿原 Task 续办；保留旧 Run，补齐需要的阶段 |
| 同人 90 秒内切换两个话题，或其他成员插话 | 时间邻近不强制绑定、不授予权限；歧义显式保留 |
| 未授权发送者、跨群任务、权限在派发前变更 | Host 拒绝，无外部效果；缺上下文不冒充权限拒绝 |
| 混合选择两条有效通知与两条有误通知 | 预检逐条判断；默认错误清理只包含有证据的两条，不扩大范围 |
| 撤回/补发后进程崩溃、返回丢失、重复点击 | 保留外部操作身份并只做核对；每条操作至多一个新发送实例 |
| 撤回详情仍返回正文、会话列表已移除 | 两种证据分别记录，不重复撤回或误报未撤回 |
| 补发已授权历史消息 | 正文与预检 hash 一致、引用正确、记入通知账，不重跑任务 |
| 六条现场消息对账 | 全部外部事实可追溯，原任务产物保留，新增外部消息数为 0 |
| 隔离重演 #51/#52 全链 | 验证新决策及任务/通知身份；真实发信、撤回、业务写入次数均为 0 |

先隔离重演和故障注入，再构建安装并核对实际源码哈希、进程、健康和账本。真实渠道发送验证使用明确的测试消息/会话及授权，不再次拿已处理业务消息做整条回放。PR 保持 Draft，直到与本次修复相关的矩阵通过；模型的语义判断仍可能出错，但错误提议必须经过事实和效果门禁，不能直接变成批量撤回或重复执行。
