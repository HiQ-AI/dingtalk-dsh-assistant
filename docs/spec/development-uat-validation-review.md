## R1 / P1：UAT 分支并发变化可先写入、后发现未验收树

**定位：** `packages/dingtalk-dsh-assistant/workflow-uat-merge-platform.js:156-164`、`:141-142`；`workflow-platform-clients.js:211-215`。

执行前回读 base，但实际 GitHub merge 请求只绑定 head。最后一次回读后，其他写者推进 UAT 分支，GitHub 可以合入新的组合树。现有校验在合并后发现树不同并报错，此时 UAT 分支已改变。纯内存 fake 平台复现已发生一次 merge 调用、模拟目标分支改变，再报 `UAT_MERGE_SOURCE_TREE_OR_BRANCH_UNCONFIRMED`。

**修改方案：**

1. 精确版本合入必须提供“目标分支仍等于冻结 base”这一原子条件；没有该能力时，合入前阻断。多读一次不能消除窗口。
2. 首选受信合入器：继续核验原 PR 身份、目标环境、检查及本地验收凭证；确认冻结 base 是待交付提交的祖先、待交付 tree 等于已验收 tree。通过 Git 的显式目标 ref/expected SHA 租约推进 UAT，仅允许上述快进关系。凭据和 ref 必须来自冻结 Host 配置，禁止任意分支和非快进覆盖。
3. 独立回读远端 ref、tree 和原 PR 的实际合并状态，再生成阶段产出；拒绝以普通关闭 PR 冒充已合并。不得绕过现有分支保护。如果仓库要求只能通过合并队列推进，则使用原生 merge queue，对实际 merge-group 提交重新验证并绑定证据。
4. 发生并发推进则拒绝本次写入，重新同步 UAT 并创建新的候选验收；不自动使用旧凭证合入新的树。

**验收：** 最后预检后推进 base，断言本次合入零写入；正常快进目标 tree 与验收 tree 一致；响应丢失只对账、不重复写；保护规则拒绝时不切换其他写入通道。

GitHub 文档明确 merge 请求的 `sha` 约束 PR head，未提供 expected base：[Merge a pull request](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request)。显式 expected SHA 租约语义见 [git push](https://git-scm.com/docs/git-push#Documentation/git-push.txt---force-with-leaseltrefnamegtltexpectgt)。当前方案不授权实施该推送。

## R2 / P1：部署排空检查与停进程之间没有调度屏障

**定位：** `docs/acceptance/topic-context-completeness/scripts/deploy-owner-repair.ps1:123-137`；`check-repair-deployment.mjs:21-24`。

排空快照与 Stop-Process 是两次独立动作，中间可能出现新的节点领取、Owner 执行或外部效果派发。停止后再检查只能发现中断，不能防止中断。三类忙碌计数也不是同一数据库读事务。尚无证据表明本次成功部署已经触发此竞争，但脚本的排空保证不成立。

**修改方案：** 新增受信 Host 维护状态，在与领取/派发同一控制存储事务边界生效；禁止新节点、Owner、消息处理及外部效果派发，入站消息可持久入队。等待已执行操作和服务进程真实排空，以单一一致快照生成停机许可。取得许可后停止准确进程，再备份安装。重启默认保持维护状态，完成包、数据和健康回读后才通过正式命令恢复派发。超时则保留原实例并明确返回未部署。

**验收：** 在“最后快照→停止”之间注入 claim、Owner 和 external dispatch，均被事务门禁拒绝；已开始操作可收口；崩溃重启后维护状态不自动丢失；部署失败不自动重复停止或重启。

## R3 / P1：确定性错误仍被自动重复执行，预算补充只解决当前停点

**定位：** `packages/dingtalk-dsh-assistant/workflow-service.js:1943-1947`；`task-workflow.js:335-350`；`test/workflow-service.test.js:25-40`。

只对 `ENGINEERING_PATCH_AMBIGUOUS` 等少数错误跳过恢复；`ENGINEERING_PATCH_BASE_CONFLICT`、`ENGINEERING_PATCH_CONFLICT` 等相同输入必然重复失败的错误仍进入 recover。现有测试甚至明确断言 BASE_CONFLICT 会再次执行。本轮真实第一代已发生 apply-changes 34 次领取，其中 33 次重复，直接耗尽后续预算。已部署修复消除了这一种歧义循环；其他同因错误仍存在。

**修改方案：** Host 统一区分“可暂时重试”“需新方案”“需用户/配置处理”“外部效果待对账”。仅明确可重试的网络/暂态错误自动恢复，持久记录重试次数和下次时间；确定性失败按 run/generation/node/inputDigest/errorCode 去重，交 Owner 一次明确修复或阻塞，输入不变不再次领取。未知效果只允许对账。保留全 Run 累计预算和现有一次性显式续行，不借换代重置计数。

**验收：** 对 AMBIGUOUS、PATCH_CONFLICT、BASE_CONFLICT、EDIT_BASE_CONFLICT、结构输入错误连续运行恢复，累计只执行一次；可重试错误按次数和退避结束；更改合法方案后才重新执行；进程重启不重置恢复计数。

## R4 / P1：前端准备失败仍会制造“清理未知”并占用共享验收资源

**定位：** `scripts/local-acceptance-review.mjs:42-52`；`packages/dingtalk-dsh-assistant/execution-local-acceptance.js:283`、`:331-336`。

review-ledger 直到进入业务 execute、后端连接检查通过后才创建。依赖安装、前端编译或依赖服务启动失败时，runner 的 finally 仍执行 cleanup，缺 ledger 一律返回 CLEANUP_UNCONFIRMED。后端 merge 已为同类准备失败加 initialize，前端尚未补齐。当前成功前端回执不受此问题推翻。

**修改方案：** 前端 prepareSteps 第一项为受信 initialize，持久绑定 identity/namespace/baseUrl、初始零资源状态；登录、浏览器创建等动作在执行前逐项登记。cleanup 对初始化但未启动的资源给出可核验零资源结果，对已开始但结果未知的资源继续阻断。旧执行缺 ledger 不自动补为 clean，应走已有正式对账机制。

**验收：** 初始化后构建失败、companion 启动失败、ready 失败都能安全释放零业务资源；登录返回丢失、浏览器启动结果未知仍维持未知状态；不能伪造空 ledger 覆盖历史执行。

## R5 / P1：共享 UAT 后台关闭证明只检查源码字符串

**定位：** `scripts/local-acceptance-project.mjs:58-70`。

七个类只检查是否含指定注解文本，BlacklistCacheService 只检查配置字符串是否出现。注解在注释中、开关字段没有参与刷新判断，也可通过预检。该预检不能证明候选进程不会消费共享队列或运行后台任务。

**修改方案：** 保留源码检查作为快速提示，增加候选的 Spring 上下文定向验证，使用替代外部客户端而不连接共享资源，断言关闭模式下七个相关 Bean 不注册、定时刷新及消费者不启动、黑名单只读初始化保留；开启/缺省模式仍保持正常行为。真实本地启动还应输出绑定候选包摘要的模式证明，完成证明前不启动相关生命周期组件。后台关闭证明纳入 prepare 门禁。

**验收：** “注释中的注解”“字段未使用”“新增未受控消费者”三类反例必须失败；关闭模式零后台启动、正常模式不回归。当前真实业务代码的合理实现不替代这项自动门禁。

## R6 / P2：构建后不再校验候选源码，验收凭证可能绑定错误对象

**定位：** `packages/dingtalk-dsh-assistant/execution-local-acceptance.js:236-242`、`:283`、`:364-380`。

manifest 只在准备命令前核验。构建/启动脚本随后可改原始源码，仍使用原 candidateDigest 形成 PASS。实际两次候选全部重新哈希一致，未发现本轮漂移。

**修改方案：** 抽取原始 manifest 校验，在准备完成、业务断言完成及生成通过凭证前重新调用；原始文件内容、路径、链接和缺失均校验。构建产物使用明确的派生目录，单独记录包摘要，不能混入源码 manifest。将源码摘要、构建产物摘要与进程身份写入验收凭证；检查到漂移后照常清理资源，但不得发 PASS。

**验收：** 准备命令改源码、删原文件、替换符号链接、验收阶段改源码均拒绝；允许声明的 build/target 输出；原始候选不变时通过。

## R7 / P2：归一化数值断言丢精度，actual 使用硬编码

**定位：** `scripts/local-acceptance-merge.mjs:216`、`:332-333`。

`Number(value) === 1` 会接受 `1.0000000000000001` 和 `0.99999999999999999`，本轮 Node 实测均被舍入为 1；随后 actual.resultValue 固定写成 `1`，掩盖原始值。该发现不说明本轮真实数据库出现了这些误差。

**修改方案：** 采用精确十进制规范化比较，数据库 numeric 按字符串读取，预览响应保持原始十进制文本。actual 保存真实预览/持久值及规范化比较值，不能复制 expected；同样处理来源 0.5 与权重和。若业务规则允许容差，必须由明确验收要求提供，不能由 JS 浮点转换隐式决定。

**验收：** 1、1.0、1.000 正确等价；两个末位差值、0.001、NaN 和空串必须失败；回执显示实际原始值。

## R9 / P2：部署自动回读与备份恢复验证不完整

**定位：** `deploy-owner-repair.ps1:79-88`、`:149-156`。

`ready=true` 没有检查恢复错误和认证 Web；备份仅比对部分主文件源/目标哈希，其余文件只算备份自身摘要，也未做恢复演练。实际备份含约 4.14 MB WAL，主 SQLite 文件匹配不能单独证明最新账已完整恢复。本轮另外人工核实了恢复问题 0、认证 Web 200，不能据此认定本次部署失败。

**修改方案：** 独占且维护状态下生成一致 SQLite 备份；对 Domain、工件、配置等保存完整源/备份清单并逐项比对。临时恢复目录执行 integrity_check、foreign_key_check、任务/节点/效果及工件引用核对。将控制面、恢复错误、认证 Web 和钉钉入站分别记录；允许已明确接受的钉钉降级，但不得泛化为全实例 healthy。

**验收：** WAL 缺失或损坏、工件丢失、HTTP 正常但恢复错误、认证 Web 401 均应明确失败相应门禁；当前只读历史核对继续保留。

## R10 / P2：待部署命令混用了包摘要与配置摘要

**定位：** 上轮实际调用把 `(Get-FileHash $pkg).Hash` 传入 `-ExpectedSha256`；`deploy-owner-repair.ps1:101` 比较的却是 `cordis.patch.yml`。

**修改方案：** 将参数明确改为 `ExpectedProfileSha256`，另收 `ExpectedPackageSha256`；在任何停机前独立核对两个摘要，检查输出明确列出各自校验结果。执行命令使用实时配置只读摘要和已冻结包摘要，各自绑定。runbook 和脚本调用样例同步更新。

**验收：** 对调两个摘要在零写预检即失败；配置漂移、包漂移分别报准确原因；正确参数可进入排空门禁。

## 建议实施顺序与闭环

1. **先保护运行与远端写入：** R1、R2，以及 R10 参数纠正；在隔离环境复现并通过竞争反例后才部署相应能力。
2. **再修同因失败与共享资源门禁：** R3、R4、R5。预算续行可保留，但不作为重复执行根因的修复替代。
3. **补验证可信度和自动化：** R6、R7、R8、R9，新增独立用例和完整命令输出索引。先便宜的反例及定向测试，再跑受影响业务场景。
4. **完成两条真实链：** 明确参数且空间充足后受控部署；保留已有候选和验收，按新门禁判断哪些证据可复用。前端正式续行并更新原 PR 到 UAT2；后端仍使用 UAT3。取得既有流水线通知授权后，先完成各自合入，再分别证明提交/构建/镜像/部署及就绪对应同一实际交付版本。
5. 只有两项全链矩阵通过，才写最终验收报告；本地通过、远程技术交付、远程业务复验按证据分别陈述。
