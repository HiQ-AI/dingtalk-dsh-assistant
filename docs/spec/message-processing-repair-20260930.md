## 3. 已复现根因及影响

### R1：输入预算不按最终信封协调分配

`message-model.js:23` 计算 system + JSON 输入的 UTF-8 字节数；`message-workflow.js:156` 对 S 固定检查 8000 bytes。`workflow-service.js:1787` 的背景选择单独使用 1800 bytes，并未扣除系统/schema、当前原文、引用、分段索引等开销。`message-context.js:101` 又把完整背景、引用同时放入 S。

用持久 snapshot 调用真实 `splitContext/prepareMessageRequest`，精确复现 8372、8273 bytes。#114/#115 也都已记 `capacityRetryVersion=s-compact-v1`，恢复代码 `message-workflow.js:697` 遇相同固定版本直接返回，因此重启不会自然解开这个状态。

影响：短正文带长引用也会失败；修改提示/schema 长度会挤占用户内容；没有节点记录时健康检查仍可全绿。

### R2：候选翻页及材料请求契约不闭合

`message-workflow.js:250` 只有 R 返回 binding/new 才由 Host 切下一页。R 返回 needs_context 则直接 `waiting()`。`message-context.js:44` 对 needs.resourceRef 仅校验非空字符串；`validateExecutionMaterialRefs`（`:239`）只保护 I/IB 的执行材料，不校验 S/R 的资源请求。

#113 的首轮有 6 个可见候选、73 个未展示候选。模型拼了一个带目录摘要的 page:1 引用。该引用不在原输入中，schema 和材料验证器仍接受；`workflow-service.js:1999` 的材料解析器没有对应分支，最终返回 ready=false。`message-workflow.js:707` 又只在 ready=true 时唤醒，没有“资源引用非法”的终态、改正或升级。

影响：内部可检索资料被变成无限等待；`message-workflow.js:272` 还存在“候选未看完就让人明确是否独立事项”的分支，容易把检索责任转嫁给用户。

### R3：业务数据集合与任务集合混淆，conversation 身份过宽

#111 在 8 次 R 中，前 7 次都认为是针对 Excel 的独立请求，第 8 次在仍有 27 个候选未看时改判 conversation。`message-model.js:10` 对“集合状态查询”的语义边界不够清楚；`workflow-service.js:1974` 对 conversation 按 `(groupId, 'conversation')` 生成唯一固定 topicId，复用旧标题及事实。

这里是业务数据集审核状态，不是询问 Agent 的已有 Task 状态。强制扫描大量无关旧任务增加了延迟、模型漂移和错误归属机会。#111 的 S/R 从 17:50:05 持续到 17:51:53，随后没有进入意图判断。

### R4：历史时间没有统一类型，未来消息进入早先请求的上下文

`dws-bridge.js:24` 保留实时事件的数值时间；`:40` 保留回补消息的日期字符串。`workflow-service.js:1799` 直接用 `>= cutoff` 比较。

现场 #109 的 occurredAt 为数值 `1790761783607`，#111 为字符串 `2026-09-30 17:15:14`。JavaScript 混合比较不能得到正确时间先后，#111 的冻结 history 实际包含 17:49 的 #109。把两者统一为时间戳后，断言确认这个文件晚于原问题，应排除在该原始历史之外。

影响：把后补材料误当原来就可见的历史、出现两份文件歧义、近期候选排序失真。修复时允许显式纳入后补材料，但必须作为后续输入/新版本，不能倒写原始上下文。

### R5：群级严格等待放大了 R1/R2，而可见性与恢复不完整

`message-ledger.js:971` 的待归类查询把尚无有效绑定的 waiting/needs_attention 消息保留在队列；`message-workflow.js:386`、`:514` 阻止该群普通话题进入 IB。现场独立查询结果恰为 `[113,114,115]`，因此 #111 一直等待。

这是既定严格归类设计的运行结果。`docs/spec/topic-intent-task-composition.md:79`—`:94` 原先明确要求全部归类完成后判意图；此设计把无关事项的进展绑定到整个群的最慢输入，导致一个无限等待可以持续阻断全群普通业务。

本轮决定将其改为“事项影响范围屏障 + 当前版本原子校验”，既修复 R1/R2，又解除无关事项之间的阻塞。未知关联不能直接当作独立；暂停、取消、目标修订、共享资源限制必须先登记影响，再允许相关外部动作领取。超时不会自动证明无关，也不会冒充归类完成。

### R6：通知只覆盖部分状态，且承接/后续报告受模型 replyPolicy 一并控制

`workflow-notifications.js:131` 仅为 pending needs_clarification 准备询问，未为 needs_context、needs_attention、长期 routing barrier 准备状态通知。内部等待不应该立即追问用户，但需要持续失败时可见告知。

`:145` 只进入 applied/rejected 且 replyPolicy 不为 none 的 command 循环。承接回复与该任务 Owner 的进度、阻塞、完成报告都在同一循环中。

用真实通知函数和仅写内存的 store 替身复现：

| 输入状态 | 当前准备通知数 | Owner 报告读取次数 |
|---|---:|---:|
| pending needs_context | 0 | 0 |
| needs_attention | 0 | 0 |
| pending needs_clarification（对照） | 1 | 0 |
| 已接受 create，但 replyPolicy=none | 0 | 0 |

最后一项是已证实的代码缺口，未声称今天七条已实际创建这种任务。

### R7：回复义务、任务准入和执行批准混在不同阶段，前后语义不一致

`message-context.js:105` 明确从 S 输入剔除群职责；`message-model.js:9` 提示问候使用 no_action；`message-workflow.js:614`、`message-ledger.js:678` 直接完成消息，不检查是否仍欠回应。#112 因而违背被 @ 必须回复的职责规则。

另有准入风险：`workflow-service.js:334` 用“名字后 50 字内出现修复/处理/排查特定句式”的正则判断交办，`:887` 只看当前原文或少量已解决确认。真实调用对 #111、#114、#115 都返回 false；其中 #111 明确叫“小小鹏”并要求查表。此结果不等于 #111 必须创建 Task，但说明不能用该正则判断一切合法交办。#114/#115 如果后续产生 create，也可能继续卡在准入，不能只修 S 就宣称任务会启动。

需要把“回应/调查请求已交办”和“生产变更已批准”分开。群里明确要求先写脚本再审批，不能因为还没获得生产执行批准，就反复询问是否需要准备方案；也不能把这条要求当作已经批准执行生产 SQL。

### 4.2 事项影响范围与推进规则

1. **接收时先登记影响。** 同一事务保存来源输入和影响记录。精确引用、编辑/撤回、Task/原请求身份先确定直接作用域；模型尚未归类的部分记为未判定。不能等 R 成功才让正在执行的 Task 知道有新输入。
2. **影响以来源和业务对象为依据。** 复用当前 barrier 的 targetSourceKey/targetTaskId 及话题绑定，补充 topic/unit 与有证据的共享资源关系。影响记录至少绑定 sourceVersion、事项修订、判定依据、目标范围及待解决原因；持久化在现有控制账，不只存在调度器内存中。发送者有无执行权不能替代事实相关性判断：无执行权的参与者提供的新业务约束，也可能需要当前任务重新核对。
3. **未判定输入先做窄范围影响评估。** 从引用对象、当前参与事项、已授权可控制目标和已知共享资源构造可能受影响集合。只有被证明独立才排除；不能因候选分页没读完、没有关键词或经过一定时间就排除。未知消息仍可阻止其可能影响的动作，不能无依据地永久占住全群业务。
4. **已证明独立的事项继续。** 某条关联失败或等待人工补充时，仍允许其他独立事项完成 S/R/I、只读调查及其合法效果。持续收到其他话题消息，不会让本事项的输入版本不断失效。同一事项仍聚合所有当前已知相关补充，保持 single-flight。
5. **未知范围保留明确边界。** 无法排除对某任务影响时，该任务的外部写入和最终交付继续受阻；可以执行不产生冲突效果的内部取证、范围消歧和准确的“已收到/正在核对”回应。若有权主体的消息确实可能控制全群多个任务，可临时阻挡该集合，必须显示影响依据、责任与恢复条件。不能为了满足“互不阻塞”而强行把范围缩小。
6. **单消息多个事项分别推进。** S 必须先证明原文完整覆盖并保留共同约束。此后已证明独立的 Unit 可继续，受阻 Unit 及依赖它的 Unit 等待；共同限制尚未消解时，所有受其影响的 Unit 仍受阻。需要新增事项级暂停/请求状态，不能继续让父 run 的一个 waiting/needs_attention 自动冻结全部 Unit。
7. **真正群范围请求按范围处理。** “暂停我负责的全部任务”等明确集合控制经过身份校验后作用于目标集合；“查看我的 Task 进度”使用群内查询范围，不把所有业务资料塞入固定旧话题。

### 4.3 各推进关口使用同一份校验

不能只改 `scheduleTopics` 的 SQL。以下关口必须调用同一影响范围判定逻辑，并由控制库事务兜底：

- 话题调度、`topicDrive` 和话题输入刷新。
- `message.topic.intent.accept`：接纳全部相关 Unit 的当前决策。
- `message.command.claim`：领取命令前重新核验。
- Task Owner 接纳/应用计划、下一阶段启动及 Controller 的 operation/job 效果领取。
- 最终结果通知领取：核对结果对应的任务需求版本；纯回应与系统状态通知使用自身事实版本。

每个候选记录其读取的来源版本、topic input/context revision、Task requirement/plan/control revision 和作用域影响版本。接纳/领取时原子确认：全部必需来源仍有效；本作用域内已入账的新输入均已纳入或有可审计的无关证明；没有未解除的相关控制/授权屏障。任一条件变化即废弃该候选，聚合最新输入重判受影响部分，不能从模型校验到写库之间留窗口。

新增输入在命令领取前到达，应先使旧领取条件失效；领取后到达按现有取消/排空/效果对账机制处理，不能承诺撤销已经发生的效果。可能已发出的 SQL、通知等仍先查账和独立回读，不靠再次执行判断是否成功。

调度不得等待其他模型时持有群锁或数据库事务。S/R、材料恢复与通知继续有执行机会，不因一个长期业务 Task 占用资源而饿死。尚未送达本机的消息无法预知，到达后作为新版本处理；不再以等待“整个群暂时没有未归类消息”制造已收齐未来输入的假象。

### 4.4 等待是有责任人的状态

复用现有 request，扩展为以下明确类别；新字段必须通过控制库 schema、API 与恢复逻辑统一校验。

| 等待类别 | 谁负责解除 | 恢复及沟通规则 |
|---|---|---|
| 内部材料/候选继续读取 | Host 材料解析器 | 仅接纳已注册精确引用或 Host 游标；记录读取位置与证据。沿用现有有界重试策略，成功唤醒原请求；引用非法进入协议纠正，不能要求用户提供内部目录。 |
| 真正缺少业务信息 | 原请求人或已核验可补充者 | 保存已查来源、仍缺字段、为何影响当前步骤，立即产生一次必要询问；新增消息匹配到该请求后更新同一事项，不要求重复表达已提供的信息。 |
| 业务确认/生产审批 | 对应验收人或授权批准人 | 绑定精确任务、阶段、数据集合和产物摘要；保持与普通缺材料分开，前置准备仍可在授权范围内推进。 |
| 系统故障/能力不可用 | Runtime 恢复或运维 | 保存确定错误、失败次数与下一可恢复条件；重试耗尽转可见系统阻塞并通知，不无限 needs_context，也不谎称用户没提供资料。 |

每个请求至少有稳定 ID、所属 Unit/Task、来源/需求版本、责任类型、具体依赖、最近失败、恢复条件和通知责任。重启从控制账续接；材料/答案变化后重新核验相关语义与版本，不能只把 ready 标志改成 true。等待解除后尚未发送的旧询问或故障通知失效；依赖未知外部效果的等待必须先对账。

### 4.5 回应、任务进展、通知送达分别记账

- **回应义务由 Host 保证。** 根据可信来源的点名/回复关系、当前群规则和语义判断记录“需要回应/可静默”。S 的 no_action 只表示没有业务事项，Host 确认不存在回应义务后才可无通知结束。点名问候走轻量回应，不扫描全部旧 Task，也不创建业务 Task。
- **业务接纳必须真实。** 尚未形成 Task 时只称已收到；持久 Task 与承接责任成功落账后才能称已承接；阶段真实领取后才称开始执行。Task 创建与承接责任在同一控制事务中完成；跨现有 reducer 时用持久待完成责任与幂等恢复补齐，不能先异步启动后寄希望于下一轮模型记得告知。
- **关键生命周期通知独立。** 人工等待、系统阻塞、承接、失败和完成不由最初 `replyPolicy=none` 一并关闭。模型可以组织正文或建议合并进展，Host 根据已核验事实保证必要沟通。用户有明确静默要求时记录其原文、适用阶段与范围，不把“不要给审核人发业务通知”扩大为助手不汇报。
- **送达单独证明。** 复用 notification 账，以稳定事件身份和事实版本去重；ACK 与独立回读仍分开。投递失败不回滚业务 Task、不重新执行业务；页面展示“任务已承接 / 通知未送达”而不把一项成功冒充两项完成。

### 4.6 本次交付边界

本次必须同时完成范围屏障、等待恢复、Host 沟通责任以及 R1—R7 修复。实现可分提交和验证轮次，但架构项不是延期项；只修复当前消息的字节上限不满足交付条件。

涉及持久契约变化时，先明确控制库/协调契约版本并提供零副作用预检、无损升级和中断恢复。不能仅靠内存新字段或旧记录默认放行完成上线。已有历史消息保留原始来源和审计结果，重建影响记录不得触发 Task、SQL 或通知重放。

## 5. 修复设计与实现顺序

### 第零组：建立上述协调契约（P0，本次必做）

1. 先把当前红例转为可复现的架构验收：A 缺材料不阻挡独立 B；相关取消必须阻挡 A；同一消息两独立 Unit 不互相冻结；父 run 状态不能跳过相关 Unit；unknown 效果不能重复。
2. 在现有控制账中实现来源影响、事项等待和沟通责任，统一调度、意图接纳、命令领取、Owner/效果领取的判定。保留精确版本校验与已认证控制通道。
3. 补上新契约的恢复、失效、迁移和观测，再接入下列归类、沟通与任务行为。所有新状态须在 API、看板和运行恢复中有一致含义。

### 第一组：使消息能够正确完成归类（P0）

1. **统一来源与上下文。** 在 DWS 入站边界规范时间为带明确时区的标准形式，比较统一使用 epoch；原始时间单独保留作证据。兼容读取现存数值/字符串时只做无损归一化，不批量重写业务来源。保留精确 fileId、来源消息、引用链、资源版本；已有文件消息的附件补全只允许独立 DWS 回读证明同源，不增加正文版本、不触发第二次任务。优先复用现有 `normalizeHistoryMessage`、来源读取及文件能力。
2. **最终信封预算。** 使用 `prepareMessageRequest` 统一核算 system/schema + 原文 + 必要引用 + 定位索引 + 已解决材料 + 可选背景。按来源身份去除背景/引用的重复正文；不裁掉当前用户条件或强制引用。在完整必需部分可容纳时自动重分配可选背景预算；确实超限走现有完整材料分页/可恢复系统失败，不截断授权条件，也不只粗暴抬高常量。恢复键使用已生效的投影/契约版本与输入摘要，避免静态 s-compact-v1 永久跳过，也避免同一坏输入无限重试。
3. **收紧 R 翻页协议。** R 只能请求 Host 发出的确切资源键或明确的目录继续动作；给定目录摘要与游标由 Host 决定下一页。读取器支持合法继续动作；未知引用在接受模型结果时即判可纠正协议错误，附当前合法资源重新判断，不能落入无限 needs_context。页结果应累积“排除/可能同一事项”的证据，在最后做有完整范围的归属裁决，不让最后一页覆盖之前所有判断。不为了取下一页强迫模型先宣称 new。
4. **纠正 conversation 使用范围。** 将“查看已有 Agent Task 集合”与“查询业务数据集合”在 R 产出中明确区分，并做 Host 契约检查。只有真实任务集合状态查询可使用群级查询范围；业务查表按独立事项或已证明的相关话题关联，不能复用群内固定通用话题的旧业务标题与事实。关联仅凭当前原文、引用、对象和目标证据，不能只改 UI 标题。
5. **接入事项影响范围屏障。** 修复 #113 的非法请求、#114/#115 的容量问题后，通过统一影响判定重新调度相关事项；#111 是否需要吸收后补材料，按真实来源关系与目标判断，不因同群就全部等待，也不因它更早就忽略后续约束。看板列出具体阻挡来源、目标作用域、阶段、等待责任与恢复条件。单消息多个 Unit 按共享约束与依赖决定推进，父 run 聚合状态不能代替事项状态。

### 第二组：恢复沟通与承接责任（P0）

1. **明确回应义务。** 按 4.5 由 Host 建立并校验回应责任；给 S 最小、来源可核验的点名与群规则事实作为判断输入。S 不再单独拥有“无需任何回应”的终结权。仍需回应的问候走轻量答复，0 业务 Task；混合问候与业务请求仍保留完整事项，不多开 Task。
2. **等待必须能解释。** 使用现有 message_items、notification 账记录状态转换的通知责任，不另建平行 Outbox。内部取数短暂等待不打扰；重试耗尽或持续受阻只告知正在被什么系统问题阻挡、用户是否需要动作。只有自主读取后仍缺、且会改变目标/方案/授权的业务事实，才生成 needs_clarification，询问最小必要项。一个缺口不应在每轮生成新 request、新询问。
3. **可靠承接与结果。** 对已真实创建/接受的业务 Task，把承接回执作为 Host 生命周期责任；若仅接收但规划受阻，应准确告知“已接收，尚未开始”并带阻塞原因。进度、等待、失败、完成报告独立于原始动作的 replyPolicy；none 只控制普通事实/闲聊等可选回复，或用户有明确、可追溯静默要求的相应范围。发送失败保留通知责任，不重建业务任务。
4. **幂等与事实一致。** 通知稳定键绑定 run/sourceVersion + task/requirementRevision + phase；落盘、发送 ACK、独立回读分别保留。失效请求的 pending 通知要 supersede；unknown 先回读再决定，不能直接补发。看板同时显示请求/Task 状态与通知准备/送达状态，不能一个“已处理”代表全部完成。

### 第三组：完整承接连续交办与多阶段目标（P0，本次必做）

1. **准入使用已核验上下文。** 明确交办、同发送者引用续接、负责人确认都保留原消息身份及范围。复用现有权限与来源校验，补齐可证明的上下文交办；不靠扩充若干关键词，也不因同群相邻就继承他人授权。
2. **先可行性与脚本，后生产批准。** 用户已要求“看看/写脚本”，在已授予的查询和文件范围内开展工作。准备脚本、发起审批、执行生产是不同能力边界；每阶段缺什么能力/授权就明确记录，不能给一个模糊“等待”。
3. **#114/#115 合并为同一刷数任务的当前要求。** 保留独立的来源消息及阶段条件，避免两条输入创建两个任务。#111 的查表答复及 #113 的可行性分析可作为来源材料，不因同话题就自动等价为同一个任务或已完成阶段。
4. **按实际需求形成可核验步骤。** 读取原始与生产状态 Excel，确认有效 69 条与原 70 条的差异以及 Y 列新审核人；核查当前生产结构/记录；生成检查、变更、验证和回滚材料；由指定审批人审批精确对象和脚本；先执行两条测试数据；等待原发送人验证通过；再在批准范围及数据前置断言仍成立时执行正式 69 条。每一个验收/批准绑定对应数据集合与脚本摘要，不能用两条测试批准替代所有生产批准。
5. **完整保留限制。** 行业专家记录/状态不变；LCA 专家映射、记录清理、审核单 REVIEWING/end_time、数据集 processStatus 和快照修正全部按原文落到需求验收。保留“不改 assignment、不新增派单、不发业务通知、不改轮次”。这里的“不发送消息”限定为数据库方案的审核业务通知，是否也限制助手进度沟通要结合原文作用域；不能擅自把它扩大成永远不回群。逻辑删除或物理删除由当前实现与新审核记录影响分析得出，不能在本方案里先替业务核验下结论。

主要改动位置：`dws-bridge.js`、`message-context.js`、`message-model.js`、`message-workflow.js`、`message-ledger.js`、`workflow-service.js`、`workflow-notifications.js`，以及 `task-owner-store.js`、`task-owner-controller.js`、`execution-controller.js`、`execution-store-worker.js` 中实际承担版本/影响/效果领取的入口。按最终行为同步 README、`docs/api/workflow-node-contracts.md`、现有部署 runbook 和 Observer 的状态投影。原则上复用既有请求、Owner、任务计划、通知与执行批准机制，不引入另一套任务系统。
