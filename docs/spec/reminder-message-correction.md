# 连续提醒订正与及时投递

## 真实问题与证据

2026-10-23 同群同人 15:11:12.877 请求“三点提醒我一下查看云端专家的开发进度”，15:11:51 订正“三点20提醒……”。两条回复分别 15:12:56.919、15:13:52.176 才确认送达，且都变成追问。

持久账显示第二条沿同一 coordination 使用 resolve，第一来源已 resolvedBy 第二来源；关联并未完全丢失。错误是没有纯提醒动作，resolve 又生成新的时间确认，当前没有 schedule。旧澄清已在第二次 resolve 后仍被发送。

原生日志确认两个规划会话分别只用约 7 秒、13 秒；均收到 time-context 的“浏览器时区不可用，要求澄清未限定日期时间”。当前工作环境的时间显示却明确为 Asia/Shanghai。协调协议只允许 read-query/task-command，因此“提醒我查看”被迫匹配任务，产生无关的任务定位问题。

通知创建到真正 notification.start 分别约 69.611 秒、91.303 秒，发送 ACK 分别 2.362 秒、1.322 秒，回读分别 2.303 秒、1.797 秒，均无重试。通知投递等待恢复链末尾，创建时不主动唤醒，串行槽释放也不主动递进。Observer 把 createdAt 标成 sendStartedAt，影响定位。

## 可验证目标与范围

1. 复用受管 coordination schedule 支持纯消息提醒：保存正文及同群收件人，不查 Task、不创建虚假 Task，复用既有时间、改期、取消、幂等和恢复合同。
2. 利用来源时间、明确工作时区及原安排证据解释连续时间订正；已有充分信息直接建立当天 15:20 提醒。真实过时、冲突时区、多个不同对象保留必要澄清；不伪造浏览器来源或修改已安装依赖。
3. 已确认订正使旧澄清失效时，只退役尚未发送的旧通知；保留已发送、已开始及未知效果，不撤回或重发。对用户回复只包含实际提醒时间和内容，不泄露 clarificationId/0成员等内部模板。
4. 通知准备后及串行槽释放后及时唤醒现有投递，保留全局限流及未知效果对账。持久记录真实发送开始时间，展示不再把创建时间冒充发送开始。

不新建提醒 skill，不让被委派的规划器绕过原生 schedule 权限。只修改插件候选和对应文档；不重新安排历史 15:20 提醒、不发钉钉消息、不部署或触发 CI。

## 实施分工与验证

- 根代理：协调提案/上下文、同事项订正及旧澄清退役、回复文本、集成与最终复盘。
- 提醒动作成员：底层时间计划动作与到期通知，针对性验证提醒、改期、取消及幂等；不改根代理持有的 planner/service。
- 通知成员：及时唤醒、串行递进、真实开始时间及投影；用受控慢规划证明回复不用等待其完成。

验证覆盖无任务纯提醒、两条相隔39秒的订正、原安排改期、独立提醒不合并、过时时间不改次日、处理迟到保留原定时间、未知发送不重发及限流不被绕过。原生模型验证使用当前真实配置与隔离合成材料，核对实际提案/文字而非只检查工具名。原始失败与每轮证据分别保留，最终本地通过后提交新 PR，未部署状态单独说明。
