# 任务统筹上下文与无效唤醒

## 现场证据

用户提供本任务真实投影文本，UTF-8为59451字节。粘贴的Windows路径存在非法JSON转义，分析副本只修复转义后按字段量出：contentIndex约21.6KB、8个执行目录12.5KB、11个来源9.9KB、材料目录8.6KB、task4.3KB。数字是文本字节，不是token。旧阶段进度、重复材料元数据和很短文本的长scope/hash引用占据显著空间。

当前task-session每轮投影reuseVisible=false，旧完整快照虽被foldSurface替换，但新快照仍全量定义；dynamic-task-store对每个operation.settle无条件唤醒统筹。现场原会话连续多轮只提交wait并重复相同说明，执行仍运行。当前授权修复只补齐来源，未解决整体输入体积和无用统筹回合。

## 方案与边界

复用现有model-context、原生surface和目录读取：减少重复路由/材料/历史执行字段，完整原记录仍由精确引用按需读；有效原话、作者、更正、最新目标、未知操作和真正需统筹判断的失败/恢复边界必须可发现且可取回。不能仅换字段位置就宣称总上下文降低，也不能把授权来源静默删掉。

调查已有owner每轮基线复用能力，在当前task/execution原生生命周期内验证压缩后恢复、同会话重开及原始审计不变；采用单一可解释路径。执行自身能消费的普通工具完成不逐个唤醒统筹，统筹在执行结束、真实未知效果/恢复、进度检查、用户输入等决策事件醒来；保留独立操作和已结束执行对账的必要唤醒。

## 验证

分开计量首次完整输入、新一轮注入、仍保留的基线及模型总可见内容。用用户现场对应持久输入做脱敏指标，不入库原业务长正文；原生SDK测试多轮、授权更正/窗口外撤销、未知效果、执行终态、重启/压缩恢复和无效wake数量。测试通过后沿原PR及本地部署runbook；当前业务在跑，等待其自然排空，不为优化打断正在发生的业务操作。
