# 同一任务统一卡片与执行历史

日期：2026-09-28。状态：设计建议，尚未实施。本轮只设计任务身份、执行次数和展示行为，不修改运行数据。

用户确认边界：可以汇总卡片，但卡片显示保持现状；任务详情页现有执行步骤保留。本约束优先于此前关于改短标题、替换来源标签、增加次数徽标及重新组织步骤区的建议。

## 决策

采用“一项任务、一张卡片；卡片显示最新执行，详情保留全部执行历史”。不采用覆盖旧结果的方式。历史中的目标、失败原因、验收和产出是解释重执行原因及核查交付的必要依据；是否清理日志和大文件属于独立存储策略，本次不改变已有保留规则。

## 当前实现依据

- `packages/dingtalk-dsh-assistant/workflow-service.js:1348` 的 `rerunWebTask` 为重执行生成新的内部 taskId，通过 `rerunOfTaskId` 关联原任务。
- 同文件 `tasks()`（2221 行）按内部 taskId 汇总，当前先读取最多 200 条 run。因此直接让前端合并当前页，可能遗漏祖先及执行次数。
- 同文件 `taskRuns()`（2626 行）只读取指定 taskId 的工作流运行，不能直接视作整项任务的历次执行。
- `packages/dingtalk-dsh-observer/web-client.js:722` 按 taskId 生成卡片；详情已有折叠历史区域，可扩展其交互。
- `packages/dingtalk-dsh-assistant/execution-store-worker.js:735` 已对重执行来源、预期运行和终态作校验；目前是针对直接来源，需补全同一任务各次执行的并发约束。
- 现有详情阅读顺序见 `docs/spec/task-detail-reading-order.md`，沿用其先状态与结果、后过程与历史的层次及现有样式。

## 概念与边界

| 层级 | 定义 | 展示方式 |
| --- | --- | --- |
| 任务 | 持续追踪的同一件事，具有稳定名称、来源与详情入口 | 唯一任务卡片 |
| 一次执行 | 首次执行，或前次结束后明确重新执行 | 第 1 次、第 2 次…… |
| 执行过程 | 本次执行中的开发、验收、合并、部署等阶段及节点重试 | 本次详情下的步骤 |

补充信息、等待确认后继续、预算继续和步骤重试保持本次执行。已经结束后重新执行才新增一次。不同目标通过“新建任务”创建；名称相同不代表同一任务，不按标题、群或相似度自动合并。

## 卡片

完全复用现有卡片显示：布局、样式、标题规则、来源标签、状态、进度、摘要、按钮及交互保持现状，不增加执行次数徽标或历史入口，不做名称缩短和来源标签替换。

只调整卡片的数据归属：同一任务汇总成一张，取最新执行的数据交给现有卡片组件渲染。新一次开始后，状态和进度随该次执行自然更新；不能混入前次的成功状态或结果。一项任务在全部状态栏及归档列表中合计只出现一次。

## 详情

保留现有执行步骤区域的布局、编号、展开方式、状态、步骤产出及交互。详情默认展示最新执行；在步骤区域之外提供轻量的执行选择入口，页内下方增加“执行历史（N 次）”，默认折叠，展开后倒序分页加载。

选择某次历史执行时，目标、结果、产物和现有步骤组件统一切换到同一次执行，不新造一套历史步骤 UI。步骤重试及被替代的运行记录放在该次执行的补充历史中，避免修改当前步骤区。详情其余区域可完善本次结果、目标变更及相关资料，但沿用现有视觉风格，不扩大为页面重设计。

每次执行显示次数、时间、执行原因、结果状态和摘要。展开后查看该次的需求快照、验收要求、过程、产物及链接。历史属于只读视图，明显标注“正在查看第 N 次执行”，提供“返回最新执行”；不能在历史页误操作当前执行。

产出、PR、报告使用可点击链接，且绑定对应执行。已按用户要求清理的旧会话或文件显示“历史记录已清理”；仍保留可用摘要，不伪造可打开入口。普通展示不用内部任务 ID、会话 ID、控制账等术语。

历史加载失败在历史区域内显示重试；不清空已显示的当前详情。展开、收起和切换均支持键盘，窄屏改为纵向布局。实时刷新不强制把正在阅读的历史切回最新执行。

## 操作规则

1. 重新执行从同一张卡片发起，成功后打开该任务的最新执行详情；服务端分配次数，重复提交只接受一次。
2. 同一任务最多一项活动执行。新增执行前事务内检查整个关联任务的活动状态、未排空执行和外部效果，不能从旧历史入口绕过约束。
3. 操作请求携带预期的最新执行及版本。旧页面提交时提示“任务已有更新，请刷新后操作”，不能静默作用到另一轮。
4. 取消、补充信息和确认只作用于当前执行；历史审批和验收不能自动复用为本次授权或成功证据。
5. 归档作用于整项任务，并检查关联执行全部结束。保留旧版工作目录安全门禁；任一不满足则整项不归档，不能部分归档后隐藏仍活动的执行。
6. 已归档任务重新执行时，同一张卡片重新出现在活动列表。归档是展示状态，不删除执行历史或工作目录。

## 数据与实现建议

新增稳定的任务归属关系，区分“展示的一项任务”和“内部隔离的一次执行”。继续使用已有内部任务记录隔离每次执行的计划、验收、会话、产出与副作用，避免把旧完成状态带到新执行。用户界面只暴露任务名称和执行次数。

服务端提供统一任务摘要和执行列表。统一任务摘要包含稳定身份、来源、最新执行、执行次数和归档状态；每次执行关联其现有内部任务记录，按服务端接受顺序编号。工作流 run 继续表示执行过程，不能复用现有 taskRuns.length 作为执行次数。

历史聚合优先利用明确的 rerunOfTaskId 关系追溯根任务。原始事件、内部 ID 和产物引用保持不变；聚合关系可从事件重建。旧版同一 taskId 的轮次按其已记录的轮次边界展示。没有明确关联依据的记录保持独立，不猜测合并。

权限检查先于聚合输出，不能因为执行来自同一链就扩大可见范围。Web 重执行继续沿用原有 Web 报告及禁止额外群发规则；任务来源展示不改变实际报告通道。无权访问的执行不能通过次数、摘要或链接泄露内容。

筛选、排序、计数和分页以统一任务为单位，关联查询不能依赖当前 run.list 的 200 条截断。旧详情链接解析后定位同一任务的对应历史执行；默认详情入口打开最新执行。

上线前只读检查关联完整性、环、缺失祖先、权限范围及历史并发分叉。有多个未结束执行的既有任务，仍只展示一张卡片，但显式显示待处理的活动执行，禁止以“最新一条”掩盖其余活动执行。归档状态混合的历史链，只要有未归档成员，就保留一张可见卡；后续统一归档需完整通过门禁。

具体落地在原生控制账增加归属索引及原子约束，复用 workflow-service 聚合接口和 observer 的卡片、详情组件。不要仅在前端按名称去重，也不重写各次执行已有的内部身份。迁移前输出关联清单并备份；迁移本身不启动任务、不发送消息、不删除历史数据。正式实施时再落定存储迁移及 API 契约。

## 验收标准

- 汇总后的卡片与对应最新执行的原卡片显示一致，不新增徽标、字段、按钮，不修改标题、来源显示或布局。
- 详情现有执行步骤区域的视觉与交互保持一致；切换历史后只改变对应数据，目标、产物、步骤不串次。
- 同一任务连续执行 3 次：看板始终 1 张卡片，详情准确显示 3 次。
- 一次执行含多个阶段及节点重试：次数仍为 1。
- 前次成功、本次失败或运行中：卡片准确显示本次状态，前次产出只在历史中显示。
- 重新执行重复提交、两个页面同时提交、从旧执行入口提交：最多新增一次，过期请求不误作用。
- 归档与重新执行：始终只有一张卡；归档失败时任务仍可见且所有原数据保留。
- 超过 200 条底层运行、跨页、筛选、刷新和服务重启：归属、次数及状态不丢失、不重复。
- 原有详情链接仍定位正确历史；文件与 PR 链接不串次；历史会话缺失有明确说明。
- 历史并发分叉不会被隐藏；权限收窄不泄露其他来源的信息。
- 历史折叠默认不加载全部明细，失败能重试；键盘、窄屏及阅读历史时的实时更新行为正确。

本轮核对源码并形成方案，未修改代码、部署或迁移任务，以上为待实施验收项。
