# 常驻会话路由与决策重复提交修复方案

日期：2026-09-20。状态：实施前方案；本轮未修改源码、运行配置或现场数据。

## 目标

减少因调度器明知有待归类输入却仍派发 Topic 决策而产生的无效工具调用。归类完成后，各事项独立处理和反馈；保留版本检查、授权依据、幂等以及 Outbox 的现有约束。

不把正常并发冲突承诺为“零重试”。模型已经生成的同批工具调用，不能依赖第一个结果让模型撤销其余调用；新消息恰在生成或提交期间到达时，允许返回 routing-required 并在归类后重试。

## 候选与选择

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| 仅修改提示词，要求先路由 | 不选 | 调度器仍会发出暂时不可提交的请求；无法撤回模型已生成的一批调用 |
| 路由优先派发，归类后按版本恢复 | 采用 | 直接修复已确认的调度不一致，复用现有协议与请求身份；保留必要的并发拒绝 |
| Host 保存被挡回的决策正文，归类后自动重新提交 | 本轮不选 | 可减少模型重提，但需要持久化待校验草稿、状态区分、失效与重启恢复；不能直接复用 accepted 业务意图，否则可能执行旧授权 |
| 移除群级未归类检查，允许所有 Topic 直接提交 | 不选 | 未归类消息可能正是取消、改需求或改执行人，不能事先认定与现有 Topic 无关 |

## 修改设计

### 1. 派发条件与接受条件对齐

在 wake 内区分“已接受意图继续应用”和“生成新决策请求”：

1. 先恢复已有未完成业务决策，沿用其执行与 Outbox 校验，不因新增路由等待而停住恢复工作。
2. 有 pendingInput 时，复用或创建当前路由请求，本轮不再创建、派发或返回可提交的新 Topic 决策。
3. 分批归类尚未清完时，继续下一批路由；不能把第一批完成当作整个待归类集合完成。
4. 清完后遍历有未处理版本的 Topic，按现有条件独立派发，不等其他 Topic 的 Task 执行结束。

不能在 wake 顶部简单 early-return：那会同时跳过已接受意图的恢复，反而拖延独立事项。

### 2. 补上异步派发窗口

在 createDecisionRequest 的实际 dispatch 时再次检查：运行态仍有效、请求仍为当前请求、Topic 版本仍一致、当前没有 pendingInput。

若因路由暂不能派发，保留请求身份并记录未派发状态；后续 schedule 必须能派发该请求，不能被“相同 requestId 已存在就直接返回”永久跳过。状态只用于可重建的内存派发管理，不新增持久业务状态，也不缓存模型决策正文。

对 onDecisionRequest 状态问答路径使用相同的路由门槛。已经开始执行的异步分支仍由现有提交前校验处理并发变化，不能用发起时的检查替代提交时检查。

### 3. 处理中遇到新消息的恢复协议

- 已进入模型上下文或已生成的调用不能视为已撤回；Store 继续返回 routing-required，不产生 Task、预约或 Outbox。
- 复用当前路由请求；同批多次拒绝只对应一个路由请求，不重复注入相同正文。
- 返回明确的当前 routeRequestId 和下一步 route-first 指引。字段及缺失分支须与现有 request-unavailable/exhausted 处理对齐，不能伪造当前请求身份。
- 提示词要求从下一次模型决策起优先归类，并停止主动追加同一批旧提交；这只是操作指引，不作为同批调用一定能停止的保证。
- 归类后，无关 Topic 保留原 requestId/revision；受影响 Topic 生成新请求并标记旧请求 superseded。授权、basisUnitRefs、Task inputVersion/runSequence 和回复审阅变化仍走原有校验。
- 不自动重放旧 decision payload。已 accepted 的请求不再恢复为待模型提交。

### 4. 协议提醒与独立进度

路由等待期间，暂缓决策请求的协议提醒及其重试次数消耗；路由请求自身的有限重试和 exhausted 报错继续工作。路由完成后恢复适用的决策提醒，沿用原请求身份及已用次数，避免重置次数造成无限重试。

不得从 Session 历史删除旧调用，也不直接清空原生 Inbox。本轮先通过派发门槛、请求级提醒控制和明确路由优先指引减少重复；已经可见的请求由版本检查兜住竞争窗口。

事项 A 已完成后，其通知可在归类确认相关输入后继续，不等待事项 B/C 完成。保留任务完成通知、普通回复各自现有的版本与 Outbox 校验，不能以本轮优化之名批量放行。

持续有新消息或路由无法完成时，仍可能延迟未接受决策。此次不通过超时强行接受旧决策解决；该边界必须在验收中披露。

## 验收用例

| 场景 | 必须观察到的结果 |
| --- | --- |
| 五个待决策 Topic，派发前已有未归类输入 | 本轮只派发路由；决策派发数为 0；清完后各派发一次 |
| 一个路由批次后还有未归类输入 | 不提前返回可提交决策；继续现有路由流程 |
| onDecisionRequest 等待期间新消息进入 | 回调完成后不泄漏旧决策派发；归类后能恢复，无永久待派发请求 |
| 模型已生成五个调用后才来新消息 | 允许 routing-required；接受前业务记录/Task/预约/Outbox 均不增加；路由请求不重复注入 |
| 新输入归到 B，A 未变 | A 原 requestId/revision 可继续提交，不重新制造决策身份 |
| 新输入取消 A 或改变 A 事项归属 | A 旧请求失效；不能按旧授权执行任务或发确认 |
| 等待路由、路由失败、恢复后再等待 | 决策提醒不空耗次数；路由 exhausted 可见；恢复后有限重试仍有效 |
| 路由等待与已 accepted 业务意图恢复并存 | 已接受意图继续原流程，不被 wake 的新派发门槛跳过 |
| A 完成，B/C 仍运行 | A 通知按自身条件处理，不等待 B/C，也不重复 Outbox |
| 归类中重启/已有 accepted 决策重复提交 | 从持久事实重建当前请求；无丢输入；无重复业务操作 |

使用受控测试 Promise 注入并发时机，避免靠 sleep 碰运气；分别统计工具调用次数、路由注入次数、accepted 决策数和业务操作数。先红后绿复现派发错误，再运行 topic/runtime/store 相关测试与全量测试。原生 Session/Inbox 的有限重试用例必须覆盖暂停后恢复，不能只断言内部标志。

## 交付与未验证边界

实施应从最新 origin/main 建独立工作区，先核对该基线与本方案差异，再修改；保留正在执行任务的工作区和本地服务。按现有 Git 流程交付可审阅 PR。

当前方案没有执行上述新验收，不声称已修复或已减少现场调用。部署另按现有 runbook 在明确的任务切换窗口执行，记录原 Task/Session、备份及恢复读回；实现和测试阶段不重启当前服务。

成功标准是：消除已知 pending 时仍新派发决策的确定性无效调用，保留必要并发重试，并证明独立事项的执行与反馈不被新增组级等待条件拖住。完全消除所有调用重试不在本轮承诺内。
