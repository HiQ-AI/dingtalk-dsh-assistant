# 需求补充后的模型恢复复核

## 问题与目标

现场正式评审任务在三次短退避耗尽后等待冷却。Web 补充网络恢复消息使 task.requirementRevision 从 1 变为 2，而失败执行仍绑定 1；调度和存储的当前版本门禁共同跳过到期复核。统筹读取失败记录后提交等待，没有续办调用。目标是让当前统筹可靠收到到期复核，同时禁止自动执行旧需求。

## 方案与边界

仅 execution.review-provider 允许需求版本不同；自动短重试仍要求原版本一致。复核保留排空、控制版本、取消、人工等待、原生日志终态和未知操作门禁，沿原执行身份发当前任务唤醒。事件提供复核时间、冷却到期时间和两个需求版本，要求统筹重审当前目标后显式续办。

不改 schema，不重置恢复次数，不自动改写旧执行输入，不新增恢复 API 或 UI。原任务部署后应沿既有到期复核继续，无需再次通过补充上下文制造需求版本。

## 验证

存储定向测试覆盖修订后复核、到期前拒绝、幂等、重启、暂停/取消/未知效果拒绝，以及原执行身份与预算保留。原生集成复现冷却中补充需求、到期唤醒和同会话续办，验证已成功写入不重放。部署遵守静止实例双包规程；其他业务仍活动时不强制中断，待其停稳再执行。
