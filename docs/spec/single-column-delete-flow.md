# 单列删除候选与需求修订边界

## 已确认缺口

恢复后的调查成功提交完整引用，却受合成需求的“必须先查列数据”前提阻止。原群消息仅要求删除准确列；新目标仍累积旧加列约束与旧阶段授权。现生产Host只支持加列和窄UPDATE，最终回查强制一行；仅修SELECT白名单不能完成删除流程。

## 实施边界

沿现有数据变更流程新增明确单列删除合同：严格单条 ALTER TABLE schema.table DROP COLUMN column，不接纳CASCADE、IF EXISTS或多语句。仅普通表、目标列存在、无继承、无identity/generated及指向该列的依赖，超出范围按真实复杂变更处理。候选固定说明删除列全部数据不可恢复，重建列仅恢复结构，不能宣称列为空。具体非空行数不是本次用户要求，审批前不强制读取列值或开放整表SELECT。

复用精确表基线与固定information_schema列投影；删除expectedChange为rows空数组。最终回读除列不存在外还确认表存在，排除整表消失误判成功。新工作流版本用于新阶段，旧定义摘要保持冻结。创建Bytebase新工单、插件私聊审批、SQL/目标/批准绑定、执行状态和最终验收沿既有链路。

需求修订须以当前真实来源为准，保留原sourceInstructions审计，不能让已经被明确替代的加列指令继续成为本次删除硬约束；系统拟定的调查步骤不能写成用户必需前提。修复原Task通过带当前版本检查的受管入口，不能伪造群消息或直接改SQLite。历史已成功加列及批准保留，不充当新删除授权。

## 验证

定向覆盖准确删除、数据损失提示、禁止CASCADE/多语句/依赖/继承、目标错配、表丢失、审批越权及晚批准、新旧定义恢复。正式部署后原Task推进到本次真实私聊审批，再由真人决定。不得代审批，未完成全链路不标测试完成。

原Task恢复采用现有Web context结构化修订，明确记录当前操作者授权的系统恢复说明，保留原群来源及旧成功阶段，不冒充需求方新消息；新生产SQL仍须独立插件真人批准。未新增恢复API或存储schema。新接纳的request及默认验收绑定当前事项原文，objective保留摘要；真实已有门禁不因摘要省略丢失。
