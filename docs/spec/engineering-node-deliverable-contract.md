# 工程节点交付物契约与语义核对

## 结论与证据

当前工程链存在产出不合理：prepare-workspace 完成外部创建后 return input，丢掉节点目录回执；prepare-generation 只传递下一轮起点但名称难懂；inspect-and-propose 仅代码补丁没有人读的方案；verify-candidate 保存执行日志但用户只能看到内部检查 ID。提交/推送准备节点保留执行计划合理，界面须解释前置条件与实际回执区别。

## 节点契约

| 现节点 | 用户名称 | 合理交付物 / 门禁 |
| --- | --- | --- |
| prepare-generation | 确认项目与修改起点 | 已选项目、工作分支、首次/继续修改、起点；远端与既有PR核对成功。不是推断项目的模型节点 |
| prepare-workspace | 创建独立工作目录 | 实际目录、来源仓库、隔离方式、创建回执。现实现 git init + fetch 是独立仓库，不冒称worktree |
| inspect-and-propose | 编写修改方案 | Markdown方案文档 + 机器可应用补丁，写明改动理由、文件、验证计划及限制 |
| validate-proposal（新） | 检查修改方案 | 文档非空、覆盖所有变更文件、存在实际改动；不伪称已证明技术正确 |
| apply-changes | 按方案修改文件 | 修改数量、工作目录与文件一致性回执 |
| verify-candidate | 构建与检查修改结果 | 可读检查报告：实际执行动作、退出结果、明确是否跳过测试；“打包通过”不等于业务验证通过 |
| prepare-commit / commit | 检查提交条件 / 提交代码 | 条件检查与提交回执分别展示 |
| prepare-push / push | 检查推送条件 / 推送代码 | 目标远端分支及实际推送回执 |
| prepare-pr / create-pr / finalize | 编写合并请求 / 创建合并请求 / 核对交付结果 | 可读PR文档、PR地址、分支与回读状态，不冒称已合并 |

## 实施边界

新工程定义使用版本9，旧已登记版本保持原实现，避免历史定义摘要漂移；不重跑旧任务、不伪造原方案。新节点实际持久化目录/起点/方案/检查报告。旧节点从同一nodeRun与代次的已成功效果回执补充目录，方案仅提供“由已有修改记录整理”的可下载文档，标明缺失原因说明；不冒充原节点曾写过文档。

只读节点接口继续鉴权与引用校验，文档下载按需请求。检查报告只读取固定检查器已保存命令及结果，不执行日志内容、不展示完整日志。逐节点核对当前工件；新契约用隔离工程仓库验证，旧版本摘要与重启恢复保持有效。
