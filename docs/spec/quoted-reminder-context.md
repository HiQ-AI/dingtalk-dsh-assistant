# 引用提醒的最小上下文

## 目标与已核实问题

2026-10-23 的 C 验收中，“提前三分钟”已原生引用 17:57 提醒的送达确认，仍先归类、再读取安排、最后提交改期，共调用模型三次。归类请求 17:52:12.504–23.700 耗时 11.196 秒；协调的两次请求分别为 17:52:27.340–31.497（4.157 秒）和 17:52:31.589–39.845（8.256 秒），没有 TRANSPORT 重试。

归类首屏含 34 个 Topic；协调首屏含 19 个任务和 5 条安排，随后读取指定安排又返回同样目录。三次输入上下文分别为 13,272、20,105、24,989 tokens，最后一次含 19,968 缓存 tokens。原消息时间 17:52:01 到归类会话创建 17:52:12.038 的 11.038 秒尚不能分拆：来源账没有 receivedAt，路由未持久保存现有 queuedAt/dispatchedAt，不能推断一定是排队或监听问题。

本轮只减少无关上下文与重复读取，不引入新的观测框架，不改时间含义、接纳权限、通知发送或已冻结的历史通知。

## 实施方案

在现有 independent-coordination-service 内提供唯一的 quotedReminderContext 只读方法。输入群、消息 ID、版本及可信作者；从不可变来源取真实 quote，不接受调用方传入引用目标。只在精确引用的已送达通知唯一对应同群、同作者、当前活动纯提醒时返回提醒规则和版本。unknown、非提醒、跨群、跨作者、歧义、失效版本均不缩小上下文。

设置者与收件人独立：A 设置提醒 B，A 的订正仍读取保存的 B；引用来源作者只确定原消息，不替代日程 recipientIds。已用真实 CLI dry-run 核实原生引用可引用 A、仅提及 B，不会自动将 A 加入提及列表。

协调首屏通过这个方法预取当前提醒，并经已有 arrangementObservations 路径记录已读版本。仅保留当前消息、引用背景、当前提醒详情、相关收件人和时间上下文。任务目录及其他安排按现有 context_get 显式分页参数读取；不把未加载目录描述成空库。

路由首屏通过注入回调复用同一关联结果，不再附带无关 Topic；仍由模型判断是否为改期、新业务或混合事项，保留原有按需目录工具。没有原生引用时不猜测“同人最近提醒”，沿原路径处理。没有自动提交、正则订正、缩减业务动作类型或绕过原接纳校验。

## 验证边界

- 精确引用当前提醒可首轮直接提交改期；正文、收件人与版本正确，省去一次模型读取。
- 异作者、异群、旧消息版本、未送达或歧义通知、已取消/非提醒安排不进入缩小上下文路径。
- 相同来源重复调用和重启不新增通知、不改写已冻结 payload；提交仍校验当前版本。
- 用户引用提醒但提出新业务或混合事项时，可主动读取完整任务/安排目录并走原接纳或安全交还路径。
- 路由与协调复用同一来源解析，不用两套身份关联实现。
- 仅运行直接相关的协调、路由、原生规划测试；真实模型与真实业务验收分别记录，不将脚本模型通过宣称为线上耗时达标。
