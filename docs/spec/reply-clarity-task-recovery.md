# 回复可操作性与真实任务阻塞修复

## 目标与现状

用户要求群回复清晰、完整，并恢复审核侧栏核验和两项开发任务。2026-10-08现场：通知代码直接将Owner摘要压平截160字符；审核侧栏Task以capability等待；生产活动Task在计划版本0发生128异常；数据集Task进入工程后等待execution_no_submission。

## 方案

1. 业务补充请求复用已验证condition.missing，明确说明需要提供的信息并保留分行及完整正文；分析细节保留任务详情。不得把系统维护问题伪装成业务补充。
2. 分别核对Owner注册工具、执行会话能力及实际查询记录；以真实注册与运行证据判断能力缺口，不把工具表面缺失归因到使用者。
3. 两项工程任务分别定位到失败节点/会话及前置条件。复用已授权、受管恢复入口，保留当前Task与效果账，不重建任务、不重放已成功副作用。
4. 定向测试后按既有runbook受控部署，独立回读包、健康、任务节点与必要的通知更正结果。

## 边界与验证

不代替业务工作流直接开发业务仓库，不扩大生产/发布授权，不修改运行数据库。代码行为回归和真实任务恢复分别记录；不能以HTTP成功或任务running替代业务完成。Owner与执行会话边界待实际证据收敛后确定代码修改范围。
