# 任务详情只展示当前完整执行状态

日期：2026-09-28。状态：方案，待实施。本轮仅核对源码和形成设计，未修改业务代码、运行数据或部署。

## 目标与决策

任务详情始终展示一份当前有效的完整执行方案及其最新结果：重执行更新原步骤，新计划已移除的步骤从列表删除，新增步骤按当前流程插入，未受影响且仍有效的步骤保留。

本方案取代 `task-card-execution-history.md` 中“详情保留全部执行历史”的展示决策；卡片沿用已有样式及同一任务聚合方式。旧文档是此前方案快照，故新增本文件记录本次决策，不回写旧快照。

“最新”指最新生效的计划及该计划认可的执行结果，不是最后一条日志、最后成功的一次，也不是仅展示最后一个阶段。“完整”覆盖当前计划中的已完成、进行中、受阻和待执行部分，不等于所有步骤都已完成。

任务详情不再提供执行次数切换、执行历史、旧结果或旧步骤列表。底层执行记录仍服务于恢复、幂等、授权和排错，不参与历史页面展示；本方案不执行数据库、日志和工件的物理清理。当前步骤可以保留其对应会话及工件入口。

## 当前源码依据

- `packages/dingtalk-dsh-assistant/workflow-service.js:2258` 按当前阶段选取一个 run；2299 行将该 run 的 `state.nodes` 作为 `executionNodes`。因此详情目前未将当前计划的全部阶段展开为完整步骤。
- 同文件 2327 行的 `taskDetail` 返回指定物理 taskId 的详情，附加逻辑任务身份；2335 行另有执行历史接口。
- `packages/dingtalk-dsh-observer/web-client.js:876` 使用 `executionNodes` 渲染步骤；886 行展示执行次数及返回最新入口，888 行挂载执行历史；末尾还有本次运行过程折叠区。
- `packages/dingtalk-dsh-assistant/execution-task-plan.js:137` 的 `insertStages` 会保留经校验的成功前缀；388 行的 `task.plan.revise` 校验计划版本、运行状态和外部效果，并以完整新计划替换后段。
- `packages/dingtalk-dsh-assistant/task-owner-controller.js:253` 区分初始化、追加和替换后段，并生成位置形式的 `stage-N`。阶段编号本身不保证跨计划语义相同。
- `packages/dingtalk-dsh-assistant/workflow-service.js:1377` 的 Web 重执行新建内部 taskId，并要求开发、合并、部署三个阶段；当前不能把这个入口解释为任意局部重跑。
- 同文件 2663 行的步骤正文读取校验 taskId、runId、nodeRunId 和 outputRef，新的详情聚合仍须保持真实来源绑定。

以上是本地源码结论，未据此声称当前安装包、页面和真实任务已经具备新行为。

## 方案比较与反例

| 候选 | 结果 | 选择 |
| --- | --- | --- |
| 只展示最后一次 run | 简单，但最后一个部署阶段会挤掉前面的有效分析、开发与验证 | 排除，信息不完整 |
| 从所有历史中按名称或 nodeId 取最新结果 | 同名步骤、不同仓库/环境、改过的输入会混在一起，也可能拼出从未成立的完成结果 | 排除，缺少有效性依据 |
| 以当前完整计划为唯一目录，读取每步当前有效执行 | 保留有效步骤，并明确新增、替换、删除及失效规则 | 采用 |

## 更新规则

| 变化 | 详情中的处理 |
| --- | --- |
| 同一步重新执行 | 原位置更新状态、耗时、正文、证据和产物；不追加重复步骤 |
| 重执行已开始但尚无新结果 | 展示进行中及本次进度；旧成功结果不再作为当前结果展示 |
| 重执行失败、取消或等待处理 | 显示本次真实状态与原因，不回退显示上次成功 |
| 原步骤仍在当前计划，输入和依赖未变 | 保留当前有效结果与证据；不因另一阶段重跑而清空 |
| 新计划移除某步 | 从当前列表、数量、进度和当前结果引用中一起移除 |
| 新增步骤 | 按新计划的顺序加入，包括尚未执行的步骤 |
| 上游输入、代码版本或目标环境变化 | 从受影响位置起使依赖结果失效，显示待重新执行/验证；不能继续计为成功 |
| 同名步骤属于不同仓库、环境或阶段实例 | 保持各自身份，不合并 |
| 临时请求失败、分页不全或新计划尚未接受 | 不能据此删除步骤；展示读取失败或正在更新，保留已读取内容并明确其尚未刷新 |
| 旧执行迟到回调或旧正文分页响应 | 根据当前计划和执行版本拒绝覆盖；不能让已删步骤复活 |

“过时删除”必须来自正式生效的完整计划，不由前端缺字段、搜索结果缺失或模型的一段自然语言判断。仍运行或外部操作尚未对账的步骤，先按现有控制规则停止/对账，再接受替换；不得仅从页面隐藏。

当前控制模型采用顺序阶段。第一版复用“保留成功前缀、从影响位置替换后段”的规则，不引入通用依赖图。即使部分后续结果看似仍可用，也必须由现有流程证明确实有效，不能由展示层推断复用。

## 示例

原计划：分析 → 开发 → 验证 → 部署。

- 只重跑部署：保留前三步的有效结果，在同一部署步骤中更新状态和结果。
- 修改开发实现：分析仍有效时保留；开发更新，验证和部署转为待重新验证/执行。
- 新流程变为分析 → 开发 → 验证 → 数据检查 → 发布：移除原部署步骤，新增数据检查和发布；只呈现这五步。
- 新执行是完整重跑：按完整新计划重置所有受影响结果，不从旧 taskId 自动补成功记录。

## 服务端与前端落点

### 1. 复用当前计划生成统一详情

扩展现有 `taskDetail` 投影：逻辑任务定位当前执行，读取当前完整计划，按阶段顺序组合每个阶段当前有效的节点，再输出一份完整详情。正常详情入口和旧详情链接均打开逻辑任务的当前详情；操作仍携带真实当前执行身份和预期版本。

保留的成功前段通过当前计划已有的 runId/outputRef 读取；被替换的旧 run、旧节点代际和旧步骤不纳入目录。新 Web 全流程重执行使用新计划；若未来支持跨内部执行保留前段，必须在计划接受时明确登记并校验来源，不能由本次展示改造自行拼接。

步骤身份由当前计划绑定的阶段实例、工作流定义和节点身份共同确定，序号仅用于显示。不单独用标题、位置或 nodeId 去重；`nodeRunId` 作为最新执行引用，不能拿来定义业务上的“同一步”。保留映射由计划变更明确提供或从已验证的保留前缀取得。

尚未开始但工作流定义已绑定的阶段，展示真实定义中的待执行节点；动态定义尚未解析时展示“该阶段步骤待确定”，不杜撰节点或标记为完成。计划本身仍是完整目录。

### 2. 同一版本返回状态、步骤与结果

详情带当前计划/需求/执行版本标识。通过一致性读取，或读取前后校验版本并重试，避免一半旧计划、一半新结果；客户端仅接受与当前详情版本匹配的正文分页与刷新响应。

每步的状态、正文、证据、时间和产物必须来自同一次有效执行。沿用正文和文件的精确归属校验，不因逻辑任务聚合放宽读取权限。缺失文件明确显示“产物不可用”，不能改取另一轮文件。

优先在现有服务端投影中实现，不另建一套可独立修改的展示状态或让模型重写历史总结。

### 3. 调整现有详情组件

保留现有任务目标、编号步骤、状态、耗时、产出正文、长文继续阅读与当前会话入口。移除执行次数/历史切换和历史运行列表；前端只渲染统一详情，不自行合并运行记录。

阅读顺序保持为任务目标与当前状态 → 当前完整步骤 → 当前结果。长文仍可分段加载，“完整”表示内容可读全，不要求一次把全部正文加载进首屏。刷新保持阅读位置；删掉正在阅读的步骤时给予简短提示并落到相邻步骤。

步骤进度按当前有效目录计算；动态待确定阶段存在时不得显示整个任务“100%”。步骤耗时展示该步当前有效执行的耗时，不能把被替换的多次执行相加后冒充本次耗时。现有任务累计耗时如保留，明确标注统计口径。

### 4. 当前结果与完成条件

当前结果归属当前需求和执行版本，只引用有效步骤产出。受影响步骤重新执行后，依赖旧证据的最终成功结论立即失效；运行中显示当前进展和未完成项，新失败显示新失败。

任务完成仍依赖现有 Owner 的当前版本验收及送达规则。前端步骤计数不是完成授权；展示隐藏历史也不改变重试、审批、归档、发信箱和实际外部操作的控制逻辑。

## 实施次序与验收

1. 明确并实跑统一详情投影：跨阶段完整性、保留前段、替换后段、待定阶段、有效结果和版本一致性。
2. 将 observer 接到统一详情，移除历史组件调用；同步现有 API/README 中任务详情的行为说明。
3. 使用同一真实任务的局部重试、计划变化、完整重执行三类场景验收，再独立验证本地安装包、API 和浏览器。

必须覆盖以下反例：

- 部署失败重试后始终只有一个部署步骤，前三阶段产出仍可完整读取。
- 上次成功、本次运行中或失败时，不出现旧的最终成功结论。
- 修改代码后，旧验证与旧部署不继续显示有效成功。
- 删除、增加、调整步骤顺序后，列表、进度和结果引用一致，重启后不反弹。
- 相同节点名分别属于两个阶段或目标时互不覆盖。
- 旧页面操作、迟到执行事件、慢正文请求不能写回过期状态。
- 计划尚未确定、文件缺失、请求失败有真实说明，不伪造完整结果。
- 当前步骤工件读取不串任务、不串执行，仍遵守原有权限范围。
- 任务卡片、详情、完成门禁对当前状态无矛盾；取消、审批和归档行为不被展示变更破坏。
- 窄屏、键盘操作、长文加载及实时刷新时的阅读位置正确。

未收敛边界：动态阶段的详细节点只能在定义确定后完整展开；当前 Web 重执行不支持任意局部重跑。实现时必须分别验收“计划内重试/修订”和“新内部任务的完整重执行”，不能把二者混为同一个已支持能力。
