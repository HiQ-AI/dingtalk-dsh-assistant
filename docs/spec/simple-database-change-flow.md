# 简单数据库变更的交办与审批闭环

2026-10-02 分析与方案快照。本轮只分析和设计，不修改运行任务、不提交工单、不执行 SQL。独立成文原因：此前任务决策恢复方案解决状态合法性，本方案纠正业务目标扩写及数据库审批流程，不覆盖原验收记录。

## 目标

将“生产 Editor 的 process_id_temp 新增 name 列”推进为：确认目标和当前列 → 拟定 DDL → 提交 Bytebase → 真人审批 → 通过后执行并回读；驳回则按意见修订后重新送审。复用当前 Task 和现有数据变更实现，不增加通用编排引擎、风险平台或第二套任务模型。

## 当前证据及因果边界

2026-10-02 从本地 Runtime `/state/tasks/task-e7e25daf5c0aac2f8bcb5ef13daef45f/detail` 独立读取：

- objective 已扩展为检查依赖、类型、长度、NULL/默认值、用途、现有数据影响，并准备风险、备份/回退和审批材料。
- plan.version=2，三个 `task-investigation` 阶段均 succeeded；计划中没有数据变更阶段。
- waitingCondition.kind=`business-input`；要求需求负责人先确认用途、类型、长度、空值、默认值及既有行处理，才能提交生产变更审批。

因此当前直接停点是“等待字段规格确认”，不是已提交工单后的真人审批，也不是正在等待生产执行。三个调查阶段成功只证明阶段完成，不能证明这样的业务停点合理。

直接原因与潜在后续障碍分开：当前 Task 尚未进入数据变更阶段，不能把 UAT 或审批适配说成已经触发的此次等待原因。也不能仅凭源码宣称当前 Bytebase 实例的审批配置、账号权限或 API 行为已验证。

核对的候选解释：

1. 字段规格不足必然需要先找人：不足以解释不能送审。确实需要确定具体类型才能形成 SQL，但可以提出明确候选供真人审批，而非声称候选已获需求方确认。
2. 数据库完全无法查询：已有成功查询产物；当前 waitingCondition 是业务定义不足，不是数据库连接故障。当前审批平台的可用性仍需在实施时单独实测。
3. 状态机无法继续：当前已合法进入 wait，阶段均成功；这说明决策可被保存，不说明业务决策正确。
4. 目标和决策规则扩大准备范围：当前 objective、三个调查阶段及 waitingCondition 互相印证，是直接原因；通用变更流程和审批来源是随后还需解决的结构性问题。

上一轮修复着重保证调查证据完整和 wait/block 合法，实际验收也允许停在“业务确认”。这未覆盖用户真正需要的工单送审闭环，是此前分析和验收目标选择的偏差。

## 调整方案

### 1. 原需求、候选方案与执行批准分开

任务目标保留原始交付：新增 name 列，提交 Bytebase 审批，通过后执行并核验。系统自行建议的检查不自动升级为业务验收项。

对未指定的字段类型，可在没有冲突依据时提出清楚的候选，例如 `character varying`、允许 NULL、无默认值、不回填现有行。工单正文明确这些是本次建议，由审批人确认；不把它们描述成孙鹏已指定的事实。若现有项目规范明确要求其他类型，按规范拟定。

只核对能够影响当前候选的最少事实：准确生产数据库、schema/表、列是否存在及已知直接限制。不默认扫描所有代码引用、补全用途说明或穷尽全部依赖；确有冲突时才追加针对性核查。

### 2. 调整现有数据变更路径

在现有 `task-data-change` 和 Bytebase adapter 内完成：准备候选 → 提交并独立回读工单 → 等待审批 → 根据决定推进 → 执行结果及列结构回读。

简单新增可空、无默认值的列，不强制先跑 UAT，也不把通用全库基线、备份和回退包作为提交工单的门槛。用户明确要求演练、平台强制检查，或实际 SQL 涉及回填、删除、收紧约束等操作时，再安排对应准备。保留平台真实强制要求，不把模型惯常建议当成组织规定。

保留精确目标和 SQL 版本绑定、外部动作幂等及未知结果先对账、执行后独立回读。这些直接保证执行的是批准的操作。

### 3. Bytebase 审批作为本次生产变更的批准来源

先实测已部署 Bytebase 的审批配置、审批状态/意见读取及修订能力；目标是使用其真实真人审批结果，不要求同一 SQL 再去 Assistant 看板重复批准。

- 待审批：Task 等待审批，记录工单链接和当前 SQL 版本；按现有后台恢复机制读取变化。
- 驳回：读取具体意见，修改候选，重新送审；不要直接置为无法推进。意见涉及无法判断的业务分歧时，才提出一个有针对性的问题。
- 通过：执行前回读目标、当前 SQL 与真人批准是否匹配；批准后由受管 Bytebase 路径执行。
- 修改 SQL：旧批准不能沿用；使用平台支持的修订方式。若实例限制不能原位修订，创建关联的新审批版本并保留旧记录，不猜测平台行为。
- 平台未设置真人审批或状态是跳过审批：不能当作已通过；需要先使本次工单具备实际人工批准路径。这是实施时要验证的集成条件，不是继续调查字段业务含义的理由。

### 4. Owner 以“下一步是否可推进”判断等待

判断 business-input 前，先判断未知内容是否真会阻止下一项获授权动作。能形成明确待审候选，就提交审核，不把“尚未获批”写成“尚不能提方案”。仅当无法确定目标、需求存在实质冲突，或审批意见需要需求人选择时，才等待业务输入。

审批等待属于正常流程；真实工具/权限故障写明具体失败。调查 Agent 可以报告未知，Owner 必须结合任务目标决定该未知是否构成阻塞，不机械继承 needs_input。

### 5. 当前任务和通知

实施后保留当前 Task 身份及已有表结构证据，修订扩大的目标和验收项，直接编制候选并送审，不重跑三轮调查。

通知围绕实际结果：“已提交工单，等待审批”“已按审批意见修改并重新提交”“已执行并核验”。原群聊中不准确的受阻说明在实际状态纠正后调整或撤回；不在分析阶段提前声称已提交。

## 实施与验收顺序

1. 核验 Bytebase 原生审批/修订能力，修正现有 adapter 和流程；同步相应 README、API/运维说明。
2. 修正 Coordinator/Owner 的目标、候选和业务等待规则；不以新增某张表的专用提示词完成修复。
3. 定向测试证明：只说“加 name 列”能到待审；驳回后能修订重审；新 SQL 不复用旧批准；批准前不执行；重启不重复建单或重复执行；执行完成后列结构不符不能报成功。增加另一个简单表/字段用例验证没有硬编码。
4. 本地部署后用原 Task 验证实际工单、SQL、目标和待审状态。真人批准和生产执行必须以真实回读单独验收，测试桩通过不能替代。

完成标准是业务能够到达真实 Bytebase 审批并按其结果继续，不是多一次查询成功或 Task 能合法保存 waiting。
