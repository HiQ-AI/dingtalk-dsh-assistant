## 核心约束

1. 原始消息、执行报告、独立核验证据、审批决定分别保留来源和发生时间；模型总结不能覆盖它们。
2. 事实可以先入账；事实已接收不代表业务结论已核实、阶段已通过或新动作已获批准。
3. 进度查询、回复纠正不自动修改 Task 目标、清空检查点或重开执行轮次。
4. 同一业务事件重试复用身份；改变业务输入才形成新版本。网络尝试编号不参与业务身份。
5. 活动上下文只有一份当前有效正文；完整历史继续保存在持久记录中，缺失和变更的内容按需恢复。
6. 外部操作结果不确定时先核对真实状态，不能因请求重试而自动重做 SQL、发布或消息发送。

## A. 共享当前事实，修正进度回复和审批重复质疑

### A1. 在现有读取工具中提供有界的当前 Task 快照

扩展 `group_task_context_get` 的直接查询结果，包含：Task/run/input 版本，已确认阶段，当前执行阶段，已接收但待审的报告，当前阻塞，相关审批摘要，以及最近有效进展。每项带 `observedAt`、来源引用和核验状态；整个响应另带 `snapshotAt` 和用于提交检查的修订标识。

三种时间不混用：状态快照的读取时间、叶子报告的事件时间、外部系统的独立核验时间。若只有旧报告，回答“截至 X 的最后记录”，不能因刚查询了 Store 就包装成刚核验过生产。

复用现有 Task/checkpoint/result/humanBlockerHistory 生成快照；增加的事实记录放在现有 Task 执行记录中，以 Session ID + seq 或稳定 submission ID 去重。不把任意工具成功结果自动解释为业务完成。事实内容使用短摘要与证据引用，详情分页读取。

`taskAssociationContext` 继续只用于关联索引；不把完整进度、审批历史加入每次动态 Task 索引。进度读取与索引召回的负载必须分开。`group_task_context_get` 的直接响应限制选中 Task 和必要字段，超出预算返回详情引用。

### A2. 审阅直接读取真实批准

检查点和完成审阅的上下文装配直接读取同一 Task 的 `humanBlocker`/`humanBlockerHistory`，传入与本次操作相关的批准 ID、原请求、答复时间、答复来源和对象版本。后续结构化审批逐步补全 taskId/runSequence、环境、资源、操作及候选/SQL 哈希等绑定字段。

同一轮次、同一操作对象的有效批准可复用；补充进度信息或更换审阅 requestId 不使其失效。范围、目标资源或批准对象发生实质变化时必须重新核准。旧记录缺少对象绑定时保留原请求原文与原始答复供核对，不能伪造为新的强类型授权。

完成审阅引用 approvalId 和 evidenceRef 即可，不能要求叶子重新把整段批准内容写进 evidence 才承认存在。审批是否足以覆盖新动作仍需判断。

### A3. 活动投影滚动保留

修正 `store.recordActivity` 达到每 Task 500 条后停止写入的逻辑：在同一个串行持久化操作内接纳新事件，按确定顺序淘汰最旧摘要，保留最新 500 条；相同 eventKey 幂等，乱序老事件不能挤掉最新事实。

记录 projection 最后处理的 Session/seq、最后同步时间和截断情况；保存 latestEventKey 等水位，已淘汰的老事件重放不能被当作新进度。叶子替换 Session 时按 Session 分别管理水位，不能直接比较两条 Session 的 seq。投影异常应进入健康状态，避免当前 `activityTail.catch(() => undefined)` 静默吞错。

原始 Session JSONL 仍为全量证据，不因投影上限而删除或改写。若看板使用该投影，同步展示最后更新时间；显示“最近 500 条”而不是暗示完整历史。

主要改动：`runtime.js` 的上下文读取、活动监听与审阅装配，`store.js` 的 Task/活动存储，`topic-runtime.js` 的审阅输入；Observer 仅同步受影响的状态说明。

## B. 区分事实接收、计划修订和最终验收

### B1. 进度质疑先核对，不能直接变成重做指令

将“询问/质疑进度”与“修改目标/操作范围”作为决策中显式区分的意图。查询和答复纠正只处理对应 Topic 与 Outbox，不自动产生 `task-context` 或 `task-reopen`。

确需修订 Task 时，提交实际差异、依据消息或证据引用、受影响阶段。Host 先比较规范化后的值：参数传了同样的 acceptanceCriteria/stageTasks 不算范围变化，修正现有 `scopeChanged` 只判断参数是否存在的问题。

保留 `preserve/replan`，但去掉“无法确认时一律 replan”。无法确认影响时先读取当前事实；仍未明确的部分进入待核对状态，保留旧证据，暂停依赖该不确定事实的新推进。确有变化时只使受影响阶段及其后续依赖失效，旧事实留档，不把旧 checkpoint 的版本号批量改成新版本冒充重新验收。

将本次输入修订的 `progressImpact` 持久绑定到该 inputVersion。`buildTaskTopicContext` 根据对应版本读取，不能依赖 executionEvents 最后一条恰好是 input-revised，否则加载流程等事件追加后会退回默认 replan。

### B2. 已发生事实先接收，待输入接纳后再验收

`submit_task_checkpoint` 和 `submit_task_result` 先进行身份、来源、结构与所属 run 校验，把报告以稳定 submissionId 持久接纳，再判断能否推进。明确区分返回结果：

| 结果 | Runtime 行为 | 叶子后续 |
| --- | --- | --- |
| 已接纳并通过 | 持久报告与推进状态 | 继续下一阶段 |
| 已接纳、等待输入或审阅 | 保存报告和等待原因，不批准推进/完成 | 不重新提交；等待对应事件 |
| 内容或身份不合法 | 返回字段、错误码和可操作说明，无推进副作用 | 修正具体内容后再提交 |
| 旧版报告仍有历史价值 | 只记录到其原 run/input 的事实，不覆盖当前状态 | 由当前版本影响检查决定是否可复用 |

保持当前输入的最终验收门禁；旧版 completed 不能覆盖新目标。群级未归类消息仍可阻止尚不明确的任务变更，但不应阻止已发生事实落账；已明确无关的 Topic 不占用该 Task 的等待条件。

Runtime 持久保存等待原因和待处理 submissionId，停止为无可执行进展安排 Goal 续轮；输入接纳、审阅完成或授权答复到达后唤醒一次。使用现有 Agent/Goal 生命周期扩展点，并用真实 DSH 验证没有后台空转；不写一个不断返回“请继续等待”的模型循环。

### B3. Schema、工具说明和运行规则同源

在 `task-result.js` 中按 checkpoint.kind/result.status 拆出精确的 Zod 分支，工具参数声明从同一契约生成或校验，错误返回字段路径、允许的字段与当前版本。

异常报告的 stageTask 定义为“受影响阶段”，不代表该阶段完成；completedItems 必须为空，不能改变阶段通过状态。这样模型可说明发生在哪个阶段，无需猜测删哪个字段。workflowAssessment 只属于计划分支。诊断记录不要求先有被接受的计划，也不要求先重读全部流程。

已有 checkpoint 的存储 schema 与工具提交 schema 分开：历史解析保留既有数据，迁移后所有新提交走唯一的新契约，不在执行路径里维护两套猜测规则。

### B4. 计划与阶段顺序一次性确认

仍使用有序阶段列表，暂不引入通用 DAG。为阶段增加持久 stageId 和明确的验收条件，保留显示名称；计划由叶子提出实际执行顺序，审阅通过时原子写入计划版本与阶段列表。

以今天为例，若候选依赖要求 SQL → 后端 → 前端，就让结构化计划采用该顺序；不能文字同意而 Host 仍执行旧列表。已完成阶段要在有意义的操作结束时立即报账，普通 stage-completed 延续已有 Host 确定性确认，不能又改回每阶段同步模型审阅。

旧字符串阶段在迁移时分配一次稳定 ID 并保留原顺序；有正在等待的审阅时不原地换计划，新计划经确认后切换。范围实质变化才重审受影响阶段，普通状态补充不重置五阶段。

主要改动：`decision.js`、`task-result.js`、`runtime.js` 的输入修订/提交/Goal 调度、`store.js` 的报告与阶段契约，以及对应测试。

## C. 消除重复读取和重复活动上下文

### C1. 将读取依据从 requestId 改为内容版本

审阅请求仍绑定本次计划、来源群、Task/run/input 和候选状态，但共享读取凭据按以下内容身份索引：

- 流程：flow ID + revision + 正文指纹。
- Topic 原文：groupId + topicId + 固定 revision + section/page 内容指纹。
- 回复候选：当前候选集合版本、必要正文和替换关系；不能只按 Task ID 缓存。

一次读取可供同一 Session 活动上下文中的后续审阅复用。Host 必须确认对应原文仍在 Session 原生 surface 或当前受管系统提示中；只有“过去读过”的记录不能过关。原文被压缩、裁剪、替换或来源修订时，恢复缺失部分。使用 DSH 自带的 surface/replaceGeneration 与事件来源，不自行扫描文本猜测可见性。

因此相同原文首页不再因五个 requestId 读五次；新计划本身仍然需要审阅，缓存不等于缓存模型的业务判断。群和任务读取权限仍按当前上下文校验，不能跨群复用正文。

### C2. 流程与 Task 当前状态各用一个载体

选择保留现有动态系统提示作为叶子“当前流程、目标、阶段”的唯一正文载体。`load_task_prompt` 只更新所选版本并返回简短选择收据；下一步系统提示确认含精确正文后，Host 才认为该流程已提供。不能因移除工具正文造成加载成功但模型未获得内容。

`TASK_TOPIC_CONTEXT` 只携带输入版本、变化摘要和固定 Topic 引用；完整当前目标/阶段不再重复放入事件正文。原始消息由按需工具和受管活动上下文提供，历史更新继续保留在日志中。

Resident 各类请求同样先带当前增量与引用；已完成/失效的协议消息通过原生 surface 替换为紧凑结果引用，原始日志保留。不能直接截断原始 Session 文件或破坏 tool call/result 配对。AGENTS 和 Skill 的缺失恢复保持正常，不把它们当成重复派发工具。

### C3. 一次装配审阅材料，减少协议试错

请求创建时由 Host 收集本次必要的当前 Task 快照、相关审批、变化后的流程/原文、回复候选及其版本，在总预算内装成一个审阅包。模型不再先失败于 `review-required`，再取资料、重新生成同一份完整决策。

对确实超限的材料只提供必要 section 引用，已有完整可见内容不再要求重新分页；缺失材料仍不可跳过。提交瞬间只重新检查实质变化的来源与业务版本，过期时返回具体 diff；复用未受影响内容，不能把新消息竞争变成整包从头重写。

主要改动：`topic-runtime.js` 的 requestReview/readPromptRefs/readSectionOffsets/reply review 装配，`runtime.js` 的系统提示和流程工具 render，原生 Inbox/surface 集成测试。

## D. 稳定协调身份、故障恢复与副作用去重

1. 保留已部署 `checkpointReviewRuns`，让提交与 Supervisor 共享同一执行 Promise，覆盖审阅、持久化和拒绝通知。审阅状态及通知身份再持久记录到现有 Task 执行状态中，以便跨重启恢复。
2. 路由身份绑定 group + message IDs/versions；决策绑定 Topic revision；审阅绑定 checkpoint/结果提交身份及其依赖版本。retryAttempt、时间戳不改变这些身份。同 ID 同内容复用，同 ID 不同内容明确报冲突。
3. 复用 `dispatchTaskInput` 与 `test/topic-native-inbox.test.js` 已验证的稳定 message ID 思路：先查原生 pending Inbox 和已消费 user/message，再决定是否投递。已消费且仍可见的请求只恢复处理；缺失内容才恢复一次。读取 Store 与 Session 后按原生接口做幂等操作，不能假设跨两者存在事务。
4. Provider 失败优先由现有 DSH 原生重试层负责；Topic monitor 只判定业务请求是否仍未完成，不与 Provider 同时重试。失败分类使用结构化错误。重试采用有上限的指数退避和抖动，建议初始 2 秒、上限 30 秒、最多 5 次；具体映射到已安装重试配置后验证。达到上限进入持久可恢复失败并给出一次明确状态，不在 1 秒后换 ID 无限重放。
5. 把审阅超时、输入被替代、Provider 失败、已完成但通知未投递分开。`whenIdle` 不是请求超时也不是失败原因；使用请求状态、处理期限和 native step 结果判断。deadline 基于队列等待/实际开始分别记录，排队请求不能被误判为模型已超时。
6. 拒绝通知、完成通知使用稳定 Outbox/event ID。进程在“记录审阅成功”与“通知写入”之间退出后补发同一条。已有外部动作与 Outbox 的独立回读保护保留，不承诺外部系统不支持幂等时能实现全局 exactly-once。

主要改动：`topic-runtime.js` 的 request/monitor/schedule，`runtime.js` 的 checkpoint 与恢复，`store.js` 的协调生命周期字段，以及现有 DSH retry/Inbox 集成配置。先验证原生配置能力，若确需 DSH 配套修复则单独交付，不能直接修改本机 node_modules 充当修复。

## E. 单独解决响应时间和执行吞吐

### E1. 简单问答使用有界读取路径

在 Runtime 增加只读状态请求的短处理路径，业务身份仍在原群、原 Topic 中持久记录，不新增常驻或叶子 Agent。关联明确的进度问答，使用当前消息、相关 Task 快照、必要引用和回复候选直接生成答复；关联不明确时先做有界目标识别，不能按几个关键词猜 Task。

使用已安装 DSH `ctx.llm.stream` 和原有 Provider/模型配置发起有界只读调用，结果按现有 Topic/Outbox 校验提交。只开放查询/答复结果类型，不能创建 Task、修改目标或执行 shell。每群至多一个在途只读短请求，同事项新消息合并并保留所有来源；它不排在长计划审阅或 Resident 历史压缩之后。

简单请求目标为 1 次模型调用；必须先识别关联时允许 2 次。涉及行动授权、目标变更、复杂矛盾时，保留同一业务请求交给 Resident，并明确记录转交原因；不强行用短路径作复杂决定。短请求与主会话之间统一提交前版本检查和 Outbox 去重，不能形成两个并发发声者。

该调用需接入现有 Session 遥测/事件来源，记录输入引用、模型使用量、处理时长和提交结果；不只留下最终文字。保持当前模型不变做基线对照，先验证流程和上下文削减的收益。

### E2. 降低模型串行往返

查询/构建/核验优先复用已有 runbook 脚本，一次返回结构化结果。独立只读查询可并行；有依赖或副作用的步骤按实际顺序。读取阶段先确定目录和具体文件，再搜索；对不存在路径、glob 超时等明确错误修正根因，不反复做同一次大范围搜索。

后台构建与测试由已有 job 完成事件唤醒，避免模型定时查询同一个 job_output；有新输出或要做决定时才调用模型。状态会变化的外部查询不做通用“相同参数不再执行”缓存。

### E3. 发布准备在前置阶段完成

调整现有生产发布与数据变更流程：从实际生产只读基线、候选依赖和迁移集合核对前置对象，提前发现“增量包假设基础对象已经存在”的缺口。固定 SQL/应用顺序、停止条件和回滚范围后再进入执行。

先读取已有 runbook 与可用环境约定；使用被允许的 UAT 隔离 schema/临时数据库或本机隔离资源。不能把共享 UAT 当作随意执行生产 SQL 的实验库。资源需要真人启动时，先判断是否确实没有已有可用环境；不要因临时选择 Docker 而把原本可运行的任务转成人工等待。

现有流程内容位于 Runtime 配置时，按 taskPrompt revision 更新并核对在途任务影响；不在发布中途静默改审批依据，也不替用户更新全局记忆。

| 批次 | 范围 | 关键验收 |
| --- | --- | --- |
| 1 | A：共享事实/审批快照、活动滚动保留；补测既有 checkpoint 去重 | 已发布状态不会被答成未开始；有效审批可直接查到；第 501 条活动可见；一次驳回只注入一次 |
| 2 | B：报告先接纳、事件唤醒、精确 schema、定向修订和阶段顺序 | 同一报告 pending 期间不重提；进度质疑不清空阶段；异常报告可达；新范围仍阻止旧 completed；顺序一致 |
| 3 | C：版本化读取凭据、唯一上下文载体、一次材料装配 | 相同流程/原文不随 requestId 重读；压缩缺失后正确补齐；流程改版/跨群引用不能误复用 |
| 4 | D：持久协调身份、原生重试协作、重启恢复 | 过载不重复整包注入；重启恢复原请求；通知单次；未知副作用不重放 |
| 5 | E：短响应路径、执行批处理、发布前置流程 | 真实模型问答达到响应目标；复杂行动不进入只读出口；生产缺前置对象在准备阶段被发现 |

不重写现有业务实现到一个新框架。新模块仅在现有职责确实放不下时拆出：例如有界状态问答处理器可以作为单独模块，避免继续膨胀 runtime.js；它复用同一套校验和提交函数。

### 必须覆盖的反例

| 场景 | 期望行为 |
| --- | --- |
| 生产已完成，常驻历史仍写着等待审批 | 读到新事实；以发生时间说明实际状态，不回退旧计划 |
| 用户只问“状态查错了吧” | 核对并纠正答复；没有依据时不推导出误连库、不发 replan |
| 传入与旧值相同的验收/阶段数组 | 判定无实质范围变更，保留有效阶段 |
| 目标不变，但新证据证实某阶段结论无效 | 显式使相关阶段失效；不能因目标字符串相同而强行 preserve |
| 原工单变成另一组 SQL/资源 | 原批准不覆盖新对象；保留历史，不伪造新批准 |
| 多条无关 Topic 消息与叶子完成同时到达 | 已发生事实落账；只对实际相关的新范围等待验收 |
| 同一 checkpoint 并发提交、连续 50 次巡检 | 相同 ID 复用结果；只产生一次审阅和一次拒绝通知 |
| 报告旧 input/run、伪造 Session、错误 Task | 不推进当前任务；非法来源直接拒绝，合法旧报告只归其历史版本 |
| 计划拒绝、流程过期或尚无计划时报告风险 | 诊断进入协调，不能推进阶段 |
| 审阅完成但落盘/通知之间重启 | 原身份恢复，不凭模型重复生成业务结果 |
| 相同页跨 5 个审阅、随后压缩移出 | 可见期间只读一次；缺失时补齐一次；不得缓存旧权限 |
| 流程正文升级或被停用 | 精确失效旧版本凭据，重新提供适用内容 |
| Provider 连续过载 | 单一重试所有者、有界退避、稳定请求身份；失败可恢复且不无限空转 |
| 原生 tool/result 裁剪替换、fork 历史与恢复目录 | 不计成实际工具重执行；完整配对仍可回放 |
| 活动第 501 条、旧事件重放、叶子换 Session | 最新事件可见、水位正确、原始证据保留 |
| 短状态问答与计划审阅同时到达 | 查询可及时答复；Task 变更和 Outbox 仍统一校验，无双重发送 |
| schema 正确，但报告只有 Pod Ready | 只能报告部署层事实；不能自动宣布业务 E2E 通过 |
| SQL 包缺生产基础迁移 | 准备阶段发现并停止，不直到生产执行才补单 |

### 性能目标与测量方式

以下是拟定验收目标，尚未实测。保持相同模型、相同任务数据规模和依赖条件，至少 30 次简单交互与 10 次长流程合成重放做前后对照；尾延迟样本较少时报告样本数与最大值，不把样本 P95 说成生产 SLA。

| 指标 | 初始验收目标 |
| --- | --- |
| Runtime 接收进展/普通阶段报告 | 本地正常负载 P95 ≤ 1 秒，不含业务核验与模型审阅 |
| 活动/快照读取反映已落盘事实 | ≤ 2 秒，显示事实本身的时间 |
| 简单确认/进度问答 | 非过载条件：收到消息至首个有意义回复 sent，P50 ≤ 15 秒，P95 ≤ 30 秒 |
| 最后一份必要证据到完成通知 | 无新范围、无待审批且 Provider 正常时 ≤ 30 秒 |
| 短问答模型调用数 | 明确关联 1 次；需识别关联最多 2 次 |
| 短问答完整输入预算 | 默认 ≤ 32k tokens，包含协议、上下文和工具说明；超限进入明确的分段/复杂处理，不截掉必需事实 |
| 长流程协调往返成本 | 相同合成流程较基线至少降低 50%；未达标继续定位，不能靠降低验收标准通过 |
| 重复协调事件 | 同一业务身份的并发/网络重试：新增拒绝通知、重复派发、重复业务副作用均为 0 |
| 不变的流程/证据页 | 在同一可见上下文期间只提供一次；版本变化或压缩恢复另计 |

新增接收时间、持久化时间、入队/消费、模型开始/结束、报告接收、审阅完成和 Outbox sent 关联字段。生产统计同时保留过载样本与整体延迟；目标排除过载只是为了分辨可控链路，不能从用户体验报表中删除慢样本。群端显示与真正投递继续独立回读，Outbox sent 不冒充钉钉客户端显示时间。

工具执行次数按 callId 计；使用 DSH 原生 surface 计算活动上下文，不按 JSONL 总行数估算重复。区分业务耗时、模型步骤、协调等待、压缩、人工等待；重叠时间按统一方法处理，不能重复相加。
