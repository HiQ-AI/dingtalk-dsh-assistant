# 群任务确认先于执行

## 现场根因

2026-09-04 21:09—21:17 的同一事项包含回滚要求、确认按新要求处理和 Bytebase MCP 补充。Resident 前三次均生成了任务重开动作及确认/订正回复，但依次因回复替换集合不完整、新 Steer 到达和回复候选快照变化被无副作用拒绝；压缩后的第四次提交保留 `task-reopen`，却把 `reply` 改为空字符串。Runtime 当时允许任务动作携带空回复，因此重开任务并启动叶子，但没有产生 Outbox。

另一个独立缺口位于提交顺序：即使 Decision 带有回复，现有实现也先创建、续接、重开或取消 Task，随后才写 Outbox。因此“有确认”并不等于“确认先于执行”。

## 目标行为

1. 任何包含 `task-proposal`、`new-task`、`task-context`、`task-reopen` 或 `task-cancel` 的 Decision 都必须提交非空群回复；空回复返回结构化 `reply-required`，本批不领取请求、不产生 Task、Outbox 或撤回副作用。
2. 非取消类 Task 动作必须在确认回复可靠写入 Outbox 后才允许创建、续接或重开叶子执行。新任务、目标修订和普通上下文补充使用同一边界。
3. `task-cancel` 保留快速止损：Runtime 在等待回复提交前先向活动叶子发出取消信号，随后可靠写入一句停止确认，再完成持久化取消；不得为了回复顺序恢复“先等 Task 串行队列再停止”的旧问题。
4. Outbox 在动作执行前先保存已有 Task ID；动作完成后补齐本次实际创建或命中的 Task ID，保持回复候选与 Task 的关联元数据完整。
5. 纯回答可以没有 Task 动作；真正无需回复的消息继续使用 `actions: []` 加 `reason`，不能通过“Task 动作 + 空 reply”绕过回复审阅和顺序门禁。

## 失败与恢复边界

- 回复审阅不完整、观察集合 stale 或任务动作缺少回复时，都在任何业务动作前返回结构化结果，Resident 可结合当前请求重新生成。
- Outbox 写入或历史回复撤回失败时，非取消类 Task 不启动；消息沿用现有提交失败隔离，避免自动重放重复动作。
- Outbox 已可靠写入后 Task 动作失败时，群内至少已经收到“已收到/将处理”的确认，Runtime 仍记录提交失败，不把确认冒充任务创建成功。
- 不修改存储 domain 版本；只给 Store 增加按 sourceMessageId 合并 Outbox `taskIds` 的原子更新。

## 验证

- 复现“Task 动作 + 空 reply”，断言返回 `reply-required` 且零副作用；补全回复后同一请求可成功提交。
- 用 Outbox listener 记录提交时快照，证明新建/重开/续接动作在 Outbox 之后发生。
- 维持取消信号在 Task 串行队列释放前触发的现有回归。
- 全量测试、三包打包、安装源码哈希和本地 DSH Web 重启回读。
