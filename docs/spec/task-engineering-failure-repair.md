# 工程失败后的正式修复

## 已确认缺口

工程 Run 在 verify-candidate 或本地验收失败时进入 waiting，但业务阶段仍为 running。Owner 仅看到阶段与成功产物；wait 不触发动作，advance 不修复等待的 Run，replaceSuffix 又不能替换运行阶段。Web context 只更新业务要求。因此“继续修正”没有执行效果。

## 本轮合同

增加显式 repairCurrentStage 决策，只支持当前工程阶段的可修代码/验证失败。Owner 输入展示真实 Run、代际、版本、等待原因、排空状态、失败日志与此前方案；读取失败证据仍由 Host 精确授权。wait 保持无副作用。

Host 必须核对 task active、阶段/run 身份、当前需求版本、run revision/generation、全部节点排空、无输入等待和未知/未完成外部效果。仅修复构建/业务验收明确失败；认证、基础设施、未知清理不能自动转修复。事务中再次执行同样门禁，任何并发变化拒绝。

复用 controller.changeInput 和既有命令回执，在同一 Run 接纳唯一修复输入并产生新代；重复 action 不新增代际。保留旧节点、日志、候选和外部效果。新要求来自 Host 最新任务要求；修复上下文引用当前失败代真实工件，不接受模型提供路径、候选、任意命令或额外授权。

## 失败候选复用边界

失败候选是只读参考而非可交付版本。新代仍从冻结 dev/UAT/taskBase 创建独立目录；允许工程读取工具按固定身份读取上一失败候选以保留有效修改并完成修复，expectedHash 必须以新目录当前文件为准。所有修改、构建、本地验收、清理重新执行，旧通过票据不能交付新候选。禁止把失败工作树伪造为已验证提交。

## 验证

真实控制器：构建失败→Owner 读取失败日志并明确 repair→同 Run 新代→修复实际文件→验证通过。反例覆盖未知外部清理、未排空、旧要求/run revision/generation、跨任务/非工程；验证重复命令幂等与旧失败证据保留。恢复重放必须复用持久接纳回执；报告只有看到真实接纳回执才能称已启动修复。
