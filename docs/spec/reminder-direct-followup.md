# 提醒引用直接进入协调判断

## 问题与目标

2026-10-23 新群实测 19:27:21 的“提前2分钟”带真实原生引用，已命中提醒预载，没有重试和补读，仍经历 Topic 路由模型 10.476 秒与独立协调模型 4.833 秒。到第一请求还有 7.934 秒，本轮不归因或改造这一段。目标是简单提醒后续只经过一次协调模型，复用已有来源归属、版本检查和接纳合同，不直接解释时间或替用户提交。

## 当前合同与最小改动

`residentStore.routeMessages` 已在同一串行事务校验群路由版本、消息版本，按完整原文创建 source unit 并保留 coordination 独占归属。`independentCoordination.recoverGroup` 随后使用原规划、接纳与恢复流程。规划一次只可提交一个提案，不能以一次 schedule-change 同时表达普通新业务。

`reject` 已有完整安全归还：冻结来源、确认无业务命令和未知效果、CAS 增加 generation 并改归 legacy-topic、重新标记消息 pending。原路由可按不同事项拆分整条消息；不能先执行提醒部分再归还剩余部分。

在现有服务增加一个有界入站方法：只有当前群恰好一条未路由纯文本消息，且当前版本没有历史 unit、来源归属或 handoff，才调用既有 `quotedReminderContext`。该方法继续要求原生精确引用唯一已送达通知、同群同设置者、唯一活动纯提醒，设置者与收件人不混用。命中后，重新检查 pending 集合和版本，以 `sourceRefs: [{ wholeMessage: true }]` 通过原 `routeMessages` 原子保留整个原文；仅该入口传 `requireAllPending: true`，在原串行事务内确认全部未路由消息的 ID 和版本恰好等于本次 routes，防止最终重读后新入站或旧消息富化改变待处理集合。既有路由版本与目标版本检查保留，其他路由调用不变，不创建新状态表或第二种提案协议。停用或 frozen 时不进入这条路径。

`kickGroup` 在普通 Topic 调度前调用该方法；新保留成功时先运行现有独立协调恢复。未命中消息和归还消息继续既有路由。已经保留的原文不重新抢占，重启只恢复已有归属。并发导致版本失效时放弃旧候选，交原调度读取新版本；其他错误仍显式报错。

首屏说明来源只是基于精确引用的候选入口，整条消息未经语义拆分。协调模型负责完整判断：单提案可完整表达的提醒修改、查询或新安排按已有合同处理；普通新业务或不能完整表达的混合要求，在任何效果前整条 reject 回原路由。不得只执行提醒片段、丢弃其他要求或误把同人消息当订正。无需新增语义正则、调度器、模型或提案入口。

## 验证

- 原生精确引用的改期省去 Topic 路由请求，首屏一次协调提交，保留 A 设置 B 的收件人和版本。
- 更换收件人、另建单一提醒仍可按需读取目录，不因快速入口被吞掉或强制改原提醒。
- 混合提醒与普通事项先无效果归还，原路由完整拆分后分别处理；归还后同消息版本不会再进入快速入口。
- 多条 pending、附件、未知送达、异人/异群、旧版本、已归属/handoff、disabled/frozen 不直接保留。
- await 期间新消息/版本变化不使用旧快照；重复调用和重启不增加 reservation、不重放已接纳效果。
- 只跑相关测试；真实模型、部署和用户实测分别记录，不将测试耗时当作线上承诺。
