# 任务等待、独立进度与群通知修复方案

## 目标与事实

本方案仅设计，不修改运行中任务或发送群消息。排查对象 task-7e10fc01558bb150f5224affeb5196e4 在 2026-09-21 17:15（北京时间）进入 information waiting；16:43:22 和 17:16:52 的两条询问已通过 DWS 原消息回读确认。问题不是漏投，而是等待状态表达、发起人触达、阶段串行记账及等待后的跟进缺口。

目标：已完成且独立的阶段可登记；确需外部输入时形成可追踪的等待；群内明确知道暂停原因、责任人和恢复条件；通知失败、无回复和新输入分别走正确路径。

## 方案选择

1. 仅修改提示词：不能消除阶段首项门禁，也无法保证通知落盘与恢复，排除。
2. 缺证据就自动完成，或定时重新唤醒叶子：前者虚报完成，后者重复取证、浪费执行轮次，排除。
3. 修改阶段登记、等待审阅和通知恢复契约，复用现有 Task/Outbox/巡检，采用。

## 阶段登记

runtime.js 不再要求 stage-completed 对应 remainingItems[0]；按当前 stagePlan 的 stageId 校验目标存在、版本有效且未完成。每次仍只登记一个阶段，remainingItems 必须精确等于未完成阶段集合，展示顺序保持计划顺序。旧 checkpoint 原样保留。

task-progress.js、task-input-revision.js 和看板统一按当前版本及保留 checkpoint 的 stageId 计算进度，支持依次完成第三项、第二项后再完成第一项。新提交优先使用 stageId；历史无 ID 记录只在当前计划标题唯一时解析，歧义必须重新规划。

阶段事实登记不等于执行授权。计划中有先验审批、部署前验证等必要前置条件时仍须满足；跨序完成通过既有主会话审阅核查独立性，不走自动 acknowledge 快路，不新增通用依赖调度系统。不得把第一阶段未知当成后续阶段均未做。

## 等待审阅

information waiting 的 blockedItems 绑定当前 stageId、原始来源和必要外部输入，并提供已尝试的相关取证入口与失败证据。主会话审阅明确检查：当前 Agent 的原始交付是否确实未完成；是否还有可独立执行的工作；依赖是否只能由参与人补充。

还有可执行工作则 continue，附明确下一步；自身交付已完成、只等他人后续检查则按现有 revise-scope 处理；确有必要依赖才 approve-wait。不得把排查方法升级成用户强制验收项；不能以无默认 Kubernetes context 推导所有服务端取证不可用。语义必要性由审阅负责，Host 校验版本、来源和阶段归属，不声称结构校验能证明自然语言判断。

## 等待通知与可靠落盘

复用完成审阅的 notification draft 模式：approve-wait 同时生成已审阅的通知。Host 在设置 waiting 时，同一次 Task 更新保存稳定 waitId、通知草稿、开始时间、补充人、任务发起人及恢复条件。waitId 绑定 taskId/inputVersion/runSequence/报告指纹；已有 Outbox 继续为投递状态唯一来源，不在 Task 复制 sent 状态。

等待通知由 Host 组合固定状态说明与审阅正文，必须包含任务名、已完成阶段、剩余缺口、所需最小信息、补充人和恢复条件。真实补充人与任务发起人都进入接收集合并去重；仅允许来源群真实参与人，缺失参与人不能猜造 ID。

示例：任务“排查主页 method-select 循环403”已暂停等待补充。已完成调用链与权限门禁核查；仍缺异常会话的持续请求时序。请反馈人提供登录后 60 秒的脱敏 Network 记录。收到后继续核查重复触发来源。@反馈人 @任务发起人。

复用 Outbox 发送及独立回读；发送失败显示为“已等待，通知未送达”，持久告警并按既有投递错误策略处理。Task 等待不阻塞其他任务。重启后凭 waitId 重建缺失 Outbox，不重复审核业务报告；如果 Outbox 已 sent，不补发同一条。

## 等待跟进与恢复

现有巡检增加 information waiting 分支，区分通知未送达、通知已送达但无新信息、已收到相关输入。建议首版固定策略：从独立回读确认送达起 30 分钟无补充，提醒一次；2 小时仍无补充，升级通知任务发起人一次并保留看板待跟进状态。每轮等待最多两次后续通知，不无限催促；提醒不唤醒叶子、不当成任务新输入。

nextFollowUpAt 和跟进意图持久化；每次外部发送前重新核对 waitId、任务版本与状态。若新输入已到、任务恢复/完成/取消、目标修订或等待被替代，旧提醒失效。并发巡检和重启只能生成同一稳定 Outbox 键；已发送旧消息不抹除其审计记录。

相关新消息沿现有 Topic 归属、版本化 task-context 和 steer 路径恢复。只收到“收到/稍后提供”等无实质信息时保留等待；部分信息可支持新工作时恢复相应工作，核对后再决定是否存在新的必要等待，不重复完整历史取证。

## 可见状态

看板显示已核验完成数、未完成项及其中阻塞项；详情显示等待开始时间、等待谁、恢复条件、通知送达/失败时间及后续跟进状态。task-report-notified 明确标注为内部报告处理通知，不能作为群通知证据；不重写历史事件名。

## 当前任务恢复

升级后通过受管通道只处理该任务，保留所有原始证据和历史通知。让叶子基于现有材料提交第二阶段完成 checkpoint；第三阶段仅在审阅确认其交付已满足时登记，不能预设 2/3。循环现象继续标为未验证。

恢复前重新检查是否已有新输入。确认仍需外部资料时建立当前等待关系，并引用或关联已发送的 17:16 通知；仅补一条明确暂停状态的更正通知，不重新发送全部历史询问，不猜账号凭据，不修改 UAT2 数据或权限。历史等待统一不做批量迁移或批量催促；本次定点恢复走任务版本和审阅契约。

## 改动位置与验收

- runtime.js / task-result.js / task-input-revision.js：按阶段身份登记、等待审阅、稳定等待意图及版本恢复。
- topic-runtime.js / store.js：等待审阅通知草稿、合法接收者及持久化字段。
- task-progress.js / 客户端：进度及阻塞投递状态投影。
- 现有 Outbox/DWS bridge：优先复用投递与回读，只补必要的等待关联。
- README / docs/ops：契约、跟进策略、安装预检与恢复步骤。

必须验证：首项受阻但第二项独立完成；重复/过期/歧义阶段拒绝；必要前置条件不得绕过；有可执行工作拒绝整项等待；他人后续检查不阻塞；真实必要输入允许等待；反馈人与发起人同时触达并去重；通知投递失败可见且不虚报 sent；进程在等待落盘/Outbox 落盘/发送回执各边界中断后的幂等恢复；30 分钟和 2 小时虚拟时钟测试；提醒与新输入并发时旧提醒失效；新版本输入保留已核验阶段；两个独立 Task 不受等待影响；真实 DWS 通知独立回读。

存储变更先对生产副本做读写保留测试，不能认为新增可选字段就支持旧二进制回滚；保留快照并验证旧包是否剥离字段。开发与测试使用隔离 worktree；本机切换遵守现有运行任务不被中断的约束。
