# 常驻会话判断上下文预算

## 现场

常驻会话并非停在业务工具上，而是在同一 Turn 中反复压缩。现场 Session 日志显示，单次模型请求输入约 257k tokens；压缩摘要本身约 21 KB，但压缩期间进入的每条群消息又各自插入约 109–202 KB 的 `GROUP_MESSAGE_STEER`。多个超大 next-step 消息持续积压，压缩只能缩减旧历史，无法消除尚未处理的新 Inbox，因此连续压缩仍无法进入判断步骤。

超大信封来自回复去重候选：每条消息都扫描全部有效 Outbox，默认选入 30 条近期回复和 20 条相似回复；每个候选又展开关联 Task 的多条消息。历史越长，单条判断信封越大。现场 280 条有效 Outbox、29 个 Task 生成了 50 个候选，序列化体积约 155 KB。

## 修复

- 回复候选最多 8 条、序列化 JSON 最多 16 KB；每个候选最多保留 4 条真实来源消息和 3 个 Task 摘要。
- 选择顺序优先当前消息或引用链直接关联、当前聚焦 Task，再选近期结构化确认、正文相似项和最近回复。引用 ID 与词面相似度只负责召回，最终同一事项判断仍由 Resident 阅读真实正文后完成。
- 候选的回复、来源正文、引用正文和 Task 目标分别截断到固定长度。预算应用在结构化候选数组边界，不截断当前群消息本身。
- Runtime 恢复既有 Resident 时，清理带旧内存 requestId 的 `GROUP_MESSAGE_STEER`、复核、恢复提醒和 `TASK_COORDINATION` 待处理信封；持久化 Inbox 再生成新 requestId 重放，避免重启后继续消费失效的大信封。

## 验证

1. 用现场只读状态重新构造候选，候选从 50 条、约 155 KB 收敛为不超过 8 条、16 KB。
2. 旧且与当前引用或 Task 直接关联的候选不会被最近窗口挤掉；最近候选仍可供无显式关联时审阅。
3. 大量长回复、长来源消息和长 Task 目标下，候选数量、来源数量、Task 数量及总序列化体积均不越界。
4. Resident 恢复时只移除依赖旧内存请求表的协议信封，普通 Inbox 内容不被清理。
5. 部署重启后，遗留 `steered` 由判断自动恢复机制按群内顺序重新投递，新的判断信封满足预算。
