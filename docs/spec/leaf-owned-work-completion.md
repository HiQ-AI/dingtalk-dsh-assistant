# 叶子按自身职责完成任务

2026-09-20，实施前方案。本轮只分析与落档，不修改运行代码、在线任务或服务。

## 目标与结论

Task 的完成表示当前 Agent 被分配的交付及必要自验证已完成，不表示整条跨人员业务流程结束。消息“你完成 X 后，某人检查一下”中，X 和该 Agent 的必要核验属于当前 Task；某人的后续检查不属于当前 Task 的验收、阶段或等待条件。每个独立事项完成后立即提交结果，由 resident 独立验收并通知，不等待其他事项、通知送达或他人回复。

保留真实前置依赖：没有必要文件无法生成交付、未获批准不能执行受控操作，不得伪称完成。先完成不依赖缺失输入的工作，再具体报告剩余受阻工作。用户明确交给 Agent 的“取得审批后发布”“收集评审意见并修改”仍包含后续执行责任，不能静默截掉；与“完成后让别人看看”区分。

## 修复设计

### 1. 任务创建、计划及范围修订统一职责规则

更新 resident 决策、叶子执行、计划审阅、完成审阅四处协议：先判断当前 Agent 承担的动作，再生成 objective、acceptanceCriteria、stageTasks。原始消息完整保留，不能通过删原文实现范围过滤。

“Agent 填写并核验，甲随后检查”：Task 仅包含填写及自核验。甲的检查保留为 Topic 上下文；仅在需要持续跟踪时使用既有 Topic 状态/openQuestions，不默认产生提醒、轮询或另一个叶子任务。若本 Agent 还被明确交付第二个独立目标，继续使用现有 unit/Topic/new-task 机制单独执行，不合并完成屏障。

计划发现自动生成的目标把他人职责加入当前任务时，通过既有 scope-conflict 检查点交 resident 修订原 Task；已有消息足以判定时内部完成修订，不向用户请求批准，不只给叶子“继续完成”的循环指令。修订必须同步目标、验收、阶段和剩余项；单改提示词或 summary 不够。

### 2. 收回 coordination 作为新等待类型

从新提交 taskResultSchema 和工具 JSON Schema 中移除 coordination；删除 runtime 等待分支、requestReply 专用提示以及 README 中“外部检查后续接 Task”的规则。新报告只使用 completed 或确有必要的 information / human-intervention。

复用 completed 的 summary/evidence/artifacts 表达自身交付、自验证及外部尚未发生的事实，不新增外部审核状态机、follow-up 任务表或无必要的配置开关。Runtime 仍完整向 resident 交付结果，叶子无需取得 parent send_message 权限。

为在线旧叶子的滞留报告返回可操作的 obsolete-kind 拒绝：说明按本 Agent 职责重判结果。不得接收后继续等待，也不得把旧 coordination 报告直接改成 completed；仍须检查当前版本、真实交付、计划及证据。

### 3. 阻止换一个 waitingKind 继续等待他人

只删 coordination 不足以防止模型改报 information 或 human-intervention。给两类新等待报告增加最小结构化 blockedItems：每项包含本 Agent 未完成的 requirement、对应来源 basisMessageIds、必需 dependency、缺少依赖为何无法完成的 reason。information 保留 questions；human-intervention 保留 risk、requestedAction 和现场证据。

Runtime 校验字段、当前来源及版本，但不根据人名、机器人名或“检查”等关键词判断语义。复用持久审阅请求基础设施，增加 waiting 审阅分支，只在真实提交等待报告时调用 resident，避免每个普通阶段多一轮审阅。

审阅有三种明确处置：

1. approve-wait：有明确未完成的本职交付，依赖真实且必要；再进入业务 waiting 并按原机制询问/请求介入。
2. continue：可自行取得输入或仍有可执行工作；返回具体继续方向，不发送人工阻塞通知。
3. revise-scope：只是他人后续动作，或生成目标扩大了职责；走现有版本化 task-context 修订，保留有效证据，让原叶子提交完成结果。

审阅未返回是内部报告待审，不能包装成“请用户协调他人”。复用报告持久化、恢复、幂等和内部重试；基础设施故障如实记录恢复问题，不得伪报完成。审阅结果绑定 inputVersion/runSequence 和来源快照，变更后重新判断，不应用过期结果。审核不替叶子捏造证据或直接判业务完成。

### 4. 完成验收和通知保持独立

resident 只核验当前 Agent 的交付及必要自验证。内部完成审阅保留；它不同于外部同事/机器人后续审核。流程或 Skill 的步骤按角色与原始授权解释，不能借通用“独立审核”规则把他人的工作强加进来，也不能取消本 Agent 本来必须执行的测试、回读或安全审批。

完成审阅拒绝须给出具体未覆盖的本职要求及来源，不得仅以“某人没回复/某机器人未检查”为理由。有误扩范围时先修订目标，不反复拒绝旧目标下的同一份结果。

保留现有顺序：审阅通过 → 原子完成 Task/Goal → 完成通知入 Outbox → 发送/回读。发信失败只影响通知投递状态，不把已完成 Task 改回 waiting。用户明确要求交给甲检查时，由 resident 在同一完成通知里向甲交接；没有该要求不额外发起检查。不得声称外部检查已通过。

后续“收到/检查通过”进入正常 Topic 消息处理，仅更新事实，不自动 reopen。若回复指出具体缺陷、且属于原授权责任，关联原任务并按既有 task-reopen 修正；新增独立范围按新事项授权处理。外部长期无回复不触发原叶子轮询或人工介入。

### 5. 已有任务及历史存储处理

存储读取契约与新报告写入契约区分：历史 coordination 及旧 waiting 报告保持可读、原始记录不改写；不维持旧行为的并行执行分支。重启恢复时，旧活跃 coordination 进入上述职责重审，不能重放过时检查通知。

实施时提供 --check 零副作用审计，输出候选 Task、版本、原始来源、实际完成证据、待删的他人阶段、需保留阶段及待失效协调请求。检查 coordination，也覆盖伪装成 information/human-intervention 的同因等待；检索词只找候选，不能批量按关键词结案。

对核实命中的活动任务经受管 Runtime/task-context 修订，不直接编辑存储 JSON。保留 taskId/runSequence、操作编号及有效阶段证据；新 inputVersion 使旧审阅和通知失效。保留存量已发送事实，取消未发送且已失效的检查请求；不默认撤回真实历史消息。完成报告必须重新经过当前版本验收。

关登已完成任务保持原状态；其他任务仅在同因证据明确时处理。任务修订不得造成已完成写操作重放；证据失效与业务重执行分开。旧报告重复上报、恢复重放和同源后续消息均需幂等。

## 验证与交付

在现有 task-result、runtime、topic-runtime、task-input-revision、task-reports、topic-store 测试中补场景，使用已有 harness。以下是待执行用例，不代表已经通过。

| 场景 | 必须满足的结果 |
| --- | --- |
| “填写核验完成后，让 leobot / 任意同事检查” | 叶子交付完成即 completed，无审批、外部等待或轮询 |
| 同义表达：“提交给甲验收”“甲有空看看”“等乙反馈” | 按执行责任及上下文判断，不依赖固定名字或文案 |
| 工时数据尚未写入或未做自身回读 | 拒绝虚假完成，继续补齐本职工作 |
| 缺必要文件或合法执行授权 | 保留有证据的真实等待；批准范围不扩大 |
| “先由甲批准，然后你发布”/“收集意见并修改” | 后续本职工作仍未完成，不偷换为已完成 |
| 计划误含他人检查阶段 | 内部修订目标/验收/阶段；保留有效证据且不重复写入 |
| 用 information / human-intervention 伪装外部后置等待 | resident 重判职责，不触发人工审批 |
| 他人检查通过、普通回执 | Task 保持 completed，不重复通知或创建任务 |
| 他人指出原交付缺陷 | 在授权范围内关联原 Task 修正，不丢失历史 |
| 同一消息 A、B、C 三个事项 | A 完成即独立进入通知；B/C 不构成 A 的屏障 |
| 通知失败、外部无回复 | 已完成 Task 保持 completed，仅 Outbox 按既有机制恢复 |
| 报告重复、审阅中改目标/取消、重启 | 旧请求不推进状态、不发过期通知、不重复写入 |
| 历史 coordination / waiting 数据 | 可读取；只有核实候选进入修订，其他任务不受影响 |

还需真实模型的隔离多轮语义验证：覆盖名字替换、多人混合指派、上下文补充和相反样例。协议测试使用预设模型输出不能证明自然语言职责判断正确；两类证据分开记录。实际群消息验证必须在授权范围内，使用一次已授权业务结果的投递回读，不制造新的工时写入或重复检查消息。

实施顺序：新分支分析/验收矩阵 → 四处职责规则及报告契约 → waiting 审阅和恢复 → 历史只读审计/受控修订 → 本地测试及隔离模型验证 → PR → 按 ops runbook 部署和现场回读。同步 README 与部署说明；本文件保持实施前快照，结果写入 docs/acceptance/ 对应目录。

部署前核实活动任务；沿用用户“不影响正在执行任务”的约束，不能因为本方案默认重启服务。若当前插件必须重启才能加载，在任务安全收尾后切换；确需中断时单独说明实际影响并取得授权。部署后分开核验已安装代码、Runtime、Task/Goal、通知与实际业务证据。

## 反证与边界

比较三种候选：只改叶子提示词无法纠正目标和阶段，排除；新增非阻塞外部审核状态机成本高且容易继续绑定完成，排除；职责过滤 + 等待审阅 + 现有完成/Topic/Outbox 链路能覆盖源头、错误报告和后续输入，采用。

未收敛点是模型在歧义、多轮和含隐式依赖的原始消息中的判断可靠性，必须通过相反样例验证，不能以 schema 校验或测试条数声称彻底消除误判。结构化门禁能要求依据和保持状态正确，不能证明自然语言结论必然正确。
