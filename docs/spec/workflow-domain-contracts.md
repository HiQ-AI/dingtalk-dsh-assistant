# 工作流领域合同收敛

基线：插件 `d0bb185`；对照 Cortex `1cdb13740`。本方案是实施前快照。

## 目标与范围

保持 Task Owner、顺序 Stage/Node、SQLite 控制账、内容寻址工件及效果账。统一接纳参数，提供领域声明的输入和产物合同、明确阶段交接、逐项验收与正式交付清单、可持久读取的失败恢复责任。不涉及沙箱、网关、真实环境部署或钉钉发送。

## 已确认问题

- Web 重执行允许 32 条验收条件，Owner 初始化最多 16 条；16 条成功，17/32 条被实际 reducer 拒绝。
- 目录、首阶段和后续输入准备分散；部分交接把前序 JSON 当正文材料，缺少显式类型和消费声明。
- 调查产物有证据归属检查，但事实、判断、未解决项和逐项验收交接不足；正式文件有摘要、角色、版本与发送回读，缺少通用业务交付清单。
- 节点已有纠错与效果对账；执行失败诊断缺少统一恢复类别与接手责任。

## 设计

1. 接纳参数共享严格合同和界限，32 条验收条件在入口及 Owner 一致；拒绝空白、超长、非法类型与超限。
2. 在现有领域合同模块提供业务声明注册/验证；具体流程声明入参、材料角色、前置产物和正式产物。首阶段与后续输入使用同一准备入口；框架继续控制身份与版本。
3. 阶段交接使用已有 outputRef、生产 Stage/Run 和需求版本，显式声明产物类型；禁止把未经当前成功阶段核验的引用作为成功依据。
4. 复用现有验收 ID；增加阶段产物与验收关系、证据类型和未完成项。结构/来源检查由代码完成，业务语义仍须 Owner 审阅；不得把非空摘要当业务真实性证明。
5. 正式交付清单从当前成功阶段和文件登记派生；必交项须齐全且匹配需求版本，外发继续使用原独立回读。
6. 失败诊断区分可修正输出、业务验收、缺输入/环境、外部未知及实现错误；持久化恢复动作与责任，不自动放宽重试或重放副作用。

## 版本与验证

- 已冻结 Workflow digest 不得静默换规则；新增合同改变执行语义时发布新版本并保留历史定义。不迁移历史成功结果、不补造证据。
- 定向验收覆盖 16/17/32/33 条入参、材料和产物错型、来源/版本失效、漏交文件、语义证据不足、恢复分类与未知效果、旧定义恢复。
- 每轮结果写入 `docs/acceptance/workflow-domain-contracts/`；完成本地验证和独立审阅后开中文 PR，独立回读状态。不把本地测试等同真实部署或业务 E2E。
