# 群消息批次决策

## 问题

当前 Runtime 为同群每条消息分别等待 5 秒、分别 `steer`、分别请求结构化判断。连续短句、文件、图片和补充说明因此被拆成多次独立解释，可能产生重复回复和相互修正的结论；失败重试提示还要求针对单个 messageId 重新判断，进一步强化了错误的单消息处理单位。

## 目标

- 同群短时间连续消息以批次作为 Agent 投递和业务判断单位。
- 5 秒作为静默聚合窗口：窗口内新增消息会延后本批 flush；一批只 `steer` 一次、结构化判断一次、最多回复一次。
- 每条原始消息仍立即持久化、按 messageId 去重，并分别记录 Agent 投递状态。
- Task 来源证据保留批次全部消息；主来源、提出人和回复引用使用批次最后一条消息。
- 失败重试重新进入当前批次，不向 Agent 注入“单独重做这一条”的特殊判断指令。

## 数据流

`DWS event → 立即持久化/去重 → 同群静默窗口聚合 → 单次 GROUP_MESSAGE_STEER → 串行 coordinator 决策 → 批次统一落地 → 各 messageId 标记 delivered/failed`

## 边界

- 不改变不同群之间的并发。
- 不改变 Resident 主会话向叶子 Task 使用 `steer` 的约束。
- 不把消息批次固化为 Task 类型；是否回答、关联、重开或新建仍由语义决策决定。
- 已经 delivered/skipped 的重复事件不重新进入批次；failed/pending 重试可以与新消息合并。

## 验证

- 两条同群消息在静默窗口内只产生一次 Resident `steer` 和一次 coordinator `followup`。
- 决策 prompt、Task 来源证据和返回结果包含两个 messageId。
- 两条消息都标记 delivered，回复只引用批次最后一条。
- 第一条失败重试与新消息合并时不出现旧的单消息重试提示。
