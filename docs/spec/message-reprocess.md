# 群消息受控重处理

今天的旧消息在澄清或取上下文节点等待，原消息 ID 再次入站只会返回幂等回执。为逐条重处理，新增本机 Web 操作入口；每次只接受一个旧 `runId`。

入口仅允许工作流群、已认证的本机 Web 操作者和尚无业务命令的 `pending`、`waiting` 或 `needs_attention` 消息。账本事务将旧运行和待答请求标为被重处理取代，保留旧节点、通知及发送回执，再为同一来源创建递增版本的新运行。已有业务命令时直接拒绝，避免重复建任务、补充或取消。

新运行重新构建上下文，读取当前群消息与任务历史。批量补处理由调用方按原消息时间串行发起，每条回读状态、命令与发信箱后再进入下一条。旧通知若已送达，仍以原渠道回执和撤回记录为准；新运行是否需要发信由节点决定。

验证包括：无命令等待消息可重处理、旧请求被封存、新版本成为唯一当前来源、已有业务命令拒绝、跨身份拒绝、按时间串行处理及本地渠道回读。

无引用、无明确对象的“先别管它”属于群聊静默消息。工作流在模型拆分前按精确短语收束为 `message_quiet`，不发澄清、不创建任务；已在等待的同一消息可在无业务命令时用相同账本命令封存待答请求。其他表达仍交由正常流程判断，避免把明确的任务暂停请求误丢弃。

对“审核问题是否改完并部署 UAT2”一类群内旧任务查询，I 读取 R 的候选身份卡；若模型误判为无动作，Host 仍按指向助手的明确状态问句执行只读集合查询。本群成员仅可取得同群旧任务的标题、目标摘要、状态和结构化 UAT2 交付标记；详细结果仍限任务所有者。检索返回候选及其已核状态，不把词面匹配当业务归属确认。后续引用消息应承接同一话题和补充线索；重处理的消息历史按原发生时间截断，避免把未来消息塞进此前判断。无业务命令且已静默结束的运行可再次重处理，通常最多五个来源版本；旧版预算缺陷造成第五版 `recovery_exhausted` 且无预算基线时只允许再补一次受控重处理，保留旧版本审计。

渠道补拉带来的旧消息版本低于受控重处理版本时，返回当前来源的重复回执，不再次调用接纳账本；否则固定接纳命令 ID 会与新的上下文字段冲突，使群补拉失败。重处理从原运行保留消息发生时间；旧渠道未提供 `occurredAt` 时以原运行的 `createdAt` 为准，不能把重处理时间当原消息时间。I 节点只接收前四个候选的身份摘要，避免把 R 的长目标卡再次复制导致容量等待。

每个节点成功提交后开启下一节点的有限时间窗口；领取前窗口已过期时明确记录阶段和单元。现场已确认一项直接原因：消息多次重处理共享来源预算计数，但新版本按单次运行的领取上限判断，8 次累计领取撞上本次 7 次上限，R 节点无法领取且预算错误原先被静默吞掉。受控重处理现在保存新版本开始时的预算基线，来源编辑仍保留累计限制；预算耗尽明确进入待处理。候选构建每条消息只读取一次旧群、旧话题和旧任务索引，I 节点记录候选准备耗时。

旧任务状态问句后的数量说明和引用的问题清单属于同一问答链：明确指向助手的状态问句先形成单个只读集合查询，不因背景预算中省略的全部历史消息而阻塞；数量说明记话题事实；引用清单按一项范围补充处理，再查询候选任务状态。Host 将这类关系写入 S/R/I 节点结果，避免模型把清单拆成多个新建指令。旧第六版若只在 S 等待上下文且无业务命令，可再重处理一次以应用确定性查询；第七版不能继续重放。候选包含本群取消、执行中及已完成任务，状态和 UAT2 交付标记都要回读；仅凭标题召回的候选仍不能宣称业务归属已经核实。

若来源消息已经在确定的话题事实中出现，新版本优先沿用该话题并保留其标题与版本，不另建同源话题。部署状态查询先排除明确仅排查且不实施的前置任务；收到逐项问题清单后按各问题与任务目标的交集筛选，仍标注“候选”而不把词面命中冒充实际验收。查询结果要分别呈现业务完成结果和 UAT2 回执缺失。

现场第三条引用说明已到 I 并绑定既有话题，但只读状态命令在结果入账前抛出 `INVALID_ARGUMENT`，记为 `unknown`；具体是哪个旧任务字段触发，尚需重试读回确认。结果投影将可选字段显式规范为 `null`；仅 `status/result`、仅该错误、无回执且未重试的只读命令可由恢复扫描再领取一次。若运行已因旧恢复窗口进入 `recovery_exhausted`，同一事务恢复为待处理并给一次短窗口；创建、修改、取消等命令绝不走此路径，二次失败保留 `unknown` 供对账。

真实渠道状态查询已返回 `SUCCESS` 和两个消息 ID，原先工作流仍把通知停在 ACK，是因为消息详情把换行折叠为空格，导致正文逐字比较失败。回读现在只归一化空白后比较完整文字，同时核对消息 ID 和会话 ID；非空白差异仍不认作送达。已发的两条宽泛候选回复经渠道撤回，后续更正须经插件发信箱及独立回读。

群职责要求回复原消息，工作流通知已有来源消息 ID 和发送人 ID，因此发送时走钉钉引用回复；仅缺来源时使用普通群消息。引用详情可能包含引用文字，只有完整回复正文经空白归一化后仍作为连续片段出现，且正文至少 24 字，才可认作已送达。确认消息身份仍依赖发送状态中的真实消息 ID 与会话 ID。
