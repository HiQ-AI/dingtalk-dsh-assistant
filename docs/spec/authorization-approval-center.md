# 授权审批中心方案

## 目标

将受控操作授权提升为 Runtime 的统一领域事实。叶子只创建授权申请；Web 看板与钉钉本人私聊是两个平级批复入口；钉钉桥接是上层通知适配器，不拥有审批状态。

## 状态模型

- 申请状态：`pending -> approved | rejected`，终态不可被第二个通道覆盖。
- 钉钉投递状态：`pending-send -> waiting-reply -> recalled`，仅描述通知载体，不决定授权结果。
- `blockerCategory + 规范化 requestedAction` 形成范围指纹；同一 Task、同一范围只存在一个有效申请。
- 批复记录保存来源（`web` 或 `dingtalk`）、时间、意见和钉钉引用消息标识；Task、Goal 和授权申请在同一 Runtime 串行事务中推进。

## 两条闭环

1. 叶子提交受控操作阻塞，Runtime 原子创建申请并展示到“授权审批”。钉钉桥接发现待发送申请后，发送本人私聊并等待引用回复；独立的个人 IM 实时订阅按被引用的申请 `messageId` 精确关联回复，通过统一审批命令落盘并恢复原 Task。历史查询只负责进程离线窗口恢复，不能作为实时回复唯一入口。
2. 真人在 Web 直接批准或拒绝，调用同一个统一审批命令。Runtime 先写入终态，将决定和批复原文送入叶子会话，再恢复原 Task 的 Goal；叶子必须结合批复内容核验当前事实后决定下一步。钉钉桥接随后停止轮询。若消息已经发送，则撤回该消息并记录撤回结果。

## 竞态与幂等

- 每次 DWS 搜索、发送、记录投递、读取回复前后都回读申请当前状态。
- Web 与钉钉同时批复时，首个终态获胜；相同决定重复提交返回原记录，不同决定返回冲突。
- Web 在 DWS 发送过程中批复时，发送可能无法取消；发送完成后立即回读状态并撤回真实消息。
- Goal 自动续跑与真人批复并发时，批复原文必须先进入叶子会话队列，之后才能恢复 Goal，避免续跑轮次基于旧现场再次提交阻塞。
- Runtime 重启后从持久 Task 审批历史恢复申请；不会依赖内存等待进程。
- 群消息 listener 与个人审批回复 listener 独立运行；任一已配置实时入口未 `ready` 时，DWS bridge 健康状态不得报告正常。

## HTTP 与页面

- `GET /state/authorizations`：读取全部授权申请及关联 Task/群信息。
- `POST /authorizations/:requestId/decision`：提交 `{ decision, comment }`，来源固定为 Web。
- Header 在“任务看板”右侧增加“授权审批”。页面按待审批、已批准、已拒绝展示列表；待审批项提供批准、拒绝和意见输入。

## 验收

- 新申请立即出现在 Web；Web 批复恢复同一 Task。
- 钉钉引用批复与 Web 使用同一状态机。
- Web 先批复时不再发送；发送竞态发生时撤回已发消息并停止轮询。
- 重复提交、重复批复、双通道竞态均不产生第二张申请或覆盖首个终态。
