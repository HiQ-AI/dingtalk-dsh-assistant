# 同话题续接与名称摘要演进

2026-10-08，用户在澄清修复实施中补充：当天“来个任务，边做边修插件→数据集导入导出规则文档→点名→按文档开发”四条属于同一交办话题，名称和摘要应随新信息更新。

## 当前证据与目标

当前协调器已支持已有 topic candidate 及同批 source 引用，不缺第二套聚类机制。`message-coordinator.js` 构造话题时优先旧 title；`message-topics.js` 仅创建对象时使用 title，后续不更新。持久 JSON、服务候选及界面没有当前话题摘要合同。因此仅改提示词无法让名称更新落地。

可验证目标：同一交办链复用话题身份，最新名称/摘要反映累计有效信息；保留每条原文、作者、来源版本；同话题不等于同授权，不按同群或相邻时间自动合并无关事项。

## 最小实现

1. 在现有协调 unit 增加可选 `topicPresentation:{title,summary}`，title 最多 80 字符、summary 最多 1200 字符。只在初次命名或实质信息变化时提交，省略表示展示不变。名称表达累计事项，摘要写当前目标、材料和明确约束，不把消息接纳写成业务完成，不臆造文档正文。
2. 每次协调提交内，同一 topic 最多一个展示更新。Host 根据已核验 binding 解析目标，沿原 topicVersions 与来源版本门禁，不按提交顺序选择最后一条。
3. 当前 `coordinator.commit` 事务将 `topicPresentation` 透传到 `message.topic.upsert`；reducer 仅在显式字段存在时更新 title、summary。真实变化递增 contextRevision，不额外递增 inputRevision；不另建表、后台总结任务或 Task。
4. 话题候选、当前上下文、列表/详情和 Observer 使用同一持久 title/summary；旧记录摘要缺失保持为空。当前正常刷新即可读取新值。
5. 提示词明确：请求提供任务、随后给材料、点名和明确开发可以逐步补足同一事项；工作方式说明保留为事实。无关事项仍拆分，作者权限逐条核验。

## 历史现场边界

先只读核对四条真实绑定、Task、命令、请求、来源版本。隔离回放证明应有归属后，仅使用可审计的原生事务修正确定的关联及展示，不重放业务命令、发信或替原业务任务开发。若当前正式入口无法安全修复历史关联，则先补足有明确版本及零业务副作用证明的受管入口，不直接改 SQLite，不靠改标题冒充合并。

## 验证

- 四条分批与同批接收：一个话题，描述从笼统交办演进为数据集过程导入导出开发；准入允许时仅一个 Task，否则保留准确授权状态。
- 同群交错不同事项、跨作者同话题：无错误合并或权限继承。
- 同批重复展示更新、旧话题版本、旧来源版本、跨群候选：整批拒绝，零部分写入。
- 名称摘要更新与重启读取：Task 身份/需求版本/生产审批不因展示更新变化。
- 列表、详情、窄屏及筛选通过浏览器验证；部署独立读回包、进程、接口与四条归属。

不扩大到任意历史自动合并、通用话题管理或生产业务执行。当前 DWS 旧登录态无法刷新是独立运行阻碍，需要原账号重新授权，不能用本地回放证明消息通道恢复。
