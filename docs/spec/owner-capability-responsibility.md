# 执行会话自主解决能力缺口

## 目标和范围

用户明确要求：原 Task 的持久执行会话是唯一负责人，必须自己解决验证和执行问题，不能由本次 Codex 会话代做业务，再给它喂成功证据。验收以原 Task 自己发起、执行、纠正、核验和交付为准。已由维护会话完成的 UAT 测试不作为本目标通过证据。

## 当前证据

- `task-owner-session.js` 的任务提示声明唯一责任人，但 `tools.restrict` 与 guard 只允许 Host 注入查询/控制工具及提交、读材料。
- 同文件明确指示未提供工具时使用 capability 等待；原任务两次据此 block，且没有操作阶段。
- `workflow-service.js` 的 capabilityCatalog 只暴露 file.write；普通调查可直接查询，但通用业务验证并无已确认执行入口。
- 页面观察实现固定返回 businessFlowReproduced=false，只覆盖侧栏，不具备所问业务验证。重放同样查询不能补足该缺口。

## 候选和反证

1. 仅改提示词或禁止 block：不能创造真实工具；会造成无进展重试，排除。
2. 维护方逐次添加特定场景回执：能够回答单次业务，但责任实际落在维护方，违反用户本次明确要求，排除。
3. 复用已有原生执行/受管操作能力，令持久执行会话能自主组织任务范围内的工具执行、纠错和核验：优先深入核对现有实现后选择最小路径；仍保留任务控制、来源、权限、未知效果和验收约束。

待确定：现有工作流/原生工具能否直接复用、如何证明执行归属、哪些外部动作已经授权。不得先写无依据的通用放权或专用业务脚本。

## 深入核对

原生标准预设已挂载 PowerShell、文件、搜索、技能工具，Owner 的 restrict/guard 将其屏蔽。原生 shell 沙箱不保证网络只读，不能把解除屏蔽描述成只读能力升级，也不能声称它自动获得受管效果的去重和资源锁。

现有 `task_execution_control` 可控制已有固定流程，`task_prepare_workflow` 仅准备失败后的 UAT 重建；它们都不是缺失的一般验证执行器。通用工作流目前仅支持 file.write，不能直接作为任意业务验证入口。

用户已明确确认：“允许原生工具，执行会话自主完成”。在当前任务授权内开放实际已挂载的原生标准工具；保留宿主沙箱及审批。生产变更、发布和消息发送仍遵守既有受管入口，不把增加某一个业务接口当成解决唯一负责人问题。

无论采用哪一路，实际执行必须记录原 Task、需求版本、会话、工具调用身份及原始结果；失败回到原会话纠正，取消/未知响应不得冒充业务失败并自动重放。工具退出码与业务断言是两层证据，维护者生成的结果不能充当会话自主执行的验收。

## 不变量

保持原 Task 与执行会话；不手改控制账、不伪造用户授权、不把维护者代做结果当执行会话的交付；未知外部效果不得重放。保留现有未提交文件。实际业务暂停/缺少授权仍应准确等待，能力缺口必须由执行会话在真实可用路径内推进。
