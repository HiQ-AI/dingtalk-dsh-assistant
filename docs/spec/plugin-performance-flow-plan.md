# 插件性能与协调流程优化实施方案

日期：2026-09-21。性质：分析后的实施设计，尚未执行新增代码修改或部署。依据为 [当日审计](../acceptance/daily-performance-20260921/audit.md) 和本机已安装代码。实现时须从当前已合并版本建立隔离工作区，不能直接修改 node_modules；文内安装路径仅用于确认行为。

## 目标与设计选择

优先降低“有效业务推进所需的模型调用和重复输入”，保留授权、事项归属、证据审查和发送回读。将工作拆为三个可独立验收的批次：止损与计量、缩减输入与协议返工、协调上下文隔离。每批独立测量，不将假设收益写成已实现结果。

三个候选的取舍：

1. 提高压缩阈值或任务并发：不采用。当前 Task queued 只有数秒级，提高阈值会让调用继续携带更大上下文，未击中主要原因。
2. 保留长期主会话，只缩短信封：先做，改动集中、可回放；但压缩后仍有 128k—189k 请求 token，不能保证仅靠此达到目标。
3. 协调请求使用独立上下文，业务状态继续保存在 Host：作为第三批目标设计。对长期上下文有直接作用，但需要验证上下文完整性、冷缓存成本、工具身份和重启恢复，不能一次性全量切换后再补验证。

## 第一批：验证故障止损，补齐恢复闭环与指标

### 1. 确定性故障不再进入叶子改稿循环

现状已安装：`task-reports.js:3,67` 对预算类错误分类为 failed；`runtime.js:1725–1742` 暂停 Goal 并转为 system waiting；`task-reports.js` 的 submit 已拒绝在 system waiting 时再次提交。此次先验这条路径，不重复实现。

需要落实的恢复规则：

- 持久故障身份沿用 `(taskId, runSequence, inputVersion, operation, errorCode)`，不同 submissionId、进程重启或 Session 重建均不解除故障。
- 确定性预算/序列化错误没有定时 LLM 重试；出现修复后的显式恢复请求时，先只读构造原始上下文，校验预算、版本与授权。探测不启动叶子、不执行 Task 业务工具。
- 探测成功复用现有 report retry，处理原 submissionId；若版本过期，将其归档为历史并仅处理当前有效输入。禁止为了恢复重新执行已经完成的写入。
- 传输类失败沿用 DSH 模型重试和现有协调器有限重试，不在外层再叠一套指数退避。参数错误返回一次完整修正信息；业务证据被驳回才允许新事实驱动的报告修订。
- 故障通知复用 `coordinateSystemWait` 和稳定 Outbox 身份，通知失败仍保持系统等待；不能调用出错的审阅模型生成这条故障通知。

改动位置：`packages/dingtalk-dsh-assistant/task-reports.js`、`runtime.js`；恢复入口复用现有 `retryTaskReport`。优先补测试，只有不满足上述规则的部分才改代码。

验收：同错误触发100次，只形成一次故障状态转换和一次初始通知；叶子不继续模型调用、不重建；重启仍等待；其它任务正常运行；修复探测不写业务；恢复推进原报告一次；授权撤销和旧版本反例必须被阻断。

### 2. 性能指标随每批实现一同落地

复用现有事件、活动聚合和 `/state/task-timings`，不新建遥测服务。以 messageId/requestId/taskId/submissionId 串联：入站、协调入箱、模型步骤开始、首流事件、完整响应、工具调用/结果、报告接收/终态、Outbox发送/回读。请求级样本可写本地验收产物；长期聚合扩展现有存储，若涉及 schema 必须按项目迁移契约处理，不能直接改历史文件。

必须区分：排队、模型步骤（含重试）、工具、审阅等待、系统等待、人工等待。统计并行时间用区间并集；同时展示资源累计时间，不能混用。TokenUsage 合并未缓存、缓存读、缓存写，同时保留分项及缺失数；fork seed、投影 replace 不计为新调用。

把“首次实质回复”与回执分开，不靠提前发“收到”改善指标。当前26条可关联回复需人工标注实质回复后才能建立此新指标基线。

## 第二批：缩减输入，减少结构返工

### 3. 路由输入改为紧凑目录，详细历史按需取

当前 `topic-runtime.js:473` 每次从所有 Topic 的索引中按上限选取，summary 每项最多240字符。今日路由信封中位31.8KB。

具体投影：

- 首包保留当前消息完整有效正文、版本、发送者、引用身份、附件引用；正文太大沿用原分页，禁止截掉未处理部分却标已读。
- Topic目录首包只带 `topicId/title/status/revision`，不为每项重复附240字符摘要。被当前消息引用命中的 Topic，以及当前关联任务的 Topic，带短摘要；其它摘要通过现有 `group_topic_context_get` 读取。
- 引用命中先按 message/unit→Topic 现有关系精确定位；一个消息有多个事项时保留全部关系，不能只选一个“最相关”事项。
- 目录超预算保留 `total/hasMore/nextOffset`，通过现有 `group_topic_list` 分页。未能确定旧事项归属时必须补查，不能因为首包没有候选就直接建新 Topic。
- 不新增向量库或基于置信度的自动授权，也不把闭合 Topic 从可检索历史中删除。

变更：复用 `topicIndex` 的既有调用位置，针对路由建立更小的投影；保持其它需要摘要的消费者原契约。预算作为模块常量，先以路由首包P50≤12KB、P95≤24KB为实验目标；超大原文按需分页，不设丢弃上限。

验收：回放81条消息并为归属/多事项建立人工期望，包含引用旧 Topic、同名业务对象、图片、跨页正文和“新事项无候选”。比较完整路由结果，而非只比较传输体积；不得新增误建、合并或漏路由。

### 4. 决策和审查复用当前可见材料，避免再造缓存

当前 `createDecisionRequest` 已使用 deltaMessages；`coordination-context.js` 已基于 surface 验证流程和 section 正文可见。因此不再新建“读过即缓存”的机制。

实施内容：

- 对 `requestId + section + contentFingerprint` 统一生成一次序列化文本，在当前请求中复用；同一材料在目标、事实快照、value、sourceMessages中的完全重复部分改为带明确引用的单份正文。
- 审阅请求首包携带本次报告、新增证据、当前目标/授权、相关阶段和适用流程；历史检查点用身份、结论和证据定位表示，需复核才读原文。
- 对已有 `visiblePromptRefs/inlineCurrentSection` 补分支覆盖：同版本、同内容且确实在当前 surface 才复用；压缩移除正文、版本变化、授权变化必须重新读取。
- 不把与授权有关的约束变成不验证的摘要。完整证据可以分段取，不强制全部放入首包。

变更：`topic-runtime.js` 的 `createDecisionRequest/requestReview`、`coordination-context.js`。验收：重复section只出现一次；压缩后失效；更新版本不误用旧批准；回放中审查信封P95从约30KB起做下降30%的目标。此处预算针对审查信封，不能混用Topic决策约60KB的P95。

### 5. 结构提交一次校验、一次反馈

保留同一提交工具，不增加模型每次必调的“预检工具”，避免为减少往返反而固定增加一步。

纯校验阶段先收集 schema、引用、归属、流程和版本问题，验证完成之前不更新路由、不预约 Task、不写 Outbox。返回结构化 issues：`field/code/message/合法候选或定位信息`。业务动作仍使用现有原子校验与提交。

例：`contextRefs.quote` 在当前消息出现两次时，返回该字段的两个匹配位置，说明它必须来自当前消息而非 quotedMessage；模型只重提相关 unit。不能由 Host 猜一个位置修正，也不能把引用正文混为原消息正文。

版本过期返回当前版本、失效的引用及需重新读取部分；仅同一请求且语义/授权仍有效时重提。授权变化使依赖旧授权的动作整体失效。取消/变更授权的入站消息处理优先级不能为了降低 stale 而下降。

变更：`topic-model.js` / 实际引用验证函数、`decision.js`、`topic-runtime.js` 的工具提交入口和 `tool-schema.js`。先定位真实校验函数后精确编辑，不另造规则副本。返回增强默认不更改已有必需参数。

验收：今日 ambiguity、uncovered text、invalid arguments、reply replacement 和 stale 场景，错误无副作用、一次返回全部可判定问题；同时保留多事项唯一effectOwner及未授权反例。参数返工调用量目标下降50%，不以“返回accepted更多”单独判断正确。

### 6. 给叶子准确的工作位置，复现并修正检索瓶颈

现状：任务资料中已有 goal/worktree/验收证据时，新会话仍可能在 `D:\baibu-agent` 从根目录重新 glob。34/67次glob超时。

派发和重开时，从已有任务工件及handoff记录传递已验证的 goal 文件、对应仓库worktree、验收目录和证据入口。直接复用现有context/artifacts字段，不先新增一套“工作区注册表”。拿不到准确路径必须标未知，不能猜路径。

验证工具本身时使用原始34条参数：测原调用、将固定路径前缀变成真实搜索根的同工具调用、原生rg限定相同目录的结果。核对隐藏文件、忽略规则和访问边界，不能只比较快慢。若固定前缀仍引起全根遍历，修复拥有glob实现的DSH工具包，不在插件里堆超时重试。

目标：相同结果集下glob超时率低于5%；已知工作区路径不再次触发全根查找。需修改独立DSH工具包时单独交付，不能把插件改动冒充工具修复。

## 第三批：协调请求使用有边界的模型上下文

### 7. 每个协调请求建立自己的上下文，Host继续持有唯一业务状态

当前 `topic-runtime.js:303` 的send使用 `getAgent(groupId)`，路由/决策/审阅都积累在群主会话。目标改为按已有requestId创建并复用协调Agent；一次请求内可有多步工具调用，有限协议提醒也复用此Agent。不是每一步创建新Agent。

| 角色 | 上下文输入 | 工具范围 | 结束条件 |
|---|---|---|---|
| Route | 当前批消息、引用链、紧凑Topic目录 | Topic/消息/附件读取，route submit | 路由提交完成或请求失效 |
| Decision | 固定Topic版本、增量unit、当前目标及授权、相关Task状态 | 相关上下文读取，decision submit | 当前增量被接纳或版本失效 |
| Review | 待审报告、目标及授权、阶段、适用流程、证据及回复候选 | 审查必要读取，review submit | 审查终态或当前版本失效 |

这些是运行期角色，不新增业务Task。群对外身份不变；Group/Topic/Task/授权/Outbox继续由Host原子提交。角色保留全部适用强制规则；工具按职责开放，不允许路由和审阅会话通过工程写工具代替叶子执行任务。

需要修改的依赖点：

1. `runtime.js` 管理requestId→协调Agent句柄、角色配置与模型设置；`topic-runtime.js` send/monitor/read校验获取请求的Agent。
2. `refreshVisibleReads/inlineCurrentSection`、工具调用者校验从群Agent改为绑定的request Agent，严格检查groupId、requestId、角色和当前版本；旧Agent不得操作新请求。
3. 请求完成后释放运行句柄，保留原生Session日志和父子/请求关系用于审计；不删除历史日志。
4. 重启按持久化coordinationRequests恢复pending请求。已提交的业务动作由现有幂等身份回读，不重新执行；未持久接纳的模型草稿可以重算。
5. 第一版保持当前并发额度和提交串行化，先验证上下文隔离的收益。需要拆分路由/审阅排队时另做公平调度实验；取消及授权撤销必须优先，已入站但尚未归属的消息不能被忽略。

这项不能只按prompt工程交付：它改变会话身份与可见性，必须测试伪造requestId、跨群、跨角色、压缩失效、重启、同时取消和审阅提交。

冷上下文会降低跨请求缓存复用。验收同时比较总输入、未缓存输入、缓存输入、首事件和完成时延；只有总token下降而未缓存成本显著上升时，不能宣称更省费用。在取得账单前不作金额承诺。

采用原81条消息及6个Task的离线只读回放，比较“第二批完成后的长期主会话”与“请求隔离”两种实现。人工预期结果为准，旧结果只能作差异线索。建议目标：协调上下文P50≤80k、P95≤120k；协调输入总量下降40%；不新增漏事项、错误授权或重复动作。达到后再发布切换，替换旧路径，不长期维护两套协调逻辑。

## 交付批次与最终验收

| 批次 | 交付内容 | 通过后才进行 |
|---|---|---|
| A | 已安装止损路径的故障注入、必要恢复补齐、正确指标 | 用新数据确认同错空转停止 |
| B | 紧凑路由目录、材料单份引用、结构校验全量反馈、准确工作目录 | 每项固定样本回放及结果正确性核对 |
| C | 请求级协调会话、身份与恢复、冷缓存对照 | 受控发布并观察新的真实流量 |

代码实施时按每批风险使用feature worktree/PR，单独维护用例×轮次证据；本地只读回放不能执行真实群发、审批、部署或数据库写入。发布后使用新的真实输入验证，不批量重放历史动作。PR/测试通过、安装成功和真实运行指标分别记录。

最终指标建议：消除同错自动空转；结构返工下降50%；协调上下文P50≤80k；现有精确关联回复口径的中位≤90秒、P95≤5分钟。实质回复另建标注基线。所有阈值为试验验收目标，不是提前承诺；样本过小、调用usage缺失或业务复杂度变化时必须单列，不能混在前后百分比中。

不纳入本次优先批次：换模型、提高并发、增大超时、向量数据库、新遥测平台、全面取消审阅。它们不是禁止事项，但当前证据不足以给出比上述改动更高的收益优先级。
