# 任务 Owner 与专业流程职责收口方案

日期：2026-09-25。源码基线：`4d720cfbe67a83ac2a6dce147bcaeb94461de8ba`，分支 `worktree-task-owner-runtime`。

状态：待实施的具体方案。本文件新增设计及验收要求，不表示下述调整已上线。上一版 `task-owner-session-orchestration.md` 保留原设计快照；本文针对现有 Owner 实现后的实际缺口，明确专业流程的删减、入口调整和交接合同。复用原验收目录及唯一 goal，不另建执行引擎或第二套任务账。

## 1. 目标和取舍

目标：同一个 Task 由一个 Owner 维护目标、计划、专业流程和通用能力的组合、变化影响以及对外报告；流程只完成明确的局部工作。用户提出“先排查，确认方案后实现，再部署 UAT”时，不需要自己拼流程或重新发起任务。

| 候选 | 结论 |
| --- | --- |
| 保留意图层完整计划，再让 Owner 监督 | 不采用。存在两份规划责任，Owner 只能监督预设步骤，无法按执行证据独立调整 |
| 所有固定流程拆成工具调用交给 Owner | 不采用。发布、SQL 变更已有的顺序、审批、回读和恢复约束会重新落到模型判断上 |
| Owner 动态组合有明确输入输出的专业流程及单步能力 | 采用。业务顺序由 Owner 决定，流程内部确定性规则及 Host 控制保留 |

本期同 Task 串行执行步骤，不建设任意 DAG。专业流程内部的确定性代码检查、执行和独立回读不因“节点多”被删减。只有重复承担任务规划、跨流程协调、完成判定或群消息汇报的职责需要移走。

反证：把复杂方案设计全部放到 Owner 会扩大其上下文并降低专业深度，因此专业 Agent 保留；把技术检查全部交给 Owner 会失去独立证据，因此 Host 验证保留。Owner 误判仍可能发生，下面通过精确权限、版本比较和实际结果核验限制影响。

## 3. 流程删减与最终目录

| 现有入口 | 处理 | 调整后的责任及结果 |
| --- | --- | --- |
| 材料分析 task-analysis | 退出新任务顶级选择，保留专业分析能力及历史定义 | 小规模纯分析由 Owner 完成；复杂材料可委托专业 Agent，返回分析产物 |
| 问题排查 task-investigation | 保留专业分析步骤，补充前后读取能力组合 | Owner 收集证据→专业分析→必要的追加读取/验证；分析结论必须区分已确认、假设、未知 |
| 方案设计 task-planning | 保留 | 输出范围、设计、影响、实施和验收；确认后做什么由 Owner 管理，专业节点不自行启动开发 |
| 代码开发 task-engineering | 保留实现、验证、Git/PR 的受控顺序 | 接受阶段目标、需求及方案产物；输出精确提交、PR 和测试证据，终点为代码交付，不自动发布 |
| PR 评审 task-pr-review | 保留为按需专业步骤 | 输入精确 base/head、diff 和检查证据；缺少远端回读只称材料评审，不声称合并/检查成功 |
| 数据口径审查 task-data-query | 调整展示名称及目录说明 | 现有定义仍是数据口径/结果审查，实际数据库查询用已授权的只读能力；不得把名称当工具能力 |
| 复盘 task-retrospective | 保留为按需专业步骤 | 输出复盘产物，不直接修改规则或知识库 |
| 通用任务 task-general | 删除新任务执行分支，旧定义仅供明确引用的历史恢复 | Owner 可直接执行简单纯文本工作或选择受信能力，不再另建规划/报告 Agent |
| task-general-intake | 退出新任务主路径 | 目标与授权冻结并入 Task 接纳事务；不能用一个伪业务 Run 表示任务存在 |
| task-general-capability | 保留单代码 Run 执行载体并去掉 general 首阶段限制 | 供排查、开发、整理等任意授权 Task 使用；不增加规划会话 |
| UAT 部署 | 保留独立流程 | 精确 UAT 分支提交→构建→镜像/运行版本/入口回读；输出部署结果 |
| UAT 同提交重建 | 保留为受条件约束的独立恢复流程 | 核对失败构建、同 SHA、无更新版本/等价运行构建，重建并回读；不得成为通用重试按钮 |
| 生产发布 | 保留固定流程及真人审批 | 先核验精确来源和 main 合并状态，冻结发布对象，审批后执行生产动作并回读 |
| 数据变更 | 保留固定流程及真人审批 | 本地 UAT 审查/事务回滚演练→Bytebase 工单回读→Assistant 真人审批→生产执行与回读 |

`prepare`、`validate-result`、`verify-candidate`、`prepare-commit`、`finalize` 等按实际职责保留。例：工程 finalize 核验 PR 的代码应保留，其产物叫“工程交付已核验”；Owner 再决定整个目标是否完成。专业节点内部对局部实现的思考不属于需要删除的任务级规划。

用户可见目录区分业务能力说明和执行状态；内部 intake/capability Run 不作为需要用户选择的流程。历史 ID 可保留用于记录，不以重命名触发无必要的数据重写。

## 4. 消息只交接意图，Owner 独占计划

保留现有同收信范围归类屏障、每 Topic 独立 I、I 提交和派发时的来源版本检查。只调整 I 后面的 Task 接口。

I 输出 `intent`、明确的 `taskId` 或新建目标、来源及版本、目标变化、约束、用户明示的验收要求、用户明示的阶段要求和目标资源线索。用户说“先给方案，确认后实现”时记录该原文及阶段约束；I 不生成可执行 workflowPlan、Run 或工具参数，不把模型补全的计划当用户授权。

接纳事务原子完成来源去重、权限核验、任务要求快照、Task/Owner 初始化及 `intent.received` 事件。返回“已接纳”只证明此事实，不能声称流程已经执行。已有任务的补充仅更新要求/事件及必要输入屏障。

Owner 读取当前要求、验收项、实际可用流程和能力、已核验产物、未处理事件，提出结构化计划。Host 决定能否接纳及执行。首次业务 Run 必须发生在初始 Owner 计划接纳之后。

准确的暂停、取消、审批答复仍由 Host 控制通路立即落账，不等待 Owner 推理。后续事件告诉 Owner 已发生的控制事实；自然语言歧义不通过关键词直接执行。

## 5. Task 与计划的最小持久化调整

当前存储强制 Task 至少有一个阶段，并以首阶段输入代替任务目标，需明确变更，而不是再增加通用 intake 占位流程。

建议本次 schema v4：在现有 Task/Owner 表中增加当前 `requirementRef` 及计划是否建立的标志；任务要求作为内容地址产物保存，包括 objective、constraints、acceptanceItems、sourceVersions 和授权引用。`requirementRevision` 随要求改变；`planRevision` 随计划改变，两者不再因普通能力追加而同时递增。控制和授权各用自己的版本。

允许“Task 已接纳、Owner 待规划、阶段数为 0”，此时不得由空数组 all-success 判定成功。计划用 pending/active/waiting/settled 表示推进情况，任务目标状态以 Owner 的验收结论为准。计划结算完成后 Owner 仍可补步骤，页面不能短暂显示“任务已完成”后又回到执行中。复用现有 Owner 状态，不再平行引入一个任意状态引擎。

Owner 提交合同增加 `planChange`：

- `initialize`：首次计划，附阶段局部目标、执行定义类型、输入产物引用及门禁。
- `append`：追加目标需要的阶段，不影响当前执行。
- `replaceSuffix`：明确 affectedFrom、修改原因、保留产物引用及受影响的验收项，替换未开始的后缀。

每次提交绑定 requirement/plan/control/authorization/inputFence 版本、事件水位和 Owner 租约。Host 校验阶段范围、能力授权、产物归属、审批需求后事务接纳；幂等身份由已接纳 turn/step 派生，重试沿用原身份，不由模型另选 ID。

正在运行的步骤受新要求影响时先持久阻断后继和新副作用，等待旧执行排空/未知效果对账，再应用替换。已发生的效果保留原事实。只修改报告语言不改变业务计划或要求已完成的流程重跑。

Owner 不必每个节点成功都推理：Host 推进专业流程内部固定节点；阶段结束、需要决策的失败、新要求、确认/审批结果和用户进展请求才唤醒 Owner。无状态变化的轮询不产生模型调用或报告。

去掉当前 general 分支的四步固定限制，统一使用 Host 配置的任务规划轮次、累计执行和无进展次数预算；预算跨重启保留，普通追加消息不自动清零。相同目标版本、能力、输入和作用域的重复提案拒绝；前次结果 unknown 时先对账，结果确定失败后的重试由既有流程恢复合同控制。

## 6. 按产物交接，取消紧邻阶段假设

复用现有内容地址工件，为每个阶段结果提供统一索引：taskId、stepId、runId、requirementRevision、定义身份、局部结果、artifactRefs、verificationRefs、limitations。具体产物正文仍沿用各流程 schema，不把所有业务结果塞成任意 JSON。

首批产物类型：调查证据、调查结论、方案、已确认方案、代码交付、已合并 UAT 来源、UAT 部署结果、SQL 变更包、数据变更结果。

每个流程在既有受信目录中声明接受的产物类型及输出类型；现有输入适配代码按 workflow kind 明确分派。Owner 只能引用本任务授权范围内的工件，由 Host 验证生产者、摘要、来源版本和需求适用性；模型自称 type/verified 不构成证明。

删除“取最近消息 objective”“只取紧邻前一步输出”“动态 workflowId 前缀等于工程”的推断。一个步骤可显式读取前面多个产物。例如开发读取当前要求、调查结论及确认方案；UAT 读取已合并 UAT 来源，即使两者之间插入了 PR 评审也能继续。

跨库或多服务分别输出来源/部署证据，不能用 dataset 的提交/Pod 证明 dataset-web。当前准入仍以受信配置中的 dataset、dataset-web 为限。

## 7. 开发到 UAT 的完整组合

Owner 的常用组合建议为“调查证据读取→排查→方案→方案确认→代码开发及检查→按需要 PR 评审→UAT 合并准入→UAT 部署→提测报告”。这是可裁剪的组合建议，用户只要求排查时不自动安排后面的写动作。

新增一项必要且有独立效果的受控能力：`merge-uat-pr`。现有 UAT 部署要求已合入 UAT 分支，而工程流程只交付 PR，两者确实缺少执行合并的连接。

- 输入冻结 repository、PR、预期 head SHA、目标 UAT 分支和必要检查策略；只有已有明确部署/合并授权才可发送合并操作，否则保持等待并说明具体缺项。
- 先读回 PR/检查/目标，检查失败或 head 改变不执行；执行走现有效果账。请求未知时只读回原 PR，不重发另一次合并。
- 输出独立核验的 merge SHA、base branch、实际 tree 与来源关系。仓库合并策略可能改变 SHA，不能要求开发 SHA 等于 merge SHA；tree 等价或差异的处理采用现有受信来源规则，无法证明时阻塞。
- 独立 UAT 请求可直接核验用户给出的已合并提交生成相同来源产物，不要求先有工程 Run，也不强制再合并一次。
- UAT 部署职责止于精确环境部署及技术回读。提测报告由 Owner 汇总变更、版本、环境、入口、验证结果及未测项，经任务报告/Outbox 发送与回读。需要创建测试平台工单时须有单独能力和工单回读，消息发送不等于测试负责人验收。

当前生产流程名为 merge-main 的操作实际只核验已合并事实。新定义将其改名为 verify-main-merge 并移除虚假的合并执行含义；如业务要求自动合入 main，需显式的合并能力与相应授权。本次不借流程整理自动开放 main 合并。

## 8. 日常能力统一接入

取消能力调用必须属于 general-intake Task 的限制。同一排查 Task 可以先查材料再做专业分析，工程 Task 可以整理结果，不另建新 Task。

复用现有能力登记及单代码 Run；能力说明必须包括输入 schema、作用域、效果类型和执行/验证/必要时对账方法。只读走受信 read；写操作明确声明效果并经过 Host 账，不再把全部能力限制为 read，也不允许借 pure/read 执行写入。

首批具体范围：当前授权消息和附件读取、受管仓库搜索/读取、显式授权文件读取、任务专属 Markdown 文件产出与独立回读。产出目录由 Host 分配到 Task/operation 下，默认只创建本任务新文件；不允许模型给任意绝对路径或覆盖用户现有文件。相同操作恢复时核对原文件归属和摘要，冲突可见阻塞。

SQL 查询与平台操作继续按已有受信适配器逐项登记：只有真实 authorize/execute/verify 均存在的能力才可执行。当前缺少某类通用查询适配器时明确返回能力缺口，不宣称已经调查。部署和数据变更优先调用已有专业流程，不复制其门禁到通用工具。

完成核验按目标类型区分：文件必须真实读回，查询结论必须绑定实际查询证据，部署必须核对运行版本；主观分析/方案由 Owner 对明确验收项判断，用户要求确认时保留人工确认。Host 不能仅凭源材料覆盖或模型自评完成就宣布客观业务目标已达成。

## 9. 方案确认、操作审批与报告

方案确认仍是 Task 计划级门禁，绑定 taskId、requestId、方案产物摘要、影响范围及当前目标版本。确认具体方案后可继续已授权后续阶段；一般的“继续”不能批准另一环境、另一 SQL 或生产动作。

生产和数据变更审批留在对应专业流程的受控效果前，保留精确服务/环境/版本或工单/SQL 摘要绑定。Owner 负责解释等待原因、汇总审批结果和后续推进，不拥有批准权限。工单创建、Bytebase SKIPPED、方案确认都不替代 Assistant 真人审批。

对外只使用 Task 报告入口。专业 Run 产物进入 Task 事件，专业节点不直接向群发结果。接纳、阶段里程碑、需用户行动、最终结果分别有报告身份；相同事实和里程碑去重，普通心跳只更新页面。进度询问可由确定性任务投影直接答复，涉及新解释时唤醒 Owner。

完成报告提交及领取发送时重新检查要求版本和输入屏障。发送前出现新目标使旧候选失效；已送达的有效阶段报告保留历史。纠正只针对明确 reportId，不按来源消息批量撤回，不把后来目标变化视为原承接错误。

| scripts/ 与 docs/ops/ | 按 v3→v4 新增离线迁移，不修改已使用的 v2→v3 脚本含义；同步恢复、部署和验收说明 |

不新建任意流程 DSL、独立通知系统或第二套授权系统。UAT 合并是新外部效果，必须单独登记其合同；不能把真实合并藏进只读“准备”节点。

## 11. 实施顺序与迁移

1. **R1：Task 与 Owner 权责。** schema v4、原子任务接纳、要求快照、初始计划及后缀变更，I 退出计划生成。先覆盖补充/控制/重启反例，避免双编排同时生效。
2. **R2：流程和能力统一。** 类型化交接、专业目录、旧通用新入口删除、全部 Task 使用能力、文件产出及回读。验证每类流程局部成功不等于 Task 完成。
3. **R3：开发到 UAT。** 受控 UAT 合并能力、精确 merge SHA 来源、独立部署与同提交重建、提测报告。沿用当前 dataset/dataset-web 准入。
4. **R4：切换和交付。** 更新页面投影/文档，旧账离线迁移与备份，精确包安装和分层业务验证；不在所有功能验收前把 PR 标为已完成。

迁移前扫描所有未终态 Task/Run、尚无 Run 的待执行阶段、待确认/审批、未知效果和 Outbox。需要恢复的定义按实际引用集合保留，不能只检查运行中的 Run 后删除后续阶段所需定义。

现有 Owner 的 taskId/sessionId 不变，原阶段、Run、回执、审批及报告不重建或重发。旧 Task 的原计划作为接管快照，要求由已持久的原文、有效变更及约束构建；无法确定的缺项明确显示，不能只取最近一条消息替换全部目标。完成的历史任务保持只读，明确续办时再按原 Task 接入新计划。

仅在执行排空且未知效果已对账时切换同一 Task 的编排权。旧命令处理器先完成已领取动作的回执对账，再标记由 Owner 接管；不得并行保留新旧两条派发路径。迁移使用 --check 零写检查、一致性备份和逐表计数/摘要对账；已升级并产生新事实后不直接换旧包可写启动。

## 12. 定向验收

复用 `docs/acceptance/task-owner-orchestration/`，新增用例及轮次；不主动全量测试。以下全是待执行项。

| ID | 场景 | 通过判据 |
| --- | --- | --- |
| W01 | I 提交创建意图 | Task/Owner 原子存在，初始无业务 Run，Owner 接纳计划后才执行；I 不能注入流程计划 |
| W02 | 用户只要求排查 | 读取→分析→目标验收；不自动创建代码/部署步骤 |
| W03 | 排查→方案→确认→开发→UAT | 同 Task/Owner，多产物可追溯，确认前零开发，合并及部署精确回读后生成提测报告 |
| W04 | 排查 Task 调文件能力；工程 Task 整理结果 | 不受 general 首阶段限制，不另建 Task 或规划会话 |
| W05 | 第一个流程成功但目标仍未满足 | 页面/通知不显示任务完成，Owner 可追加步骤 |
| W06 | 运行中补充上下文/新目标/换环境 | 分别复用、追加或替换受影响后缀；旧副作用与验收不错误套用 |
| W07 | 开发与 UAT 间插入 PR 评审 | UAT 依据明确来源产物继续，不依赖紧邻工程阶段 |
| W08 | PR head 变化、检查失败、无合并授权 | 零合并；明确阻塞原因；正确授权/对象只执行一次 |
| W09 | UAT 合并请求超时 | 独立回读原 PR 收敛；重复恢复无第二次合并或重复构建 |
| W10 | 直接部署已合并 UAT 提交 | 无工程前置、无多余合并 Run；精确来源仍验证 |
| W11 | 生产/数据审批、SQL 或目标漂移 | 原审批不适用于新对象，Owner 无法自行批准或越过效果账 |
| W12 | 报告语言变化、重复唤醒、发送前补充 | 业务执行次数不增加，报告精准去重，旧候选失效；有效历史承接保留 |
| W13 | 文件产出中断、重试、越界路径、同名冲突 | 文件可独立读回；不越界或覆盖原文件，不伪报成功、不重复产出 |
| W14 | 零阶段初始 Task、待确认阶段及已领取 Owner 决策重启 | 原 Task/会话/决定恢复，无空计划假成功、漏阶段或重复执行 |
| W15 | 迁移旧计划/未来阶段/未知效果/历史通知 | 依赖定义保留；未知效果不重放；原任务和通知计数及证据可对账 |
| W16 | 请求调查但只有聊天材料 | 不宣称查明；显示实际缺失能力或证据，不用来源覆盖代替业务验收 |

真实平台调用、消息送达、数据库迁移、包安装和隔离测试各自留证。真实验证只使用对应既有业务授权；涉及新的具体目标则先固定对象和范围，不用合成适配器 PASS 代替平台行为。

## 13. 完成边界

完成本轮调整的判据是：I 不再决定可执行计划；Owner 能在权限内初始化、组合和调整流程；专业流程不承担整体任务完成及群消息发送；所有 Task 可组合受信能力；开发到 UAT 的来源、合并、部署和提测报告分别有证据；原任务/审批/效果/通知迁移不重复。

本方案不承诺任意自然语言任务都有工具覆盖，也不把所有已有专业分析节点删除。能力不足必须可见；新增业务适配器按实际需要单独登记。方案确认后按 R1–R4 在原目标及验收记录中推进。
