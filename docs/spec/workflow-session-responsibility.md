# 流程编排的职责与结果交接方案

日期：2026-09-27。依据：main `89df536` 的实现、[round-39 审查](../acceptance/topic-context-completeness/round-39.md)及用户对修复层次的反馈。本文件是调整后的建设方案，尚未实施；原[审查范围快照](workflow-authoring-framework-review.md)保留。

## 1. 调整后的目标

让新流程的建设主要围绕“目标、阶段、可用能力、实际产物、验收条件”展开。阶段执行会话处理授权范围内的常见问题；框架可靠保存和交接结果；业务流程声明自己的规则。新增一个业务流程，不应再到通用控制器里增加一组业务名称或错误码分支。

验收重点是：一次普通执行问题可以在阶段内解决；确实需要改计划的问题能带着证据交给 Owner；未知外部结果不会被重复执行；已有结论的调查能合理结束；修复任务没有业务验收证据仍不能结束。R1–R3 是验证这些能力的三个已知案例。

本轮交付修订方案与[建设手册](../../packages/dingtalk-dsh-assistant/README.md)，产品实现、运行实例及真实业务任务保持原状态。

## 2. 方案取舍

| 方案 | 适用价值 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 逐个补错误码与业务条件 | 可快速修复三个已知触发点 | 新流程继续向中心服务堆判断；执行会话收不到完整失败上下文 | 单点修复纳入统一边界实施，不作为总方案 |
| 所有执行、恢复和完成都交给一个会话 | 会话能理解业务并灵活调整 | 会话无法独自保证崩溃恢复、持久状态、权限及外部操作不重复 | 不采用 |
| 沿用现有 Owner、执行会话与控制账，统一职责和交接 | 复用已有基础，把业务判断与可靠执行各自落实 | 需要先补交接缺口，再迁移现有业务接入 | 采用；不新建监督 Agent 或另一套调度框架 |

**反证与限制**：现有固定节点已经能稳定约束输入、权限和产物，粗化全部节点会丢失检查点；现有 Delivery 的效果身份是 `nodeRunId + action`，也不能直接让一个会话任意重复同类写操作。因此本方案保留有效执行边界，先统一交接，随后仅在已有授权能力能承载时调整会话内部动作。阶段划分的效果仍需用接入案例验证，不能凭文档认定已收敛。

## 3. 四方职责

| 责任方 | 应负责 | 交给下一层的内容 |
| --- | --- | --- |
| 任务 Owner 会话 | 理解整个目标，安排阶段，逐项判断验收，处理补充信息与计划调整 | 当前阶段目标、约束、可用能力、前序产物和完成判据 |
| 阶段内执行会话 | 利用已授权工具完成当前工作，阅读失败证据，修正可处理的问题；预算不足或条件缺失时说明原因 | 实际产物、已验证事项、剩余问题和相关证据 |
| 业务流程与受信能力 | 定义业务输入、产物校验、必要验收和允许的恢复动作；执行并核验领域操作 | 可供框架检查的结构化结果与可信证明 |
| 框架 | 接纳输入/结果、持久化状态与事件、隔离身份与版本、预算/租约/排空、授权及外部效果对账 | Owner 可以重读的执行事实；进程重启后可继续处理的待办 |

“阶段内执行会话”是职责称呼，当前实现中的会话仍绑定 Agent NodeRun/租约。一个业务 Stage 可以有多个执行节点和会话，不强制每个 Stage 永远只有一个会话，也不依赖会话记忆作为唯一证据。

需要推理的工作由模型会话处理，确定性的执行和核验继续由 code 执行器承担。无需给每个确定性节点再配置一个模型会话。

**当前权限限制**：Agent 节点只允许 `pure/read`；工程修改和平台写操作由受信 code 节点及 Delivery 执行。第一轮建设继续使用这条路径。需要让会话主动请求写入时，必须另行接入受信能力的准备、授权、执行、核验和对账；仅扩大提示词或工具列表不构成实现。

## 4. 按业务交付划分阶段

建设者先写出业务阶段，例如“调查与方案 → 实现与本地验收 → UAT 交付”。是否继续拆分，取决于以下实际边界：

- 有独立可验收产物，后续可复用或重新开始。
- 权限、执行环境或外部操作身份发生变化。
- 需要用户确认、等待外部结果，或崩溃后从此处恢复。

读几个文件、调整查询条件、修正一次工具参数，通常是会话内部动作；涉及不同外部操作或独立验收的步骤仍保留控制节点。构建通过和业务验收通过必须分别留证，不能因合并为一个业务阶段就合并判断。

页面展示步骤可以来自节点，也可以来自节点内部事件。事件用于呈现动作、耗时和产物，调度节点用于提交状态与恢复；二者不要求一一对应。内部事件不是成功证明。当前 Observer 主要按 Node 展示，本轮不改页面，也不承诺新增事件展示已可用。

## 5. 统一结果和失败的交接

当前有两处直接影响该目标的接口限制：[execution-session.js](../../packages/dingtalk-dsh-assistant/execution-session.js) 的 `tools/result` 遇到 `isError` 就停止，提交前先设置 `attempted`，使错误提交也无法在本轮修正；[task-owner-controller.js](../../packages/dingtalk-dsh-assistant/task-owner-controller.js) 的一般工件读取只覆盖成功阶段，失败材料依赖工程专用路径。以下交接约定是建设目标，不能通过修改提示词直接获得。

### 5.1 最小交接内容

复用现有 Artifact、节点状态、事件及验收引用，形成 Owner 可读取的统一视图，不要求所有业务产物改成同一种大 JSON。

| 信息 | 来源与规则 |
| --- | --- |
| 执行结论 | 框架持久状态及业务结论分开呈现；代码执行结束不直接推导目标完成 |
| 实际产物 | 文档、目录、变更、调查结论、操作回执的工件引用；无产物时说明原因 |
| 验收进展 | 当前要求下哪些条件已有证据、哪些仍未满足；确定性检查由受信能力核验 |
| 后续所需 | 缺失输入、失败位置、可恢复条件及外部效果是否已确定；范围说明不自动变成阻塞 |

业务失败、等待和结果接纳错误都应可读，不能只把成功阶段的产物交给 Owner。失败材料可以用于诊断和修复，不能冒充成功验收证据；嵌套工件引用仍要检查来源和作用域。

### 5.2 从执行结束到 Owner 可见

1. 受信工具合同明确哪些反馈可在当前能力和预算内修正，再交给执行会话继续处理。未接纳、无副作用的格式错误可以反馈修正；已接纳的提交、失效身份和控制约束不得被同轮覆盖。保留现有累计步数、时限和恢复计数，重领或新 generation 不应无意重置成本。
2. Controller 统一负责产出规范化、结构校验、后继输入准备及持久接纳。已确认的契约错误保存失败原因和可安全保存的诊断，不让已排空节点无解释地残留 running。
3. 状态与结果引用可靠落盘后，Owner 通过持久事件获知；事件重复消费不产生第二次决定，进程在提交与唤醒之间退出后仍可重新发现待处理结果。
4. Owner 读取成功或失败证据，选择继续、安排修复、请求缺项、调整后续阶段或结束任务；Host 再检查当前要求/计划版本与准入条件。

持久化不可用或提交回执未知时，先停止推进并核对原记录。尚未落盘的诊断不能声称已可靠交接，不能用 catch 将其伪造为确定失败。框架程序错误（例如 mapper 缺字段）需修复定义或实现，执行会话没有修改运行框架的隐含授权。

## 6. 异常应该由谁处理

| 情况 | 负责人和动作 | 升级条件 |
| --- | --- | --- |
| 读取失败、工具参数错误、可以调整的分析方法 | 当前执行会话按具体反馈修正，保留尝试与预算 | 缺能力、超范围、反复无进展或预算耗尽时交 Owner |
| 验收不通过，已有受信修改能力可以修复 | 执行会话分析原因；现有工程流程通过 Owner 接纳修复、新 generation 和受信节点实施 | 候选改变后重新验收；不会复用旧通过票据 |
| 缺目标 UAT、验收要求或必要配置 | Owner 根据缺项请求补充；无关可执行工作可继续 | 回复接纳后核对版本和受影响阶段，不猜环境 |
| 需要调整业务步骤或目标 | Owner 修订计划，保留有效前缀，失效受影响后缀 | 已发生的效果不因计划改写消失 |
| 外部操作结果未知、执行器未排空 | 框架和对应适配器核对原效果/进程 | 未确定前禁止重发相关操作；Owner不能以“重试”绕过 |
| 存储、版本或结果接纳异常 | 框架阻止推进、保存可持久事实并暴露原因 | 需要实现修复时明确暴露维护阻塞，不让模型循环重做业务 |

模型没有收到错误、没有所需能力或没有合法续行入口时，“交给会话处理”并不能解决问题。统一交接与受信恢复入口是让已有会话发挥作用的前提。

## 7. 业务合同放在流程接入处

复用当前 workflow/capability 注册及 `authorizeCompletion`、修复入口等回调，逐步让每个受信流程提供自身的产物读取与核验、完成条件和允许恢复动作。通用 Host 调用合同并执行公共约束；流程代码负责业务含义。

- 调查任务：用户需要“根据现有证据回答”，如实交付无法确认的结论可以满足目标；`limitations` 不是统一的未完成标记。
- 修复任务：必须有同候选的业务验收证明，构建通过、模型说通过或材料引用非空均不够。
- UAT 交付：指定 `uat1`～`uat9` 才能选择对应分支，main 合入属于独立流程。

这些规则仍是硬约束，只是由领域合同承载。Owner 判断语义是否满足用户要求；Host 核对证据身份、版本和流程要求的必要证明，最终完成须两者都成立。先迁移只读与工程两个现有流程验证扩展点；不预建插件 DSL、万能策略引擎或一长串可选 hooks。

领域合同来自发布的受信代码，规则变化纳入定义版本和摘要；不能给旧冻结阶段套用当前校验器。业务回调只返回其合同允许的事实或建议，不能自行签发派发许可、绕过公共门禁或直接改控制账。

## 8. 版本与恢复是一项通用保证

新建且尚未绑定的运行使用当前定义；已经冻结的 Stage 和既有 Run 都按绑定 digest 解析。当前定义和历史定义的身份校验走一致路径；原定义不可用则明确阻塞，不能暗中切换版本。

结果、失败、修复请求和验收依据均绑定当前任务要求及执行身份。新输入使旧决定失效；新候选使旧验收失效。重启、重复唤醒和操作回执丢失，分别从持久事件、控制账和原效果身份恢复，不能依赖会话记忆猜测。

## 9. 实施分三步

| 顺序 | 改动范围 | 交付标准 |
| --- | --- | --- |
| 一：补齐通用交接 | `execution-controller.js` 的结果接纳；`task-owner-controller.js` 的失败材料和事件交接；冻结定义解析。按需调整现有 Store/事件接口 | R1/R3 反例关闭，失败确实送达 Owner，持久化未知仍不重复执行；不只补两条错误码 |
| 二：收拢业务合同 | `workflow-service.js` 中散落的完成和工程修复判断迁回受信流程接入处；复用现有能力校验、Owner 决策与 Store 准入 | R2 关闭；调查可结束、修复缺证据不可结束；接入第三个最小流程无需修改 Controller/Store 的业务分支 |
| 三：恢复会话内处理并校准阶段 | 调整 `execution-session.js` 的受信工具反馈与提交前修正循环；用只读调查与开发验收检查划分、反馈和交接。保留外部效果及独立验收节点 | 可修正问题在原预算内完成，控制类错误仍停止；跨阶段问题有明确接手者，既有授权、清理、版本与对账反例持续通过 |

涉及 schema 或持久事件变化时，先确认现有字段能否表达；确实不能才提出迁移、备份和回退设计。第一轮不重写任务历史、不批量合并节点、不改为每话题永久会话、不开放任意写工具，也不把事件展示改版列为完成前提。

每步先用一次性库与受信替身能力验证，之后按部署 runbook 维护切换。真实开发/UAT 验收使用明确环境和现有开发分支；外发权限按原有授权范围核对。本方案不等同于实际部署或重新提测指令。

## 10. 必须通过的框架验收

| 案例 | 要证明的结果 |
| --- | --- |
| 非 JSON 产出、后继 mapper 错误（R1） | 持久失败可定位，Owner 可读相关诊断，无虚假 running、无误推进或重复效果 |
| 已回答但含范围限制的调查（R2） | 按当前用户要求完成；对应反例“必须交付仍缺失”保持未完成 |
| 升级后启动冻结旧阶段（R3） | 有原 digest 可执行，无原定义明确阻塞，不套用当前版本 |
| 会话修正普通工具错误 | 当前租约和预算内完成，记录尝试；无进展能退出，不能无限重试 |
| 业务验收失败后的修复 | 失败材料进入修复判断，新候选重新验收；伪造或旧证据被拒绝 |
| 结果落盘后、Owner 唤醒前重启 | 结果仍被处理；重复事件不重复决定或派发 |
| 外部操作超时且结果未知 | 按原操作对账；Owner 要求重试也不能产生重复副作用 |
| 提交回执未知、磁盘不可写、取消与新输入并发 | 不伪造终态、不丢控制约束；恢复后核对原状态和身份 |
| 第三个最小业务流程接入 | 只补流程合同及必要注册，复用同一套交接、恢复与验收准入；不增加中心业务特判 |

上述是后续实施的通过标准。本轮仅审阅方案及文档一致性；R1–R3 仍为已知未修复问题，运行时验收结果不由这份方案改变。
