# 常驻会话上下文按需读取

## 现场与根因

当前 Runtime 在每条 `[GROUP_MESSAGE_STEER]` 中直接序列化完整历史回复候选。候选上限虽然从无界收敛为 8 条、16 KB，但选择器仍无条件加入最近回复，因此现场最近 30 条消息全部携带候选，候选占单条判断信封的 97%–99%。短消息的判断信封中位数仍约 15 KB。

常驻系统提示同时展开本群全部 Task 的完整 `messageHistory`。现场 30 个 Task 形成约 46.7 KB 的动态任务索引，其中约 34.5 KB 是重复消息历史。两部分共同挤占上下文并触发频繁压缩，进而干扰同一 step 中近期消息的关联判断。

## 修复设计

- 完整回复候选继续由 Runtime 在请求进入时生成并绑定到内存中的判断/通知请求，保证提交校验使用的仍是同一快照。
- `[GROUP_MESSAGE_STEER]`、`[GROUP_DECISION_RECHECK]` 与 `[TASK_COORDINATION]` 只写候选数量和按需读取指引，不再写候选正文。
- Resident 只有准备提交非空群回复时才调用只读工具 `group_reply_review_get`，按当前请求 ID 取得完整候选；`group_decision_submit` 与 `group_reply_submit` 继续要求 `reviewedOutboundIds` 精确覆盖快照，保持去重、撤回和 stale 门禁不变。
- 系统提示中的本群 Task 索引只保留 Task ID、标题、目标片段、状态、归档标记和消息数量。索引只负责召回，不能作为最终关联结论。
- 新增只读工具 `group_task_context_get`。当摘要索引或当前消息显示可能关联既有 Task 时，Resident 按 Task ID 获取完整目标、验收标准、阶段任务、消息历史和已记录上下文后再决定关联、重开、取消或新建。
- 两个读取工具仅接受当前 Resident 所属群的内存请求或 Task，限制单次数量；未知、过期、跨群或重复 ID 均失败关闭。

## 验证

1. 大量历史 Outbox 下，普通 STEER 不包含候选正文，单条信封只增加有界候选计数提示。
2. 读取工具能按一个或多个普通判断、关联复核及 Task 通知请求返回其绑定的完整候选快照；过期和跨群请求失败。
3. 未读取或未完整提交 `replyReview` 时仍不产生 Outbox、Task 或撤回副作用；读取后原有同事项替换与不同事项保留逻辑继续通过。
4. Task 系统索引不再包含 `messageHistory`，但详情工具可回读完整任务上下文；所有状态和归档 Task 仍在摘要索引中。
5. 使用现场只读状态重放最近消息，STEER 体积相较旧协议显著下降；全量测试、打包、本地安装、重启和 Runtime 状态回读通过。
6. 部署后逐条核对最近消息在 Inbox、Task 时间线与 Outbox 中的真实处理结果；仅在发现缺失或错误时做精确纠正，不重复发送已正确的确认。
