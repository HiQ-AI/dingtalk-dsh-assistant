# 叶子完成审阅与群通知收敛

## 问题

叶子提交完成结果后，Runtime 先向常驻主会话发送完成审阅请求；Task 落为 completed 后，又发送一份包含完整结果和 Topic 消息的通知协调请求。两次串行模型调用重复携带目标和结果。现场第二次调用发生 300 秒流空闲超时，使完成通知在 Task 完成约 349 秒后才提交。

## 目标

- 常规完成路径只调用主会话一次，由同一次请求返回完成审阅结论和通知草稿。
- Task 仍须审阅通过并以当前 inputVersion、runSequence、目标和检查点原子落盘后，通知才能进入 Outbox。
- Topic 版本、待归类消息、历史回复候选、回复对象和收件人门禁保持不变。
- 审阅拒绝不产生通知；提交竞态使通知草稿过期时，继续使用现有通知协调请求重新生成，不投递旧草稿。
- 完成请求只携带通知所需的近期消息投影；完整 Topic 历史仍通过固定版本工具按需读取。
- 在 Task executionEvents 记录完成审阅请求、完成落盘、通知入队或回退协调的时间；Outbox 回读确认时记录 deliveredAt，用于区分模型等待和投递等待。

## 方案

完成审阅请求增加 `notification`：包含通知正文、历史回复判断、引用消息和接收人。Runtime 在请求建立时同时固定相关 Topic 消息、Topic revision、历史回复候选和稳定结果键。主会话如有历史候选，先通过既有 `group_reply_review_get` 读取，再以 `group_task_review_submit` 一次提交审阅与通知草稿。

工具先校验草稿的候选、回复对象与参与人，但不写 Outbox。Task 审阅通过后，Runtime 在原有 CAS 中完成 Task，再用同一请求快照执行第二次提交前校验并写 Outbox。若出现待归类消息、Topic revision 变化、Task 版本变化或历史候选变化，则丢弃草稿，进入已有 `TASK_COORDINATION` 恢复路径。

等待信息不是完成验收，继续使用独立通知协调请求。进程重启后没有内存中的草稿，仍由 `reconcileCompletedNotifications` 走现有恢复路径。

## 上下文预算

完成审阅请求内联最多 12,000 字符、20 条相关消息；优先保留最近消息，并包含总数和截断标记。完整结果只注入一次。通知请求的历史候选只暴露数量，内容按需读取。

## 验证

- 正常完成仅出现 `TASK_COMPLETION_REVIEW`，通知进入 Outbox，不出现第二个 `TASK_COORDINATION`。
- 拒绝完成、目标版本变化、Topic 变化、候选变化和 Outbox 首次写入失败均不产生重复通知。
- 草稿 stale 后才出现独立协调请求，旧草稿不能投递。
- 重启恢复仍能为缺失通知的 completed Task 生成一条通知。
- 请求消息数量和字符数受限，完整结果不重复注入。
