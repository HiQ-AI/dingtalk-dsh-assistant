# 群消息澄清与任务准入优化方案

日期：2026-10-08。源码基线：main / 1aaef1b4195bf3f7618daee7da5b26f2046c116f。本文件是实施前方案，未修改运行逻辑、配置或历史请求，也不表示已经通过验收。

新建理由：现有 `message-no-action-clarification.md` 处理旧 S 节点静默收口；本方案处理当前群协调会话的澄清接纳、交办来源和权限事实，不回改历史方案或已有未提交审计文档。

## 1. 目标与当前证据

目标：已明确的交办直接承接；可由系统取得的材料自行读取；需要授权时准确等待授权；确实缺少会阻止下一步的信息时，只询问该信息。减少无效追问，同时不虚构任务、不扩大修复范围、不放宽生产写入和发布审批。

当前实查的两个来源：

| 来源 | 原文及实际决定 | 已确认的问题 |
| --- | --- | --- |
| `msg-a5e4031a162a8eca4976166e2bf3cf704bee6777`，孙鹏，09:17:57 +08:00 | “来个任务，边做边修插件”；没有命令，生成澄清“你想修插件的哪个问题” | 将执行中发现的问题误当作用户必须预先描述的修复目标；没有充分保留工作方式这一理解 |
| `msg-afb0ab3c3e6a5c7fd1a573919ea44ae320369347`，李辰，09:23:43 +08:00 | “按文档开发”；已关联文档话题并识别开发目标，没有命令，生成负责人确认请求 | 意图已经明确，权限问题仍落成 `needs_clarification`；不能从模型解释直接认定发送者确实无权 |

当前链路依据：

- `message-coordinator.js:141-148`：模型提交 `needs_clarification` 后直接形成 request；这条路径不经过 `validateActions`。
- `message-context.js:62`：等待合同主要是自由文本 reason/question，缺少实际阻塞动作与已检查来源。
- `workflow-service.js:912-934`：`mayCreate` 已允许 owner、明确交办、关联来源等情况；不是“仅 owner 可要求执行”。
- `workflow-service.js:2583`：注入“只有已认证任务所有者可以要求执行”，与上述准入规则不一致。
- `workflow-service.js:2040`：`actorMayCreate` 是布尔值，缺少判断依据；`actorPermissions` 默认空数组也不能证明没有权限。
- `workflow-service.js:2063-2072`：创建开发动作前即要求原消息明确 UAT，尚未利用完整文档和关联来源确定执行条件。
- `workflow-notifications.js:284-299` 与 `workflow-service.js:2920-2924`：澄清统一通知请求人，并显示通用“有效补充”恢复条件。
- `docs/manual/install-and-configure-dsh-web.md:466` 的准入模板要求“已经形成可验证目标”，容易被理解为创建任务前必须完成需求、技术与交付细节审查。

盲点：第二条的模型可能受提示词影响，也可能读到未完整反映交办来源的权限事实。当前证据不足以判定是哪一个导致了具体拒绝，实施前需冻结工具输入与关联来源。方案同时消除规则不一致和权限事实不可追溯的问题。

## 2. 路线选择

| 方案 | 取舍 |
| --- | --- |
| 仅追加“少澄清、多执行”的提示词 | 不采用。自由文本仍可直接落成等待，无法防止模型把权限和技术问题重新包装成澄清 |
| 取消澄清与权限限制，所有命令自动创建任务 | 不采用。会虚构目标、误接同事间交办，并绕过必要的环境选择和执行授权 |
| 复用当前协调会话，收紧澄清合同，统一 Host 准入事实，分开等待原因 | 采用。不增加第二个意图模型、评分阈值、通用策略引擎或独立任务队列 |

## 3. 一条明确的承接路径

`关联当前消息与已提供来源 → 确定用户要求 → Host 核对任务准入 → 承接或记录真实阻塞 → Owner 读取材料、确定计划、推进执行`

协调层判断“要做什么、关联哪个事项”；不要求先找出 bug 根因、写完技术方案、拆完开发阶段或列完验收清单。Owner 在执行前逐步落实这些细节。

| 情况 | 处理 |
| --- | --- |
| 文档或上下文足以确定交办目标 | 承接任务，读取材料并推进；技术未知写入调查/实施步骤 |
| 已唯一关联的文档尚未读取 | 使用现有只读材料工具；已提供的链接、引用正文不重复索取 |
| “边做边修”“先看再改”等工作方式 | 保留为关联事项约束；已有任务继续该任务，没有具体事项时保留对话事实，不虚构插件专项任务 |
| 任务准入不满足 | Host 生成等待授权或明确拒绝；不让模型索要泛称“项目负责人确认” |
| 多个目标或约束冲突，内部来源无法排除 | 澄清一个真正改变下一步选择的问题，列出真实候选 |
| 材料读取失败、登录失效、能力未配置 | 记录系统阻塞及具体原因；不改成“用户补充需求” |

“无具体事项”的边界：可以确认工作方式，不需要追问具体插件 bug；如果当下确实需要用户选择下一项业务任务，只询问业务事项，不要求先编造一个插件故障。

## 4. 澄清必须证明阻塞，而非证明需求不够详细

仅在下列条件同时满足时接纳新的协调澄清：

1. 缺失或冲突的信息会改变当前目标、目标对象、授权范围或下一步必要参数。
2. 当前原文、引用、同一事项来源和已提供材料仍无法确定该信息；可内部读取的必要来源已经读取。
3. 问题具体到一个缺口，能够说明其阻止哪个动作；不索要完整现象、方案或验收清单来替代承接。

沿用现有 `needs_clarification`，在当前协调提交合同中要求三个字段：`missingField`、`blockedAction`、`checkedSourceRefs`。既有 `reason` 使用小范围原因码：目标冲突、范围冲突、必要执行参数缺失、确实没有可确定的事项。`question` 仍是面向用户的自然语言。

Host 核对引用是否真实、同群、版本有效，以及必要的来源读取是否有真实结果；权限、读取故障和能力缺失不能作为澄清理由。Host 不声称靠字段就能完全证明语义正确，语义误判由真实模型回放与人工审阅继续检查。

不合格候选在持久化 request 和通知前返回结构化反馈，由同一个原生协调会话修正。没有 request、通知或任务副作用。持续无法修正时按现有条件性失败进入系统处理受阻，不能改成无限重启模型或强制放行。

## 5. 权限由 Host 的同一规则决定

把 `mayCreate` 内现有规则提取为同一评估函数，由事实读取、候选接纳和真正创建三个入口调用；结果包含 `allowed`、`reasonCode`、`sourceRefs`。不增加并存的一套模型权限规则。

- 删除拼接的 owner-only 绝对规则，改为“Host 决定任务准入，阶段动作另行校验授权”。
- 模型可以提出 create/research 候选，不得把 `actorPermissions=[]` 或不认识职务理解为无权，也不得据此直接发起权限澄清。
- 文档、点名、后续开发指令可以通过同一事项关联组合成交办证据；必须核对同群、真实身份、有效 sourceVersion 和同一关联事项。群内相邻消息本身不构成授权，其他人的点名和答复不能移作当前人的授权。
- 针对李辰的“文档 → @孙鹏 → 按文档开发”，回放时必须检查已关联的点名来源；不要求他在每条后续消息重复点名。是否成立以 Host 来源核验为准。
- 候选接纳时和真正执行前再次核验源版本及权限；源编辑、事项变更使旧结论失效。

确实需要 owner 授权时，在现有 message request 存储中增加 Host 专用 `needs_authorization`，不建新的授权平台。记录待授权的动作、原始来源版本、事项绑定、确定的授权人和恢复条件；模型不能选择授权人或伪造该状态。

回复必须绑定具体授权请求，核对身份和版本，再通过同一准入函数处理。一次任务交办批准不自动授权生产 SQL、发布、合并 main；这些继续走现有阶段审批。无允许的授权途径则明确拒绝，不制造永久等待。

权限服务读取失败或授权人无法确定属于系统阻塞，不能自行推断一个“项目负责人”。

## 6. 必要执行参数放到实际需要的位置

任务准入、用户业务意图和工程执行准备分别判断。保留 `workflow-engineering.js` 对仓库、UAT 与目标分支的硬校验。

对于“按文档开发”，允许在目标及任务准入明确后持久化同一个开发事项，由 Owner 读取文档、核对仓库和交付条件。目标 UAT 若已由有效关联来源提供，直接复用；确实未提供则在工程准备前只问目标 UAT，不重问“是否开发”。

将 `validateActions` 中“原消息必须直接包含 UAT”的前置条件移动到工程准备接纳边界；在环境未明确前只允许已授权的材料/代码读取与计划整理，不创建工程 worktree、不修改源码、不提交 PR。工程准备函数仍拒绝缺失或多个环境，绝不默认选择 UAT、main 或生产。

该调整必须与 Owner 对执行条件缺失的等待/恢复一起实现，不能只删除早期校验后把缺参数变成工程错误。继续使用原 BusinessTask、requirement 与 Owner，不降级成另一调查任务，也不在回复环境后创建第二个任务。

## 7. 状态与通知准确表达原因

- `waiting_clarification`：显示缺少的具体信息及其阻止的动作；恢复条件是该字段补齐或冲突消除。
- `waiting_authorization`：显示待批准动作、实际可批准身份；恢复条件是当前版本对应的有效授权。
- `waiting_context` / `waiting_system`：保留材料获取和系统阻塞的实际原因。
- 已接纳任务沿用 Task 状态，不再同时遗留原澄清等待。

复用现有 notification / outbox；相同请求版本只通知一次，答复后继续原事项。通知送达与请求解除分别取证。历史通知保留，不伪造新的 delivered 状态。

## 9. 验收矩阵

实施时记录到 `docs/acceptance/message-clarification-admission/` 的 matrix.csv、每轮 round-N.md 与跨轮脚本；以下为拟验用例，不是 PASS 记录。

| 用例 | 必须观察到的结果 |
| --- | --- |
| 原例一，已有可承接业务事项 | 复用该事项，保留“过程中发现插件问题再修”的范围约束，不索要预先存在的插件 bug |
| 原例一，没有具体业务事项 | 记录工作方式，不虚构专项修复任务，不产生“请说明哪个插件故障”的等待 |
| 原例二，文档＋同一作者点名＋开发答复 | 有效来源组合被 Host 接纳；创建一个业务任务，不再索要负责人重复确认 |
| 文档唯一且已可读取 | 工具读取发生在询问之前，不重复索取链接、截图或文档内容 |
| 文档无法读取 | 系统阻塞保留真实错误，不生成需求或权限澄清 |
| 确实无任务准入权限 | 零执行副作用，Host 明确拒绝或等待真实授权人；普通请求人补需求不能解除权限阻塞 |
| 两个可选目标／删除与隐藏冲突 | 保留一次必要澄清，真实候选可读，答复后继续原事项 |
| 开发目标明确但 UAT 未给出 | 一个 Task 承接、材料及计划可推进；工程准备前只询问环境；无 worktree/代码/PR 副作用 |
| UAT 已在有效关联来源明确 | 复用确切环境，不再要求当前句重复环境；冲突时仍阻塞 |
| 交办指向其他同事或只是闲聊 | 不创建任务、不发任务提议、不靠相邻消息取得授权 |
| 授权回复来自错误身份、旧版本或别的事项 | 不恢复、不执行；生产写入与发布的独立批准仍必须满足 |
| 澄清答复／授权答复重复、重启、通知回执丢失 | 请求只生效一次、仅一个 Task、原事项继续；已送达通知不重发 |

验证分层：合同与真实状态存储的定向测试 → 原生协调/Owner 生命周期 → 固定上下文下的真实模型候选及 Host 接纳回放 → 安装包/进程/健康 → 两条原消息的现场收口。

单测不能只写死“模型输出正确”作为语义验证；需要保留真实模型输入和输出，人工核对“没有新增无必要追问”。定向测试至少覆盖 message-coordinator、group-coordinator-session-native、workflow-service、message-workflow、通知与 observer 相关测试。没有实跑结果前，不记录通过。

## 10. 历史现场处理与完成条件

部署后仅核对并处理上述两个来源及其明确关联请求，不批量重放全部历史。确认是否已生成任务、动作、发信和后续答复，再选择现有逐条 reprocess；有已执行命令的来源不能强行重跑，使用原事项恢复/补账路径。旧请求以真实事实 supersede/resolve，旧通知保留。

现场重处理不是自动授权实施开发或生产操作。先用无外部写能力的隔离回放确认新判断，再按用户明确授权范围执行现场动作。

完成条件：两例不再被错误归为补充需求；必要澄清、权限、环境与生产审批反例仍成立；真实 Task/请求/通知读回一致；文档与运行配置一致。有限测试不能保证所有未来语义判断绝不出错，每个新澄清保留缺失字段、阻塞动作和来源依据，供后续核验。
