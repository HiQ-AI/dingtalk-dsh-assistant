# 单条消息多事项的 Topic 路由方案

日期：2026-09-17。分析基线：本地 main，`e961e512d34d09f12f5720a3ae1b2c49070e95bb`。

复审修订：2026-09-17，补充事项独立通知、隐藏的群级门禁、确认与执行分离、附件边界及协议入口覆盖。仍处于实施前分析阶段。

本轮只分析、读取实际记录、运行隔离复现并编写方案；没有修改业务代码、调整真实 Topic/Task、发群消息或部署。本文是实施前快照。

## 1. 结论与可验证目标

当前不是数据库强制“一条消息只能一个 Topic”，也不是协议强制“一个 Topic 只能一个 Task”。实际问题有两层：

1. 语义归类按共同业务领域合并，缺少“消息内分别识别独立交付目标”的显式中间结果。
2. 执行权和已消费状态以整条消息事实为单位，即使归入多个 Topic，也只有一个 Topic 可以执行任务动作。

建议在现有 Resident 路由中增加“消息内事项单元（unit）”，先识别独立事项，再分别匹配持久 Topic。每个事项保留唯一动作主归属，整条消息可以有多个事项、多个动作主归属。继续复用一个群 Resident、Topic 决策、Task 叶子和 Outbox；不增加 Topic Agent 或另一套调度系统。

目标：#1066 对应三个可独立推进的话题，各自创建或续接任务；回归阻塞不阻止两个需求分别分析和反馈。一个事项关联多个话题时仍不重复执行。

用户补充的硬要求：每个事项执行结束即可独立反馈自己的结果/进度，不等待同一消息中的其他事项结束，不等待全群任务结束，也不等待主会话整轮结束。反馈仍经过该事项自身的验收、版本校验和可靠投递；这些检查不得扩大为其他事项的完成门槛。

## 3. 本条消息的目标拆分

| 事项/Topic | 任务交付边界 | 应保留的约束 |
| --- | --- | --- |
| 审核增强功能回归 | 核验本轮四项改动，分别验证后反馈回归结论 | 四个编号是同一次回归的验收项，不拆成四个互不相关任务；非管理员分配权限明确排除 |
| 审核草稿需求 | 单独确认保存方案、影响与排期，后续实施按有效授权推进 | 当前审核人、当前审核任务隔离；不改变其他人、其他任务和现有流程状态；不能把“允许本地或入库”改成两种都要实现 |
| 审核撤回通知需求 | 单独确认通知方案、影响与排期，后续实施按有效授权推进 | 基于撤回成功，通知原全部审核人，明确对应任务已撤回 |

PR、分支、@对象、时间以及适用的范围声明作为来源/背景按需共享，不因为共享项目或历史资料合并独立目标。“非管理员分配权限已上线、不在范围内”是排除项，不是第四个待办。

“请回归后反馈”绑定回归事项；“新增需求确认实现方案和排期”分别绑定两个需求，不人为添加“所有回归结束后才能开始需求分析”的依赖。当前真实 Task 采取了先方案/排期的边界；拆分本身不得升级为自动实施或发布授权。

每个事项先查找是否已有匹配 Topic 和 Task；命中同一具体目标就续接，不能为了满足“三个”而重复创建三个新任务。这里要求三个独立目标，不建立通用的 Topic 与 Task 永久一对一规则。

## 4. 候选方案

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| 只加强提示词，要求多建 Topic | 不采用 | 即使模型拆对，另两个 Topic 仍被 Host 拒绝执行 |
| 保留一个 Topic，只创建三个 Task | 不采用为最终方案 | 当前协议可行，但后续补充、摘要、原文和处理状态仍混在一起，不满足话题独立要求 |
| 每个 Topic 都放开整条消息的执行权 | 不采用 | 把业务拆分和防重复混为一谈；同一请求关联多个 Topic 时会重复建任务、重开或确认 |
| 消息内事项 + 每事项唯一 owner | 采用 | 分离不同请求的执行权，同时保留同一请求只能执行一次的约束 |

不按换行、编号、关键词或字符长度机械切分；例子中四项回归属于一个交付目标，两个需求各自独立。判断标准是能否独立接受补充/取消、形成交付、单独验收和反馈，而不是有没有相同“审核”关键词。

## 5. 推荐协议与数据改动

### 5.1 路由一次提交事项清单及归属

继续使用 `group_topic_route_submit`，不增加固定的模型调用阶段。普通消息单次推理完成“识别事项 → 匹配 Topic → 提交”，Host 原子接受结构化结果；超预算输入按 5.6 的同快照分页规则处理。

拟议概念结构：

```text
route(messageId, messageVersion)
  units[]
    unitKey / 已存在的 unitId
    summary                     该事项的讨论或交付目标
    sourceRefs[]                支持该事项的固定来源及精确原文锚点
    contextRefs[]               共享背景、约束、排除项的来源，带用途说明
    topics[]                    延用 continuation / affected 与 reason
    effectOwner                 该事项的唯一动作主归属
  ignoredRefs[] + reason        不进入话题的内容及原因
```

- 原文继续仅存一份；sourceRefs/contextRefs/ignoredRefs 引用固定 messageVersion 和精确原文锚点，不把重写摘要冒充原始授权。服务端唯一解析后持久化 sourceRanges/contextRanges/ignoredRanges；范围可不连续、共享背景可被多个事项引用。
- 持久化的文本范围统一以服务端保存字符串的 UTF-16 半开区间表示，服务端校验长度、有效字符边界和来源版本；模型无需心算下标。附件/引用链使用真实来源 ID，不能伪造为文本片段。
- 结构性校验覆盖来源有效、无遗漏区间的解释、目标归属及 owner 合法、重复标识等；范围覆盖完整不证明语义拆分正确，仍需语义评测。
- unit 也可只是讨论事实，并不自动对应 Task。无意义内容说明原因即可。
- 本例三个 unit 分别归入三个目标 Topic；一个 unit 实质影响多个 Topic 时仍只设一个 owner。纯粹需要查询历史资料不建立归属。
- 不允许一次已冻结的同版本复核靠改 unitKey 重新制造执行权。Host 生成稳定 unitId，复核只引用已有 ID；真正拆分/合并走显式修订，并记录前后事项映射。

### 5.2 持久化、版本与幂等

在现有 Group 聚合内保存事项及版本来源；与 messages、topics、routeHistory 在一次原子更新中提交，不新建跨表事务依赖。

unit 是某条原始消息中的语义输入单元，Topic 才是跨消息延续的目标。下一条补充消息创建自己的 unit 并续接原 Topic，不复用上一条消息的 unitId；同一原消息的复核则保持 unitId。不能把业务目标相同当成同一原始输入，也不能因为新 unit 就新建 Task。共享片段要保留其适用的 unit 引用；共同约束被明确改变时，所有受影响事项分别获得增量，不能只更新最先选中的一个。

Topic entry 扩展为事项引用（unitId、unitRevision），同时保持可解析的 messageId/messageVersion 证据链。固定 Topic.revision 必须解析当时的事项范围及对应原文，不能读取后来变更的范围。

执行权和消费改为 `unitId + unitRevision`，而不是整条 `messageId + messageVersion`：

- 每事项唯一 owner，事项 A 被接受不会消费 B/C。
- 决策接受时在现有 Group 原子 preflight 中校验并预留事项，避免不同 Topic 并发抢占；现有 Task 版本保留、operationId、Outbox 身份继续复用。
- failed/applying 的已接受事项保持占用，按原 operationId 恢复；不能因业务执行失败重新创建任务。
- 任务动作接受、Topic 输入已处理、确认/结果通知是三个独立状态。纯“收到”只消费自己的 Outbox 身份，不消费业务动作资格；存在可执行目标时，不能仅发确认便把该事项标成已经完成任务关联。确认和任务动作同次提交时，按已持久化的动作意图占用并恢复。
- 单纯补齐发送人、媒体或引用元数据不得重授执行权；只有确实产生新的业务输入才形成可执行增量。保留原文事实版本和事项语义版本两种含义，并冻结旧版来源。
- 修改事项范围、归属、拆分/合并不能清空旧消费记录。显式修订必须继承已执行效果，说明剩余工作如何归入原任务或新任务。
- 同一 Topic 内同一 messageId 的多个 unit 可以共存；当前按 messageId 的 Map、findLast、delta、remove 等代码必须统一改到事项引用粒度，不能只给 entry 加字段。

拟升级 storage domain 7 → 8，采用一次性显式迁移，不保留永久双路协议。源数据到单事项基线的机械转换只保留原行为，不假装自动知道历史语义拆分。旧 Task/Decision/Outbox、固定版本来源和已接受效果都要保留；迁移不重放群请求。

### 5.3 决策、叶子与回复

- decision 和每个 Task action 都携带可校验的 `basisUnitRefs`，原始 messageId 从其来源派生。逐动作验证本 Topic 当前可执行事项，不再用“整份决策找到任意一个 owned 消息”放行全部动作。
- Task 继续只存 topicRefs，不复制群消息或独立维护消息列表；固定 Topic 版本解析出“本话题事项 + 范围 + 背景/排除项 + 原文”。
- group_topic_context_get、增量分页、已读门禁、叶子系统输入、计划审阅、完成审阅同步使用该视图。完整原文保留可查，但明确哪些片段属于当前目标，防止叶子看见另外两项就再次纳入工作。
- 原始 @、发起人、引用转交等授权按事项适用范围检查；不能因为消息某一段 @Agent，就接管另一段明确交给同事的工作。
- 附件不可读按 unit 引用的来源隔离。缺失材料只阻塞依赖它的事项；若尚无法判定附件影响范围，明确保存待澄清关联，不猜测其无关，也不能把已确定不依赖该附件的其他事项一起阻塞。
- 新任务 objective/acceptanceCriteria 只覆盖一个独立目标；实现/验证步骤继续放 stageTasks。Host 能校验来源引用，语义是否混入别的目标由路由约束、审阅与评测共同验证。
- Outbox 增加事项来源；同一原消息不同事项的确认、结果分别可发送，不能互相替换。已有 replyReview 和 Task 结果去重保留，messageId 仅用于来源关联，不作为同一事项的充分条件。
- 首版沿用每个独立 Task 动作前有一条简短确认的规则，不额外引入跨 Topic 合并通知事务；可独立反馈自己的结果，不等待兄弟事项全部完成。
- Task 的 topicRefs 只承载实际业务输入，不把“为查资料访问过的话题”升级为完成依赖。后续修订分别作用于对应目标；真正存在的业务依赖需要来源和理由，但其他事项未完成不能阻止本事项报告已完成部分或自身阻塞。

### 5.4 查询与展示

扩展现有 HTTP Topic/消息投影：

- 消息仍显示为原始一条，列出对应的三个话题。
- 话题详情展示本话题关联的事项范围、共享限制，并可展开完整原文。
- 消息“已处理/已投递”的聚合依据所有当前事项关联的 Topic 增量完成，不以首个 Topic 完成为准；这个状态依旧不等同于全部业务 Task 已完成或群回复全部送达。
- 消息聚合状态只用于展示，不得作为事项结果回复的准入条件；事项 A 已反馈时，原消息仍可显示另有事项待处理。
- 更正已处理消息的事项划分时，应形成新的待处理增量；旧版历史与 Task 来源保持可查。

### 5.5 事项结束后独立反馈

规定单事项链路：`事项 A 结果 → A 自身验收/版本检查 → A 完成状态和通知意图持久化 → A 的 Outbox → DWS 发送与回读`。B/C 的执行、审阅或投递状态不参与这条链路的完成判定。

1. **立即调度自己的通知。** A 完成后即安排反馈；B/C 仍 queued、running、waiting 或重试不影响 A。继续复用 Resident 的结构化审阅和 Runtime 唯一群消息出口，叶子不得自行绕过 Runtime 发群消息。共享模型/执行资源可以有短时调度排队，但不能等待兄弟任务 Promise、所有结果收齐或 Resident turn/end；不承诺零网络延迟。
2. **移除已确认无关输入的全群门禁。** 统一调整 `hasPendingTaskInput`、`completionPreflight`、`group_reply_submit` 以及 Store 决策准入，完成/通知只依赖本 Task、执行事项、真正影响目标的输入和相关回复。不能仅删除某一处检查，留下另一处继续拦截。
3. **未归类输入按有限快照处理。** 通知请求冻结此时已接收入站的序号和事实版本边界；该边界内尚未归类的输入，先完成影响归类，再判定能否发送，不必等待它们产生 Task 结果。不能因为之后不断到来无关消息而反复扩展旧通知的边界。通知表达的是该快照下已核验事实；发送提交前若已有明确影响 A 的取消/范围/授权变更，仍必须使旧通知失效。超出边界的新输入是后续事件，不能宣称旧结果已经包含它；同一时序中的取消与发送须按持久化操作先后裁决。
4. **相关性过滤必须同时作用于请求身份和刷新。** `reviewRequestIdentity`、`scopedCandidates`、`refreshReview`、只读快路径的候选指纹都按事项/Task/实际替换关系计算。共享原 messageId 只能提供溯源或查询候选，不能单独让 B 的新回复改变 A 的审阅身份或强制重新审阅。仍保留真正同事项订正、替换和发送人检查。
5. **通知恢复独立于其他事项。** 稳定业务身份沿用 Task、执行轮次、结果身份和事项来源；同一结果重试保持同一 Outbox。A 完成后、Outbox 前崩溃能够恢复通知，Outbox 后崩溃通过发送记录和群回读去重。A 发送失败只恢复 A 的通知，不重跑 A 业务或阻塞 B/C 的通知。
6. **发送前复查与待发失效。** 版本核验不能只发生在 Outbox 写入前；`prepareOutbound` 还需验证 A 的当前执行轮次、结果和事项来源。新 schema 为待发通知增加 superseded 状态及失效依据；已经被取消/重开/订正的待发通知转入此状态并排除自动重试，按最新有效结果生成通知；已发送的旧结果作为历史保留，必要订正走既有审阅链路。检查仅针对 A，不能借机恢复全群 pending 屏障。
7. **区分业务与投递结果。** 分别展示“执行/验收完成”“通知待投递”“群回读确认送达”；三者不能互相替代。任一事项的失败或需人介入也可以独立反馈自身情况。该要求不扩大成每个内部 checkpoint 或周期性状态都发群消息。
8. **内容只报告当前事项。** 例如“审核草稿方案已完成：……”，不默认拼接其他事项的推测状态，也不为等待统一汇总延迟反馈。后续用户明确要求汇总时再按实际状态汇总。

发送层已有事件独立触发及批量 `Promise.allSettled`，应优先复用并验证。需要的是事项来源和相关性边界，以及单条失败/慢回读的隔离，不是新增全群串行通知队列。

### 5.6 入口、读取预算和材料边界

- 新协议必须覆盖普通群消息、`group_topic_route_review`、Web `submitWebTaskInput`、内部输入、历史迁移以及只读决策快路径，不能只修改普通 group_decision_submit。Web 明确的一次 Task 操作可由 Host 生成一个输入 unit；其附加背景不自动授权其他任务。
- 路由与 Topic 决策是不同读取阶段。超长单消息/引用/附件在路由阶段也要有固定来源分页与已读证明；未读完可能包含目标或范围的部分，不允许声称完整拆分。Host 输出给模型的分页必须保留原文坐标，不能让分页后的偏移冒充原消息偏移。
- 路由输出的单位数量、范围/背景和工具返回整体受预算约束；超出单次提交预算时，允许在同一冻结快照暂存分段结果，最后一次原子接受完整路由。在完整校验前不执行部分 unit，也不静默丢弃尾部需求。普通短消息仍只有一次提交，不增加固定的模型往返。
- 文本范围使用可校验原文锚点；实现时验证中文、重复句、表格、Markdown、emoji、没有换行的长句，不依赖模型准确心算 UTF-16 下标。服务端根据明确且唯一的来源锚点解析并持久化范围；锚点缺失或歧义应要求修正来源，不能宽松搜索后随意命中一段。
- 附件/引用中的多事项可以有多个 unit 指向同一来源文件或消息；保留页码、段落等可核验位置和权限范围。阅读范围不明、材料不可访问时，保留不确定性，而非把它们统称无关噪声。

## 7. 已存在合并 Task 的处置

仅更新路由不能修好 #1066：它已接受的消息事实被消费，原 Task 的 objective 和固定 topicRefs 仍覆盖三个事项。简单重放还可能重复回归或发群确认。

后续实施若包含修正历史任务，应形成可读的拆分计划：

1. 读取旧 Task 的实际叶子状态、已完成证据、批准计划、待执行动作和通知记录。
2. 明确原任务与三个目标任务的承接关系，逐项记录哪些成果可继承、哪些尚未完成；不能按一个总状态给三个任务都判完成。
3. 对仍活动的合并任务受控停止，核验执行真正停止后再启动替代任务。沿用取消语义保留“因事项拆分停止”的记录，不能把取消标成业务验收通过。
4. 在新的事项归属和已执行效果映射下创建或续接三个独立任务；复用原始授权、已验证成果和通知回执，避免重做已完成业务。
5. 跨 Task 的迁移保存稳定操作身份和可恢复进度；失败时停在可查询状态，不允许旧/新任务同时处理同一未完成动作。

本轮不执行上述变更。历史语义修正应作为显式操作，与机械存储升级分开。
