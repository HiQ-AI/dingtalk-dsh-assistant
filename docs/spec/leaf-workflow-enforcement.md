# 叶子通用提示与任务流程按需加载

日期：2026-09-08。状态：待实施方案。本轮根据用户最新要求，将单段提示词调整为“通用提示词 + 可配置任务流程库 + 系统提示词索引”。本文件为讨论中的设计草案；不表示配置界面、加载工具或版本校验已经上线。

## 目标与职责

叶子会话提示词承载所有任务通用的处理规范。不同工作的详细处理流程和验收要求分别保存，系统提示词只列轻量索引，叶子按需加载相关正文。用户通过插件配置即可新增场景，不需要修改代码、发布插件或把全部流程拼进一个长提示词。

主会话负责理解诉求、话题管理、任务派发、补充信息、依赖与授权协调、反馈结果。话题承载持续讨论和事实。叶子根据原始任务选择流程，负责专业执行、验证与交付。Host 负责配置、加载、上下文版本、通用状态协议和可靠通知，不理解或硬编码各类业务步骤。

## 方案选择

1. 全部正文常驻注入：实现简单，但每类任务都携带无关流程，不满足上下文目标。
2. 主会话预先分类并替叶子选择唯一流程：会扩大主会话职责，遗漏或混合场景也容易被分类锁死，不采用。
3. 通用规范常驻、流程索引常驻、叶子自主按需读取正文：采用。无需向量检索、关键词路由引擎、嵌套流程依赖或固定业务类型枚举。

## 一、插件配置

保留现有“叶子会话提示词”，用途调整为通用规范：理解任务、授权边界、选择流程、执行与验证、结果报告、何时请求主会话协调。它不再建议存放所有具体场景正文。

新增“任务流程提示词”列表，每条配置包含：

| 字段 | 用途 |
| --- | --- |
| 名称 | 例如需求开发、问题排查、调研分析、文档整理；名称由用户自由定义 |
| 适用说明 | 简短描述何时使用，必要时说明不适用情况；这是模型选择的主要索引信息 |
| 提示词正文 | Markdown 自然语言，描述具体流程、验收、异常及分期交付边界 |
| 启用状态 | 是否进入当前可用索引，停用不删除正文 |

Host 生成稳定 ID 和条目修订号；改名不换 ID，条目实质变化更新修订。正文不复制到索引，适用说明不从全文每轮重新抽取。用户明确维护简短说明，可预览实际索引，防止摘要自身变成长手册。

区分配置保存的并发版本与任务执行的失效依据：前者用于防止配置覆盖，后者分别取通用文本摘要、索引内容摘要和已选正文修订。索引摘要只覆盖 ID、名称、适用说明和启用状态，不纳入全部正文修订；否则修改一条未选正文也会让所有任务失效。这些摘要由 Host 派生，不新增用户填写字段。

配置界面支持新增、编辑、启用/停用、删除条目，显示名称、适用说明和状态，编辑时再展开正文。复用现有配置读写路径；通用提示与流程条目分别保存对应字段，避免携带陈旧的模型、代理等无关配置。列表修改带修订检查，冲突返回刷新提示而不是覆盖他人更新。

原有自然语言规范继续适用于每条正文，推荐“适用范围—处理流程—验收标准—异常处理—完成边界（可选）”。这只是写作模板，不是固定业务 schema，也不要求把步骤另存为规则表。

## 二、系统提示词索引

叶子默认模型输入由以下内容组成：通用内置协议、用户通用提示词、当前任务及必要上下文、已启用流程的轻量索引。各流程正文默认不注入；主会话无需常驻这份流程库。

索引示例：

```text
可用任务流程（根据任务选择，使用 load_task_prompt 读取后再执行）：
- dev-delivery｜需求开发与修复｜适用于已授权的代码实施及交付；仅分析原因不适用
- investigation｜问题排查｜适用于定位原因并提交证据和建议
- research｜调研分析｜适用于资料核对、方案比较和研究结论
```

稳定 ID 为工具定位依据，名称和适用说明用于模型判断；当前选中条目的版本作为 Task 专属的短元数据展示，不把全库正文修订拼进公共索引。名称、说明、正文和启用条目的索引总量都须有可验证的大小上限，界面展示占用，保存时明确反馈超限，不能静默截断或隐藏已启用条目。具体上限在实施前用当前模型的输入预算和极限用例确定并记录；不能只限制单条说明而放任无限条目累计。第一版不另建搜索分页层，超限明确要求精简或停用无关条目。

## 三、正文按需加载

新增叶子专用只读工具 load_task_prompt({ id })，按服务器当前配置查找，返回 id、名称、修订、完整正文。复用现有工具注册和 Task/session 归属校验，不接受任意文件路径或外部 URL，不新增执行器。

执行路径：

1. 叶子结合原始诉求查看索引，选择零个、一个或少量互补流程；不能为了保险全部加载，也不能只凭名称中的关键词强行分类。
2. 调用工具读取正文，确认实际适用性；发现不适用可改选，并在任务记录说明必要的原因。
3. 按正文制定本任务计划并执行验证。未命中时按通用规范和用户要求执行，不因没有流程条目而阻塞任务。
4. 组合流程时去重；冲突能根据原始用户指示消解则自行处理，确需范围或授权决策才请求主会话协调。
5. 完成前对照已选择的当前有效流程自检，提交结果、证据及不足。已读取不等于已遵循，更不等于已验收。

首次通过工具读取候选正文；叶子确认当前采用的流程后，Host 根据 Task 中持久化的流程引用，在唯一的“当前任务流程”动态 system prompt 区块中渲染对应正文。该区块在每次构建模型请求时重建，因此压缩或恢复后的请求自然包含当前流程，不要求叶子重新调用加载工具。

区块按稳定 ID 去重并整体替换，不在历史消息里反复追加；历史工具读取记录可保留用于追溯，不为了去重改写会话日志。首次读取与当前区块可能有一次内容重叠，需计入上下文评估，但不会随每次压缩不断追加副本；始终不注入未选中的全库正文。

Host 记录实际加载的 Task、执行轮次、输入版本、流程 ID、修订和工具事件引用；不信任叶子自填“已经加载”。区分历史读取记录与当前适用流程，不能把读过的全部流程永久绑定为当前要求。只保存引用和必要元数据，不在 Task、Topic、主会话消息中复制整份正文。缺失、停用或删除的 ID 返回明确状态，不静默落到另一条同名流程；正文过大时明确反馈，不能将截断内容伪装成完整加载。

当前流程引用就是本轮任务处理类型的可执行定位信息，可包含一个或少量条目；不要再维护一份与引用可能不一致的固定 taskType 枚举。现有 workType 只在结果中可选记录 development/non-development，不能定位用户自定义的排查、修复、调研等提示词，因此仍需新增持久化 promptRefs。

### 选择与计划的登记入口

load_task_prompt 只负责读取并留下实际读取记录，不因读取就将条目设为当前必用流程。复用 submit_task_checkpoint 的计划提交/更新通道，增加通用的 promptRefs（ID 与已读修订）、选择/变更理由，以及叶子生成的 acceptanceCriteria、stageTasks。不新增独立的选择工具或业务流程状态机。

Host 校验所声明的引用都已通过工具结果或动态系统区块实际交付给该 Task，绑定当前输入版本后保存当前选择；明确提交空列表表示未选择场景，需要简短理由，不能用字段缺失推断“没有适用流程”。简单任务可以在 submit_task_result 中一次提交同样的选择和简短验收记录，不强制先制造计划 checkpoint。

已有计划的更新只替换当前执行安排，保留历史和变更理由；不修改用户原始目标和授权。正文读取记录可跨普通上下文补充复用，但当前适用性需在目标/授权改变后重新确认；正文未变且仍完整可见时，不为确认适用性而重复加载。

结果逐项对应当前任务的验收条件，并提供结论和证据引用；Host 校验遗漏、引用及版本。它仍不能证明模型是否漏选了配置流程，或虚构了“不适用”的理由；这些由真实场景回归和执行证据核验发现，不能宣称已经由 schema 杜绝。

### 任务目标变化与流程切换

任务表示一个可交付的工作事项，流程是当前目标的处理方式，不把“排查/修复/调研”等设成不可变任务类型。流程选择必须在目标或授权变化时重新评估，而不只在创建 Task 或编辑配置时发生。

三种设计取舍：始终原任务推进会让独立事项混在一起；始终新开任务会割裂自然连续的工作并重复交接；按交付事项是否仍为同一个决定延续或拆分，采用第三种。判断依据是交付边界、依赖与执行分工，不单看流程名称、同一群或话题关键词。

| 场景 | 推荐动作 |
| --- | --- |
| 排查仍在执行/等待，用户明确要求修复同一问题 | 原 Task 修订目标与授权，增加 inputVersion，重新规划并选择修复流程；不为换流程新开 Task |
| 排查任务已完成，后来要求修复同一问题，仍按同一事项跟踪 | 原 Task 重开新执行轮次，增加 runSequence 和 inputVersion，保留排查交付历史 |
| 一次排查产生多个可独立修复的问题，需要并行推进、不同分工或独立验收 | 创建关联的修复 Task，各自交付；通过 Topic 和来源 Task/证据引用关联，不复制整段历史 |
| 用户明确要求另开任务，或修复形成另一个独立交付事项 | 新建关联 Task，按用户要求执行 |

“同一问题”也不等于永远使用同一 Task。长期后出现的新故障、不同系统的新目标应重新判断关联与交付边界，不默认重开旧事项。排查本身满足用户要求后应正常完成，不能为可能出现的未来修复授权一直停在 waiting。

群聊确认后的标准路径：

1. 主会话识别原消息、引用及有效回复，确认是对该任务的修复授权，更新相关 Topic 和任务目标。找到根因不等于取得修复授权；“收到”“原因对了”等回复也不能自动解释为同意修复。一次明确授权生效后不重复询问。
2. Host 复用 task-context 或 task-reopen，原子修订任务版本，并可靠向叶子交付新输入。旧版本的完成提交不能覆盖新目标；重复消费同一确认不能产生多个修复任务或重复执行轮次。
3. 叶子重新判断索引中的适用流程，读取修复正文，更新当前执行计划和验收条件。历史“仅排查、不修改”成为旧授权范围，不能继续压过用户的新授权；修复也不能被理解为未授予的生产发布权限。
4. 原来的定位证据和已验证事实按当前版本/环境核验后复用，不必重做完整排查；排查已完成不表示修复的实现、回归或交付验收已完成。
5. 保留旧目标、授权来源、阶段结果及其证据，当前要求明确标记属于新输入版本。原流程可作为历史或仍适用的辅助流程，不与新流程无差别叠加；切换不承诺能抹去已有模型历史，但不得继续把失效规则声明为当前约束。

已有实现可复用：runtime.js:1132 的 reopenCompletedTaskInternal 保存 runHistory 后重开；runtime.js:1152 的 appendTaskContextInternal 更新 inputVersion 并记录失效检查点。仍需补齐流程选择失效/重评估和验收更新：当前目标变化而未显式给出新标准时会沿用原 acceptanceCriteria/stageTasks，不能据此用“已查明原因”完成修复任务；应保留为历史，由叶子形成新目标的当前计划。

Task 与叶子 Session 分别处理：业务上延续同一 Task，不要求模型会话永不更换；正常延续/恢复既有叶子，必要的会话恢复沿用现有机制，不为流程切换额外建立一套会话类型。

## 四、配置更新、压缩与恢复

- 通用提示更新：活动叶子下一次模型请求使用新文本，并收到需要重新考虑计划的简短通知；旧上下文不能直接提交完成。
- 新增、启用或修改适用说明：刷新轻量索引，叶子按当前剩余任务重新判断是否需要加载；不把新正文广播给全部任务。
- 正文更新：只有当前选中该流程的活动任务，在下一请求的系统区块中替换为最新正文并得到简短变更提示，重新自检计划；不要求再调工具。未选中的正文变化不影响其他任务。
- 停用/删除：从索引移除，已使用该条目的活动任务收到失效信息，重新判断流程依据；不能因条目消失就声称业务已完成，也不自动撤销已经发生的操作。
- 加载与编辑并发：工具按同一快照返回完整正文与修订；结果提交在写入前检查通用提示/索引在实际模型请求中使用的版本及当前选中条目的修订。发现过期，要求同步并重新自检。版本以 Host 的请求记录为准，不能由叶子填“最新”或仅将通知加入队列代替实际交付。
- 新建、恢复和重开：索引始终从当前配置读取。相同任务目标的会话恢复，直接按持久化的当前引用重建正文；新建任务无选择时只注入索引。重开或目标修订时，历史选择仅供参考，由叶子按新目标确认或切换，不能把“会话恢复”一律当作重新选型。
- 任务目标或有效授权改变：即使配置完全未变，也重新判断当前适用流程；旧输入版本的加载状态不能代替对新目标的选择和验证。
- 上下文压缩：不改变 Task 中的当前流程引用。下一次模型请求由 Host 根据这些引用重新渲染正文，与正常请求共用同一条路径。已取消选择的条目不恢复；不跟踪历史正文是否可见，不增加 needsReload 状态或强制工具重读流程。

用真实 request/header、request/context 验证压缩前后及恢复后的请求均包含当前选中正文，且只有一个当前流程系统区块；不再把逐条检测工具正文可见性作为实现前提。

这里的代码保证限于标记上下文失效和拒绝过期的计划/结果提交；“任何业务工具执行前都必须先读流程”属于叶子的执行指令。叶子保持完全权限，本方案不引入全工具拦截，不能声称 Host 可以阻止所有抢先执行的动作。

选中正文会占用固定系统上下文，须将通用提示、索引及所选正文的总量纳入容量检查；不能期待压缩历史就能缩小超大的系统提示。一旦最小有效上下文仍装不下，应明确反馈容量问题，要求精简流程或将操作细节引用到现有 runbook，不反复压缩、不静默省略验收内容。

更新不强杀已运行命令，不自动重放副作用，不批量重开已完成任务。新要求下哪些既有结果可复用，由叶子结合实际证据判断。

## 五、执行协议与职责修复

主会话派发原始诉求、事实和协调边界，其生成摘要不能裁掉已授权任务中适用的流程。叶子在授权范围内补齐计划并持久化；不需要主会话审批每个专业步骤。

Host 校验任务/输入版本、配置与加载状态、合法状态转换、明确协调阻断和结果协议；不将 workType 当作启用/关闭门禁的开关，不解析 PR、UAT、报告等具体业务条件。

普通进展 checkpoint 仅记录事实，需要协调时才请求主会话；guidance 是否阻断及影响范围必须明确。取消所有任务都需两个 checkpoint 和主会话总体专业验收的完成前提，但保留未完成验收项、有效协调阻断、原始授权及输入版本的完成校验。简单任务仍可直接执行、验证和提交；明示的外部验收按任务要求办理。

协调阻断按 requestId、任务版本和影响范围保存，普通进展更新不能覆盖它。解除必须关联相应回复或实际补齐的事实，不能以“最新 checkpoint 已 acknowledge”抹掉此前阻断。受阻与否不取决于最后一条事件。

完成状态与通知事件可靠衔接。主会话收到精简结果、证据索引和后续协调事项，详细执行记录留在 Task；通知失败重试，区分已登记、已投递、已确认。叶子继续保持完全权限及现有消息出口边界。

默认“通知主会话”定义为 Host 在业务结果被接受时可靠登记并推进结果通知，不将实际送达作为叶子提交 completed 的前置条件。业务完成和通知待投递可以同时存在，且分别展示。若某任务明确要求先取得主会话/用户的确认，叶子应在最终提交前用协调通道发送待确认材料，收到回执再提交结果；不能借用仅在 completed 之后触发的通知链等待前置确认。

## 六、迁移及实施范围

新字段 taskPrompts（拟名）默认空列表。升级保留 leafSessionPrompt 原文，不能自动猜测拆分后覆盖或删除用户配置；这意味着旧长文本未拆分前仍会全量注入，不能提前宣称获得上下文收益。迁移当前配置时，应在可审阅的编辑结果中保留通用规范，把具体流程原文移入对应条目并补充简短适用说明，然后核对无遗漏、无重复；本次方案讨论不修改真实配置。

配置迁移是一次原子保存：同时写入精简后的通用提示和新流程条目，随后发送一次变更通知；日常编辑仍只提交修改的字段。不能先删除通用文本里的流程再分多次新增条目，使活动任务在中间状态丢失引导。迁移失败恢复原配置，不保留半份新结构。

去掉强制专业 review 时，明确迁移已有活动任务：保留目标、既有计划、已提交结果与真实授权阻断；不能自动把旧总体 accepted 当成新协议验证通过，也不能默认放行全部旧任务。终止/作废旧完成审阅请求，沿用当前 Task/轮次通知叶子同步新协议并重新提交；历史完成任务不追溯改写。新必需元数据在活动任务恢复时建立，不能以“旧数据无字段所以跳过校验”长期旁路。

涉及 store.js 的流程条目和加载元数据；runtime.js 的配置更新、索引、工具及恢复；task-result.js 的必要版本检查；topic-runtime.js 的协调职责调整；client.js 和生成的 web-client.js；README、配置手册与运行/迁移说明。复用现有存储域及 HTTP 入口，是否需要升级域版本按实际 schema 演进机制验证，不凭空增加迁移层。

实施先完成配置存取和按需加载主路径，再完成版本/压缩恢复及状态边界，最后部署本地验证。只新增界面、只证明 load 工具成功或只跑解析单测，都不能宣称本目标完成。

## 验收方案

1. 配置 CRUD、启停、稳定 ID、修订和重启持久化；旧文本不丢失，空流程库可正常工作。
2. 保存一种此前不存在的工作流程，无代码修改即可索引、选择和加载。
3. 多条正文设置不同标识，检查真实首次模型输入只有通用文本和全部轻量索引，没有任何流程正文。
4. 选择其中一项后，只出现对应完整正文；未选择正文不出现在叶子 system/history、Topic 或主会话输入中。
5. 分别验证开发、调研、文档以及未命中任务；多场景组合不全库加载，简单任务不强套阶段。
6. 配置更新后仅相关正文系统区块被替换；索引变化、并发编辑、停用/删除返回正确状态；过期结果不能直接完成。
7. 真实压缩/裁剪及重启恢复后，Host 自动注入当前选中正文，不需要额外加载调用；始终只有一个当前流程系统区块，历史取消选择的流程不恢复。
8. 主会话繁忙不阻塞正常专业执行；实际协调阻断、用户范围限制和可靠通知仍有效。
9. 重放此前开发任务漏交付的案例，检查选择、读取、计划、工具执行和结果证据，不能将成功加载当作流程已遵循。
10. 在相同任务和流程库下对比全量注入与按需加载的实际请求字符量及可获得的 token 用量，报告索引、正文和重复读取各自成本；不虚构节省比例。
11. 排查中收到有效修复授权：同一 Task 更新目标、重选流程，新验收生效；原排查证据保留，旧版本结果被拒绝。
12. 仅定位到原因或收到模糊确认：不会未经授权执行修复；排查完成后可以正常结束，不为潜在修复一直等待。
13. 已完成排查后要求继续修复：同一 Task 新轮次，旧结果可回查；多项独立修复则建立关联任务，避免全部塞入一条顺序计划。
14. 流程切换与旧结果提交竞态、重复群聊确认：按有效版本收敛，不丢新目标，不产生重复任务；旧流程约束不会持续阻止已授权动作。
15. 加载后未选用的流程不进入当前要求；明确取消选择、空选择、选择未实际读取的 ID、普通补充后的内容复用分别有覆盖。
16. 仅修改其他任务使用的正文：不改变本任务索引内容摘要、不使本任务完成失效；更改适用说明则刷新索引并重新判断。
17. 普通进展不能抹掉尚未解除的协调阻断；取消专业复核后，缺少验收项或引用的结果仍被拒绝。
18. 单条正文、索引累计量及所选正文总量的边界用例：不截断，不靠反复压缩解决系统提示本身超限。
19. 通用文本与流程库拆分原子生效；已有待审阅任务升级后能继续提交；通知待投递不形成相互等待，真实前置确认仍有效。

## 实施前仍需实证的边界

方案层面已明确选择登记、版本失效范围和通知顺序。压缩恢复改为复用动态系统提示区块，不再实现正文可见性跟踪。实施时验证压缩后区块确实重建、流程切换只渲染当前引用，以及去除旧 review 等待后活动任务能正常恢复；长度上限经容量探测后定稿，不将未测数字写成已验证限制。

确定性测试证明存储、工具、版本和状态正确，真实模型行为评估证明具体场景中的选择与遵循表现。自然语言适用性、是否完整执行及专业结论仍有模型判断边界；本方案降低上下文开销和漏项风险，不承诺自动解决所有语义误判。
