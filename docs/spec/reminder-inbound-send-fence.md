# 入站订正与提醒发送补充修复

## 现场证据与目标

PR #253 已合并为 `bc57dccfda12dbeb8e54c3b30897ace2e03df1fd` 并部署。2026-10-23 本地真实群验收中，16:16:08 的过时时间请求在 16:16:19 已被用户订正，但旧澄清仍于 16:18:14 发出；随后订正成功，只有一项 16:22 提醒，无业务 Task，也没有再次询问日期。

现有发送事务只检查已形成的 `resolvedBy`。第二条已进入 durable source，但尚未完成归类/协调语义处理，所以此门禁太晚。模型第一条归类经历两轮 TRANSPORT 错误及约 30 秒恢复等待；第二条等待同群路由结束。通知 prepared 后约 0.25 秒即取得许可，不能把本轮前段网络延迟归因于旧发送队列。

到期提醒另被钉钉接口以外部 uuid 超过 128 字符拒绝，通知仍为 unknown。保留原通知及失败证据，不直接重放或改 SQLite。

本补充方案在首次线上失败后单独建立，保留原方案和第 5 轮失败证据。

## 实施边界

1. 对尚未领取发送许可的协调来源澄清/接纳回复，在发送事务内检查同群同作者更新的已准入来源是否仍在本轮判断中。存在则暂缓发送；语义确定后，订正使旧回复退役，不同事项使原回复恢复发送。不同作者、不同群、已开始/unknown/已送达不受此暂缓影响。
2. 复用已有持久来源、归类与协调事实，必要时只投影 Host 可核验的本轮判定完成事实。`needs_clarification` 已完成本轮判断，不能当作永不完成；`routed/settled` 的业务完成含义不能冒充判定结束。拒绝文本正则猜订正、固定等待后盲发或靠人工授权释放。
3. 暂缓不消耗发送次数，也不得缓存成永久拒发的 `notification.start` 幂等回执；重复扫描不得空转。后续判断完成后唤醒原投递路径，并在发送事务再次核验，避免入站竞争。
4. 现有 DWS 发送编译边界统一把超长外部幂等键映射为固定前缀与完整 SHA256，短键保持原样，内部通知 ID 不变。回读使用相同映射并保留历史证据识别，不改变 unknown 自动重发边界。
5. 不调整模型、网络重试或恢复时间配置；保留真实延迟分拆。新增代码分别走定向测试、PR 和受控本地部署，再用新测试消息验证，不补发历史测试提醒。

现场负回执核验补充：原失败完整记录平台 tool_validation 的 uuid 长度拒绝，许可/摘要/尝试身份一致且无 ACK/receipt。仅此严格合同可沿现有 notification.reconcile 结清 failed 并保留原证据；不为泛参数错误提供重发许可，也不直接写数据库。

## 验证

- 后续同人订正已入账、语义处理故意阻塞：旧消息不能发；订正完成后旧消息退役，只有新确认。
- 不同事项与新的待澄清事项完成判断后释放旧回复；不同作者/群不误阻塞。
- 暂缓后相同命令重试与重启可恢复；已开始和未知效果不重发；无新来源时即时发送不退化。
- 四类现有发送编译覆盖长键、128 边界、短键、稳定性和不同键不碰撞；真实回读匹配映射后的 uuid。
- 两包摘要、进程、健康、原配置回读，真实新群消息订正、独立 DWS 回读、到期提醒与端到端耗时分别留证。
