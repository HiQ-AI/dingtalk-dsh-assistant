# 独立 UAT 部署流程边界修正

## 现状与根因

当前 `task-uat-delivery` 在部署前要求同一工程 Run 的业务 E2E、开发 PR、UAT PR 和来源包证明。此门禁把“部署代码到 UAT”与“部署后业务回归、提测和验收”倒置：代码尚未运行于 UAT 时，不能要求 UAT 业务验收；独立部署请求也不应依赖先前必须由 Assistant 工程流程产生的 Run。其固定节点还有只回读既有合并结果的 `integrate` 效果，名称使人误认为它执行 PR 合并。

## 目标与合同

- 改为 `task-uat-deployment`，可单独发起，也可作为工程任务的后继阶段。登记 UAT2 `dataset-web` 和 UAT3 `dataset` 两个精确目标。
- 部署准入只需受信 Host 确认目标分支当前 SHA、唯一已合入该分支且 merge SHA 等于当前 SHA 的 PR、完整流水线扫描，以及目标与执行权限。PR 尚未合入时明确等待集成，不伪称部署流程自动合并。工程任务后继阶段可附带原 Run 工件与 Git tree 身份核对，但不要求业务 E2E。
- 节点为冻结目标→预检→按精确 SHA 构建/查询已有构建→回读构建制品→回读 Registry、Deployment、Ready Pod 与入口→形成“UAT 已部署”结果。已有同 SHA 成功构建可直接核运行态；失败构建走独立同提交重建流程，未知结果只对账。
- 部署结果只证明技术运行版本。业务 E2E、测试负责人提测和正式 UAT 验收分别登记，不能混入部署前置条件或被部署成功自动标为通过。
- 本机未有 `task-uat-delivery` 的持久 Run，可将新注册 ID 改为 `task-uat-deployment`；历史文档保留原始验收时点，不改写过去事实。

## 验证

隔离测试覆盖独立部署无工程 Run、工程后继阶段、未合并 PR、分支 SHA 漂移、已有成功构建、失败构建转重建、未知效果不重复触发、构建摘要与 Pod 不一致，以及“已部署”不等于业务验收。本地安装后回读目录、目标、运行版本；没有新授权部署任务时不为测试触发真实 UAT 构建。
