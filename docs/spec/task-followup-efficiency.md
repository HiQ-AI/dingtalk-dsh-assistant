# 等待中追问与执行效率修订

## 目标和当前证据

复盘“排查终审数据点击编辑后状态未持久保留”发现：人工实施确认期间的事实追问积压；实施会话跨阶段复用旧技能；低成本检查和夹具准备后置；验证完成后集中补材料。源证据在主检出 docs/acceptance/final-review-edit-retrospective/。本轮基于 origin/main 17491783，已包含 #261 群来源只读复核及 #264 约束、自检和交付异议合同，复用这些机制。

## 方案与范围

1. 在既有 humanReview 中处理相关事实追问：维持当前问题，读取已有证据后明确回复，而非把追问当作实施批准。先核对当前 wait 是否有通知出口，再改必要落账/发送路径；禁止借此写业务、委派实施或关闭未答问题。覆盖相关/无关来源、真实答复、权限和重复唤醒。
2. 沿原生 skill 工具和会话生命周期提供相关规则刷新：只考虑本会话实际读取或被委派的技能，变化/新阶段在安全模型步骤可见；不扫描全部技能或每轮注入全文，不改原生工具权限与加载实现。优先复用宿主技能发现/读取事件；记录实际版本证据，不能把通知视为已读。
3. 补强现有 business-development 的阶段重读、测试编译/依赖或页面初始化冒烟、失败分类和随里程碑归档；目标/PR指引只做必要收尾，不新增统一检查模板。脚本改动只为可验证重复问题，禁止自动推断并执行项目命令。
4. 统筹回答关联任务问题先核实各版本已实施/未实施部分；巡检针对真实剩余工作纠偏。必要验证完成后明确剩余交付，不将未覆盖边界自动升级为新门槛。

## 验证和交付

本地相关存储/原生宿主测试，skill 结构及有意义的脚本/行为验证；保留失败和复验，沿原生依赖 profile。各成员仅修改分派文件，共享源码编辑串行整合。无需全仓测试、CI、真实发信、合并或部署。工作区既有未跟踪材料保留。默认新分支提交与 PR；外部已安装 skill 的修改留精确补丁和独立摘要回读。
