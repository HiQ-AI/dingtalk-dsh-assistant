# 消息工作流修订设计：节点上下文、耗时与恢复

日期：2026-09-23。核对源码：`38e968ec2b8467ac9c949e297db539d8276609ee`。

状态：设计修订，待实现验证。本文回应 `../acceptance/runtime-redesign/message-adversarial-review.md` 的 MR01—MR12 和节点效率审查；没有取得新链路性能结果。

本文完整替代 `runtime-message-workflow.md` 的消息设计；旧文件和审查报告保留原样。执行、效果、租约和工件基础沿用 `runtime-execution-redesign-v2.md`，其中固定单 Processor 的约束由本文的 S/R/I 契约替代。唯一进展记录为 `../acceptance/runtime-redesign/goal.md`。本轮只修订设计，不修改运行代码、部署或操作业务任务。

## 1. 决策与实施边界

保留三个逻辑判断节点：**S 拆事项、R 关联话题、I 判断意图**。改进重点是每个节点拿什么、何时可以开始、完成后交什么，以及错误只退回哪个节点。代码负责材料、校验、持久化、调度、状态查询和通知；不再让常驻、话题、协调 Agent 反复理解同一请求。

### 1.1 选择与反证

| 方案 | 取舍 |
| --- | --- |
| 群或话题长期 Agent 包办消息和任务 | 不采用；业务与新消息竞争同一上下文、执行槽和恢复过程 |
| 多角色 Agent 逐层理解、审核、汇报 | 不采用；增加重复上下文及往返，责任无法靠会话名隔离 |
| 一个模型一次完成拆分、关联、意图 | 保留为对照；可能因请求固定开销而更快，但上下文并集和整包重算可能更差，不能先验认定 |
| S/R/I 独立契约，确定性代码短路，事项有界并行 | 采用；可以定向提供材料、纠正和恢复。是否更快须在同等质量与负载下验证 |
| 全规则分类 | 仅用于完整结构化操作或精确命令；关键词不能可靠理解否定、条件和多事项 |

逻辑节点不等于固定三次模型调用。代码能证明结果时直接产出同型结果；有语义判断才调用窄模型。首版不跨 S/R/I 融合模型请求，允许后续用相同契约做对照实验，不能用减少调用数代替耗时结论。

### 1.2 复用与缺口

当前已有 execution 控制库、节点会话、代际/租约、候选工件及部分效果适配；当前 Controller 仍是固定顺序节点。它尚未提供逐事项消息运行器、源消息控制屏障、完整暂停、本文切换协议或新消息实测。

新消息运行器复用同一控制库和调度基础，只增加预定义状态转换及有限 handler，不造通用 DAG/BPMN 平台。MessageRun 不冒充用户业务 Task，Topic 是持久业务事实而非必须在线的模型会话。无需 Docker；插件模块通过现有 Host 注册，不能假定放入 `.agents/plugins/*.ts` 就会自动生效。

## 2. 主流程与时间边界

```text
接收并落盘 ── 精确结构化操作 ───────────────┐
    │                                      │
    └─ 骨架快照 → S 完整拆分                 │
                     ├─ R(A) → I(A) ────────┤
                     ├─ R(B) → I(B) ────────┤→ 逐事项接纳 → handler
                     └─ R(C) → I(C) ────────┘                ├─ 状态/控制
                          ↑ 局部补材料/纠正                    ├─ 问答/调研
                                                           └─ Task Workflow
实际回执/结果 ───────────────────────────────→ 通知准备 → 发送 → 读回
```

- 一个已去重的消息版本对应一个 MessageRun。首版不把多条自然语言合成一个 S 输入；接收批量写入不改变每条的处理身份。
- S 必须覆盖当前消息全文及适用的共享限制，随后各事项独立推进。R(A) 未完成不挡住 R(B) 或 I(B)；共享条件未明确的相关事项不能提前执行。
- `decisionDeadline` 截止于事项的有效接纳或明确处理归宿，不包含业务长任务完成、附件供业务执行使用的准备及通知送达。后面各自有独立生命周期与计量，不能因此从收到消息至送达的墙钟中扣除。
- 消息接纳、Task 建立、首个有效业务活动、有用答复准备、平台 ACK、实际送达分别记录。只说“已收到”不计有用答复；只建 Task 不计已开始执行。
- 已完整且独立的 `/cancel task-id` 或受认证控件可代码直达；“/cancel A，等等先别取消”作为整个自然语言输入经过 S，不能执行前半句。

接收时仅用代码可确定字段选择调度标签：已认证、有相应修订/控制资格且可靠关联 Task 或待处理源的输入标记 `linked_pending_input`，使用30秒首次窗口和待判控制预留；它可能最后被判为查询、补充或取消，入队前不猜意图。其它自然语言使用普通45秒窗口。标签/时钟入站即固定，不增加前置分类模型、不在 I 完成后追溯选择更短期限。纯查询判定后仅解除本输入造成的屏障。

## 3. 每个节点的输入、产出和启动条件

### 3.1 节点合同总表

| 节点 | 必需上下文 | 禁止默认携带 | 开始条件 | 持久产出与完成边界 |
| --- | --- | --- | --- | --- |
| receive | 原事件、当前正文、认证主体、渠道身份、引用/媒体 ID、发生和接收时间 | 下载后的附件、历史话题、模型提示词 | 原事件已通过入口认证和体量限制 | MessageRecord、版本、seq、去重 receipt、可确定的源/Task 屏障；提交后才确认可靠接收 |
| prepare | 当前消息及水位、最近30条的记录/覆盖、引用索引、资源状态 | 全部话题正文物化、全量附件下载、预先调用模型总结所有历史 | receive 已持久化 | 骨架 ContextSnapshot、资源 manifest；splitReady/linkReady/intentReady 分开推进 |
| S | 当前全文、必要指代原文、否定/共享限制、附件身份及用途 | Task 执行流水、全话题目录、工具和工程/审批规则 | splitReady；所有可能影响全文边界的缺口已解决或显式产等待 | MatterSet、来源覆盖、文本目标/限制、未决同指、依赖；不决定业务 Task 身份 |
| R | 当前事项原文及限制、引用映射、有限候选身份卡 | 再次传全部30条、所有候选完整聊天、工程日志 | linkReady(unit)，S 版本有效 | existing/new/context-only/unresolved 绑定及依据、目标/run/result 候选 |
| I | 本事项原文、主体、有效绑定、适用目标/限制、必要当前状态/请求事实 | 无关事项、完整 Topic、全部前序输出、技术实施计划 | intentReady(unit)，R 有效或明确 conversation 查询范围 | 意图、参数建议、执行材料引用/缺口、依赖、回复必要性；不制定工程方案 |
| accept | 有效节点结果身份、预验证参数/工件引用、必要现时版本、权限、幂等键 | 模型对话；事务内读大文件、调连接器或模型 | 该事项决定完备，事务外材料验证完毕 | 同库写归属、命令/拒绝/无动作结果、receipt、派发意图及屏障转换 |
| dispatch | 已接纳命令、handler 版本、TaskInput/限制/工件/依赖引用 | 群30条、分类推理、重新解释“属于谁” | 当前资格有效、依赖满足、相应资源可领取 | handler 回执或工作流绑定；不在事务/控制槽里等待 Agent 启动 |
| answer | 问题、明确选择的事实/run/result、可披露投影 | 向工作 Agent 请求进度、重跑 S/R/I、完整工程历史 | 查询选择已确定、必要事实可读 | 状态由模板回答；复杂结果解释才用独立受限语义节点 |
| notify | 真实 receipt/结果、因果序列、目标会话、允许披露的事实引用 | 全 MessageRun、其他事项结果、固定回复审核 Agent | 当前事项有可通知事实 | 通知意图、发送尝试、ACK、读回证据分别持久化 |

脚本承担 receive/prepare、检索与投影、结构/schema/来源校验、预算、接纳、派发、状态回复和通知。S/R/I 的开放自然语言判断及必要的问答/材料语义提取仍使用模型，不能把 JSON 校验当成语义正确性的证明。

### 3.2 可执行的 ContextContract

每种节点的版本化定义至少含：

```text
requiredFields / optionalFields / forbiddenFields
inputBudget / outputBudget / contextExpansionPolicy
readinessPredicate / outputSchema / allowedNextStates
```

实际发请求前检查完整 envelope，而不是只检查正文长度。输入记录含 `snapshotId、nodeVersion、unitRefs、sourceSpans、dependencyVector、resourceRefs、omissions`；每个 sourceSpan 有消息版本/字段/起止范围/hash。记录真正发给 provider 的材料与 usage，不能写“已读取全部上下文”却只发摘要。

- requiredFields 缺失：不领取模型槽，生成定向材料请求或等待结果；禁止静默截断后继续。
- optionalFields：按该节点价值和预算裁剪，保留省略理由及定位引用。否定、动作作用域和共享限制不得作为普通可选背景裁掉。
- forbiddenFields：由投影构建器白名单阻止进入，不依赖模型自觉忽略。
- 模型无任意 shell/网络/业务写工具；返回 typed `needs_context` 后由材料节点补指定字段，再恢复同节点。补取次数及语义再调用记共同预算。
- 下游接收类型化事实与来源引用，由代码拼最小原文；不把整个 MatterSet 或 TopicBindings 序列化给每个 I。
- 参数只作为参数；不能把候选里的提示词、历史命令或附件内容提升为节点规则。

材料缓存只节省 I/O。相同段落进入 S/R/I 三次仍计三份输入；provider 缓存命中只按实际 usage 统计，不把“本地命中”当 token 优化。

## 4. 材料骨架与分层就绪

### 4.1 最近30条、引用和完整话题

当前消息全文单列；前30条指本群在该消息接收水位之前的最近30条可见对话。包含已送达的助理回复，排除待发草稿；自发回显只补送达事实，不触发业务。保留平台时间/本地 seq/回填标记，历史抓取不能重放旧指令。

30条是代码默认准备的上下文集合，不是三个节点共用的模型大包。S 只取拆分所必需的背景；R/I 各取其投影。不能证明被省略对话无关时保留缺口并定向补取，不能凭窗口长度断言上下文完整。

引用按渠道/账号/会话/消息 ID 查原记录，出站引用经送达映射到 unit/topic/task/run/result。缺失项由连接器补取；引用链去重、防循环、限深和分页，保存游标及缺口。一个原消息包含多个事项时返回候选集，不默认“这个”指全部或第一项。

命中话题后冻结 revision，完整消息清单和原文均可按固定版本取得。完整 manifest 的远程枚举本身也可能慢，初始记录必须允许 `manifest_pending`，只先登记已知范围/游标。不得为了取得“全量目录”阻塞已满足需要的节点，也不得把局部清单标成完整。

原文只按需物化。有效目标/限制/最后决定来自已接纳事实及来源；历史无可信投影时，相关事项进入独立材料整理分支，逐段提取有来源的事实/冲突，不要求无关事项共同等待。长历史的语义充分性仍是评测盲点，schema 不能证明没有遗漏。

### 4.2 资源与三个就绪谓词

```text
Resource = resourceRef + sourceVersion + contentHash?
         + state(pending/available/unavailable/denied)
         + requiredBy + blockingScope + coverage + nextWakeAt?
```

`requiredBy` 由可信节点合同和已验证的具体语义缺口确定，不是附件默认全部必读。`blockingScope` 为 message / unit-set / unit；范围不明先保留相关歧义，不能为了并行强猜只影响 B。

| 就绪 | 必要条件 | 不必等待 |
| --- | --- | --- |
| splitReady | 当前正文完整可用；拆分所需引用/指代和可能共享的限制有可见证据 | 明确只供某目标后续实施的附件全文、全话题历史、所有候选状态 |
| linkReady(unit) | 有效 S 单元及适用限制；引用映射和候选关键判别信息足以关联，或可以明确产 unresolved | 其他事项的候选、业务执行工件 |
| intentReady(unit) | 有效绑定；本次意图依赖的目标/状态/活跃请求事实足够 | 不影响“要做什么”的实施材料、技术方案、无关进度日志 |

例：“查 A 进度，另按附件调研 B”。正文能证明附件仅归 B 时，S 可完成，A 继续 R/I/answer；B 可以先接纳“按附件调研”及 artifactRef，业务节点等待附件，不必等下载才能判断这是调研。若附件是“以下所有任务的共同限制”，受影响事项必须先取得限制，不能接纳忽略限制的意图。

S 可输出某单元 `needs_context`，但只有全文已覆盖、与其他单元及共享条件边界有证据时才允许其他单元前进。正文自身缺失、全局指代或共享限制未解时，splitReady 不成立；不能只执行已看到的前半段。

超大正文无法装入合同：先代码分段保持源位置，再做独立且有预算的材料整理；全覆盖/跨段限制合并之前不发布可执行 MatterSet。不得把超大消息切成多个独立授权以绕过全局否定或预算。

## 5. S/R/I 的职责、产出与纠正

### 5.1 S：文本事项，不抢做业务关联

`MatterSet = matterSetRevision + coverage + units + sharedConstraints + dependencies + unresolvedCoreferences`。

每个单元含稳定 `unitId、sourceSpans、goalText、actor/assigneeEvidence、constraints、contextNeeds`。源码范围覆盖所有当前内容，每段归为事项、共同限制、背景或明确无动作，不以换行/动词数机械拆分。“一个需求四个验收点”通常是一事项；三个可独立取消/验收的请求通常是三事项。

S 保留“单位不一致那个任务”和“生成单位修复”的两处来源及未决同指，不为识别别名重复 S。R 确定目标后代码建立执行组：只有目标、规范意图、参数/限制及顺序兼容，才能指向同一个命令；两个原单元都保留独立归宿映射。相同 taskId 的“继续修”和“先别发布”不是可吞掉的重复命令。

### 5.2 R：有判别力的小型身份卡

代码先查引用/稳定 ID，再查30条里的归属、活跃澄清、近期明确对象及有权话题索引。候选卡固定字段：

```text
topicId + taskId? + runId? + resultRef?
title + goal/entity keys + scope + state + relevantTime
explicitReferenceMatches + distinguishingFacts + sourceRefs + versions
```

`relevantTime/state` 用于“昨天已成功的”和“今天正在做的”消歧；不把状态、run/result 判别全部推迟给 I。候选数/字段体量受合同约束，超限必须定向检索更多判别条件；未选项不被悄悄当作不存在。

输出 `existing / new / context-only / unresolved` 及对象/理由源。引用只提供关联证据，不能推出任务启动/继续/授权。找不到目标不等于新话题；“继续”“补”“停掉”指代不清走澄清。群任务集合查询可输出 conversation 范围，不强制新建 Topic。

### 5.3 I：处理意图与参数，不做技术实施

输出 `actions[]、constraintRefs、requiredExecutionMaterials、replyPolicy`；每个 action 含 `actionId、ordinal、intent、target、arguments、dependencyRefs`。意图覆盖闲聊/事实补充/问答/调研/创建/修订/暂停/取消/恢复/状态/历史结果/重开/审批/澄清。actionId 由服务端按持久动作映射分配，模型的临时序号不充当幂等键。

同一事项可以有多个动作，如“停掉 A，然后告诉我停在哪里”：一次停止控制，后续查询依赖该控制的真实回执；尚未排空只能报告取消请求/对账状态，不能假报已停。查询失败不重放停止；动作各有回执和重试身份。只支持合同中固定的先后/成功条件，不运行模型自造表达式，不为了多个动作让 S 重拆同一目标。

参数必须来自合法来源或声明待确认；模型只选快照允许的目标，不能创造已有 Task/request ID。明确交给别人的事项登记无动作；讨论、反问、转述批准不能被执行。有效技术工作进入 Task Workflow 后由对应业务节点规划，不在 I 重读工程规则、拼完整执行计划或写最终回复。

### 5.4 只修正错误所属节点

| 返回类型 | 路径 | 保留/失效 |
| --- | --- | --- |
| needs_context | 材料节点→原节点 | 已有效的其他节点不重跑 |
| needs_relink | R→I | 保留 S/unitId；只失效相关 R/I，提供反证与所需候选字段 |
| needs_resegmentation | S→受影响 R/I | 必须提供原文边界/限制反证、旧新单元映射；不能以“另一个别名”触发 |
| schema_invalid | 原节点一次受预算约束修正 | 不要求业务节点重做；禁止无限 repair |
| needs_clarification | 持久澄清请求→原 blockedNode | 用户答复消费后恢复，不创建新的独立任务 |

每个单元最多一次语义回跳、同 MessageRun 最多两次；两者合计计入共享额外调用预算，超出进入可见 `needs_attention`。真实新用户输入是新版本/事件，不能由调度器伪造新输入来清零预算。普通 provider 重试和 schema 修正也占预算。

## 6. 身份、版本与原子接纳

### 6.1 稳定身份与必要依赖

```text
sourceKey = channel/account/conversation/messageId
MessageRun = sourceKey + sourceVersion + engineEpoch
NodeInstance = messageRunId + stage + unitId(or message) + effectiveInputVersion
CommandIntent = persisted unit/action identity + commandRevision
```

服务端分配 unitId，并保存 S 修订前后映射；模型临时 localKey、batchId、attemptId 不作为业务幂等键。重试复用同命令身份，结果 ACK 丢失先读 receipt。

同一 `sourceKey` 维护权威 currentSourceVersion 和跨版本 Unit/Action/Command 映射。平台消息编辑进入新版本时，在接收事务先 CAS 当前版本、建立编辑屏障、撤销旧未提交计算和未派发资格；不能等新 S 完成才阻断旧结果。来源作者/编辑权限必须重新核验，迟到旧版本不能按本地到达 seq 反向覆盖已知较新版本；平台无可靠版本序时，代码回取当前正文并保存证据，期间只保留待判状态。

新旧版本按来源范围与意图对照：仅措辞改变复用旧命令/消费记录；真正改变需求走 ChangeSet；删除事项撤销尚未派发命令并记录修订，已派发/已有效果保留并按修订范围对账。旧来源的未决引用屏障继续继承。每个版本可有独立审计 MessageRun，但共享源的预算账继承消耗，不能因重启/编辑事件重复或元数据更新重新领取整份额度。下载/引用补齐只是 ResourceVersion 变化，不是新用户授权、也不产生新的业务消息版本。

R/I 可独立计算，但存在未解同指/共享作用域的单元不得抢先派发；只等待其有关联边的单元组，不全消息 wait-all。同源、同目标、同规范动作和参数/限制相同的结果在接纳事务内以唯一操作身份复用一个命令，每个单元仍保留动作映射；不能仅凭标题、相同 taskId 或模型声称“重复”合并。两动作不同或条件矛盾时保留各自身份/先后或澄清，不先发一个再靠事后去重纠正。

版本分开记录 `matterSetRevision、unitRevision、sharedConstraintRevision、bindingRevision、taskRequirementRevision、taskControlRevision、evidenceVersion`。每个节点只依赖相关版本向量；追加一条无关进度日志不使 I 失效。目标/限制改变必须重判；完成/取消等实际影响意图资格的状态改变不能作为“仅进度”忽略。

纠正采用两个事务：`correction.begin` 接纳可信原文反证后，立即登记受影响范围、建立修正屏障、撤销旧 R/I 租约和未派发资格；预算只决定随后能否计算 S2/R2，不能决定是否保留已知不可靠结果的执行权。纠错预算耗尽时保留屏障进入 needs_attention。`correction.publish` 以 correctionId 做 CAS，在一个短事务内发布新的 MatterSet/Binding、旧新映射、受影响单元的有效版本，并 supersede 旧结果及尚未 claim 的命令、转移对应屏障。不能只在 S2 发布时撤权，让旧 I 在重算期间继续派发。

共享限制改变使全部依赖它的单元失效；未受影响单元可由代码依据相同 source/限制/依赖 hash 建立显式复用记录，不能仅因全局 revision 增长让全消息重跑。修正失败进入同一恢复服务，保留修正屏障，不自动退回旧结论取得执行权。

结果接纳和命令 dispatch 两处都检查**当前有效资格**，不仅验证 hash。已 claim 但未取得效果许可的命令同样撤销许可；已发出效果进入 unknown/对账，保留历史事实，不宣称重拆能回滚。更改已经接纳的业务要求通过 ChangeSet 处理，不再创建同义 Task。

### 6.2 源消息屏障：Task 未创建也要保护

接收带可靠引用且具备控制资格的新输入时，同事务登记 `PendingInputFence(fenceId, sourceKey, targetSeenVersion?, actor, inputId, scope, seq, authorityBasis)`，即使被引用的消息尚未产出 Task。源未取回时可先以稳定 sourceKey 保留待解析关联，但不能凭未知引用冻结任意 Task。屏障绑定稳定来源并记录看到的版本；原消息编辑不能绕过既有未决修订。

- 控制资格来自已有 Task 权限，或同认证作者对自己待处理请求的修订权及现行角色策略；无权输入不建阻断资格。引用文本或模型猜测不能赋权。
- 该源后续产生 Unit、Command 或 Task 时，接纳事务查询并继承未决输入屏障。`源→单元→Task` 映射与继承同库提交，不留“Task 已派发后再补屏障”的窗口。
- 屏障阻止受影响的业务派发/新效果资格，不阻止 M1 保存 S/R/I、生成身份或接纳带 waiting 状态的 Task 记录；因此 M2 可以取得目标身份完成分类，不形成“M1 等 M2、M2 等 M1 身份”的死锁。
- 多事项源只圈定有证据且有权的候选。歧义未解时保持有限候选范围并请求定向澄清，不全群冻结、不默认全部取消。
- 若 I 判定纯查询/无关，持久化结论后仅解除对应 fenceId；同目标其它未决输入的屏障仍有效。若是新要求/取消，屏障原子转换为正式控制或 ChangeSet，没有先放行再建的间隙。
- 超时/进程重启不释放屏障。恢复状态必须指出被挡的 Task/源、缺什么及恢复入口；不能显示业务 Agent 正在执行。

未能可靠关联的自然语言不能在理解前精准冻结未知目标；因此不承诺任何一句无引用“停”到达时已停止所有潜在任务。已经发出的外部动作无法被后到控制倒转。

### 6.3 accept 与 dispatch 的事务边界

大工件读取、hash、schema 和纯参数准备在事务外；短事务重验来源版本、有效单元/绑定、权限/控制 revision、幂等键、依赖及屏障，原子写入：

```text
归属/事实变更 + UnitDisposition + CommandIntent/无动作或拒绝结果
             + receipt + 下游派发意图 + 屏障转换
```

事务不调用模型/连接器/业务工具，不等待通知。事务后派发器凭持久意图唤醒；崩溃可重领，但业务身份不变。确定身份冲突可复用；新增候选确实影响归属时只重判相关 R，标题相似不自动合并话题。

dispatch 再验版本、权限和屏障，先登记执行归属/效果许可，再释放控制槽去准备业务环境。停止/查询不排在工程启动后面；任何外部效果仍通过执行底座的许可与读回，不因为命令已接纳就永久获得权限。

## 7. 分支、澄清、审批与任务调整

### 7.1 各意图的确定路径

| 意图 | handler 与产出 | 是否启动业务 Agent |
| --- | --- | --- |
| 闲聊/仅他人任务/无需回复 | 有来源的 no_action disposition；必要时登记讨论 | 否 |
| 事实补充/附件登记 | 版本化事实/工件引用；有需求变化才产生 ChangeSet | 否；相应业务节点需要时再读 |
| 状态查询 | 读投影、生成模板及证据时间 | 否，不 steer 工作 Agent |
| 历史结果解释 | 选定 run/result 后只读投影；复杂解释单独 answer 节点 | 按需窄问答，不重开任务 |
| 新问答/调研 | 有限问答/调研流程，材料与工具按节点授予 | 按所需节点 |
| 创建/修订/重开任务 | 绑定 Task Workflow 或提交 ChangeSet/新 run | 有业务执行需要时 |
| 取消/暂停/恢复 | 控制 handler 与实际排空/恢复状态 | 控制本身不需要 |
| 审批/澄清答复 | 校验固定请求、首终态/消费 receipt、唤醒 blockedNode | 答复处理本身不需要 |

未实现的 handler 返回 `unsupported` 并保留可操作待处理项；不得暗中回旧多 Agent 链或声称执行中。此分支不能用于让整条消息“成功”或绕过上线准入。

### 7.2 查询必须选择具体版本

`Query = targetTaskId + runSelector(explicit/current) + resultRef? + queryKind`；集合查询另有 conversation/filter/snapshot 水位。

引用历史结果默认选被引用 run/result；明确问“现在”才解析当前 run 并记录解析时刻；比较请求各自取两份快照。不可用 run-2 的当前状态解释 run-1 的历史产物；查询不创建 run、不更改业务版本。事实查询到回答发送间有变化时，答复注明事实时间或重新投影，不重新分类整条消息。

### 7.3 普通澄清也有固定请求身份

```text
ClarificationRequest = requestId + owner(messageRunId | unitId) + blockedNode
                     + questionRevision + candidateRefs/versions
                     + permittedActors + state + createdSeq
```

“第一个”只对该问题版本展示的候选顺序有效，不能对应当前搜索列表。引用/按钮/唯一活跃请求可定位；存在多个候选请求时不猜测。

S 尚未形成有效 MatterSet 的全局指代/共享限制问题以 messageRunId 为 owner，绑定当前源版本和 S 节点；S 之后的问题以 unitId 为 owner。不得为询问而先发布未验证的可执行单元。

答复接纳事务同时做：验证 actor 与请求版本、消费答复、记录来源、更新原消息判断或单元输入、写固定 receipt、登记有界继续窗口并唤醒原 blockedNode。重复答复返回原 receipt；互相冲突的迟到答复返回已决定事实。问题被替换、单元被取消或 supersede 后的答复记 stale，不创建新 Task。多问题分别消费，答复一项不能解除另一项等待。晚于原 deadline 的有效答复按§9.1继续，不能要求用户再点系统恢复。

### 7.4 审批的两端等价和适用范围

认证 Web 和本人 IM 入口映射到同一 requestId/动作身份；首个有效 approved/rejected 终态生效，两端重复或冲突答复均读同一 receipt。不能仅因来源是 Web 再索要私聊批准，也不能为每个普通节点重复审批。

授权绑定动作、目标、范围、基线和身份。只有这些适用条件真实改变才重新判断；模型换会话、进度查询、重试不制造新审批。历史消息中的“批准”只作为材料；模型识别意图不代替认证、请求绑定和权限校验。预算不足是系统问题，不发业务审批让用户批准更多 token。

### 7.5 暂停、取消和故障恢复分开

- `pauseRequested`：原子冻结该 run 的新 node/job 领取和新效果资格，请求在途节点停在安全点；pending 输入/产物全部保留。用于停止、状态投影和对账的代码工作仍可执行，纯分析业务节点不能在安全点后续领新节点把暂停无限拖长。
- `waiting:user_pause`：已证明相关执行者排空且无未对账效果后才进入。未知操作仍显示 pausing/reconciling，不能只改标签假装停住。
- `resume`：只从用户暂停状态进入重新校验；先处理暂停期间有效新要求、权限/审批适用性和 unknown，再继续合法 checkpoint。不得清除其他屏障。
- `cancelRequested → cancelling → cancelled`：实际排空/对账后终态；保留事实和未执行输入的明确处置。之后“恢复”不能静默复活，明确重新开展才创建关联的新 run。
- `system_recovery`：恢复故障节点/租约，不解释成用户要求继续业务，不解除用户暂停或取消。

新要求按相关依赖失效节点，纯进度查询不改任务输入。受影响工作在安全点接入新版本，实际进度由控制账投影，Agent 不需要边执行边回复协调方。

## 8. 计时、预算、排队与合批

### 8.1 每个节点怎样计时

```text
createdAt → inputReadyAt → startedAt → resultReadyAt → committedAt
              输入等待       队列等待       执行             提交
```

按 attempt 记录单调时钟持续时间、UTC 时间及持久事件 seq，进程重启不通过重设 createdAt 缩短墙钟。节点执行内另分 connector I/O、provider 请求/首 token/生成、输出校验、退避；provider 不暴露远端排队时只报告观测请求延迟，不捏造“推理时间”。

输入就绪才排入模型 runnable 队列并领取槽；等待附件/澄清不占模型槽。出队再检查有效版本和 deadline。可用时间：`min(nodeAttemptCap, remainingDecisionWindow - commitReserve)`；不足就进入持久恢复状态，不启动注定越期的调用。结果与超时竞态由接纳事务判定；迟到输出可留审计，不能越过失效许可派发。

按 unit 记录完整依赖，重建关键路径；不得把各节点 P95 相加当整链 P95，也不得只报最快事项。A 的附件、业务环境启动和通知读回不能进入无关 B 的接纳关键路径。

### 8.2 明确的试运行预算策略

下列是**隔离校准起点和硬上限配置，不是已测性能或生产保证**。配置以版本化 `MessagePolicy` 显式传参并持久绑定运行。冻结基准后才能调整准入值；不能每次失败临时放大。

| 范围 | 初始策略 | 超限处理 |
| --- | --- | --- |
| 语义决策首次窗口 | 普通45秒；入站代码标记 linked_pending_input 的输入30秒；从 receive durable 计墙钟 | 未决单元入 recovery，不重放已接纳单元 |
| 节点单次窗口 | S/R/I/材料语义最多20秒，且受共同剩余时间约束；预留500ms提交 | 中止新计算资格，记录具体耗时段；底层请求取消/late result 受控 |
| 输入/输出 envelope | S 8k/2k，R 4k/1k，I 6k/1.5k token；含 system/schema/引用/图像等全部内容 | 可选项按合同省略；必需项进入定向材料整理或可见容量错误 |
| 扇出及候选 | 单条至多8个可处理事项；每次 R 至多8候选卡 | 不只处理前8项；生成覆盖完整的容量等待及拆解/材料处理入口 |
| 累计模型账 | 原始+恢复全 MessageRun 输入64k、输出12k token；初始必要调用≤1+2N，额外尝试≤4，其中首次窗口≤2 | 所有材料语义、schema/HTTP 重试、回跳共用账；不得藏入另一个 Session |
| 语义纠正 | 每单元1次，同消息合计2次，仍受上行额外调用限制 | 留反证和原节点恢复入口，停止互相回跳 |
| 故障自动恢复 | 最多2个恢复窗口，每窗30秒；最早退避5秒、30秒；自动故障等待总跨度至多10分钟 | 用完进入 needs_attention；不自动新建 MessageRun 续费 |
| 业务输入等待后继续 | 每个有效请求答复/已登记必需输入就绪事件最多触发一次30秒继续窗口；输入未齐不启窗 | 复用剩余累计额度和调用身份，不重设初始SLA；事件重复不续窗 |
| 模型并发 | 试运行全消息2槽，每群至多2个；工程模型单独本地槽但共享配额准入 | 公平队列/背压；不是宣称远端配额已隔离 |
| 模型合批 | 首版 batchSize=1；实验上限4单元/等待50ms，token和截止取最紧上限 | 大/不就绪/临近期限事项不合批 |

N 为首次有效 S 的单元数；重拆不能增大原预算额度。S 之前只有1次初始 S 额度，R/I 额度在有效 MatterSet 发布后一次登记；后续拆分超额度走系统容量路径。精确代码短路不消耗模型额度，但保留端到端墙钟。

64k 等限额以 provider 对当前模型的可用计量为准；发前使用 tokenizer/已校准上界估算及输出预留，拿 usage 后结算。无法确定请求是否计费的失败按预留值保守占账，保留 unknown 标记；不能把未回 usage 算0。协议重试、材料语义和恢复分别有标签、共用额度。预算策略不把正常业务执行/复杂结果解释成本藏起来：它们有独立子流程上限及父源关联，报消息到业务的总成本时合并，且不得替 S/R/I 完成其未完成职责以绕限额。

这些上限可能使复杂消息无法在首次窗口完成，必须通过固定样本校准；不把“强行超时更多任务”算变快。生产目标与硬超时分开，失败和恢复都进入质量/成本分母。

### 8.3 合批不是免费并行

只合并同节点合同、相容模型/权限和已就绪的小单元；不跨 stage，不为等 A 材料而扣住 B。合批是执行优化，不更改 unit/result/command 身份和成本归属。

完整 JSON 可解析后，分别校验/保存各单元，有效项不因另一项字段无效而重算；整包不可解析时失败成本归入全部受影响项。完整 JSON 未校验前不宣称其中 B 已完成；同请求仍会一起等 provider 和生成。已知大项提前独立，未知慢项照实记录拖累。先实测 batchSize=1，再对照有界批量的吞吐/尾延迟/质量，不能默认“合批必然提速”。

### 8.4 共享资源与过载

在现有调度器里分别维护材料 I/O、消息模型、工程模型、短控制事务、发送/读回容量。模型准入同时按 provider/model/account 的并发、RPM、TPM 计预留，入站代码可确定的 linked_pending_input 优先并保留份额；普通消息需公平份额，避免持续控制流饿死普通请求。不为选择队列先运行意图模型。

只有 DSH Host 能拦截工程和消息请求共同准入时，才可声称有配额预留。不能控制的其它客户端共享同一 provider 额度时，这是容量外部变量，记录429/退避并验证退化；若因此无法满足声明负载，相关配置不得准入，不能以“本地两队列”宣称隔离。精确结构化控制/状态模板不依赖 provider，但仍需存储/认证可用。

每个队列都有持久积压量、高水位、最老年龄、拒收/重投指标。容量内积压不得持续增长；超容量先保存接收事实并标 waiting_capacity，停止扩大模型扇出。不允许用失败/settled 清空积压伪造吞吐。达到持久存储硬容量时入口明确不确认可靠接收，依赖可核验的渠道重投/游标恢复；若连接器不支持，必须如实暴露可能丢消息，不能以“不落盘 ACK”掩盖。

批量落盘也有事件数/字节上限；单事件过大保留平台引用和拒收原因，不能只保存前半条执行。具体存储高水位按实际保留策略/磁盘校准，生产未配置这些限额不得宣称有界容量。

## 9. 恢复责任与消息归宿

### 9.1 持久恢复状态机

```text
ready → running → committed
          ├─ transient/timeout → recovery_wait → ready（同一节点）
          ├─ needs_resource → waiting_context → ready（材料事件）
          ├─ needs_user → waiting_clarification → ready（答复消费）
          └─ nonretryable/budget_exhausted → needs_attention
```

每个等待持久记录 owner=`message-recovery`、原因、blockedNode、有效输入版本、wakeCondition、nextWakeAt/expiry、attempt/cost ledger、阻断范围。恢复服务启动扫描到期索引，领取带租约的恢复工作；退避和等待只用代码定时器/事件，无模型轮询。每个继续/恢复窗口绑定 scope（S为message，R/I为相关unit-set），不能顺带续期无关单元。故障累计等待按 incident 记录，业务等待只暂停其自身的故障时钟；另一项provider故障仍正常到期，共享成本额度不变。

- provider/连接器暂时故障：按§8.2有限退避、最多两窗恢复，已成功 S/R 不重跑。恢复窗内处理剩余依赖和未决单元，不是每节点另领30秒。
- 连接器/provider故障等待：原始30/45秒窗口到期只记录首次SLA违约并转有界恢复等待，不立即耗尽两个恢复窗。资源就绪时若还在10分钟自动故障期限内且有剩余额度，可开启恢复窗；无材料时不空耗窗口。10分钟到期/恢复窗耗尽后才进入 needs_attention。
- 正常业务输入等待：需要用户答复、上传或明确承诺稍后提供的材料，记录 waiting_clarification / waiting_input，暂停自动故障等待期限，不占模型槽，可以跨天存在。请求过期是显式状态，不自动当拒绝或取消业务。有效答复/登记材料就绪事务为该输入建立一次30秒继续窗口，原节点复用有效S/R，消费尚未执行的基础调用或剩余额外额度；原接收起点、累计token/attempt账仍保留。重复事件不新开窗口，多个同次已齐输入合并一窗，依次新请求仍受累计纠正/预算上限，不能模型无限追问来续命。
- 等待类型由可信handler及请求事实决定，不能把provider故障伪装成业务输入等待。连接器返回稍慢不是“用户稍后上传”；已承诺输入到达但处理又故障时回到故障恢复预算，不重新取得两窗额度。累计预算确已耗尽则如实系统故障，用户正常回答本身无需另批业务权限。
- 初始窗口用尽与累计 token/尝试用尽分开；累计预算用尽直接 needs_attention，恢复窗不重置累计预算。
- 进程重启不清 deadline/nextWakeAt/计数，未观测模型成本保守登记，已提交结果按 receipt 复用。
- 故障恢复窗用完或自动故障等待累计10分钟后持久发一次故障通知，展示哪些输入挡住哪些任务、失败节点与动作。正常业务输入等待不触发这条故障期限。抑制重复通知，不让用户反复“继续”承担调度。
- `needs_attention` 有受认证系统恢复命令：同一 MessageRun 先验证依赖已修复、效果已对账，再登记一次恢复决策及显式新增预算上限；累计历史不清零。这是运维恢复，不是业务审批，也不是定时自动扩额。正常自动恢复未耗尽前无需用户动作。

屏障解除只允许：有效分类证明不影响目标、已原子应用正式控制/ChangeSet、或有权主体明确撤回这条未决输入；不能以超时/通知成功解除。需要人工澄清的是业务歧义，系统不可用是系统故障，两者不得混为“待用户批准”。

### 9.2 settled 的完整分母

当前有效 MatterSet 中**全部单元**都有明确归宿，且消息判断节点拥有的重拆/材料/澄清/资格冲突全部解决，才可 `settled`。每单元归宿包括命令已接纳且派发责任已持久移交、有效 no_action、明确拒绝或源输入经有权撤回。多个同义单元映射一命令仍各有 disposition；已明确交给Task Workflow的业务材料等待不重新阻塞MessageRun。

一个单元包含 actions[] 时，全部有效动作及依赖都有上述归宿才算该单元处理完成；不能因停止动作已接纳，就遗忘同事项尚未持久移交的后续查询。业务handler已持久接管依赖等待时，以接管回执证明归宿，并独立追踪其后续完成/失败。

`waiting_context / waiting_capacity / waiting_clarification / needs_attention / unsupported` 不是成功终态。A 已处理、B 无命令且缺材料必须显示部分处理，B 留在独立恢复索引；不能只看已产生命令都结束了。

Task 长业务和通知送达不阻塞“消息判定已归宿”；另报 dispatch/业务/投递状态和总墙钟。业务 handler 若尚未持久接管，不能用临时内存队列当已移交；任务尚未开始不得显示“正在执行”。

## 10. 回复披露与通知

读取资格和披露资格分开：`readScope` 决定连接器/模型可读哪些来源；`disclosureScope` 决定这些事实可向哪个会话/受众发送。服务账号可读、请求人可读，都不自动证明群内所有收件人可读。

- 来源/派生事实保留 scope 与 lineage。answer/文案节点只拿允许目的地披露的投影；仅让模型最后“注意保密”无效。
- 首版使用现有来源权限和明确目的会话规则；无法证明可披露的跨群/私有材料不给群答复模型，返回不含隐私的不可披露说明或使用已有受支持的私有回复路径。不给未知材料默认 public，不另造通用 ACL 平台。
- notify 接纳与实际发送前都检查目的地、当前权限/撤销版本、事实引用及因果。权限变化使未发送草稿失效；不得通过重发绕过。已发出的事实无法追回，记录实际状态。
- 同事项必要通知保因果；独立事项有事实就准备，不等所有任务完成。发送/ACK/读回为独立队列和状态，读回慢不占业务/控制槽。
- ACK 不明先按渠道能力对账，禁止盲重发造成双通知；无可靠独立读回时明确 delivery_unknown。投递失败只恢复 Outbox，不重做 Task 或 S/R/I。

## 11. 群切换、排空和回退

首版坚持单群单执行归属，不在线搬迁活动旧 Task。接收权威为一个持久入口 journal，记录每事件归属与 engineEpoch；旧/新消费者凭同一入口授权领取，不能两个进程分别读两个存储就宣称“切换原子”。该入口 fencing 是切换前必须实现的能力。

```text
active(old,e) → draining(cutoff=W,e) → old_sealed → importing → active(new,e+1)
                         └─ drain_aborted → active(old,e)
```

1. `--check` 验证旧入口可受 fencing、journal 接收/去重/重投、两边待处理清单、恢复路径；没有能力时停止准入，不猜测旧 worker 已停。
2. 一个入口事务固定 W 和 draining。≤W 保持旧归属；>W 持久缓冲，不能同时交两边。必须由入口接收确认后的 seq 定序，迟到平台事件仍按新接收 seq 入账。
3. 旧侧排空清单包括：所有 MessageRun/有效单元/未决 S/R/I/澄清、accepted 未claim 命令、已claim 执行、控制/审批、活动 Task、unknown 效果和未对账 Outbox；逐项取得终态或已明确处置证据。不能只数运行 Task=0。
4. draining 期间，明确结构化且指向旧对象的控制/澄清/审批仍交旧归属并记 journal。若 >W 自然语言可能影响旧未结输入/任务而代码无法证明是纯新工作，**中止此次切换**，恢复旧准入并按来源去重释放全部缓冲给旧侧；不要求用户重发或重新批准。含新旧混合事项也整体中止，不偷偷拆成跨引擎执行。
5. 首版 drain 窗口最多60秒；未排空、有无法判断归属的新输入或入口/旧 worker 状态不确定即持久 abort，旧侧继续正常处理。选择空闲群/短维护窗口切换；持续活跃群可能本次无法切换，不能无限缓存等待排空，也不自动取消任务。
6. 清单核验完成，先封存旧侧：旧入口、派发及所有迟到异步回调的写入都受 owner/epoch 栅栏控制，取得执行者排空及停止写入证据后记录 old_sealed。旧 JSON 和新 SQLite 不能同事务迁移；导入是有 manifest/hash/游标、可幂等续办的 importing 阶段。导入验证通过后，入口事务才原子更换活动 epoch 和接收归属；>W 缓冲逐条授予新引擎，消费者只接受授权。
7. draining 中崩溃恢复到原状态并重新检查；封存/导入间崩溃继续持久交接，不自动解封旧侧；发布新 active 后按新 epoch 继续。封存后仍有新输入则可靠缓冲，适用60秒总窗口；发布前需中止时，确认新侧从未取得执行资格，再以入口事务撤销交接并恢复旧授权，按来源释放缓冲。超过窗口且无法证明安全解封时显示切换故障，不能猜测任一侧有权执行。所有旧写路径无法受控时不得进入封存。
8. 旧 Topic/历史提供只读冻结快照及归档来源映射。新引擎不得接管旧未完成任务；旧完成结果追问可只读，新的明确工作在新引擎建立新 run。
9. 回退禁止恢复旧数据库快照覆盖新事实。新引擎已有命令/效果时先停止新增准入、排空/对账并走同样交接条件；不能把已派发消息重新分给旧引擎。需要搬迁活动任务须另做显式迁移方案。

此选择牺牲繁忙群的立即无缝切换，换取首版无需跨引擎事项转移协议。不是运行期间每条消息的延迟成本；上线前仍须实测缓冲、abort和崩溃窗口。

### 13.3 质量、延迟和成本的准入口径

1. 固定现有6条 multi-topic 种子和已核实历史故障，新增至少100条不用于调参的留出消息。人工标注事项、目标、意图、限制、权限、是否回复及运行版本；报告漏任务、误启动、误取消、错误续接、漏约束和澄清率。结构正确不能代替语义评测；高风险误动作测试必须0，有限样本0不证明普遍零错误。
2. 对照至少三个配置：旧链；新 S/R/I 单事项；新 S/R/I 有界合批/代码短路。模型、采样、硬件、provider配额和判定质量固定；可加单次综合模型作对照，不因调用少就胜出。
3. 到达计划在运行前冻结，不能上一条完成才发下一条。按历史峰值负载及其0.5/1/2倍、明确突发窗口、共享工程负载分别测试；保留 arrival trace/随机种子。1倍容量须定义为运行前选定的目标，不能事后下调到测试能过的值。
4. 沿用待验证目标：入站持久化 P95≤1秒；精确状态有用答复准备 P95≤5秒；普通消息有效接纳 P50≤15秒/P95≤45秒；代码控制提交 P95≤300ms；已知取消撤销新增效果资格 P95≤2秒。自然语言控制另报收到→识别→提交，不把结构化控制的目标冒充所有自然语言结果。首次窗口 timeout 单列，不能把超时样本从P95分母删去或强算45秒成功。
5. 同时报每单元、首个有用归宿、全消息归宿、业务首次有效活动、通知实际送达的墙钟；报告成功完成分布、超时/未完成数量与等待年龄、有效吞吐、积压峰值、恢复/排空时间。不能仅凭成功样本尾延迟达标准入。
6. 全成本包括输入/缓存输入/输出、全部attempt、材料语义、补取、排队/存储/渠道及失败/恢复。精确控制0模型，等待0模型轮询；总体token是否下降以相同正确业务产出的对照为准，不先填节省百分比。
7. 小范围准入必须同时满足质量、负载、恢复和可观测性；出现等待原因不明、未决事项从索引消失、无界预算或权限错误即不准入。单元测试或文档审阅通过不替代真实渠道/业务验证。

## 14. 未收敛点与不可混淆的结论

设计已明确节点合同和失败出口；实现尚不存在，不能宣称消息已变快、任务已可靠恢复。必须实测的变量包括最近30条的相关性选择、长历史限制提取的遗漏、模型误拆/误关联、provider波动/Host配额钩子以及渠道读回能力。

初始预算值允许在冻结样本校准阶段修改；修改必须留下策略版本和对照数据，不能以增加超时、放宽质量或隐藏未完成任务制造改善。第11节的繁忙群切换失败是明确的首版边界，若确需无缝迁移活动任务，应单列迁移需求评估，不把复杂协议混进本次消息节点实现。
