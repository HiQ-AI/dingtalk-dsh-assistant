## P0：内部故障不能变成叶子的重复改稿与人工审批

**证据**：菜单组任务共收到 114 份报告；108 次 task-report-settled 为 rejected，错误完全相同：topic_context_budget_exceeded。首次 17:22:24，最后 18:48:21，跨度约 86 分钟。监督器记录 12 次 idle 续接、2 次 paused 重建。最终 waiting 请求却要求人工修复 Runtime 再重新派发。

代码：task-reports.js:61–71 仅将少数传输类错误归为 failed，其余异常落入 rejected；runtime.js:1288–1334 按 Goal/Session 状态重建或催跑，没有以同因审阅失败判断恢复无效。内部异常由此被呈现为报告被驳回，叶子反复压缩、更换 submissionId。

反证检查：候选一是叶子报告正文过长，但多次压缩未改变错误；候选二是 Session 损坏，但两次重建仍失败；候选三是固定 Topic 上下文构造错误，已由前轮真实 56 条消息的复现及分页游标修复证实。修复位置 topic-runtime.js:61–105 已安装，本次不重复修该单点。

**方案**：

- 使用明确的错误分类和处理责任：业务审阅驳回、输入版本失效、可重试的系统故障、确定性的系统故障。保留失败报告与稳定身份；内部预算/序列化异常不能要求叶子改业务计划。
- 同任务、同 runSequence/inputVersion、同操作类别和错误码形成失败指纹；换 submissionId 或 Session 不清零。临时故障采用有限退避，确定性故障立即停止同路径重试。
- 系统暂停由 Host 记录并释放并发名额，通知走现有可靠 Outbox，独立于发生故障的 LLM 审阅/上下文构造路径。只发送任务、已完成工作、故障责任和下一步；不向业务群索要内部故障的执行批准。
- 恢复条件为故障依赖修复并通过探测，或出现相关新输入。只恢复原授权内、当前版本仍有效的审阅报告，不重放已经完成的业务写操作。禁止扩大权限或伪造完成。

**验收**：注入相同预算错误 100 次，只形成一个故障事件和一次初始通知，不连续唤醒/重建叶子；其它任务正常推进；修复探测后同报告只推进一次；真实业务 reject 仍要求改稿。群发送不可用时保留待发送和本地故障状态。

**验收**：审阅中连续补充三条不改范围的消息，不重复业务写入、不丢有效阶段；真正改目标只失效关联阶段；撤销授权立即阻断旧报告推进。

## P1：修正可观测性后再优化调用成本

**证据**：观察样本约 19:47 的 914 条保留 tool/result 全部为 unknown，isError 未显示错误。runtime.js:147–150 从 event.data.name/isError 取值；当前已安装 DSH 的 dsh-agent-loop/lib/index.js:302–321 实际将结果放在 data.message，并用 sourceEventSeqs 关联调用。故“工具零错误”不可信。活动存储每任务仅保留 500 条（store.js:167、1055 起），四个活跃过的任务已到上限，不能用当前保留记录估计全天工具次数或 token 成本。

另有 17 条 Outbox deliveryAttemptCount=2。dws-bridge.js:301–305 在 dispatchOutbox 每次处理后计数，包括 pending 回读，因此该值不等于真实 send 次数；不能据此声称重复群发。

**方案**：

- 按当前 DSH 事件契约关联 call/result，记录工具名、真实错误、耗时、结果大小和执行阶段；找不到关联时明确标记未知，不能默认成功。
- 复用事件幂等身份，持久化不随 500 条明细裁剪消失的按日/任务聚合：实际调用、错误码、审阅次数、重试原因、业务推进次数、等待时长。保留明细跳转；不复制敏感参数或工具正文。
- 分开记录 sendAttempt 与 readbackAttempt、实际 deliveredMessageId 和通知耗时。重复调用必须区分重复提交、合法重审、回读和真正重复外部动作。
- 当前群消息中位数 60 字，最长 568 字，暂不统一强行截短。优先减少内部失败报告重复和上下文重复；token 优化需补齐实际 usage 统计后再定量。

**验收**：成功、工具失败、取消、重启回放均能正确关联；501 条事件裁剪后聚合不丢失、不翻倍；一次发送加两次回读显示 send=1/readback=2。构造跨午夜的本地字符串与毫秒时间，统计归属一致。

## P1：健康状态要区分当前故障、历史故障和已恢复

**证据**：18:59 一次 activity-projection EPERM 至今仍使 health=degraded；此后任务完成且活动仍更新。runtime.js:1578 的 catch 只追加告警，没有同类成功回查的清除路径。recovery ledger 在进程内，不能把“重启后告警消失”当作修复证据。

**方案**：保留失败事件和投影 seq，以原事件身份有限重试；成功补齐对应事件、连续水位和持久化验证后标记 resolved，历史告警仍可查。当前失败/未补齐为 degraded，单次历史故障恢复后不永久污染健康状态。先定位 EPERM 的实际写盘/文件占用原因并验证底层原子写的行为，再决定是否需要改写入层。

**验收**：一次临时锁定后补齐无重复；持续锁定仍显示未恢复；崩溃后续补不会跳过失败序号。不能仅因为后一个事件成功就清除此前数据缺口。

**盲点**：没有证据认定杀毒软件、并发写或本轮文件读取导致 EPERM，也没有性能测量证明需迁移数据库；本轮不建议先上数据库重构。

## P2：等待与阶段通知的后续验证

现有 #110 已支持独立阶段完成、必要信息等待通知、30 分钟/2 小时有界跟进、恢复后旧通知失效，应先验真实运行而非重做。method-select 的代码/权限结论已经有证据，但原进度仍显示无已验收阶段，是阶段粒度与历史报告未提交独立检查点的问题；不能将自然语言结论直接改为已验收。

后续在计划中让可独立取证的阶段分别提交，通知展示“已验证事实”和“未完成验收”；通知的业务状态与发送状态分开。验收覆盖单项完成即通知、其余事项等待不影响完成项；恢复与提醒并发时不得发过时暂停通知；只等待正式测试方的任务可独立收束。

## 建议实施顺序

1. 内部错误分类、同因停止重试、Host 故障通知与恢复闭环（P0），同时修工具事件观测，确保能准确验证。
2. 派发范围/流程前置校验、输入变化影响范围、独立阶段成果和通知回归。
3. activity-projection 故障补齐与健康状态收束，再基于完整统计优化上下文和审阅成本。

实施以今天六个真实场景的脱敏固定样本为回归集，先做故障注入与离线回放；正式接入时不重放真实群发、审批或数据写入。每项分别验收，不能以总测试通过或服务端口正常替代业务闭环。
