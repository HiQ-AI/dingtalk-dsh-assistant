# 消息处理延迟修复方案

2026-10-22，基线 origin/main 192e808。用户报告今天部分消息耗时 2–3 分钟，以及“三分钟后汇报”被处理成过期澄清。复用已挂接工作树，新分支 worktree-coordination-latency，保留主检出和旧审查草稿。

## 已确认事实与候选解释

该消息 07:31:45.381Z 发出，07:31:53 首次规划，07:35:24 回复确认送达。两次规划分别耗尽 8 步而未提交；包含 limit=100 和过多 taskIds 触发 COORDINATION_CONTEXT_RANGE，以及逐批读取所有 17 个 Task 详情；第二次失败后进入既有 60 秒退避。第三次于 07:35:02 开始，提交了过期澄清。结论来自本机原始 session.v4.jsonl 与只读 API。

候选解释：①消息接收/路由排队，仅约 8 秒，不能解释 219 秒；②单次模型慢，存在数秒至 20 秒调用，但前两轮共 16 次重复读取和重试是主要可消除成本；③协调工具合同/上下文设计，现有上下文工具无公开参数边界且只读查询仍要求详情观察，已找到直接反例。其他今日消息、投递耗时及性能投影覆盖缺口继续只读取证，不能套用同一根因。

## 修改边界

1. 公开与 Host 一致的工具输入 schema，减少参数猜测；保留严格越权和版本检查。
2. 只读定时查询基于已观察目录选择固定 taskIds，执行时由 Host 读最新事实；改变任务仍必须读取完整任务合同。减少冗余目录/详情轮次，不提高重试上限掩盖问题。
3. 提供稳定消息时间与当前时间。到期与过期规则按现有账本窗口统一，不把系统处理延迟变成无谓澄清，也不擅自改变业务执行时间或重放旧通知。具体边界由源码与回归证明后确定。
4. 为今日样本拆分阶段并输出脱敏摘要；真实会话正文、群成员标识、业务数据及凭据不得提交。修复代码、测试、README/runbook 经本地风险验证后 PR 交付；无现场部署、无真实消息发送、无手动 CI。

## 验证

正式单元与原生 Host 测试覆盖 17 个以上 Task 的定时只读安排、参数边界、两种时间先后顺序、目标越群/未观察拒绝、任务变更仍须完整合同、重启与投递身份保持。采集真实前置耗时与受控同场景调用数对比，受控测试耗时不冒充真实模型加速。复用现有测试文件与测试映射机制。
