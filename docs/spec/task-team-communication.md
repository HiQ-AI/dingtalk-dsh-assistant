# 执行团队与定向协作

用户在上一轮实现完成后追加：每任务执行团队 3–10 个会话，每个成员有本轮职责和任务，按复杂度、依赖及独立性安排；允许直接通信，同时避免过拆与通信成本。原先允许简单任务单执行的策略被本要求覆盖，历史验收不作新策略通过证据。

## 当前缺口

统筹可用 task_delegate feedback 持久投递，执行可用 stage/result 回报；执行侧目前没有查看同任务成员和定向投递能力。不能仅在提示词宣称可以互通。现有 execution.feedback 已具备持久化、幂等、模型步骤消费和提交竞态保护，应复用。

## 实现边界

- 同一 Task 复用 3–10 个 execution 身份，最大 10 在 dispatch 事务检查；重试、续办和反馈不新增人数。最少 3 在有执行任务的统筹完成前核对，不在 wait 时强制派发依赖未齐工作；纯咨询不因人数规则被伪造为执行任务。
- objective/context 明确本轮职责、小目标、输入、依赖、负责资源、交付物与验收条件。简单执行任务用三个简短且不同的必要职责；复杂任务在明确收益时增员，最多 10。实现、验收、交付核对只是例子，部署仍须有原任务授权与前置证据。
- execution_team_read 只读同 Task 成员及当前职责/版本/状态/结果，输出沿现有内容引用压缩；成员可按需要寻找协作对象，不加载完整聊天。
- execution_send_message 使用当前执行绑定、目标 executionId、稳定 key 和短 message。Host 验证发送者当前租约、双方同任务/当前需求控制版本及目标非终态；写入原 feedback 数组，记录来源身份与版本。运行中进入原生安全模型步骤，排队成员开始时消费。已结束成员不被消息重启，交给统筹按原身份续办。
- 点对点通信只用于交付接口、证据位置、依赖就绪或具体冲突；无新事实不重复、无无意义确认、不广播。消息不是用户授权或统筹改派，不能扩范围或越过资源互斥；关键阻塞/目标变化仍报告统筹。

## 验证

数量边界与幂等续办、同任务通信与跨任务/过期/已终态拒绝、消息持久消费/结果竞态用生产 Store 与原生会话测试；真实模型场景单独验证 3–10 分工、依赖时序、简单任务成本和成员复用。复验打包 smoke。既有 R1–R3 保留，最终结果明确新规则对应轮次。
