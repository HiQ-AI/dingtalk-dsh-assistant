# 话题批量意图与任务流程组合

日期：2026-09-24。核对基线：本地 main，`f1c3a13`。

状态：待实施设计。本轮只读取当前实现、运行两项现有行为测试并编写本文；没有修改业务代码、运行配置、真实消息或任务，没有部署。本文的新增字段、命令和流程均是建议契约。

本文修订 `runtime-message-workflow-v2.md` 中 R 后逐事项立即进入 I 的设计，并补充一个业务任务组合多个执行流程的契约。既有 spec 是历史快照，不回写；`task-prompt-composition.md` 属于旧叶子提示词组合机制，不能直接代表当前代码编排。新建本文是为了完整描述这次跨消息、话题、任务和流程的变更。

## 1. 目标与主要决策

1. 接收、补全上下文、拆分事项、关联话题仍逐消息/事项处理；意图判断改为按话题聚合处理。
2. R 后由代码等待同一收信范围内的新消息全部完成话题归属，再分别启动各话题的 I。不同话题使用独立判断上下文和运行身份，可并行；同话题只允许一个有效 I。
3. I 完成后，代码原子检查待归类消息、话题输入版本、来源版本和被操作任务版本。存在同话题新输入则集合新输入重判 I，复用已经有效的 S/R；没有新输入才接纳派发。
4. 新意图进入正在执行的任务时，先判断变化类型和影响范围，再合并输入或调整计划；不把所有新消息都变成任务重启。
5. 一个业务 Task 可以有多个顺序执行的工作流实例。排查、方案、开发、UAT 是可组合阶段，各有独立会话、工件和验收；业务 Task 身份连续。
6. 未固化事项使用受控的通用流程，允许根据证据调整计划和调用已登记能力，不要求事先为每种杂活写模板。

本文建议“全部收信箱”范围为同一接入账号/profile、同一群/会话、同一处理引擎。界面虽然汇总展示多个群，群之间不共享话题意图和等待锁。跨群任务关联必须有显式身份与访问授权。若产品要求所有群共用一个全局等待点，这是另一个产品语义，会扩大阻塞范围；本文不默认采用。

| 方案 | 决策与反证 |
| --- | --- |
| 每条消息独立 I，再立即更新任务 | 排除；同话题连续补充会产生多次判断与执行换代，不能满足本次要求 |
| 固定等几秒，或只处理冻结批次后放行 | 排除为主规则；等待结束时仍可能有已入箱但未归类的消息，不能证明已收齐当前输入 |
| 严格归类等待点 + 话题独立 I + 原子版本检查 | 采用；满足归类后聚合与防旧意图派发，但必须接受持续收信/归类受阻造成的等待 |
| 恢复长期话题 Agent，由它同时判意图和执行所有业务 | 排除；混合消息与执行职责，长任务占据上下文，难以按版本拒绝迟到结果 |

本方案减少重复处理，但不能保证“未来不会再来补充消息”。可证明的边界仅是某次事务提交时已经可靠进入本地收信账的消息；渠道尚未投递的消息作为后续输入处理。

## 3. 新消息主链

```text
1 接收消息并落盘
2 补全上下文
3 拆分事项 S
4 关联话题 R → 提交稳定话题身份与事项归属
4.5 代码等待：当前收信范围仍有未归类输入？
      有 → 继续推进这些输入的 S/R；持久记录等待原因
      无 → 冻结每个待处理话题的输入集合
5 各话题独立判断意图 I
      话题 A → IntentRun A
      话题 B → IntentRun B（独立上下文，可并行）
5.5 代码校验：未归类输入？话题有更新？任务语义状态已变化？
      有未归类 → 保留候选，等待 R 完成后检查
      同话题更新 → 旧候选失效，用最新集合重新判断该话题
      仅别的话题更新 → 本话题候选保持有效
      无变化 → 原子接纳决策和命令
6 派发到业务 Task 的计划/控制入口
```

### 3.1 等待点的准确定义

收信时分配单调 `ingressSeq`。关联状态与意图状态分开：

- `routing_pending`：准备、S、R 正在处理，或仍待解决材料/身份歧义。
- `routing_complete`：当前源版本的全部有效事项都有稳定 topicId，或有明确无话题处理归宿。
- `routing_superseded`：被新版源消息替代；必须追踪新版，不能当作没有后续输入。
- `routing_blocked`：失败、需澄清、缺材料；仍阻塞等待点，不因耗尽重试而冒充完成。

“无话题处理归宿”仅包括可核验的重复、已撤回无须执行、明确无动作输入，或完整结构化控制已交对应处理器。`needs_attention`、模型超时、容量超限均不等于无动作。

`pendingRoutingCount == 0` 是放行主条件；`ingressSeq/routingFrontier` 用于审计与检测遗漏，不能把“最大已完成序号”冒充连续完成水位。尚未 S 的消息也计入待归类。多事项消息必须全部 R 完成，才能解除它对群等待点的阻塞。

等待不持有模型并发槽、不持有数据库事务、不阻塞收信和其他消息的 R。Host 持久记录等待者；receive、R 提交、澄清解决、重启恢复等事件触发重新检查。

本轮采用严格排空：等待期间已经入箱的新消息也纳入等待。连续输入超过处理能力时可能一直无法清空；记录最老等待时长、积压数量和具体阻塞来源，进入可见告警/排障状态，仍不擅自按超时放行。分批水位放行能提高活性，但违反这次“全部归类再判意图”的严格要求，不能作为隐藏降级。

准确且已认证的暂停/取消控制、审批答复和引用澄清答复有独立控制通道，不能被它们要解除的 R 等待点阻塞。无法确定目标或包含相互否定的自然语言仍需语义解析，不能按关键词截断执行。澄清回复若需语义解析，用绑定原 request 的窄解析处理器；它仅解决该请求，不借此派发新业务。

### 3.2 R 的落盘与新话题身份

R 提交的是 `unitId + sourceVersion + matterRevision + topicId + bindingEvidence`，只承担归属，不承担执行授权。话题待判输入账保留原文片段、发送者、引用与范围；尚未 I 的材料不直接成为已接纳的任务要求。

新话题不能继续等 I 决定后才落盘。R 判断 new 后，由 Host 分配稳定 topicId 并提交。为避免同时到来的两个“新话题”实际属于同一话题：

1. S 和 R 推理可以并行，群内话题归属提交串行、短事务执行。
2. R 输入记录 `topicCatalogRevision`；new 提交时核对候选目录版本。
3. 若期间新增相关候选，刷新候选并重跑该项 R，保留 S；不得用标题字符串或文本 hash 代替语义关联。
4. 后续事项的候选必须能看到已提交的暂存话题及其原文来源，即使该话题尚无业务 Task。

话题与任务身份解耦：一个话题可有多个独立任务；R 关联话题，I 根据目标和现有任务集合决定修改哪个任务或新建哪个任务。不能将“同话题”直接解释为“同一个任务”。

R 纠正、事项重拆、源消息编辑/撤回需要使旧绑定失效，并递增旧/新话题的输入版本。已派发动作不会被删除历史绑定而自动撤销，必须走相应任务变更。

### 3.3 话题独立判断与输入覆盖

每次 I 创建唯一 `intentRunId`，绑定 `(inboxScope, topicId, inputRevision, attempt)`，保存独立输入/输出和模型用量；当前模型 API 无长期 session，可直接用此身份形成逻辑判断会话。若之后采用 DSH Session，则每个 IntentRun 建独立 Session，不能复用一个群会话串行装入多个话题。

同一话题 single-flight；不同话题使用独立并发队列，并保留 S/R 的处理份额，防止 I 占满并发后新输入永远无法归类。上下文不共享，即使资源限制导致排队，也不是在同一模型会话中逐话题判断。

I 输入只包含：

- 该话题所有尚未被有效决策覆盖的事项，原文、源版本、时间、真实发送者和权限来源。
- 该话题已经接受的事实/有效约束及必要原文引用。
- 相关业务 Task 的目标、授权边界、计划、当前阶段、关键产物与正在等待的确认。
- 上次有效意图和未应用命令的处理状态；不把候选当作已接受事实。
- 当前可执行流程/能力索引及不可用原因。

多条消息保持各自来源，不拼成一个虚假的作者。I 输出覆盖清单：每个待判 unit 必须对应动作、事实、被后续消息替代、明确无动作或澄清；Host 检查无遗漏、无重复和来源权限。同话题可以输出多个 action，不强制合成单一动作或单一 Task。

重判使用“当前完整有效要求 + 本批全部增量”，不能只把最后一条消息覆盖旧要求。冲突按来源、权限与明确更正判断，不能简单取最后一个说话者。未知冲突进入澄清；取消和随后重新授权要分别留存。

超出上下文容量时保留完整输入 manifest，按需读取引用；可以做无副作用的分段证据整理，再形成统一 I。必须证明每个输入的覆盖归宿，不能截尾或先派发一部分。仍无法容纳则进入容量阻塞，不把有界上下文包装成完整理解。

### 3.4 I 后必须由脚本完成的原子核验

新增 `topic.intent.accept`，在现有单写入控制库的一次事务内：

```text
校验 IntentRun 的 lease、输入摘要及仍为当前候选
若同一 inboxScope 有待归类输入：WAIT_ROUTING，保留候选
若 topic.inputRevision 不等于 candidate.inputRevision：STALE_TOPIC
若任一 sourceVersion/matterRevision/binding 已失效：STALE_SOURCE
若动作依赖的 taskRequirementRevision/planRevision/阶段前置条件变更：STALE_TASK
校验每条动作的来源权限、效果范围、事项覆盖与动作依赖
原子写入：有效决策、覆盖关系、Task 更新意图/派发命令、通知意图
推进 topic.processedRevision，返回已提交的业务回执
```

`WAIT_ROUTING` 后如新消息最终属于 B，A 的原候选可以重新走原子检查，不重调 A 的模型。若属于 A，则待归类清空后用最新集合再判 A；旧候选只留审计，不派发。任务日志和进度时间戳变化不应触发 I 重算；仅检查该决策实际依赖的业务版本与条件。

检查和写命令不能分成“脚本读一次 → 模型/异步等待 → 普通写入”。事务是线性化边界：在提交之前落盘的新输入会被看到；之后才收到的输入属于下一次更新。

命令的业务幂等键由 Host 分配，绑定 acceptedDecisionId 和稳定 actionKey；attempt 不生成新业务身份。重复恢复返回原命令/任务。新派发命令领取时再检查群待归类计数、topic 版本和目标任务条件；如果已接纳但未派发期间来了同话题输入，尚未执行的命令参与下一次 I 的合并/替代，不能先执行旧 create 再创建新 create。仅候选/未领取命令可以被替代；已领取、已经应用和结果未知的命令必须连同真实回执一起参与判断，不能重新生成等价业务动作。

跨多个任务的 action 在决策层同次接纳，执行层各有回执与依赖；不伪造外部动作跨系统原子性。A 动作成功、B 失败时只恢复 B，已经发生的效果单独对账。

### 3.5 时序示例

1. 入箱 m1“排查导出失败”、m2“只影响大文件”、m3“先给方案”。三条完成 S/R 后都属于话题 A。
2. 归类等待点关闭，A 的 I 一次取得三条，输出“排查并给方案，暂不实施”。
3. I 运行中收到 m4“仅 UAT 环境”。先完成 m4 的 R，A 版本增加；旧 I 结果不派发，集合四条只重判 A 的 I。
4. 重判期间另一条消息归入 B，B 使用自己的 IntentRun；B 的输入不会使 A 的候选失效。
5. A 的核验通过后创建一个业务 Task，当前授权终点是方案；后续“确认，继续实现并自动提测”成为原 Task 的计划续办。

### 3.6 等待时钟与调用预算

当前 MessageRun 使用 30/45 秒窗口且成功节点会更新 deadline，不能原封不动套在跨消息等待点上。实施时分开记录：消息接收到有效派发的总墙钟、归类排队/阻塞时间、每次 S/R/I 调用的执行期限、累计恢复和 token 预算。等待点不占模型槽，不因被动等待反复消耗 claim；总墙钟统计仍完整保留，不能扣掉等待以美化延迟。

同一输入版本的模型失败沿用有限重试；新消息造成的 I 失效记录为 input_changed，不混为模型失败。一个话题最多一个有效 I 和一个“需要重判最新版本”的标记，连续到来十条消息不排十个 I。已经算出的候选先完成代码核验再决定是否重判，不能每条新消息都强杀模型并立即重启。模型费用按实际 IntentRun 记一次，再关联来源；跨多个源消息不能重复扣同一调用或绕过总预算。预算耗尽时持久阻塞并报告原因，不丢消息、不放行旧候选。

## 4. 执行中的新意图

话题新输入与任务变更分为两次接纳：TopicIntent 决定业务含义，TaskUpdate 校验执行状态并决定如何应用。TaskUpdate 内记录 `changeId、decisionId、sourceRefs、baseRequirementRevision、basePlanRevision、changeKind、affectedStages、fullRequirementRef`。

| 新意图/输入 | 处理方式 | 是否重做 |
| --- | --- | --- |
| 查询进度、读取已有结果 | 查当前账和对应产物，独立答复 | 不修改执行输入，不中断 |
| 重复事实、致谢、不改变要求的信息 | 记录来源/已读版本，必要时关联材料 | 不换代 |
| 可用的新证据，目标和验收不变 | 校验对当前阶段结论的影响；无影响则进入下个节点输入 | 已完成且依赖不变的阶段复用 |
| 新约束、纠错、验收变化 | 汇总为最新完整需求，定位最早受影响阶段/节点 | 只使该阶段后缀及其下游依赖失效 |
| “方案确认，继续实现” | 绑定方案工件及范围，激活/追加开发和约定的 UAT 阶段 | 复用排查/方案，不重跑它们 |
| 新增相对独立的交付目标 | 建同话题下另一个业务 Task，必要时声明依赖 | 不打断原任务 |
| 暂停/取消 | 立即持久化控制状态，阻止新效果；等待正在发生的效果对账 | 不是普通补充，不等批次执行完 |
| 与执行中外部动作冲突 | 封住后续效果，先读取真实结果，再决定补偿/后续计划 | 不盲目重试或声称已撤销 |
| 已完成任务的返工 | 原业务 Task 开新计划版本/阶段尝试，保留旧结果 | 只返工受影响范围 |

不能依据关键词简单判“无影响”。模型提出影响范围和证据；Host 根据步骤声明的输入依赖、产物摘要、验收项与效果范围校验。无法证明可复用时，保守失效相关阶段，明确原因；不把不确定解释为无影响。

### 4.1 什么时候阻塞、什么时候中断

- 收到可可靠定位 Task 且发送者有控制资格的补充时，沿用现有源/任务输入屏障；R 关联到话题后，为有修订资格的待判输入建立该话题相关任务的待判标记。
- 待判期间允许无副作用的计算/只读节点到检查点；阻止其结果作为当前最终交付，并阻止关联任务领取新的修改/发布效果。无权用户输入不能获得控制权，也不能无期限暂停任务。
- I 判定仅查询/无影响事实后解除自身屏障，继续原阶段，不调用 `changeInput`。
- I 判定实质变更后，已排队任务合并所有未应用变更后启动一次；运行任务排空受影响节点，更新 generation，旧会话的迟到结果拒绝入账。
- 屏障建立前已领取/启动的外部效果无法靠撤销令牌抹除；记录 in-flight/unknown 并对账。全局归类等待点用于新意图和新派发，不倒推保证所有既有外部动作都能停止。

### 4.2 增量复用规则

每个阶段/关键节点产物带 `inputComponentHashes、workflowDigest、sourceRefs、criteriaIds、artifactRefs、effectReceipts`。重新规划后必须验证：影响它的输入未变、流程定义未变、产物存在且 hash 一致、外部读回仍适用，才能复用。

在同一工作流内，首版复用已成功前缀，只重建最早受影响节点起的后缀，复用当前 `input.apply` 的后缀契约；暂不增加任意图式节点重排。跨工作流则由 TaskPlan 标记阶段依赖失效。例如“报告补充说明”不应重做代码构建；代码/环境变化会使相关验证和 UAT 证据失效。

多条更新先形成完整需求快照，再用 task requirement/plan 版本比较提交。当前 controller 取最后一个完整输入的机制只有在每个输入都已包含之前有效变更时才正确；不能直接取最后一条聊天正文。

授权持续有效到其绑定范围改变。仅文案/报告更新不重问；仓库、目标环境、变更范围或需要授权的动作变化时核对既有授权能否覆盖。业务确认和平台效果审批分别记录，不能将“方案可以”当成任意生产发布许可。

## 5. 一个业务 Task 组合多个流程

### 5.1 对象职责

```text
Topic 话题：消息与事实集合，可关联多个业务 Task
  BusinessTask：连续业务目标、授权范围、验收目标、当前计划
    TaskPlan revision N：有序阶段、交接、条件与确认点
      Stage investigation → ExecutionRun + 独立节点会话
      Stage planning      → ExecutionRun + 独立节点会话
      Gate confirmation   → 等待消息/控件确认，不占模型执行槽
      Stage engineering   → ExecutionRun + 独立节点会话
      Stage uat-delivery  → ExecutionRun + 独立节点会话
```

保留现有 execution_runs.task_id，令它指向稳定业务 Task；新增业务 Task/计划事实表，不复用旧 JSON Task 引擎作为另一个真相源。现有一个 run 的任务可投影成单阶段计划，业务 ID 保持不变。

TaskPlan 首版是有条件的顺序阶段组合，不引入通用 DAG 引擎。阶段能够通过显式返工创建新 attempt，旧阶段历史不改写。一个业务 Task 同时最多一个有效执行阶段；不同业务 Task 可并行，共享仓库/环境仍受资源锁约束。

### 5.2 阶段合同与交接

每个阶段至少包括：`stageId、workflowId、workflowDigest、purpose、inputRefs、requiredCriteria、gate、status、attempt、runId、outputRefs`。

- `workflowDigest` 冻结实际定义，不因目录更新自动改变活动任务。
- 阶段输入由前序验证过的产物和当前需求生成，不传整段模型会话。
- 阶段产出是结构化结论、工件引用、证据、未解决问题和业务边界。
- Host 检查产物 schema、依赖摘要、验收证据与授权，再提交阶段完成和后续启动意图。
- 后续 run 创建使用 `(taskId, planRevision, stageId, attempt)` 的稳定身份；阶段完成后崩溃重启也只启动一次。
- 计划状态、执行状态、验收结果和通知送达分别保存。前序 run 成功不代表整个 Task 交付成功。

### 5.3 用户给出的经典场景

| 时点 | Task 计划和行为 |
| --- | --- |
| “先排查 xxx 问题，给出方案” | 排查 → 方案 → 等待确认；明确不进入写代码 |
| 排查/方案产出 | 记录复现范围、证据、方案工件、方案版本与验收标准，发送方案结果 |
| “确认，继续实现” | 若准确指向当前方案，记录 plan-confirmation；在同一 Task 追加/激活开发阶段 |
| 方案确认后自动 UAT | 采用已登记的开发完成后 UAT 规则，且此次授权范围覆盖该规则；开发交付完整后自动触发 UAT |
| 开发通过 | 交接精确 commit/PR、测试、构建要求与版本证据，不重新解释需求 |
| UAT 通过 | 记录制品、运行版本、可访问性、约定的冒烟证据、提测单与送达；报告“已提测，待业务验收” |
| UAT 基础设施失败 | 阻塞 UAT 阶段并恢复该阶段；不回退重跑排查和开发 |
| UAT 发现代码缺陷 | 在原 Task 添加开发返工 attempt，完成后重新走受影响验证/UAT |

若初始只要求“排查原因”，排查完成即可完成当时授权范围；不人为保持永久待确认。以后明确继续实施时，在同一业务 Task 续办新计划版本。只有明确的“给方案后等我确认”等语义才建立确认等待点。

“继续”不能仅由文本命中决定：须对应一个待确认的方案/阶段和有资格的确认者。多个方案并存或方案关键内容已变化时澄清。批准一个旧方案不会批准后来变化的方案；与批准无关的文案修订也不应让批准失效。

UAT 自动衔接是一条可配置、可审阅的业务规则，不从“写代码”三个字推导任意交付范围。用户本次描述是希望系统具备这条默认编排；未来每个实际任务仍结合群职责、项目默认交付规则和本次限定，比如“只本地改、不提测”必须覆盖默认。

“提测”与“UAT 业务验收通过”分开：若任务终点是提测，提测证据和送达齐备后完成；若用户要求业务验收通过，则继续等待对应验收结果。生产发布另设阶段和授权，不能被 UAT 成功自动带出。

### 5.4 真实能力缺口

当前 task-investigation/task-planning 只能处理已给材料。实施组合时需要增加受范围控制的证据获取步骤（仓库只读、日志/运行态只读等实际配置能力），再交材料分析节点；没有采集能力就明确等待材料，不能声称完成现场排查。

当前 UAT 模板的最后证据侧重提交、制品、运行版本与入口访问。用户要求的“自动提测”还需要验收清单/提测材料、目标接收人或提测平台记录及读回能力；已有发布模板不自动证明完整提测已实现。适配器缺失时任务应显示“开发完成，UAT 阻塞：缺少某能力”，不能把整条链标为完成。

## 6. 未固化任务的默认流程

新增 `task-general` 通用流程：

```text
理解目标与验收 → 形成简短可执行计划 → 校验能力/范围/已有授权
  → 执行当前一步 → 独立核验 → 更新进度与剩余计划
  → 需要下一步则继续；满足验收则交付
```

“没有专用模板”本身不是拒绝条件。默认流程由 Agent 制定和调整少量步骤，Host 管步骤状态、工具准入、预算、效果和证据；日常低风险事项可以单步完成，不强制每次向用户确认计划。

| 事项 | 默认处理例子 |
| --- | --- |
| 查资料并总结 | 读取已准入来源 → 整理 → 核对引用 → 答复 |
| 整理本地文档/数据文件 | 读取指定文件 → 在授权路径生成/修改 → 独立打开或检查 → 交付 |
| 日常运维查询 | 只读采集实际状态 → 对照口径 → 汇报证据与未验证项 |
| 临时组合事项 | 动态计划中调用现有专用流程阶段；其余步骤由通用能力执行 |

专用流程是可复用的强合同；通用流程是受控的动态步骤容器。命中已有开发、数据库变更或发布范围时，必须使用相应执行/授权能力，不能因为专用模板不可用就退回一个无约束 shell Agent 绕过它。

通用步骤合同：`stepId、objective、capabilityId、scope、inputRefs、expectedEvidence、status、outputRefs`。只读工具可以按登记范围开放；写文件、发消息、提交、外部变更等通过效果适配器，沿用 execute/reconcile 和独立回读。任务中携带的网页、附件、日志是数据，不会扩充授权。

执行循环需有每步时限、总预算、最大无进展重试和持久检查点。超预算或缺能力显示明确阻塞原因，不把半成品报告成成功。缺能力需要补适配器或用户材料，缺模板则继续走通用流程。这两个情况要在产品上区分。

有稳定重复模式后，可将已验证步骤固化为新 workflow；不在本轮加入自动生成并执行任意工作流代码的机制。

## 7. 持久化与模块修改

### 7.1 最小状态增量

以下为逻辑记录，可以复用 message_items 等表，但需要受 schema 约束的字段与索引；不全部塞进无约束 JSON。

| 记录 | 关键字段/约束 |
| --- | --- |
| inbox routing state | scope、ingressSeq、routingStatus、阻塞原因；连续水位/待处理索引可重建，不依赖内存计数 |
| topic input ledger | unit/source 版本、bindingRevision、原文引用、发送者、valid/superseded、inputRevision；单有效归属 |
| topic intent state/run | inputRevision、processedRevision、activeRun、leaseEpoch、inputDigest、candidate、coverage、waitReason；单话题有效运行唯一 |
| accepted topic decision | decisionId、来源覆盖、动作及权限依据、task 预期版本；与 dispatch command 同事务 |
| business task / plan | taskId、目标/验收、requirementRevision、planRevision、授权、阶段实例与产物；历史不可覆写 |
| task update | changeId、decisionId、变化类型、完整需求、影响范围、pending/applied/blocked；同业务变化幂等 |
| stage transition | 前阶段证据、后阶段身份、gate/confirmation、启动回执；恢复不重复创建 run |

应区分 `topic.inputRevision`、`topic.processedRevision`、`task.requirementRevision`、`planRevision` 和 execution generation：收到消息不等于有效需求变化，接受意图不等于动作已经执行。现有 topic.revision 不能同时承载所有含义。

### 7.3 迁移和恢复边界

- 先升级控制库 schema 的明确版本和验证器，迁移脚本提供 `--check`、备份和独立回读；不能只运行 CREATE TABLE 后仍让版本保持不变。
- 老的 JSON Task/旧引擎继续保留既定只读边界，不在本次设计中迁移并重放历史业务。
- 当前 workflow-v2 的历史执行记录投影为单阶段业务 Task；不凭空推断已完成 UAT 或用户批准过后续流程。
- 活动 MessageRun 在切换前排空或形成可恢复交接清单；已接纳命令沿用原身份，新调度不能再生成第二套 create。
- 崩溃后按持久 lease 和待办状态恢复；IntentRun 迟到提交被 fencing 拒绝。候选已写但未接纳、接纳后未派发、阶段结束后未启动下一阶段均可分别恢复。
- 一旦新 schema/新流程已经产生外部效果，不能直接换旧包继续消费新账；回退先排空和对账，再按已验证迁移/恢复方案处理。

## 8. 实施顺序与验收

建议按四个可独立验收的阶段实施；每阶段先落契约与反例测试再改运行器，不并行修改同一状态机。实施时在现有 runtime-redesign 验收目录维护 matrix.csv/round-N，本文仅是前置设计，不宣称已有验收结果。

| 阶段 | 交付与退出条件 |
| --- | --- |
| A 话题归属提前落盘 | S/R 与 I 分离、稳定 topicId、归类等待点；重复/编辑/歧义恢复不丢输入且不自锁 |
| B 话题批量意图 | 独立 IntentRun、覆盖校验、I 后原子接纳和命令领取校验；所有竞态反例通过 |
| C 执行增量与计划组合 | 无影响输入零中断、后缀失效、稳定 Task 多流程、确认续办；先打通隔离的排查→方案→确认→开发链 |
| D 通用任务与 UAT 交付 | 默认流程能力注册、现有专用流程复用、UAT 适配器/提测证据；真实授权目标单独验收 |

最低验收矩阵：

| 编号 | 场景与必须断言 |
| --- | --- |
| M01 | 三条同话题消息预先入箱：最后一个 R 前 I=0；归类完成后该话题一次 I、一个有效创建动作 |
| M02 | 两话题同批归类：IntentRun/上下文完全隔离；并发许可足够时真实重叠执行；不是共享会话串行判断 |
| M03 | I 运行时新增同话题输入：旧结果零派发，仅重跑 I；原 S/R 调用次数不增加 |
| M04 | I 运行时新消息最终归其他话题：等待其 R，但原候选不重调模型 |
| M05 | I 完成与新 R 提交并发：在不同事件顺序下都不接纳过期版本 |
| M06 | I 后仍有尚未 S/R 的消息：不得先派发再发现是同话题 |
| M07 | 候选接纳后、命令领取前又有同话题输入：旧未派发命令参与合并，不重复建 Task |
| M08 | 两个 R 同时判 new 且实际同话题：目录版本冲突后刷新 R，最终只有一个有效 topicId |
| M09 | 一条消息多事项、共享限制、编辑/撤回/重关联：来源覆盖完整，旧约束不通过简单 union 永久保留 |
| M10 | R 失败/澄清、持续收信和容量不足：等待原因可见、不占模型槽、不超时偷放；暂停/取消和澄清答复可达 |
| M11 | 收到多个发送者的同话题消息：无权补充不能修改任务、继承他人批准或无限暂停任务 |
| M12 | 在 R/I/accept/claim 各窗口重启、重复投递：一次业务身份，旧 lease 候选拒绝，未知外部效果先对账 |

性能比较采用相同消息轨迹和语义金标：单消息、同话题连续补充、混合话题、I 期间补充、持续积压分别测量。记录 S/R/I 次数、token、废弃候选数、Task 换代数、复用阶段数、首次有用结果/最后输入到有效派发的延迟、队列年龄和误关联率。

可确定的目标是减少同批同话题的 I 和不必要的 Task 换代；严格等待点可能增加单条消息延迟，不能预先宣称整体性能一定提升。新话题合并准确率、现场排查/UAT 适配器能力和持续流量下的等待体验仍需实施实测。
