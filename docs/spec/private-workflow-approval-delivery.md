# 插件审批私聊投递

## 目标与现状

同一原生工作流待审请求必须实际送到配置审批人的钉钉私聊，并支持引用该消息明确批准或拒绝。当前桥接未等待异步授权列表，且只识别旧 humanBlocker；服务又将生产审批限定在 Web，造成原 #857 待审却无私聊。

## 实施合同

复用 execution_approvals 和 execution_events，不增加数据库表或第二任务模型。通知冻结 requestId、effectId、配置收件人、原生授权 actor、实际审核文本。发送前持久记录意图；发送回执确认 conversationId/messageId 后才显示 waiting-reply。未知发送保留并查询，不盲目重发。重启沿同一请求恢复。

桥接等待原生列表，原生请求走专用工作流接口，旧 humanBlocker 合同保持。实际回复必须来自请求 approverIds 中的身份，匹配持久化私聊及被引用消息。仅明确批准/同意或拒绝/不同意作为决定，普通文字不能批准生产变更。原生账继续保证首个决定生效；Web 提前决定与投递竞争要正确撤回失效通知。驳回意见进入既有修订路径，批准沿既有执行恢复路径。

普通本地部署按用户要求取消历史副本备份，仍执行维护排空、精确包校验、进程/健康/持久状态独立回读；已有历史迁移专用恢复能力不扩大改动。

## 验证与交付

定向覆盖真实 SQLite/工作流服务与桥接组合、异步列表、错误身份/引用、模糊回复、重复回复、未知发送及重启、Web 竞争。正式部署后独立读取原 #857 私聊消息、通知账和原生待审状态，确认未创建新工单、未执行生产 SQL。同步 README/runbook，更新原 goal 与 round-13 验收，交付现有 PR152。
