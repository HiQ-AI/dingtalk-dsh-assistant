# 群聊确认与执行约束修复方案

## 目标和已读现状

复盘任务显示，业务确认人 B 回复由 A 交办的任务后，task-context 被接纳为 supplement，但 task-session-service 的 waiting-reply 门禁阻止统筹处理；用户再次从 Web 回复才恢复。相同消息中的确认及改变方案含义的条件又被拆到不同 Unit，原任务仅接收了“可以”。现有规范已禁止业务悲观锁，却被统筹当作一般偏好放行。验证还存在昂贵构建前缺少低成本预检、原始证据未即时保存的问题。

## 实施范围

1. 在原任务协议内接纳等待期间的新来源。业务 requester 等待可由同任务的已接纳群消息触发统筹只读核对；没有相关新输入时不轮询、不执行。待答事项在统筹核实来源、角色及完整条件前保持 waiting。显式解决操作保留来源和判断证据，不将业务信息答复扩成发布/生产等授权。operator 私聊和 Web 身份验证保持。
2. 路由与任务输入保留同一消息的语义完整性：确认、限制、订正与主事项一起理解；效果所有权限制动作归属，不允许据此删掉影响原方案的条件。复用现有原消息/上下文引用与 preserve/replan 合同，不新建一套任务图。
3. 在现有技术方案、代码审查及业务开发技能中落实明确约束的闭环。禁止把用户明确约定降格为偏好；本次新增调用对旧禁用实现的复用也属于审查范围。定位冲突的旧项目说明，按实际授权修正说明，不扩展为全仓业务锁迁移。
4. 复用现有技能与脚本：包管理器/锁文件识别、隔离依赖实际就绪、夹具最小验证、修改文件 lint 先于昂贵构建；命令、候选、退出状态和原始输出执行时即归档。新增脚本仅用于现有脚本无法承载的可复用确定性行为。

## 验证与交付

定向回归覆盖 A 交办/B 确认、同消息附带条件、不匹配/过期/跨群来源、operator 问题不被业务消息解除、普通执行结果不解除等待、恢复与去重、原执行身份和已完成效果保留。技能做结构验证与独立场景评估，不用关键词出现冒充行为有效。维护唯一 goal 与本轮验证记录，提交插件 PR；技能直接更新实际安装位置并独立读回。当前请求不包含合并 PR、重启本地服务、真实钉钉发信或修改 UAT 业务代码。
