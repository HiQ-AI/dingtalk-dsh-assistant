# 叶子会话原始证据信封

## 目标

主会话只负责判断群消息应创建、补充还是重开哪个 Task，不向叶子传递未经任务执行过程验证的根因、完成度、方案优劣或排除性结论。叶子必须根据原始消息、当前代码、运行态和工具证据独立判断。

## 现状问题

当前 `new-task.objective`、`task-context.context` 和 `task-reopen.context` 都由主会话生成，并直接成为叶子 Goal 或 follow-up。主会话没有叶子的完整执行现场，摘要中的“已经闭环”“应直接复用”“无需再检查”等判断会锚定后续执行。

## 方案

1. 主会话仍输出严格决策 JSON，但其中的 `objective/context` 只用于选路和可观测记录，不作为群消息到叶子的事实来源。
2. Runtime 根据真实入站消息生成统一原始证据信封，包含 messageId、发送者、时间、引用消息 ID、原始正文和附件读取异常。
3. 新 Task 的 objective 使用原始证据信封；已有 Task 的 related context、重开 context 和叶子 follow-up 也使用同一信封。
4. 信封明确标注：群消息属于待核验输入，不代表根因、完成状态或实施方案已经成立；叶子须独立核验，且动作授权不得超出原文。
5. 主会话产生的任务关联解释不进入叶子，不允许用“该线索已排除某方向”等协调判断替代现场验证。
6. Web 主会话工具和 Runtime 纠偏消息同样遵循事实优先：只传用户原文、稳定状态或明确 Runtime 事件，避免加入业务结论。

## 验证

- 新任务 objective 包含原始群消息和稳定来源字段，不包含主会话生成的 objective。
- task-context 与 task-reopen 传给叶子的内容包含原始消息，不包含主会话生成的 context。
- 叶子提示明确要求独立核验，禁止把来源消息当作已证实结论。
- 现有 Task 关联、重开、引用回复和授权边界保持不变。
